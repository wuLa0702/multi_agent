## 场景（2026-08-11，成本控制实施）

设计-成本控制 v1（d1bec59）评审通过后实施，用户问"**为啥 api 层直接就能执行 sql 了呢？**"——`api/cost.py` 直接 `conn.execute("SELECT ... FROM token_cost_ledger")`，`agent/middlewares/token_usage.py` 也直接 INSERT ledger/cost_alerts。

## 发现（分层违规）

| 位置 | 违规 | 违反规则 |
|------|------|----------|
| `api/cost.py` | 直接 SELECT token_cost_ledger / cost_alerts | 06-structure-optimization「db/ 唯一 SQL 出口，禁其他目录手写 SQL」|
| `agent/middlewares/token_usage.py` | 直接 INSERT ledger / SELECT sessions.context_used | 同左（agent → db 应经 repository）|

**根因**：设计文档 §7.4 **给的代码就是 api 直 SQL**——设计评审只审了"功能对不对/面试点全不全"，没审"代码分层合不合规"。评审通过的设计代码自带违规，实施照抄。

## 教训（两层）

1. **设计文档的核心代码也要过"分层合规"检查**——§7 的代码是"可运行形态"，评审时应逐文件对照 06-structure-optimization（SQL 是否走 db/、跨层是否直调）。设计代码违规 = 实施照抄 = 隐患入库
2. **架构约束是"写代码时的第一性"**——任何新增数据读写先问"该走哪个 repository"；api 层只编排，agent 层经 adapter/repository 中转

## 修复（已落地）

- 新增 `db/cost_repository.py`（ledger 插入/会话汇总/告警插入/去重/列表）——成本全部读写收敛
- `session_repo` 加 `get_context_used`（只读单列，避免 Session 对象 datetime 解析开销）
- `token_usage.py` / `cost.py` 改走 repository，无直 SQL
- 教训：**设计代码和业务代码同一套分层纪律**

## 面试价值

> "成本控制实施时被追问'api 为什么直接 SQL'——抓到设计文档代码自带分层违规（api 直连 db、agent 直写 SQL）。修复：抽 cost_repository 收敛 SQL 出口。**设计代码也要过分层合规，架构纪律不因'评审通过'豁免**。"
