## 现象

本地 `curl /v1/health` 返回 `redis: connected`，但本机 6379 无监听、Docker 未启动——
"connected" 来源可疑，验证后确认：**连到了 Clowder AI 生产 Redis（localhost:6399）**。

## 根因链

1. Clowder 运行环境向 shell 注入了环境变量 `REDIS_URL=redis://localhost:6399`
2. pydantic-settings 的取值优先级：**环境变量 > .env 文件 > 字段默认值**
3. `SettingsConfigDict(env_file=".env.dev")` 只在 cwd 下找文件；从 `backend/` 启动时
   `.env.dev` 根本加载不到 → 环境变量直接命中 `redis_url` 字段
4. health 接口如实 ping → 真连上了 6399 生产 Redis（幸好只做了 ping，未读写数据）

## 修复（两层防护）

1. **护栏（config.py）**：`model_validator` 拦截——任何来源的 redis_url 端口 == 6399
   一律替换为 `redis://localhost:6398/0` + UserWarning。本项目代码路径永不触碰 6399。
2. **约定（.env.dev）**：注释明确"禁连 6399，dev/test 用 6398"；默认值改 6398。

## 连带发现：from-import 的 mock 陷阱

`from src.core.redis import get_redis`（import 时绑定）后，`mocker.patch("src.core.redis.get_redis")`
替换的是**模块属性**，health 模块内的绑定引用不受影响 → mock 静默失效。
第一次"测试通过"其实是真实连 6399 假通过的。

**规则**：patch 目标必须是被测模块命名空间里的名字（`src.api.health.get_redis`），
不是来源模块。写测试时先确认 import 形式（from-import vs import 模块属性访问）。

## 验证

- 护栏单测：`test_redis_url_never_points_to_clowder_prod_port`（6399 → 6398）✅
- 真实运行：环境注入 6399 → 护栏替换 → 连上自起 6398 实例 → `redis: connected` ✅
- 无 redis 时：`redis: disconnected` + `status: degraded`，服务不崩 ✅

## 可复用检查清单

- [ ] 新项目 config 层：是否存在会被外部环境变量污染的裸键（REDIS_URL 等通用名）？
- [ ] 是否在 Settings 层做端口/地址白名单护栏？
- [ ] 测试里 mock 的 patch 目标是"被测模块的绑定名"而非"来源模块"？
- [ ] "connected" 类断言是否验证过真实性（netstat / 独立探测）？
