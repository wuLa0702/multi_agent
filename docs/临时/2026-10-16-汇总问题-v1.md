## 0. 本文档使用规则 🔴 v1

> 本节定义**本文件自身**怎么用、怎么加、怎么改。**先读这节再看问题条目。**

### 0.1 这是什么

一份**活跃问题清单**——把排查中发现的缺陷集中挂在一个地方，逐条跟踪到修完。
**不是**设计方案，**不是**决策记录，**不是**测试报告；修复动作本身另开设计稿 / 提交。

### 0.2 分区规则（硬性）

| 区 | 位置 | 放什么 |
|----|------|--------|
| **后端问题** | **§1，文档前部** | `backend/` 下的问题（含契约定义侧） |
| **前端问题** | **§2，文档末尾** | `frontend/` 下的问题 |

前后端同源的问题（如契约不匹配）：**主条目放在受影响更重的一侧，另一侧写交叉引用**（如 B1 ↔ F1），不重复描述。

### 0.3 条目编号规则

|------|------|-----|
| `B` | Backend（后端） | `B1`、`B2` … |
| `F` | Frontend（前端） | `F1`、`F2` … |

**编号只增不复用**：条目作废标 📦，不删、不回填空号；新增条目取**当前最大号 +1**。

### 0.4 优先级定义

| 标记 | 级别 | 判定标准 |

### 0.5 每条问题必含字段

每个条目按**固定五段**写，缺一不可：

1. **现象** —— 一句话说清"现在的实际行为"

## 1. 后端问题 🔴 v1

### B1 🔴 P0 — 错误响应被 FastAPI 多包一层（嵌套 `detail`） ⏳

**现象**
后端抛错写法是 `raise HTTPException(status_code=4xx, detail=ErrorResponse(...).model_dump())`。
FastAPI 内置的 `http_exception_handler` 会把 `detail` 作为**唯一键**再包一层，实际落到 HTTP 响应体是：

```json
{ "detail": { "error": "...", "detail": "...", "code": "..." } }
```

**位置**（13 处 `raise`，其中 3 处是助手函数、被 13 个调用点复用）

| 文件 | 行范围 | 场景 |
|------|--------|------|
| `backend/src/api/chat.py` | `127-134` | message / resume_run_id 互斥（400） |
| `backend/src/api/chat.py` | `136-143` | 两者都未提供（400） |
| `backend/src/api/chat.py` | `145-152` | model_id 不存在（400） |
| `backend/src/api/chat.py` | `156-163` | resume 缺 session_id（400） |
| `backend/src/api/chat.py` | `236-243` | 会话不存在（404） |
| `backend/src/api/sessions.py` | `72-79` | `_raise_404()` 助手（调用点 `:149` / `:172` / `:196`） |
| `backend/src/api/sessions.py` | `129-136` | title / is_pinned 都未提供（400） |
| `backend/src/api/sessions.py` | `139-146` | 标题超长（400） |
| `backend/src/api/mcp_servers.py` | `67-71` | `_error()` 助手（2 个调用点） |
| `backend/src/api/uploads.py` | `41-45` | `_error()` 助手（6 个调用点） |
| `backend/src/api/skills.py` | `33-38` | `_error()` 助手（5 个调用点） |
| `backend/src/api/context_usage.py` | `33-35` | 会话不存在（404），**内联 dict** |
| `backend/src/api/providers.py` | `57-60` | 模型不存在（404），**内联 dict** |

**判定依据**
- 契约原文（扁平）：`docs/架构/参考-后端接口.md:38`
  `- **错误统一**：{ "error": "...", "detail": "...", "code": "..." }，非 2xx 时返回`
- 契约原文（Pydantic 形态）：`docs/架构/参考-后端接口.md:83-93`
- `docs/架构/参考-后端接口.md:385` 明确"请求阶段错误（参数/鉴权）→ HTTP 4xx + ErrorResponse（不走 SSE）"
- 推导：`HTTPException.detail` 由 FastAPI 默认处理器序列化为 `{"detail": <detail>}` —— 本项目未注册自定义 `exception_handler`（见 B4），故走默认路径

**影响**
前端拿不到 `error` 与 `code`（`body.error` / `body.code` 均为 `undefined`，`body.detail` 是**对象**）。
前端"按 code 分支处理"的错误码表（契约 §7）**永不命中**；用户看到的错误文案退化为 `[object Object]`（详见 **F1**）。

**建议**
二选一并**只选一个**（当前是"契约与实现各说各话"）：
- **方案甲（推荐）**：新增统一错误响应助手（如 `api/errors.py::raise_api_error()`），内部抛 `HTTPException` 的同时**注册自定义 `exception_handler`** 把信封摊平 → 契约与前端**都不用动**
- **方案乙**：改契约与前端接受嵌套 → 需同步改 `参考-后端接口.md` §3.3、`frontend/src/lib/api/types.ts`、`client.ts`、`sse.ts`，波及面更大

### B2 🔴 P0 — `error` 字段被填成类名 `"ErrorResponse"` ⏳

**现象**
`ErrorResponse` 的 `error` 字段语义是"**人类可读错误信息**"（契约 `:90`），但 4 处把它填成了**类名**：

```python
# context_usage.py:33-35
raise HTTPException(status_code=404, detail={
    "error": "ErrorResponse", "detail": "会话不存在", "code": "SESSION_NOT_FOUND",
})

# skills.py:33-38
detail={"error": "ErrorResponse", "detail": detail, "code": code},

# mcp_servers.py:67-71
detail=ErrorResponse(error="ErrorResponse", detail=detail, code=code).model_dump(),

# uploads.py:41-45
detail=ErrorResponse(error="ErrorResponse", detail=detail, code=code).model_dump(),
```

**位置**

| 文件 | 行 | 形态 |
|------|-----|------|
| `backend/src/api/context_usage.py` | `34` | 内联裸 dict |
| `backend/src/api/skills.py` | `37` | `_error()` 助手内裸 dict |
| `backend/src/api/mcp_servers.py` | `70` | `_error()` 助手内 `ErrorResponse(...)` |
| `backend/src/api/uploads.py` | `44` | `_error()` 助手内 `ErrorResponse(...)` |

**判定依据**
契约 `docs/架构/参考-后端接口.md:90` 注释：`error: str  # 人类可读错误信息`。
填入 `"ErrorResponse"` 是**复制粘贴改了一半**——类名被当成文案占位符留下。

**影响**
- 13 个 `_error()` 调用点 + 1 处内联 = **14 个响应**的 `error` 字段全错
- 前端 `client.ts:44` 的取值优先级是 `body.error || body.detail` → **`error` 永远先命中**且恒为 `"ErrorResponse"` → 用户看到 `"ErrorResponse"` 而不是"参数非法""服务器不存在"等真实信息
- 叠加 B1 嵌套后前台显示 `[object Object]`，**本 bug 被掩盖**——修 B1 之后它会立刻显形，**必须同批修**

**建议**
4 处统一改为真实文案（或干脆改为短标签如 `"请求失败"` / `"参数错误"`）。
**注意**：若采纳 B1 方案甲，应顺手把这 4 处并进统一助手，避免第 5 次复制。

**现象**
同一条契约（`error` / `detail` / `code`）在 `api/` 层有 **6 种**不同写法：

| # | 形态 | 位置 |
|---|------|------|
| 1 | `class ErrorResponse(BaseModel)` | `backend/src/api/chat.py:102-107` |
| 2 | `class ErrorResponse(BaseModel)` | `backend/src/api/sessions.py:62-67` |
| 3 | `class ErrorResponse(BaseModel)` | `backend/src/api/mcp_servers.py:59-64` |

| 6 | 不定义类，裸 dict 手写 | `backend/src/api/providers.py:59` |

四份类定义**字段完全一致**（`error: str` / `detail: str` / `code: str`），仅 docstring 措辞微差（`uploads.py:34` 写"统一错误响应。"，其余写"统一错误响应（契约 §3.3）。"）。

**位置**（逐行）
- `backend/src/api/chat.py:102-107`
- `backend/src/api/sessions.py:62-67`
- `backend/src/api/mcp_servers.py:59-64`
- `backend/src/api/uploads.py:33-38`
- `backend/src/api/skills.py:37`
- `backend/src/api/providers.py:59`

**判定依据**
- `.claude/rules/06-structure-optimization.md` §2：Pydantic 模型统一放 `src/schemas/`
- `.claude/rules/10-api.md`：错误统一 `ErrorResponse`（error/detail/code）
- 这是项目已反复踩过的同类坑第 4 次：工具清单写两遍 → 审计方言 5 种 → 重试参数写两处 → **现在错误响应 6 种**

**影响**
新增一个错误响应字段（如 `trace_id`）需改 6 处；漏一处则该路由的响应形态与前端类型不符。

**建议**
收归 `backend/src/schemas/errors.py`（或 `src/schemas/error.py`）一份 + 6 处改引用；配合 B1 方案甲一并收口到一个 `raise_api_error()` 助手。

### B4 🔴 P0 — 无全局异常处理器 ⏳

**现象**
全仓**没有注册任何** `app.exception_handler` / `add_exception_handler`。未捕获异常走 Starlette 内置 `ServerErrorMiddleware` 兜底，响应体是**纯文本**：

```
Internal Server Error
```

——不是 JSON、不含 `code`、不符合 `ErrorResponse` 契约。

**位置**
- 缺失点：`backend/src/api/main.py`（应用装配处，全文无 `exception_handler` 注册）
- 契约要求：`docs/架构/参考-后端接口.md:95`（"500 内部错误"）、`:38`（非 2xx 统一 ErrorResponse）
- 前端兜底：`frontend/src/lib/api/client.ts:61-63`（`catch { /* 非 JSON body 用默认占位 */ }`）——**这一层把问题接住了**，所以线上表现为"请求失败"而非崩溃

**判定依据**
`grep -rn "exception_handler" backend/` → **0 命中**（已实测）。
Starlette 源码：未注册 handler 时 `ServerErrorMiddleware` 返回 `PlainTextResponse("Internal Server Error", status_code=500)`。

**影响**
- 契约中"所有 REST 错误统一 ErrorResponse"在 500 路径上**不成立**
- 前端无法按 `code` 区分 500，只能靠 HTTP 状态码
- 排障时前端日志只留一句"请求失败"，**丢失后端异常线索**

**建议**
在 `main.py` 注册两个处理器：
1. `Exception` → 记 error 日志（带 `trace_id`）→ 返回 500 + `ErrorResponse(code="INTERNAL")`，**不外泄堆栈**
2. `RequestValidationError` → 返回 400 + `ErrorResponse(code="BAD_REQUEST")`（当前 Pydantic 校验失败也会返回**默认的 `{"detail": [...]}` 列表形态**，同样不合契约）

### B7 🟡 P2 — `core/retry.py:73` 使用将被移除的 API ⏳

**现象**

```python
def decorator(func: Callable) -> Callable:
    if asyncio.iscoroutinefunction(func):   # ← core/retry.py:73
```

`asyncio.iscoroutinefunction()` 自 Python 3.12 起进入 `DeprecationWarning`，**Python 3.16 移除**。

**位置**
- `backend/src/core/retry.py:73`

**判定依据**
CPython 官方弃用记录：`asyncio.iscoroutinefunction` 由 `inspect.iscoroutinefunction` 取代（后者自 3.8 起支持 `functools.partial` 解包）。
项目 `CLAUDE.md` 声明 Python 3.11+，尚可运行，但**升级即断**。

**影响**
- 当前：跑测试时多一条 `DeprecationWarning`（易被其它噪音淹没）
- 将来：升到 3.16 时**该行直接 `AttributeError`** → 重试装饰器**整体失效**（工具不再重试，且是静默失效——历史上这行刚修过一次"静默失效"事故）

**建议**
`asyncio.iscoroutinefunction` → `inspect.iscoroutinefunction`，1 行改动 + 跑 `backend/tests/test_core/test_retry.py` 验证。

## 2. 前端问题 🔴 v1

### F1 🔴 P0 — 错误体按【扁平】解析，实际【嵌套】→ 界面显示 `[object Object]` ⏳

**现象**
前端拿到非 2xx 响应后，把 JSON **当作扁平** `ErrorResponse` 用：

```typescript
// client.ts:57-65
if (!res.ok) {
  let body: ErrorResponse = { error: "", detail: "请求失败", code: "HTTP_ERROR" };
  try {
    body = (await res.json()) as ErrorResponse;   // ← 直接断言，不校验形态
  } catch { /* 非 JSON body 用默认占位 */ }
  throw new ApiError(res.status, body);
}
```

```typescript
// client.ts:43-49
constructor(status: number, body: ErrorResponse) {
  super(body.error || body.detail || "请求失败");   // ← 命中 body.detail（对象，truthy）
  this.code = body.code;                          // ← undefined
  this.detail = body.detail;                      // ← 对象，类型谎称 string
}
```

但后端实际返回的是**嵌套**形态（见 **B1**）：`{"detail": {"error": ..., "detail": ..., "code": ...}}`。

**位置**

| 文件 | 行范围 | 说明 |
|------|--------|------|
| `frontend/src/lib/api/client.ts` | `43-49` | `ApiError` 构造函数按扁平取值 |
| `frontend/src/lib/api/client.ts` | `57-65` | `as ErrorResponse` **无形态校验**，嵌套结构照样通过 |
| `frontend/src/lib/api/types.ts` | `204-208` | 前端自己的 `ErrorResponse` 定义（扁平）——契约的**第 2 份拷贝** |
| `docs/架构/参考-后端接口.md` | `38`、`83-93` | 契约原文（扁平）——与前端一致，**是后端实现跑偏了** |

**判定依据**（逐步推导）
设后端返回 `B = { detail: { error: "参数冲突", detail: "…", code: "BAD_REQUEST" } }`：
1. `body.error` → `undefined`
2. `body.detail` → `{ error, detail, code }` —— **对象，truthy**
3. `super(undefined || 对象 || "请求失败")` → `super(对象)` → `Error` 构造把参数强制转字符串 → **`"[object Object]"`**
4. `this.code = body.code` → `undefined`
5. `this.detail = body.detail` → **对象**，但类型标注是 `string`（`client.ts:41`）

**影响**
- **用户可见**：任何 4xx（参数错、会话不存在、审批过期）界面都显示 `[object Object]`
- 前端 `catch (e) { if (e instanceof ApiError && e.code === "SESSION_NOT_FOUND") … }` 这类**按 code 分支的处理永不命中**（`code` 恒为 `undefined`）
- `ApiError.detail` 类型标注 `string` 但运行时是对象 → **类型系统骗人**，下游 `.includes()` / `.slice()` 之类调用会抛 `TypeError`

**建议**
**首选跟 B1 方案甲一起修**（后端摊平 → 前端零改动）。
若最终选择保留嵌套，则前端需同步改 4 处：`client.ts:43-49`、`client.ts:57-65`、`sse.ts:124-134`（见 F2）、`chatStore.ts:115-121`（见 F2）。
**无论选哪条**，建议 `client.ts:60` 加**形态校验**（`typeof body.error === "string"` 之类），断言 `as` 换成校验——否则同类跑偏无告警。

### F2 🔴 P0 — SSE 请求阶段错误同源问题 ⏳

**现象**
SSE 通道的"请求阶段错误"（HTTP 非 2xx）走的是**同样的扁平解析**，因此中同一个招。

**位置**

| 文件 | 行范围 | 说明 |
|------|--------|------|
| `frontend/src/lib/api/sse.ts` | `124-134` | `body = (await res.json()) as ErrorResponse` → `cb.onHttpError(res.status, body)` |
| `frontend/src/lib/api/sse.ts` | `11`、`25-26` | docstring / 类型均声明"body 为 ErrorResponse JSON"（扁平假设） |
| `frontend/src/lib/stores/chatStore.ts` | `115-121` | 消费侧：`text: \`请求失败（HTTP ${status}）：${body.detail \|\| body.error} [${body.code}]\`` |

**判定依据**
`chatStore.ts:118` 的模板串直接插值 `body.detail`（嵌套时是对象）→ 渲染为 `[object Object]`；`body.code` → `undefined`。
提示文案实际变成：**`请求失败（HTTP 404）：[object Object] [undefined]`**。

**影响**
- 与 F1 同根因、不同出口 —— `chatStore.ts:118` 的文案**直接进用户可见的 notices 列表**（比 F1 更直白）
- 流内 `error` 事件（SSE 已建立后的业务错误）走 `chatStore.ts:492-497`，那条路是 `event.detail` / `event.code`（`ErrorEvent`，**后端单独构造的扁平结构**）→ **不受影响**。故受影响面**精确为"请求阶段错误"一条路径**

**建议**
同 F1，与 B1 一并收口。
**另外**：`sse.ts:126` 与 `client.ts:58` 是**逐字重复**的兜底初始值（`{ error: "", detail: "请求失败", code: "HTTP_ERROR" }`）——建议抽公共 `parseErrorResponse(res)` 一处，避免后续再分叉。

### F3 🟠 P1 — 测试 mock 固化了错误假设（测试永远绿） ⏳

**现象**
前端 SSE 的 HTTP 错误测试，mock 出来的响应体是**扁平**的：

```typescript
// frontend/src/test/sse.test.ts:180-201
it("HTTP 非 2xx → onHttpError 携带 ErrorResponse", async () => {
  globalThis.fetch = vi.fn().mockResolvedValue(
    new Response(JSON.stringify({ error: "互斥", detail: "message 与 resume_run_id 二选一", code: "BAD_REQUEST" }),
      { status: 400, headers: { "Content-Type": "application/json" } }),
  ) as unknown as typeof fetch;
  // …
  onHttpError: (status, body) => { got = { status, code: body.code }; },
  // …
  expect(got).toEqual({ status: 400, code: "BAD_REQUEST" });   // ← 通过，但后端不这么返回
});
```

**位置**

| 文件 | 行范围 | 说明 |
|------|--------|------|
| `frontend/src/test/sse.test.ts` | `180-201` | mock body 用扁平形态；断言 `body.code === "BAD_REQUEST"` |
| `frontend/src/lib/stores/chatStore.ts` | `115` | body 类型写成 `{ detail?: string; error?: string; code?: string }`（**全可选**） |
| `frontend/src/lib/api/client.ts` | `43` | 同一契约写成 `body: ErrorResponse`（**全必填**） |

**判定依据**
- **测试的 mock 是"人手写的理想体"，不是真实后端输出**。真实后端输出嵌套（B1），mock 输出扁平 → 测试覆盖的是**不存在的世界**
- 这是"**测试固化错误假设**"（assertion 与实现同源跑偏），比"没测试"更危险：它给出**虚假的安全感**
- 类型不一致：同一契约在 `chatStore.ts:115`（全可选）与 `client.ts:43`（全必填）被描述两次 →

**影响**
- 修 B1/F1 时，**测试不会变红**——无法作为回归护栏
- 任何人读到该测试都会以为"扁平契约已验证"，进而按扁平写新代码

**建议**
1. 把 `sse.test.ts:180-201` 的 mock body 改为**真实后端形态**（嵌套），断言相应更新——**先让它红**，锁定 B1 的事实
2. 类型收口：`chatStore.ts:115` 与 `client.ts:43` 共用同一类型（若采纳 B1 方案甲，统一用 `types.ts:204-208` 的 `ErrorResponse`）
3. 补一条**契约形态测试**：起真实 FastAPI 应用打一个 404（或直接把后端响应体固化为 fixture），断言"扁平三字段"——这样后端跑偏时前端能报红
