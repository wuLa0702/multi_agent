## 0. 本文档使用规则 🔴 v1.2

> 本节定义**本文件自身**怎么用、怎么加、怎么改。**先读这节再看问题条目。**

### 0.1 这是什么

一份**活跃问题清单**——把排查中发现的缺陷集中挂在一个地方，逐条跟踪到修完。
**不是**设计方案，**不是**决策记录，**不是**测试报告；修复动作本身另开设计稿 / 提交。

### 0.2 分区规则（硬性）

| 区 | 位置 | 放什么 |
|----|------|--------|
| **后端问题** | **§1，文档前部** | `backend/` 下的问题（含契约定义侧） |
| **前端问题** | **§2，文档末尾** | `frontend/` 下的问题 |

前后端同源的问题（如契约不匹配）：**主条目放在受影响更重的一侧，另一侧写交叉引用**（如 B1 ↔ F1），不重复描述。

### 0.3 条目编号规则

| 前缀 | 含义 | 例 |
|------|------|-----|
| `B` | Backend（后端） | `B1`、`B2` … |
| `F` | Frontend（前端） | `F1`、`F2` … |

**编号只增不复用**：条目作废标 📦，不删、不回填空号；新增条目取**当前最大号 +1**。

### 0.4 优先级定义

| 标记 | 级别 | 判定标准 |
|------|------|----------|
| 🔴 | **P0 必修** | 用户可见的错误 / 契约违反 / 线上行为与测试断言不符 |
| 🟠 | **P1 应修** | 结构性隐患：同一件事写多遍、类型骗人、测试假绿 |
| 🟡 | **P2 择机** | 规范违反但当前无可见影响 / 技术债 / 前瞻性替换 |

### 0.5 每条问题必含字段

每个条目按**固定五段**写，缺一不可：

1. **现象** —— 一句话说清"现在的实际行为"
2. **位置** —— ⚠️ **必须索引到具体行范围**（`文件路径:起止行`），多个位置分行列出
3. **判定依据** —— 为什么算问题（引用契约 / 规则 / 推导过程）
4. **影响** —— 谁会被影响、影响成什么样
5. **建议** —— 修的方向（**不代表已授权动工**）

> 位置索引是硬要求：**行号必须可点击跳转、可复核**；不许写"某处""相关文件"。

## 1. 后端问题 🔴 v1.2

### B1 🔴 P0 — 错误响应被 FastAPI 多包一层（嵌套 `detail`） ✅

> **状态**：✅ 已修（`f2777eb`）。方案甲落地——新增 `api/error_handlers.py::install_error_handlers()` 注册 `HTTPException` 处理器把信封摊平；**契约与前端零改动**（跑偏的是后端实现）。新增契约守卫 `test_error_contract.py`（4 用例）防回归。

**现象**
后端抛错写法是 `raise HTTPException(status_code=4xx, detail=ErrorResponse(...).model_dump())`。
FastAPI 内置的 `http_exception_handler` 会把 `detail` 作为**唯一键**再包一层，实际落到 HTTP 响应体是：

```json
{ "detail": { "error": "...", "detail": "...", "code": "..." } }
```

**位置**（13 处 `raise`，其中 3 处是助手函数、被 13 个调用点复用）

| 文件 | 行范围 | 场景 |
|------|--------|------|
| `backend/src/api/chat.py` | `127-134` | message / resume_run_id 互斥（400） |
| `backend/src/api/chat.py` | `136-143` | 两者都未提供（400） |
| `backend/src/api/chat.py` | `145-152` | model_id 不存在（400） |
| `backend/src/api/chat.py` | `156-163` | resume 缺 session_id（400） |
| `backend/src/api/chat.py` | `236-243` | 会话不存在（404） |
| `backend/src/api/sessions.py` | `72-79` | `_raise_404()` 助手（调用点 `:149` / `:172` / `:196`） |
| `backend/src/api/sessions.py` | `129-136` | title / is_pinned 都未提供（400） |
| `backend/src/api/sessions.py` | `139-146` | 标题超长（400） |
| `backend/src/api/mcp_servers.py` | `67-71` | `_error()` 助手（2 个调用点） |
| `backend/src/api/uploads.py` | `41-45` | `_error()` 助手（6 个调用点） |
| `backend/src/api/skills.py` | `33-38` | `_error()` 助手（5 个调用点） |
| `backend/src/api/context_usage.py` | `33-35` | 会话不存在（404），**内联 dict** |
| `backend/src/api/providers.py` | `57-60` | 模型不存在（404），**内联 dict** |

**判定依据**
- 契约原文（扁平）：`docs/架构/参考-后端接口.md:38`
  `- **错误统一**：{ "error": "...", "detail": "...", "code": "..." }，非 2xx 时返回`
- 契约原文（Pydantic 形态）：`docs/架构/参考-后端接口.md:83-93`
- `docs/架构/参考-后端接口.md:385` 明确"请求阶段错误（参数/鉴权）→ HTTP 4xx + ErrorResponse（不走 SSE）"
- 推导：`HTTPException.detail` 由 FastAPI 默认处理器序列化为 `{"detail": <detail>}` —— 本项目未注册自定义 `exception_handler`（见 B4），故走默认路径

**影响**
前端拿不到 `error` 与 `code`（`body.error` / `body.code` 均为 `undefined`，`body.detail` 是**对象**）。
前端"按 code 分支处理"的错误码表（契约 §7）**永不命中**；用户看到的错误文案退化为 `[object Object]`（详见 **F1**）。

**建议**
二选一并**只选一个**（当前是"契约与实现各说各话"）：
- **方案甲（推荐）**：新增统一错误响应助手（如 `api/errors.py::raise_api_error()`），内部抛 `HTTPException` 的同时**注册自定义 `exception_handler`** 把信封摊平 → 契约与前端**都不用动**
- **方案乙**：改契约与前端接受嵌套 → 需同步改 `参考-后端接口.md` §3.3、`frontend/src/lib/api/types.ts`、`client.ts`、`sse.ts`，波及面更大

## 2. 前端问题 🔴 v1.2

### F1 🔴 P0 — 错误体按【扁平】解析，实际【嵌套】→ 界面显示 `[object Object]` ✅

> **状态**：✅ 已解（`f2777eb`，**后端侧修复**）。选定的方案甲让前端**零改动**即恢复正确：前端一直按契约（扁平）解析，跑偏的是后端。`body.error` / `body.code` 恢复正常，`ApiError.detail` 不再是对象。
> ⚠️ **未验证**：前端测试套件未在本 worktree 跑过（worktree 无 `node_modules`）。因**前端零改动**，其既有测试不受影响；但"界面不再显示 `[object Object]`"属**静态推导**结论，建议合入后由 co-creator 实机确认一次。

**现象**
前端拿到非 2xx 响应后，把 JSON **当作扁平** `ErrorResponse` 用：

```typescript
// client.ts:57-65
if (!res.ok) {
  let body: ErrorResponse = { error: "", detail: "请求失败", code: "HTTP_ERROR" };
  try {
    body = (await res.json()) as ErrorResponse;   // ← 直接断言，不校验形态
  } catch { /* 非 JSON body 用默认占位 */ }
  throw new ApiError(res.status, body);
}
```

```typescript
// client.ts:43-49
constructor(status: number, body: ErrorResponse) {
  super(body.error || body.detail || "请求失败");   // ← 命中 body.detail（对象，truthy）
  this.code = body.code;                          // ← undefined
  this.detail = body.detail;                      // ← 对象，类型谎称 string
}
```

但后端实际返回的是**嵌套**形态（见 **B1**）：`{"detail": {"error": ..., "detail": ..., "code": ...}}`。

**位置**

| 文件 | 行范围 | 说明 |
|------|--------|------|
| `frontend/src/lib/api/client.ts` | `43-49` | `ApiError` 构造函数按扁平取值 |
| `frontend/src/lib/api/client.ts` | `57-65` | `as ErrorResponse` **无形态校验**，嵌套结构照样通过 |
| `frontend/src/lib/api/types.ts` | `204-208` | 前端自己的 `ErrorResponse` 定义（扁平）——契约的**第 2 份拷贝** |
| `docs/架构/参考-后端接口.md` | `38`、`83-93` | 契约原文（扁平）——与前端一致，**是后端实现跑偏了** |

**判定依据**（逐步推导）
设后端返回 `B = { detail: { error: "参数冲突", detail: "…", code: "BAD_REQUEST" } }`：
1. `body.error` → `undefined`
2. `body.detail` → `{ error, detail, code }` —— **对象，truthy**
3. `super(undefined || 对象 || "请求失败")` → `super(对象)` → `Error` 构造把参数强制转字符串 → **`"[object Object]"`**
4. `this.code = body.code` → `undefined`
5. `this.detail = body.detail` → **对象**，但类型标注是 `string`（`client.ts:41`）

**影响**
- **用户可见**：任何 4xx（参数错、会话不存在、审批过期）界面都显示 `[object Object]`
- 前端 `catch (e) { if (e instanceof ApiError && e.code === "SESSION_NOT_FOUND") … }` 这类**按 code 分支的处理永不命中**（`code` 恒为 `undefined`）
- `ApiError.detail` 类型标注 `string` 但运行时是对象 → **类型系统骗人**，下游 `.includes()` / `.slice()` 之类调用会抛 `TypeError`

**建议**
**首选跟 B1 方案甲一起修**（后端摊平 → 前端零改动）。
若最终选择保留嵌套，则前端需同步改 4 处：`client.ts:43-49`、`client.ts:57-65`、`sse.ts:124-134`（见 F2）、`chatStore.ts:115-121`（见 F2）。
**无论选哪条**，建议 `client.ts:60` 加**形态校验**（`typeof body.error === "string"` 之类），断言 `as` 换成校验——否则同类跑偏无告警。
