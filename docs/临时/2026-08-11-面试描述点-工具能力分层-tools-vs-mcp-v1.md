## 1. 一句话面试点

> **"内置能力用函数（高内聚、零协议开销），外部能力走 MCP 接入（协议复用），registry 做统一注册出口——按需分层。"**

## 2. 展开描述

**三层职责不是一回事：**

| 层 | 放什么 | 本质 |
|----|--------|------|
| `agent/tools/` | **内置能力**（search / sandbox / ask_human / publish_report）| 项目自己的 Python 函数，**直接**传给 deepagents |
| `skills/` | **Skill 生命周期运维**（Smithery 市场安装/卸载/启停）| 外部技能脚本的"安装管理"，不是工具实现 |
| `mcp/` | **纯协议网关**（registry/client/server）| 外部 MCP server 的接入层（跨进程/跨语言） |

**为什么内置能力走 tools 不走 MCP：**

MCP 的价值是**协议标准**——让不同进程/语言/组织的工具互相发现调用（需要 server 进程、JSON-RPC、生命周期管理）。项目内置工具是**同进程 Python 函数**，走 MCP 是**纯开销**（序列化、进程通信、生命周期）无收益。

**统一出口在哪：**

`mcp/registry.py` 已是**工具注册表（名→实现）**——内置函数注册进 registry，外部 MCP 工具经 client 收集也进 registry，`main_agent.py:296` 合并传 deepagents。**统一在注册表层**（所有工具名可查），不是"所有工具都走 MCP 协议"。

## 3. 追问链预演

**Q：MCP 不是说要作为统一能力中心吗？为什么内置不走 MCP？**

- 区分**协议标准**（跨进程/跨语言的价值）vs **同进程函数调用**（高内聚零开销）
- MCP 适合：跨组织、跨语言、需独立部署/鉴权的外部工具
- 内置能力走函数：直接调用、无序列化、易调试、可单测
- 演进预留：`mcp/server.py` 已有 FastMCP 端点，将来某内置工具要暴露给外部时再协议化

**Q：registry 是做什么的？**

- 工具注册表：`{工具名: 实现}`，统一出口
- 内置函数 register，外部 MCP 工具经 client 收集后 register
- main_agent 合并全部工具传给 deepagents——**"工具从哪来"集中管理**，冲突仲裁（工具命名冲突时 registry 决定谁优先）
