## 2. 结论速查 🔴 v1

### 2.1 云端 Agent 原清单的核对结果

| 原清单要的 | 本地 `.env.dev` 实情 | 判定 |
|-----------|---------------------|------|
| `ARK_API_KEY` + `ARK_MODEL` | ✅ 有值（`:14` / `:16`） | **可给**（豆包模型要用才给） |
| `ZHIPU_API_KEY` | ❌ **本地无此行** | **给不了** —— 需去 open.bigmodel.cn 申请，或跳过 |
| `LANGCHAIN_API_KEY` | ✅ 有值（`:33`），且 `.env.prod` 已填 | **已就绪，无需再给** |
| `TAVILY_API_KEY` | ⚠️ 有行但空值 | **伪需求，不要给**（见 2.3） |

### 2.2 原清单遗漏、但必须补的

| 遗漏项 | 为什么关键 |
|--------|-----------|
| 🔴 **`DEEPSEEK_API_KEY`** | `LLM_PROVIDER` 默认 provider 的 key，`.env.prod` 现在是**空值**。不配则云端启动后可正常响应，但**一调 LLM 就失败**——比 ZHIPU/TAVILY 重要得多 |
| 🟡 `BOCHA_API_KEY` | 联网搜索工具的实际 key（`.env.prod` 已有值，需确认与本地是否同一账号） |
| 🟡 `SMITHERY_API_KEY` | 本地有值，`.env.prod` **无此行**；用 Smithery MCP 市场才需要 |

### 2.3 两个 key 是伪需求（有代码证据）

| 变量 | 证据 | 说明 |
|------|------|------|
| `TAVILY_API_KEY` | `grep -rn "TAVILY_API_KEY" backend/src` → **零命中** | 搜索工具实际用的是**博查 Bocha**（`backend/src/agent/tools/search.py:112` 检查 `BOCHA_API_KEY`）。Tavily 未接入，**不要申请** |
| `ZHIPU_API_KEY` / `ARK_API_KEY` | 仅作为字符串出现在 `backend/src/db/model_repository.py:38,48` 的 `api_key_env` 元数据 | 模型注册表给设置页列模型用；**不是启动必需**，缺失只在切到该模型时失败 |

### 2.4 缺失 key 的失败形态（重要，避免误判为 bug）

`backend/src/core/config.py` **没有任何强制校验器**（无 `model_validator` 要求 key 非空），settings 字段全部给了空字符串默认值。因此：

> **缺 key 不会导致启动崩溃，只会在实际调用时失败。**

这意味着云端"服务起来了"**不等于**"配置正确"。验收必须真正发起一次 LLM 调用（或看 `/v1/health` 之外的业务接口）。

## 3. 全量环境变量表 🔴 v1

> 来源：`backend/src/core/config.py`（字段定义，行号为该文件内行号）。加载规则见 3.1。
> "prod 现状"= 当前 `.env.prod` 文件状态（2026-09-11 核对）。

### 3.1 加载机制（先理解，再配）

`core/config.py:27-30`：

```python
_APP_ENV = os.getenv("APP_ENV", "dev").lower()
_PROJECT_ROOT = Path(__file__).resolve().parents[3]   # backend/src/core → 项目根
_ENV_FILE = _PROJECT_ROOT / (".env.prod" if _APP_ENV == "prod" else ".env.dev")
```

三条硬规则：

1. **由 `APP_ENV` 决定读哪个文件**，`dev` → `.env.dev`，`prod` → `.env.prod`；
2. **绝不叠加读取**——不会两个都读（`CLAUDE.md` 核心约束 2）；
3. **`.env` 必须放项目根**（不是 `backend/` 下）。路径是绝对路径推算的，因为后端从 `backend/` 启动，cwd 里没有 `.env`，用相对路径会**静默读到全空配置**（`config.py:29-30` 注释记载了这个坑）。

> ⚠️ 云端部署时注意：`.env.prod` 要放在**项目根**，且容器内路径需与 `parents[3]` 推算结果一致。容器化时这一步最容易出错。

另有安全护栏 `core/config.py:36-41`：`REDIS_URL` 端口若是 **6399**（Clowder AI 生产 Redis），一律强制替换为 `6398`。此为家规硬约束，云端不适用但不要删。

## 4. 密钥交接安全路径 🔴 v1

### 4.1 原则

密钥值**只走本地文件系统 → scp**，不经过聊天、不写进任何 `docs/` 文档、不提交 git。

### 4.2 本地合并（把 `.env.dev` 的值补进 `.env.prod`）

在本地项目根执行。**只打印变量名，不打印值**。

> ⚠️ **执行前必读**：本脚本会**用 `.env.dev` 的值覆盖 `.env.prod` 中同名变量的现有值**（含已填好的 `LANGCHAIN_API_KEY`、`BOCHA_API_KEY`）。若云端这两个值是有意与本地不同的，请先从 `KEYS` 列表中删掉再跑。
> `PYTHONIOENCODING=utf-8` 是必需的——Windows 控制台默认 GBK，不加会输出乱码（`.claude/rules/04-logging.md` 编码要求）。

```bash
cd /d/gtiHub/multi_agent
cp .env.prod .env.prod.bak          # 先备份，可回滚

PYTHONIOENCODING=utf-8 python - <<'PY'
from pathlib import Path

KEYS = ["DEEPSEEK_API_KEY", "ARK_API_KEY", "ARK_MODEL",
        "BOCHA_API_KEY", "LANGCHAIN_API_KEY", "SMITHERY_API_KEY"]

def parse(p):
    d = {}
    for line in Path(p).read_text(encoding="utf-8").splitlines():
        if "=" in line and not line.strip().startswith("#"):
            k, v = line.split("=", 1)
            d[k.strip()] = v.strip()
    return d

dev, prod_lines = parse(".env.dev"), Path(".env.prod").read_text(encoding="utf-8").splitlines()

for key in KEYS:
    val = dev.get(key, "")
    if not val:
        print(f"  跳过 {key}（.env.dev 无值，需另行申请）")
        continue
    for i, line in enumerate(prod_lines):
        if line.startswith(f"{key}="):
            prod_lines[i] = f"{key}={val}"
            break
    else:
        prod_lines.append(f"{key}={val}")
    print(f"  已写入 {key}")

Path(".env.prod").write_text("\n".join(prod_lines) + "\n", encoding="utf-8")
PY
```

脚本逻辑已在本地用假数据验证（2026-09-11）：覆盖已存在空值、覆盖已有旧值、追加不存在的行、跳过本地空值，四种分支均正确。

### 4.3 上传到服务器

```bash
scp .env.prod ubuntu@<云端IP>:/home/ubuntu/multi-agent/.env.prod
```

### 4.4 云端验收（只查有值，不看值）

### 4.5 本地收尾

确认上传成功后，建议删除本地 `.env.prod.bak`（含密钥，别留垃圾），并确认 `git status` 无 `.env*` 文件进入暂存区。

## 6. 给云端 Agent 的执行说明 🔴 v1

**你可以直接从本节获得所需信息，无需再向本地索要密钥值。**

### 6.1 你要配什么

按 §3.2 / §3.3 / §3.4 / §3.6 四节逐项配置。最关键三项：

1. `DEEPSEEK_API_KEY`（原清单遗漏，不配则 LLM 调用全失败）
2. `SANDBOX_URL` + `SANDBOX_API_KEY`（指向你自己的 OpenSandbox）
3. `REDIS_URL`（指向你的 Redis）

### 6.2 你不要什么

- ❌ **`TAVILY_API_KEY`** —— 代码零引用，本项目未接入 Tavily。搜索走 Bocha。
- ❌ **`ZHIPU_API_KEY`** —— 本地没有，且非默认 provider。除非明确要用 glm-4-plus，否则不必配。

### 6.3 你怎么拿到值

密钥值**不会经由聊天传递**（项目硬约束）。路径是：本地合并 → `scp` 上传 → 你直接在 `/home/ubuntu/multi-agent/.env.prod` 读到。见 §4。

### 6.4 你的验收标准

⚠️ **不要以"服务启动成功"作为验收通过**——§2.4 已说明，缺 key 不会导致启动失败，只在调用时暴露。请真正发起一次 LLM 调用验证。

### 6.5 若你发现本文档与代码不符

以 `backend/src/core/config.py` 为准（本文档行号基于 2026-09-11 版本），并在回传时指出差异。
