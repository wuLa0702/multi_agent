## 3. 配置管理决策（散落现状 → 治理建议） 🔴 v2.0

> co-creator 问：配置散落多文件——**统一维护 vs 视情况而定**？哪些统一、哪些不给用户改、哪些落库、改后能否热更新不重启？

### 3.1 现状盘点（4 个载体）

| 载体 | 存什么 | 谁改 | 示例 |
|------|--------|------|------|
| `.env.dev/.env.prod`（gitignore）| **密钥 + 环境差异** | 运维/manual | API key、REDIS_URL、SANDBOX_URL、CORS |
| `core/config.py`（Settings 82 字段）| **代码默认值 + 环境开关** | 开发者改代码 | hitl_enabled、recursion_limit、llm_cache_ttl |
| `core/constants.py` | **跨文件共享常量** | 开发者 | 截断长度、超时默认 |
| **DB `settings` 表**（key/value）| **用户可改配置** | 前端设置中心 | hitl_enabled（前端开关写 DB）、log_report |
| 前端 store/localStorage | 前端 UI 态 | 用户 | 主题、mock 开关 |

### 3.2 治理建议（回答 4 问）

| 问 | 建议 | 依据 |
|----|------|------|
| **统一维护 vs 视情况** | **视情况，按"谁能改 + 改的频次"分流**——不是一刀切统一 | 密钥给用户改=事故；用户开关不给改=反需求 |
| **哪些统一维护（不给用户改）** | 密钥（.env）、路径（paths.py）、代码常量（constants.py）、核心安全开关 | 改错会崩/泄露 |
| **哪些给用户改（落 DB settings 表）** | 业务开关（hitl_enabled / log_report / auto_update / stream_accel）、模型单价（可调）| 前端设置中心已接 settings 表（upsert_many）|
| **哪些落库 vs 不落** | 用户可改且需持久 → DB；环境/密钥 → .env；UI 态 → localStorage | DB 幂等 upsert 已实现 |
| **能否热更新不重启** | ⚠️ **当前不能**——`core/config.py` 的 `get_settings()` 是 `lru_cache` 单例，进程启动读 .env，**改 DB 后运行中 settings 不刷新**；前端改 DB 后需重启后端才生效 | `config.py:252 @lru_cache` |

### 3.3 热更新建议（P2 待做）

- **方向**：DB settings 表改后需"重读机制"——方案 A：`get_settings()` 去 lru_cache（每次读 DB，慢）；方案 B：**config 加 `refresh()`**，settings API 写 DB 后调 `get_settings.cache_clear()` + 重载 DB 覆盖（快，仅 DB 项刷新）
- **面试点**：能讲"配置分层 + 热更新设计"（哪层热更新、哪层重启）
- **本清单定位**：热更新属配置工程优化，**二次推迟**到 db 改动批次（项 10 同类）

## 7. bad case 处理（生产导向，不能只关心 good case） 🔴 v1.3

> 📌 **co-creator 拍板（2026-08-11）**：往生产上靠，**一定要落实 bad case 处理，不能只关心 good case**——评估/实测发现的 bad case 逐条记录处理方式，落实后标记 ✅；生产会遇到的 bad case 优先于边缘偶发。

**处理原则**：
1. 每个 bad case 必须记录四要素：**发现途径 → 根因 → 处理方式 → 状态**
2. 处理方式**往系统层落地**（prompt 护栏 / 工具约束 / 权限校验 / 配置化），不靠人工盯
3. 优先级：生产会遇到的 bad case > 边缘偶发；**落实 bad case 优先于追求 good case 指标**
