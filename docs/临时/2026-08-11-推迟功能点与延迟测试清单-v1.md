## 1. 背景 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

评估体系开发（2026-08-10~11）过程中，发现若干**需要验证/补全但当前不阻塞主线的功能点**——评估跑数实证了模型行为倾向（自写爬虫/交付形式偏差等），系统层 prompt + 工具护栏已落地（生产自动生效），但**真实用户场景的完整验证依赖前后端联调**（前端由另一任务开发中）。

本清单集中记录这些**推迟项**，供 co-creator 后续专门处理：**延迟测试**（等条件具备）+ **补充遗忘功能**（复盘补漏）。

## 4. bad case 处理（生产导向，不能只关心 good case） 🔴 v1.3

> 📌 **co-creator 拍板（2026-08-11）**：往生产上靠，**一定要落实 bad case 处理，不能只关心 good case**——评估/实测发现的 bad case 逐条记录处理方式，落实后标记 ✅；生产会遇到的 bad case 优先于边缘偶发。

**处理原则**：
1. 每个 bad case 必须记录四要素：**发现途径 → 根因 → 处理方式 → 状态**
2. 处理方式**往系统层落地**（prompt 护栏 / 工具约束 / 权限校验 / 配置化），不靠人工盯
3. 优先级：生产会遇到的 bad case > 边缘偶发；**落实 bad case 优先于追求 good case 指标**

**已发现 bad case 清单**（已处理 ✅）：

| bad case | 发现途径 | 根因 | 处理方式 | 状态 |
|----------|----------|------|----------|------|
| 模型自写爬虫（绕过搜索自写 curl 抓取循环）| 评估体系跑数（2026-08-11）| 模型为求数据绕过受控搜索 | `fetch_url` 受控抓取工具 + 沙箱禁网（决策 2026-08-11）+ prompt「信息获取链路」指引 | ✅ 已处理 |
| 交付形式偏差（报告格式/章节不符）| 评估体系跑数 | 模型自由发挥交付格式 | `review_agent` 审核回路（P0-2）+ 修订重审 ≤2 轮 | ✅ 已处理 |
| resume 伪造 checkpoint 静默新跑（状态丢失不报错）| HITL P0-V2 实证（§3.3-③）| langgraph 无效 checkpoint_id 静默新跑 | `checkpoint_exists` 校验 → RESUME_NOT_FOUND | ✅ 已处理 |
| 报告交付被拒无限修订 | HITL 设计评审 | 无修订轮次上限 | `publish_review_max_revisions` 配置化 + resume 注入停止提示 | ✅ 已处理 |
| 审批参数超长撑爆 SSE 事件 | HITL 评审（v1.2）| publish_report 长正文未截断 | `_truncate_args` 脱敏截断 ≤300 | ✅ 已处理 |
