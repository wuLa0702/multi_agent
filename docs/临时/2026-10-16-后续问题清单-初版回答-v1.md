## 1. P0 地基（决定其余怎么放） 🔴 v1.1

### #7 工具统一格式描述，体现在哪里？ ✅

> **状态**：✅ **已开发**（`feature/20261016-tool-params`）。
> **缺口实测比初版更具体**：11 个工具 **27 个参数 description 缺失 27/27**
> ——LLM 看到的是 `{"query": {"type":"string"}}`，零语义。
> **修法**：8 个 impl 的入参改用 `Annotated[..., Field(description=…)]`
> （langchain 经 `functools.wraps` 推断签名 → 直达 `args_schema`，实测有效）。
> **不加约束**（`le=`/`min_length=` 等）——那会**拒绝现有调用**，属下一批次。
> **守卫**：`tests/test_tools/test_tool_params.py`（3 用例）——新工具漏写 description 当场红。
> **初版设想的 `contract/params.py` 未建**：约定用**测试**锁，比写一份文档更有效（文档没人查）。

**现有两处**：`tools/registry.py::ToolSpec`（**声明**——name/domain/description/risk_level/is_idempotent/requires_approval…）+ `tools/contract/result.py::ToolResult`（**出参**三态信封）。

LLM 看到的描述取自 `ToolSpec.description`；程序看到的取自 `ToolMessage.artifact`。

**顺带发现（未修，留档）**：`config`（`RunnableConfig` 内部注入参数）**仍出现在 `args_schema` 里**，
即 LLM 能"看到"它。实测 `tool()` 只自动过滤 `FILTERED_ARGS = ("run_manager", "callbacks")`；
`InjectedToolArg` 对 `RunnableConfig | None` 这种 Optional 写法**不生效**
（疑因 `_is_injected_arg_type` 只认 class 类型）。影响低（可选且无描述 → LLM 不会填），属 schema 卫生问题。

### #11 返回值结构化放在了哪里？ ✅ 无缺口

> **现状核实（2026-10-16）**：已完整落地，**无需开发**。

**原则**：落点已定，**别再开第二处**——本项目已因"同一件事写两遍"吃过四次亏（工具清单/审计方言/重试参数/错误响应）。

### #5 工具管理中心，在哪里处理（鉴权、超时、重试、埋点、异常、业务）？ ✅ 无缺口

> **现状核实（2026-10-16）**：六项**都有落点**，无需开发。
> 唯一可议项——「**超时**未进登记表」：但各工具**已自设超时**
> （`fetch_url` 读 `settings.tool_timeout_seconds`、`run_command_in_sandbox` 有 `timeout` 入参、
> `search` 有独立常量）。再包一层 registry 级超时会与工具内超时**重复**，
> **判断：不引入**。（若将来确有统一需求，再按 `retry` 的模式补 `ToolSpec.timeout`。）

**分三层，别都塞进一个中间件**：

| 关注点 | 落点 |
|--------|------|
| 鉴权 / 审批 | `agent/hitl/`（读 registry 的 `requires_approval`） |
| 超时 / 重试 | registry **声明** + 装配时包装（`_apply_retry()`） |
| 埋点 | `tools/runtime/audit.py` → `emit()` |
| 异常 / 错误码 | `tools/contract/error_map.py`（**唯一翻译处**） |
| 业务 | 各 `tools/impl/*.py` |

**一句话**：注册表只**声明**、运行时不决策；策略判断全在编排层。

### #8 如何分层分领域放工具？ ✅ 无缺口

> **现状核实（2026-10-16）**：四层已定，无需开发。

### #10 如何引入工具向量检索？何时用？

**触发条件**：**工具数 > 20** 才值得（人/LLM 都记不住清单时）。**现在 8 个，不需要。**

**引入方式**：工具描述 embed → 存向量 → 用户请求 embed → top-k 工具注入 prompt。

**与意图识别共用同一套向量设施**——你说的"刚好引入"判断正确。

**选型**：`sentence-transformers` + **pgvector**（你已有 PG，不必引 faiss）。

---

### #18 向量召回如何做？bm25 基线？

**现状：完全没做**——记忆检索也只有关键词 `search_memory()`，依赖里无 numpy/faiss。

**推荐路径（顺序不可颠倒）**：
1. **先做 bm25 基线**（`rank_bm25`，纯 Python 零依赖）→ 建评测集 + **recall@k 基线**
2. 再上向量（`sentence-transformers` + pgvector）
3. 最后 **hybrid**（bm25 + 向量 RRF 融合）

**没有基线就别上向量**——否则无法证明"提升了"（面试也讲不出数据）。

### #6 A2A 代码例子，是用来做子 agent 吗？

⚠️ **概念要先分清**：**A2A 是跨系统协议**（HTTP/SSE，服务对外），**子 agent 是进程内调用**——两者不是一回事。

本项目 A2A 设计稿**已被撤下**（2026-10-16 拍板：意图服务仅供内部、不对外暴露）。

**做子 agent 用现成的更轻**：deepagents 内置 **`task` 工具**（主 agent → 子代理委派）+ Send API 并行。真有**外部系统对接**需求时再上 A2A。
