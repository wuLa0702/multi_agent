## 0. 结论（先读这里） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v2</span>

**核心结论**：最终版 13 条规范与项目现役规则**约一半已有、一半新增**——直接照抄会造成双规则打架。本方案做三件事：

1. **冲突裁决**：最终版"文件 >800 行 / 函数 >80 行"与现役"750 关注 1000 强制 / 80·160 铁律"→ **统一为"精确口径 + 更严值"**（§2）；"分层目录 agent/service/repo/util"通用模板与项目现有目录（api/agent/mcp/…）**以项目现状为准做职责映射**（§3.2）
2. **现状确认**：13 条中 **6 条已有落地**（路径 paths.py、异常 errors.py、日志基础 04-logging、环境 .env 体系、错误码 10-api、测试 20-testing）——不重复造，转成检查项
3. **补空白**：新增 7 项——**跨层调用禁令、模块 README、统计口径精确化、异常四分类 + 禁裸捕获、依赖与导入规范、代码干净度、可测试性补强**；工具侧补 **AST 校验脚本**（现役"提交前过线"无工具支撑）

**v2 相对 v1 的关键修订**（对应最终版深化）：
- **统计口径精确化**：有效代码 = 总行 − 注释 − 空行 − 单独导入行 − 类型注解 − 装饰器 − 常量定义区（§2.1）
- **底层函数精确定义**：通用工具/基础算法/通用解析/通用封装豁免；业务逻辑/Agent 逻辑/流程控制**一律不豁免**（§2.3）
- **跨层调用禁令**：Agent 禁直调底层存储/第三方 SDK/跨多层跳跃（§3.3）
- **日志认知修正**：注释 ≠ 日志——关键节点/入参出参/异常**必须有日志**（中间件统一打点），注释只负责开发阅读（§6）
- **异常四分类 + 禁裸捕获**：可重试/不可重试/业务/系统四类；禁止超大范围 try-except 掩盖故障（§7）

**执行顺序**（§14）：P0 先建 AST 校验脚本 → P1 批次整改存量（规范文档与目录结构 → 路径/常量/文案收口 → 超大文件函数拆分 → Agent 清业务 → 降级/日志/异常 → 环境/依赖/测试）→ **评审通过前不改任何后端代码**。

## 2. 阈值统一决策（文件 / 函数 · 精确口径） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v2</span>

### 2.1 统计口径（v2 精确化，最终版 §2 采纳）

**有效业务代码行** = 总行数 − 以下不计项：

| 不计项 | 说明 |
|--------|------|
| 注释 / docstring | 单行 # 注释、多行 docstring |
| 空行 | 纯空白行 |
| 单独导入行 | `import` / `from ... import` 独占行 |
| 类型注解 | 签名行注解、变量 `: Type` 注解（与语句同行不剥离） |
| 装饰器 | `@xxx` 独占行 |
| 常量定义区 | 文件头部模块级 `UPPER_SNAKE = ...` 块（判定：模块级常量赋值连续区） |

> 实现：AST 遍历（`ast.parse`）统计——AST 节点行号集合 + 注释/空行行号剔除，§13 工具落地。

### 2.2 文件阈值（统一后）

| 线 | 阈值（有效业务代码行） | 动作 |
|----|------------------------|------|
| 关注线 | > 750 | 标记拆分候选，人工评估 |
| **强制线** | > 800 | **必须拆分**（最终版采纳，替代现役 1000）；拆分按**单一职责/业务能力/场景维度**，禁止随机切块 |

> 现状核查：当前最大 `main_agent.py` 501 行 / `chat.py` 423 行（总行）——去注释/导入后有效行更少，**存量无超限文件**，阈值主要约束增量。

### 2.3 函数阈值（统一后）+ 底层函数精确定义

| 线 | 阈值（非底层函数，有效代码） | 动作 |
|----|------------------------------|------|
| **强制** | > 80 行 | **必须拆分解耦**（最终版采纳 80 强制；v1 的 160 线降级为拆分质量底线） |

**裁决说明（v2 明确）**：最终版"非底层 >80 必须拆分"与现役"80 考虑拆分 / 160 必须拆分"的差异在**强制力**：
- **采纳最终版更严语义**：>80 行 → 必须拆分（不再是"考虑"）
- **160 线保留为拆分质量底线**：拆解后任何单一函数仍 >160 → 拆分失败，必须继续拆
- 底层豁免 **精确判定**（最终版补全，采纳）：

| 可豁免（底层） | 不豁免（必须拆） |
|---------------|-----------------|
| 全局通用工具函数 | 业务逻辑 |
| 基础算法（如 tokenizer、分页计算） | Agent 编排逻辑 |
| 通用解析 / 通用封装类 | 流程控制逻辑 |

> 豁免函数必须在 docstring 声明"底层函数，按规范豁免"，便于校验脚本白名单。

### 2.4 对现役规则的修订建议（评审通过后回写 01-coding-style.md）

- 文件线：`>1000 必须拆分` → `>800 必须拆分`；口径改"有效业务代码行"（§2.1 精确定义）
- 函数线：80 从"考虑拆分"升级为"必须拆分"；160 保留为质量底线；补底层函数精确定义表

## 3. 目录、命名与分层（含跨层禁令 + 模块 README） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v2</span>

### 3.1 目录归属表（backend/src/，以项目现状为准）

| 项目目录 | 放什么 | 禁止 |
|----------|--------|------|
| `api/` | 路由/处理器（仅编排，禁业务实现） | 禁直接写 SQL、禁调 LLM 细节 |
| `agent/` | **Agent 编排 + 全部 Agent 能力子域**（v2.3 统一收纳）：tools/（工具实现，自 mcp/tools/ 迁入）、memory/、tasks/、subagents/、middlewares/、prompts/、hitl.py、rubrics.py | 禁业务域实现散落其他目录 |
| `mcp/` | **纯 MCP 协议/网关层（v2.3 收敛）**：client.py（多 server 连接管理）、registry.py（注册表=工具出口）、server.py（FastMCP 端点）——**只注册/转发，零业务实现** | 禁放业务工具实现（→ agent/tools/） |
| `sandbox/` | 沙箱适配层（仅 API 面，实现细节不泄露） | 禁直接依赖 api/ 层 |
| `db/` | schema/DAO/repository（**唯一 SQL 出口**） | 禁其他目录手写 SQL |
| `core/` | 横切：config/paths/errors/logging/constants | 禁依赖业务目录（反向依赖违规） |
| `schemas/` | Pydantic 请求/响应模型 | 禁含业务逻辑 |
| `llm/` | LLM 适配/重试（唯一 LLM 出口） | 禁绕过 adapter 直接调 SDK |
| `skills/` | **Skill 生命周期运维域（顶层保留）**：marketplace/installer/templates——外部 skill 安装/卸载/启停，非 Agent 能力 | 禁放业务工具实现 |

### 3.2 六层模型映射（最终版 §4/§8 融合，以项目现有目录为准）

> 最终版的通用分层模板（agent/service/repo/util/config/constant/common/middleware）是**行业通用命名**，与项目既有目录不一——**不重命名现有目录**（架构文档已拍板依赖单向），做职责映射：

| 最终版分层 | 项目对应 | 落地说明 |
|-----------|---------|---------|
| Agent 编排层 | `agent/`（main_agent.py） | 只调度不实现 |
| Service 业务层 | **`agent/` 下能力子域**（v2.3 统一）：`tools/`（工具实现）、`memory/`、`tasks/`、`subagents/`、`skills/`（Skill 运维域） | 业务能力实现统一收纳，不再散落 |
| Repo 数据层 | `db/` | 数据读写/持久化唯一出口 |
| Util 工具层 | `core/` 内工具函数、`llm/adapter.py` | 通用能力、无业务属性 |
| Config 配置层 | `core/config.py` | 环境配置/开关唯一入口 |
| Constant 常量层 | `core/constants.py`（§4.1 新建） | 跨文件常量唯一归处 |
| Common/中间件 | `agent/middlewares/`、`core/` | 横切能力 |
| 协议/网关层 | `mcp/`（v2.3 收敛为纯协议层） | 工具出口：registry 注册 + client 连接 + server 端点，零业务实现 |

**跨层禁令（v2 明示，最终版 §4/§8 采纳）**：
1. 只能上层调用下层：`api → agent → 能力目录 → db/`；`core/llm/schemas` 为公共底座
2. **禁止跨多层跳跃调用**：如 api/ 直接调 db/、agent/ 直接调第三方 SDK

## 6. 日志体系深化（修正"注释替代日志"误区） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v2</span>

### 6.1 认知修正（v2 关键修订，最终版 §6 采纳）

> **注释不能替代日志**——二者分工明确：
> - **代码注释**：负责开发阅读、逻辑说明
> - **日志**：负责线上排查、链路追踪、异常定位
> - v1 表述"只保留关键注释 + 异常日志"易被误读为"用注释代替日志"——**v2 更正**：关键节点/入参出参/异常**必须打日志**（由统一中间件覆盖，函数内仅异常分支与关键状态补打），注释不做日志用途。

### 6.2 现状与差距

- ✅ 已有：`core/logging.py` 唯一配置点、UTF-8、每日/50MB 滚动、14 保留
- ❌ 缺口：**无链路埋点**（request 级调用链追踪）、日志级别**无运行时开关**、函数内日志冗余无约束

### 6.3 统一埋点中间件设计（新增 `agent/middlewares/logging_trace.py`）

| 设计点 | 方案 |
|--------|------|
| 职责 | 每个请求/图执行注入 `request_id`，LLM 调用/工具调用/图阶段自动打点（info 级：耗时/输入摘要/异常） |
| 机制 | 复用现有 middleware 链（与 ToolAudit/TokenUsage 同构，`wrap_model_call` 挂模型调用 + 图事件钩子） |
| request_id | `api/` 层生成 → context 注入 → 中间件透传 → 日志 `extra={"request_id": ...}` |
| 分级开关 | `settings.log_level`（DEBUG/INFO/WARN/ERROR 严格区分，**可配置开关**——最终版 §6.1）→ 中间件按级过滤 |
| 日志内容 | 只保留**关键节点、入参出参、异常报错**（最终版 §6.1）；不逐 token；中间件已覆盖的节点函数不再自行打点 |
| 全局格式 | 统一打印格式，含链路关键信息（request_id/agent 名/耗时） |
| 与 04-logging 关系 | 04-logging 管"写到哪/怎么滚"，本中间件管"打什么点"——不冲突 |

### 6.4 校验项

- 函数内 `logging` 调用 > 3 处且非异常分支 → 标记"冗余日志，应移交中间件"
- 关键节点（业务入口/出口/异常）**零日志** → 标记"缺日志"（注释不抵日志）

## 7. 容错降级设计（异常四分类 + 链路兜底） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v2</span>

### 7.1 异常四分类（v2 新增，最终版 §7/§10 采纳）

| 分类 | 定义 | 处理 |
|------|------|------|
| 可重试异常 | 瞬时故障（网络/超时/限流） | 重试（llm/retry.py 模式）后仍失败 → 降级 |
| 不可重试异常 | 参数错/状态错/不存在 | 直接返回业务错误码，不重试 |
| 业务异常 | 业务规则不满足 | 业务错误码 + 降级返回/默认兜底数据 |
| 系统异常 | 未知内部错误 | 记 error 日志 + 告警提示，按链路矩阵降级 |

**禁令（最终版 §7 采纳）**：**禁止超大范围 try-except 裸捕获**（`except Exception` 包整段业务）掩盖真实故障——捕获必须精确到异常类型、必须处理（记录/转换/降级），不吞异常、不盲抛异常。

### 7.2 chat 链路降级矩阵（v1 保留）

| 链路节点 | 失败形态 | 降级策略 | 断流？ |
|----------|----------|----------|--------|
| 会话/消息落库 | SQLite 错误（可重试） | 重试 1 次 → 降级内存会话（响应正常，标注未持久化） | 否 |
| 记忆注入/读取 | Store 不可用 | **静默降级**：跳过记忆注入，Agent 无记忆继续 | 否 |
| 记忆写入 | 同上 | 记 error 日志 + 队列重试（P2），不阻塞响应 | 否 |
| LLM 调用 | 超时/不可用（可重试） | 重试耗尽 → SSE `error` 事件（retryable=true），前端可重试 | 是（协议设计如此） |
| 工具调用 | 工具异常（业务/系统） | 工具级精确捕获 → 错误结果回传 Agent（Agent 自行处理/放弃） | 否 |
| 子代理 | 子图异常 | 错误摘要回传主 agent（继续主流程） | 否 |
| 沙箱执行 | 沙箱不可用 | 返回工具错误 + `AUTH/ENV` 提示，主流程继续 | 否 |
| 审批（P1 后） | checkpointer 异常 | 拒绝审批请求（400 RUN_NOT_FOUND），会话状态保持 | 否 |

**原则**：除"LLM 主链路"外，全部**不因单点失败断流**——失败降级 + 默认兜底数据 + 日志留痕（最终版 §7）。实施时逐节点核对现有 try/except 是否满足精确捕获。
