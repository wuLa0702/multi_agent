## 1. 背景与目标 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

**Why（双动机）**：
1. **面试**（2026-08-10 调研定案）：面试第一分水岭 = 评估与可量化结果（baseline 对比）；面试指南 §3.2 标红「项目缺评估体系」为 🔴 高短板——没有数据，多 Agent 全部技术工作无法证明有效
2. **工程**：生产落地必须回答"你的 Agent 到底有没有用"——准确率、成本、延迟是可交付的底线

**目标**：建一个**可复跑、可对照、有数据的离线评估管道**——给定研究任务集，跑 Agent（可切换单/多配置），输出：研报质量分 + 事实性指标 + 成本/延迟指标 + **单 vs 多 Agent 对照报告**。

**边界（不做）**：不做在线评测平台、不做 dashboard、不做线上灰度——个人项目离线评估脚本足够。

## 2. 评估对象与指标定义（四类 9 项） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

**评估对象**：研究任务（task）→ 产出研报（report）+ 执行过程（trace 收集：消息/工具调用/耗时/成本）。

| 类别 | 指标 | 定义/公式 | 计算方式 | 可信度 |
|------|------|-----------|----------|--------|
| **A 事实性** | A1 引用可溯源率 | 可核验引用数 ÷ 引用总数（引用编号在 sources 列表中且指向真实条目） | **规则自动**（正则提取引用标注 → 对表） | 🟢 高（确定性） |
| | A2 来源真实率 | 来源 URL/文档经 LLM 抽查确认真实存在 ÷ 抽查数（每报告抽 3-5 条） | LLM-judge + 人工复核抽样 | 🟡 中 |
| | A3 事实准确率 | 抽样 N 条论断人工核对正确 ÷ N（golden 标注对照） | 人工标注（P2，流程化） | 🟢 高（人类仲裁） |
| **B 质量** | B1 章节完整度 | judge 按 report_completeness rubric 打分 1-5 | LLM-as-judge（复用 rubrics.py 模板） | 🟡 中 |
| | B2 来源可靠性 | judge 按 source_veracity rubric 打分 1-5（无编造/区分事实与推测） | LLM-as-judge | 🟡 中 |
| **C 过程** | C1 任务完成率 | 成功产出终稿任务数 ÷ 任务总数 | 规则自动 | 🟢 高 |
| | C2 工具调用成功率 | 成功工具结果 ÷ 工具调用总数（从 trace 审计） | 规则自动 | 🟢 高 |
| **D 成本** | D1 端到端耗时 | 任务 start → done 秒数（SSE done 事件 duration_ms 已有） | 规则自动 | 🟢 高 |
| | D2 Token/费用 | 上下文用量统计（token 中间件已存库） | 规则自动 | 🟢 高 |

> **设计原则**：**规则可算的指标优先**（A1/C/D 全自动、确定性高）；LLM-judge 只用于"质量主观维度"（B 类）且**输出走纯文本 + 规则解析**——复用项目已实证教训：国产模型 response_format 三态全挂（P1-2 实证），judge 禁止依赖结构化输出强制。

## 3. 数据集设计（任务集 + golden 标注） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

**存储**：`data/eval/tasks.jsonl`（每条一行 JSON）+ `data/eval/golden/`（每任务一个 golden 标注文件）。路径在 `core/paths.py` 登记（§4.2 规则：新增数据目录必须登记）。

**任务集规格（10-20 个起步，可扩展）**：

| 字段 | 说明 | 示例 |
|------|------|------|
| `id` | 任务唯一 ID | `task-001` |
| `title` | 任务名 | 调研 DeepSeek 2026 最新模型能力 |
| `query` | 用户输入（喂给 chat 接口） | 请调研 XX 并产出报告 |
| `difficulty` | easy / medium / hard | medium |
| `expected_sections` | 期望覆盖章节 | [市场格局, 竞品, 风险] |
| `expected_sources` | 期望出现的来源类型 | [官网, 行业报告] |
| `fact_points` | 期望论断要点（人工预填，供 A3 核对） | [模型参数量, 发布时间] |

**golden 标注文件**（`golden/task-001.md`）：人工预写的参考答案（事实要点 + 来源 + 完成标准）——**评估的 ground truth**。

> 标注工作量：10 个任务约 2-3 小时（人工预填 fact_points + expected_sections），可分批建。

## 4. 评估流程（harness 管道） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

```
eval_harness.py --tasks data/eval/tasks.jsonl --config single|multi
  │
  ├─ 1. 加载任务集 + golden
  ├─ 2. 逐任务：调用 chat API（真实 LLM，mock 不适用——这是 eval 不是测试）
  │     └─ 收集：SSE 事件流（done 事件含 context_used/duration_ms）+ 工具审计 trace
  ├─ 3. 规则指标计算（A1/C/D：引用对表、完成判定、成本聚合）
  ├─ 4. LLM-judge 打分（B1/B2：复用 rubric 模板 → 文本输出 → 规则解析 1-5）
  ├─ 5. 生成报告：data/eval/reports/{run_id}.json + .md（含逐任务明细 + 汇总表）
  └─ 6. baseline 对照：--config single 与 --config multi 各跑一遍 → 对比表
```

**复跑性**：同任务集 + 固定模型配置 → 可复现；报告带 run_id + 时间戳 + 配置指纹（§4.6 要求"可复现"）。

## 5. baseline 对照实验（单 Agent vs 多 Agent） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

**目的**：回答面试必考题「多 Agent 到底值不值」——用数据说话，也是整个评估体系最大的面试卖点。

| 配置 | 结构 | 说明 |
|------|------|------|
| `single` | 主 agent 直连工具（搜索/沙箱），无子代理 | baseline（对照组） |
| `multi` | 主 agent + search_agent 子代理（P0-2 后 + 审核子代理） | 实验组 |

**对照输出表**（每任务 + 汇总）：

| 指标 | single | multi | 差值 | 结论 |
|------|--------|-------|------|------|
| 任务完成率 | X% | Y% | Δ | 多 Agent 是否值得 |
| 引用可溯源率 | X% | Y% | Δ | 质量是否提升 |
| 章节完整度（1-5） | X | Y | Δ | |
| 端到端耗时 | Xs | Ys | Δ | 代价（延迟） |
| Token 用量 | X | Y | Δ | 代价（成本） |

> **面试话术模板**（§4.2 STAR 数据收尾）："我做了对照实验：同 20 个任务，多 Agent 引用可溯源率从 X% 提到 Y%，但成本是单 Agent 的 Z 倍——所以我又加了工具审计和用量告警控制成本"——**主动讲代价 = 证明踩过坑**。

### 7.1 代码骨架（`backend/scripts/eval_harness.py`）

```python
"""评估管道：研报质量评估 + 单/多 Agent 对照实验（设计-评估体系-v1 §4）。

用法：
    python scripts/eval_harness.py --tasks data/eval/tasks.jsonl --config single
    python scripts/eval_harness.py --tasks data/eval/tasks.jsonl --config multi
产出：data/eval/reports/{run_id}.json + .md（含汇总对照表）
"""
from __future__ import annotations

import argparse
import asyncio
import json
import re
import time
import uuid
from dataclasses import dataclass, field
from pathlib import Path

# ── 指标聚合结果 ──
@dataclass
class TaskMetrics:
    """单任务评估结果（§2 四类指标）。"""
    task_id: str
    completed: bool = False            # C1
    tool_calls: int = 0
    tool_success: int = 0              # C2 = tool_success / tool_calls
    duration_ms: int = 0               # D1
    context_used: int = 0              # D2
    citations_total: int = 0
    citations_verified: int = 0        # A1 = verified / total
    completeness_score: float = 0.0    # B1（LLM-judge 1-5）
    veracity_score: float = 0.0        # B2
    errors: list[str] = field(default_factory=list)

    def a1_ratio(self) -> float:
        """引用可溯源率（规则计算，§2 A1）。"""
        return self.citations_verified / self.citations_total if self.citations_total else 0.0


# ── 规则指标：引用可溯源率（A1）──
CITATION_RE = re.compile(r"[\[【](\d{1,2})[\]】]")  # 研报中 [1] 式引用标注


def count_verified_citations(report_text: str, sources: list[str]) -> tuple[int, int]:
    """统计可核验引用数：引用标注编号是否在 sources 列表范围内。

    Args:
        report_text: 研报全文
        sources: 收集到的来源列表（搜索/文档）

    Returns:
        (verified, total) 引用可溯源率 = verified / total
    """
    refs = {int(m) for m in CITATION_RE.findall(report_text)}
    if not refs:
        return 0, 0
    verified = sum(1 for r in refs if 1 <= r <= len(sources))
    return verified, len(refs)


# ── LLM-judge（B 类，纯文本 + 规则解析，规避 response_format 三态全挂）──
JUDGE_PROMPT_TEMPLATE = """你是研报质量评估员。对以下研报按两个维度打分（1-5 分，整数），
只输出两行，格式严格如下：
完整度: <1-5>
可靠性: <1-5>

评分标准：
- 完整度：{completeness_rubric}
- 可靠性：{veracity_rubric}

研报内容：
{report}
"""


def parse_judge_output(text: str) -> tuple[float, float]:
    """解析 judge 纯文本输出为 (completeness, veracity)。失败 → (0.0, 0.0) 计入错误。

    坑（P1-2 实证）：国产模型 response_format 三态全挂 → judge 输出不强制 JSON，
    用正则解析；解析失败降级为 0 分并记录（可重试一次后放弃）。
    """
    m_c = re.search(r"完整度:\s*([1-5])", text)
    m_v = re.search(r"可靠性:\s*([1-5])", text)
    if not (m_c and m_v):
        return 0.0, 0.0
    return float(m_c.group(1)), float(m_v.group(1))


# ── 单任务执行（复用 chat SSE 契约，mock 不适用——eval 走真实链路）──
async def run_one_task(task: dict, config: str, api_base: str) -> TaskMetrics:
    """跑一个研究任务：调用 chat 接口 → 收集产出 + trace → 算指标。

    Args:
        task: tasks.jsonl 单条（id/query/expected_sections/...）
        config: single | multi（决定挂不挂子代理）
        api_base: 后端地址（默认 http://127.0.0.1:8010）

    Returns:
        TaskMetrics：四类指标聚合
    """
    import httpx  # 复用后端 chat 接口（SSE 流，事件协议不变）

    metrics = TaskMetrics(task_id=task["id"])
    # 1) POST /v1/chat/stream（session_id 新建）
    # 2) 流式收集：done 事件 → duration_ms / context_used；
    #    tool_call 事件计数 → tool_calls；error 事件 → errors
    # 3) 终稿 = 全部 token 事件拼接 → count_verified_citations(report, sources)
    # 4) judge 调用（llm/adapter.get_chat_model 文本输出）→ parse_judge_output
    raise NotImplementedError("§7 骨架——实施时按此形态手写核心逻辑")


# ── 汇总报告 ──
def build_report(run_id: str, config: str, metrics_list: list[TaskMetrics]) -> dict:
    """聚合为报告 dict（写 reports/{run_id}.json + .md）。

    Returns:
        报告 dict：config/run_id/汇总（完成率/A1/B1/B2/D1/D2）+ 逐任务明细
    """
    n = len(metrics_list) or 1
    done = [m for m in metrics_list if m.completed]
    return {
        "run_id": run_id,
        "config": config,
        "summary": {
            "tasks": len(metrics_list),
            "completion_rate": len(done) / n,
            "avg_citation_traceability": sum(m.a1_ratio() for m in metrics_list) / n,
            "avg_completeness": sum(m.completeness_score for m in metrics_list) / n,
            "avg_veracity": sum(m.veracity_score for m in metrics_list) / n,
            "total_duration_ms": sum(m.duration_ms for m in metrics_list),
            "total_context_used": sum(m.context_used for m in metrics_list),
        },
        "per_task": [m.__dict__ for m in metrics_list],
    }


async def main() -> None:
    """CLI 入口：--tasks / --config / --api-base。"""
    parser = argparse.ArgumentParser(description="研报质量评估管道")
    parser.add_argument("--tasks", type=Path, required=True)
    parser.add_argument("--config", choices=["single", "multi"], default="single")
    parser.add_argument("--api-base", default="http://127.0.0.1:8010")
    args = parser.parse_args()

    tasks = [json.loads(line) for line in args.tasks.read_text(encoding="utf-8").splitlines() if line.strip()]
    run_id = uuid.uuid4().hex[:8]
    metrics = await asyncio.gather(*(run_one_task(t, args.config, args.api_base) for t in tasks))
    report = build_report(run_id, args.config, metrics)
    out_dir = Path("data/eval/reports")
    out_dir.mkdir(parents=True, exist_ok=True)
    (out_dir / f"{run_id}.json").write_text(json.dumps(report, ensure_ascii=False, indent=2), encoding="utf-8")
    print(json.dumps(report["summary"], ensure_ascii=False, indent=2))


if __name__ == "__main__":
    asyncio.run(main())
```

### 8.2 追问链预演（§3.3 五层自答）

| 追问 | 预演答案 |
|------|----------|
| **为什么做评估体系？** | 生产落地必须回答"Agent 有没有用"；面试第一分水岭就是可量化结果 + baseline |
| **对比过什么方案？** | RAGAS（偏 RAG 检索指标，不覆盖报告质量/成本）；人工全量评测（成本高不可复跑）；LLM-as-judge（快但需防偏见）→ 组合：规则指标（确定性）+ judge（主观维度）+ 人工抽样（仲裁） |
| **遇到什么坑？** | ①国产模型 response_format 三态全挂（P1-2 实证）→ judge 纯文本 + 规则解析；②judge 自赞偏见 → 只做相对对比（single vs multi 同 judge）不报绝对分；③报告无引用标注 → 任务 prompt 强制引用编号格式 |
| **怎么量化效果？** | 同 20 任务集，多 Agent vs 单 Agent：引用可溯源率 Δ%、章节完整度 Δ、成本倍数、延迟 Δ——数据说话 |
| **为什么这个指标集？** | 事实性（A：数据可不可信）> 质量（B：报告好不好）> 过程（C）> 成本（D）——面试官最关心可信度，先回答"信不信得过" |

### 8.3 可量化结果（落地后预期产出）

- 10-20 任务评估集 + golden 标注（人工 2-3 小时）
- `eval_harness.py` 可复跑（run_id + 配置指纹）
- **对照报告**：单 vs 多 Agent 六项指标对比表（§5 表）——面试直接甩数据
