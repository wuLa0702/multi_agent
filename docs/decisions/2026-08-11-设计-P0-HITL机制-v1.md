### 2.2 追问链预演（指南 §3.3 五层链 × 三问自答）

**Q1：为什么做 HITL？什么时候该停下来问人？**

- 为什么：Agent 自动执行有副作用动作（沙箱跑代码、写文件、执行技能脚本）时，人类必须保留执行权闸门——模型判断不可 100% 信任（有"模型绕过搜索自写 curl 抓取循环"的跑偏实证，见 learnings 2026-08-11 爬虫循环）。同时目标模糊时盲目执行 = 浪费 token 和出错概率上升。
- 对比过什么方案：① 全部工具无差别审批 → 打断感强，只读搜索也被审（否决：只读工具无副作用不审）；② 全部不审 → 无执行权闸门（否决：危险动作裸奔）；③ **按风险分级审**（✅ 选定）：高危（任意代码执行）→ approve+edit+reject；中危（命令/文件/技能）→ approve+reject；只读（搜索）→ 不审。选型依据：官方 InterruptOnConfig 天然支持按工具声明决策集，配置即挂中间件。
- 坑与量化：审批恢复链路是最大坑——`astream_events` 不产中断事件（旧设计假设错误），伪造 checkpoint_id 静默新跑；用 `GraphCallbackHandler.on_interrupt` 拿到真实 checkpoint_id 才闭环（§3.3 实证）。量化：需求澄清 + 审批双场景端到端实测通过（§2.3）。

**Q2：需求澄清怎么实现？为什么不靠"模型自己猜"？**

- 为什么：研究任务的用户输入天然模糊（"帮我调研一下 X 行业"——范围、深度、交付形式都不明），模型猜 = 大概率跑偏 → 返工 → 成本翻倍。**让模型在模糊时主动问**，比事后纠错便宜。
- 对比过什么方案：① 提示词"模糊时先问"（纯 prompt，模型自律不保证）；② 独立澄清接口（前端强约束流程，重）；③ **ask_human 工具 + respond 决策**（✅ 选定）：把"问人"做成工具调用，模型想不清楚就调 ask_human(message)，命中 interrupt_on 审批 → 人类回答经 respond 决策以 ToolMessage 形式回给模型——**"问"成了模型的工具能力，不需要自律**。官方 respond 决策语义正是为此设计（"仅 ask_user 类工具"）。
- 坑与量化：respond 决策绝不能配给副作用工具（官方警告：会被模型当成功结果）——ask_human 的 allowed_decisions 只开 respond；工具体内 stub 抛错防御真执行。量化：澄清场景 = 1 次工具调用 + 1 次人类回答 + 恢复后模型带答案继续（端到端实测断言，§8 用例 9）。

**Q3：审批链路怎么恢复？中断点状态怎么找？**

- 为什么：审批中断时图状态在中断点落 checkpoint（langgraph 自动），恢复必须精确回到该点继续——"从哪里断，从哪里续"，且不能重放已审动作。
- 对比过什么方案：① resume 走最新 checkpoint（不带 checkpoint_id，langgraph 默认语义）；② **中断时从 GraphInterruptEvent 取真实 checkpoint_id，approve 事件携带，resume 用它精确定位**（✅ 选定）——多轮审批场景（同会话多次中断）下，最新 checkpoint 可能是别的断点，精确 id 最稳。
- 坑与量化：发现现有 resume 链路潜伏 bug——chat.py 把自生成 UUID 当 checkpoint_id 传，langgraph 精确匹配不到 → **静默新跑**（状态丢失不报错，实证 §3.3-③）。修复 + 回归测试（§8 用例 10）。量化：resume 恢复状态一致性测试（mock 中断 → 决策 → 恢复后工具参数正确）。

## 4. 分·机制设计：四场景 × 一机制

### 4.1 场景总览

> **一机制**：所有场景都是"模型要做一个动作 → 命中人类决策点 → 中断挂起 → 人类决策 → 恢复继续"。区别只在**中断对象**（工具动作 vs 提问）与**决策集**。

| 场景 | 触发 | 中断对象 | 决策集 | 状态 |
|------|------|----------|--------|------|
| **A 需求澄清** | 模型目标/约束模糊，调 `ask_human(message)` | ask_human 工具 | respond（人类回答 = 工具结果）| ✅ P0 落地（§4.2） |
| **B 高风险审批** | 副作用工具命中 interrupt_on 风险分级 | run_code / run_command / 文件 / 技能 | approve / edit / reject（按风险分级）| ✅ P0 落地（§4.3） |
| **C 中途确认** | 模型计划完成，调 `ask_human("计划如上，是否开始？")` | ask_human 工具（同 A）| respond | 🟡 同一机制顺带覆盖（§4.4） |
| **D 输出审核** | 交付物（研报）生成后人类确认发布 | 交付动作（P2 新增审核工具/发布闸门）| approve / reject / edit | ❌ P2 预留（§4.5） |

### 4.2 场景 A：需求澄清（ask_human 工具 + respond 决策）

```
用户：帮我调研一下 AI Agent 行业（模糊目标）
  → 模型：目标范围/深度不明 → 调 ask_human(message="调研范围是？侧重哪些细分？报告形式？")
  → interrupt_on 命中（ask_human 已注册）→ ⏸ 中断挂起（checkpoint 落盘）
  → 前端澄清卡片（B2 卡片 respond 模式）→ 用户回答："2026 年市场规模 + 头部玩家格局，800 字摘要"
  → POST /v1/chat/approve {action:"respond", note:"2026 年市场规模 + 头部玩家格局，800 字摘要"}
  → 恢复：Command(resume) → ask_human 收到 respond → 合成 ToolMessage(答案) → 模型带着答案继续
```

- 工具签名：`ask_human(message: str) -> str`——**真实实现是 stub（抛错防御）**，因为 respond 决策下工具永不被执行（中间件合成 ToolMessage 顶替）
- allowed_decisions **只开 `["respond"]`**（官方语义：respond 仅用于 ask-user 类工具；绝不配给副作用工具）
- 系统提示词补一行引导：*"用户目标/约束模糊时，调用 ask_human 澄清后再继续"*（prompts 分层组装增量，§7.2）
- 面试点：模型"学会先问"不是靠自律，是**把问人变成工具能力**（respond 决策语义）

### 4.3 场景 B：高风险审批（interrupt_on 风险分级，现状配置直接复用）

```
模型：调 run_code_in_sandbox({code:"rm -rf /data"})
  → interrupt_on 命中（高危：approve+edit+reject）→ ⏸ 中断挂起
  → approve 事件（run_id=真实checkpoint_id + action_requests + allowed_decisions）→ 本次流结束
  → 前端 B2 审批卡片（按钮：批准 / 拒绝 / 编辑参数）→ 用户决策
  → POST /v1/chat/approve → 202 → resume 重连 → 图继续（approve 原样执行 / reject 跳过+反馈）
```

- 分级配置已在 `hitl.py`（§3.1-#1），本设计**只补链路**：事件、API、恢复
- reject 的 message 是质量关键（官方：反馈决定模型是否换方案）——前端 note 输入框已有

### 4.4 场景 C：中途确认（同一 ask_human，计划确认）

- 零新增代码：模型研究计划拟定后调 `ask_human("检索计划：1)…2)…，确认开始？")`——走场景 A 同链路
- 实现时机的保障：prompt 引导（计划类任务在委派子代理/沙箱前先确认）；评估体系实证过"任务跑偏"（模型跳过约束自写 curl 循环，learnings 2026-08-11），**中途确认是对跑偏的工程兜底**——面试讲"计划确认"时引这个 bad case
- 面试价值：四场景达标三个（做二超一），且每个都是同一机制的不同决策集——架构统一性好讲

### 4.5 场景 D：输出审核（P2 预留，只给方向）

- 需求：研报生成后人类审核再"交付"（发布/发送/落盘）
- 方向（P2 落地时二选一）：
  - **a. ask_human 收尾确认**（零新机制）：报告完成时模型调 `ask_human("报告已生成，确认交付？")`，reject 带修改意见 → 模型修订重出（借"修订回路"经验，评估体系 review_agent 同款）
  - **b. 独立发布工具 + interrupt_on**：`publish_report` 工具配 approve/reject/edit——语义更"重"，适合对外动作
- 本设计不做：指南要求"四选二"，A+B 达标；D 留给面试"如果时间充裕"的加分回答（§5.8 不做清单）

### 4.6 全流程时序（审批流 + 澄清流）

```
【审批流（场景 B）】
POST /v1/chat/stream {session_id, message}
  → stream_agent_events（config 挂 HitlCallback）
  → 工具命中 interrupt_on → on_interrupt 回调（真实 checkpoint_id + HITLRequest）
  → 流内产出 approve 事件（run_id=真实checkpoint_id，前端按 run_id 原样回传）→ 流结束（不发 done）
  → 前端 B2 卡片 → 用户决策
  → POST /v1/chat/approve {run_id, action, note?, edited_arguments?} → 202 {accepted}
  → POST /v1/chat/stream {session_id, resume_run_id=run_id}
  → chat.py 查 pending 决策 → Command(resume={"decisions": [...]}) → 图从中断点继续

【澄清流（场景 A）】同上，决策 action="respond" + note=答案文本
  → 中间件合成 ToolMessage(答案) 回给模型 → 模型带答案继续（ask_human 工具不真执行）

【多 action 中断（P1 限制，§6）】一轮多工具命中 → N 条 approve 事件 → 前端逐卡提交
  → 最后一条 accepted=true → resume（决策数与 action_requests 数一致才允许恢复）
```

## 5. 分·设计决策（D1-D8）

### 5.1 D1：ask_human 工具（新） 🔴 v1

- 位置：`backend/src/agent/tools/ask_human.py`（工具域分包，同 search.py/sandbox_tool.py 模式）
- 挂载两处：① main_agent `internal_tools` 列表；② `hitl.py` 注册 `"ask_human": InterruptOnConfig(allowed_decisions=["respond"])`
- 工具描述写清用途（模型据此决定何时调用）：*"当用户目标、范围、约束或交付形式模糊时调用，向用户提问澄清；也用于执行计划开始前请求确认"*
- 工具体内 stub：`raise RuntimeError(...)`（防御：allowed_decisions 只有 respond，正常链路不执行；若未来误配决策集立刻炸出声）
- **不回归**：hitl_enabled=False 时 ask_human 工具仍挂载但 interrupt_on=None → 模型调用它 = 直接抛错 → 工具报错回模型（可接受：关 HITL 场景不鼓励问人）；**更优方案**：hitl_enabled=False 时不挂载 ask_human 工具（§7.2 实现，避免模型叫一个永远报错的工具）

### 5.2 D2：approve 事件契约（对齐前端已交付 B2） 🔴 v1

- `schemas/events.py` 新增 `ApproveEvent`，字段**以 `frontend/src/lib/api/mock.ts` 已解析形态为准 + 后端必需扩展**：

| 字段 | 类型 | 说明 |
|------|------|------|
| type | "approve" | 事件类型 |
| run_id | str | **中断点真实 checkpoint_id**（GraphInterruptEvent 提供）——前端原样回传作 resume_run_id |
| call_id | str | 工具调用 id（interrupt action 的对应 tool_call id，前端去重用）|
| tool_name | str | 工具名（如 run_code_in_sandbox / ask_human）|
| arguments | dict | 待审参数（**脱敏截断**，同 ToolCallEvent ≤300）|
| message | str | 人类可读审批说明（工具名 + 参数摘要；ask_human 时为问题原文）|
| allowed_decisions | list[str] | 该工具允许的决策集（前端按钮渲染依据；前端忽略未知字段，向后兼容）|

### 5.3 D3：POST /v1/chat/approve（审批 API） 🔴 v1

- 请求体（**对齐前端 `ApproveRequest` 契约 + 扩展 respond**）：

```json
{ "run_id": "<真实checkpoint_id>", "action": "approve|reject|edit|respond", "note": "可选", "edited_arguments": {"code": "..."} }
```

- 校验：run_id 无待决中断 → 404（`APPROVAL_NOT_FOUND`）；action 非法 / edit 无 edited_arguments / respond 无 note → 400
- 语义：把一条人类决策写入 **pending 决策存储**（§7.4），与中断的 action_requests **按提交顺序一一对应**；返回 `202 {status:"ok", accepted:bool}`——`accepted = pending 决策数 == 中断 action 数`（前端据此决定 resume 时机；单 action 中断下首次提交即 accepted）
- 与旧预研文档 D2 的差异：旧设计"decisions 参数复用 /v1/chat/stream"——**前端已交付独立 approve 端点形态**（§3.1-#5），选前端契约零改动（D7 决策记录）

### 5.4 D4：恢复链路（resume 消费 pending 决策 → Command(resume)） 🔴 v1

- `chat.py` resume 分支改造：`is_resume` 且 pending 存储命中 `run_id` → 输入改为 `Command(resume={"decisions": pending.decisions})`（不再传空消息列表）；`checkpoint_id` 传 `run_id`（此时是真实 checkpoint_id，§3.3-① 实证 astream_events 接受 Command 输入）
- **消费即删**：pending 决策读取后清除（一次性；防重复恢复重放决策）
- 无 pending 命中 → 既有断点续聊路径（**顺带修复**：校验 checkpoint 有效性，伪造 id → RESUME_NOT_FOUND，不再静默新跑）
- 决策数 ≠ action_requests 数 → 400（对应官方 middleware 的 ValueError 约束，提前在 API 层拦）

### 5.5 D5：流内中断检测（GraphCallbackHandler，修正旧设计假设） 🔴 v1

- `main_agent.py` 新增 `HitlCallback(GraphCallbackHandler)`（`agent/hitl/callback.py`）：
  - `on_interrupt(event)`：提取 `event.checkpoint_id` + `event.interrupts[0].value`（HITLRequest：action_requests / review_configs）→ 追加到流局部收集器（同步回调，与流同事件循环，无需线程同步）
  - 回调**只采集，不决策**——产出由流内逻辑做（保持 stream_agent_events 单一事件出口）
- `stream_agent_events`：新增 `hitl_callback` 参数（None 时不挂）→ config 加 `"callbacks": [hitl_callback]`；流循环内检测收集器非空 → 逐 action 产 approve 事件 → **终止流（不发 done）**
- 前端 awaiting_approval 状态机已按"approve 事件后流结束"实现（mock 契约），对齐
- 中断语义：done 事件只在"完成"发；中断是"等待人类"——前端据 approve 事件切换状态

### 7.4 `backend/src/agent/hitl/pending.py`（待决决策存储，全量）

```python
"""待决审批存储（P0 HITL 设计 §5.3/§5.4）：run_id → 中断 + 已收决策。

- 单进程内存 dict（部署现状单 uvicorn 进程）；TTL 10min + 容量上限防泄漏
- 中断时登记（action_requests/review_configs），approve 端点逐条写入决策，
  决策数 == action 数 → accepted=True；resume 消费即删（一次性）
- 重启/过期 → 404 友好提示（前端提示重开，同 RESUME_NOT_FOUND 处理）
"""

from __future__ import annotations

import threading
import time
from dataclasses import dataclass, field

_PENDING_TTL_SECONDS = 600          # 10 分钟（人类决策窗口）
_PENDING_MAX_SIZE = 256             # 容量上限（防泄漏，超限逐出最旧）
_lock = threading.Lock()
_store: dict[str, "_PendingApproval"] = {}


@dataclass
class _PendingApproval:
    """单次中断的待决审批上下文。

    Attributes:
        action_requests: 中断的待审动作（HITLRequest 语义，按序一一对应）
        review_configs: 各工具允许的决策集
        decisions: 已收决策（approve 端点逐条追加，顺序=提交顺序）
        created_at: 登记时间（TTL 过期回收）
    """

    action_requests: list[dict]
    review_configs: list[dict]
    decisions: list[dict] = field(default_factory=list)
    created_at: float = field(default_factory=time.monotonic)


def register_interrupt(run_id: str, hitl_request: dict) -> None:
    """中断发生时登记（流内检测到中断后调用，设计 §5.5）。

    Args:
        run_id: 中断点 checkpoint_id（GraphInterruptEvent 提供）
        hitl_request: {"action_requests": [...], "review_configs": [...]}
    """
    with _lock:
        _sweep()
        _store[run_id] = _PendingApproval(
            action_requests=hitl_request.get("action_requests", []),
            review_configs=hitl_request.get("review_configs", []),
        )
        # 容量上限：超限逐出最旧（登记时间升序）
        if len(_store) > _PENDING_MAX_SIZE:
            oldest = min(_store, key=lambda k: _store[k].created_at)
            _store.pop(oldest, None)


def add_decision(run_id: str, decision: dict) -> bool:
    """approve 端点追加一条决策（按提交顺序）。

    Args:
        run_id: 中断点 checkpoint_id
        decision: {"type": action, "message": note, "edited_action": ...}

    Returns:
        True=决策数已达 action 数（前端可 resume）；False=还需继续审批
    """
    with _lock:
        pending = _store.get(run_id)
        if pending is None:
            raise KeyError(run_id)
        pending.decisions.append(decision)
        return len(pending.decisions) >= len(pending.action_requests)


def consume(run_id: str) -> dict | None:
    """resume 时消费待决审批（一次性，读后即删）。

    Args:
        run_id: resume_run_id（approve 事件回传值）

    Returns:
        {"decisions": [...]}（Command(resume) 输入形态）；无待决 → None
    """
    with _lock:
        pending = _store.pop(run_id, None)
        if pending is None:
            return None
        return {"decisions": pending.decisions}


def _sweep() -> None:
    """TTL 过期回收（登记超时未完成审批的删除）。"""
    now = time.monotonic()
    expired = [
        k for k, v in _store.items() if now - v.created_at > _PENDING_TTL_SECONDS
    ]
    for k in expired:
        _store.pop(k, None)
```

### 7.5 `backend/src/agent/hitl/callback.py`（中断检测回调，全量）

```python
"""HITL 中断检测回调（P0 HITL 设计 §5.5）：GraphCallbackHandler 采集中断点。

⚠️ 实证修正（2026-08-11，设计 §3.3-②）：astream_events 不产 on_interrupt
事件——中断检测必须经 config["callbacks"] 的 GraphCallbackHandler.on_interrupt；
事件携带真实 checkpoint_id + interrupts（value = HITLRequest 形态）。

回调只采集不决策：中断上下文写入收集器，流内循环检测到后产出
approve 事件并终止流（单一事件出口，保持 stream_agent_events 职责）。
"""

from __future__ import annotations

from langgraph.callbacks import GraphCallbackHandler, GraphInterruptEvent


class HitlCallback(GraphCallbackHandler):
    """采集 graph 中断事件（checkpoint_id + HITLRequest 负载）。

    Attributes:
        interrupted: 最近一次中断上下文（None=未中断）——
            {"checkpoint_id": str, "hitl_request": {"action_requests", "review_configs"}}
    """

    def __init__(self) -> None:
        self.interrupted: dict | None = None

    def on_interrupt(self, event: GraphInterruptEvent) -> None:
        """中断回调：记录 checkpoint_id 与审批负载（流内据此产出 approve 事件）。

        Args:
            event: langgraph 中断生命周期事件（含真实 checkpoint_id）
        """
        if not event.interrupts:
            return
        self.interrupted = {
            "checkpoint_id": event.checkpoint_id,
            "hitl_request": event.interrupts[0].value,
        }
```

def _iter_action_reviews(hitl_request: dict):
    """HITLRequest → (action, review) 逐条（按序一一对应）。

    Args:
        hitl_request: {"action_requests": [...], "review_configs": [...]}

    Yields:
        (action_request, review_config) 二元组（review 缺省给空 dict）
    """
    configs = {c.get("action_name"): c for c in hitl_request.get("review_configs", [])}
    for action in hitl_request.get("action_requests", []):
        yield action, configs.get(action.get("name"), {})


def _build_approve_event(checkpoint_id: str, action: dict, review: dict, seq: int) -> dict:
    """approve 事件构建（对齐前端 B2 契约 + 后端扩展，设计 §5.2）。

    Args:
        checkpoint_id: 中断点 checkpoint_id（run_id 语义）
        action: action_request（name/args）
        review: review_config（allowed_decisions）
        seq: 流内事件序号

    Returns:
        SSE 事件 dict（approve）
    """
    allowed = review.get("allowed_decisions", ["approve", "reject"])
    return {
        "type": "approve",
        "run_id": checkpoint_id,
        "call_id": action.get("call_id", action.get("name", "")),
        "tool_name": action.get("name", ""),
        "arguments": action.get("args", {}),
        "message": f"工具 {action.get('name')} 需要审批",
        "allowed_decisions": allowed,
        "kind": "clarification" if action.get("name") == "ask_human" else "approval",
        "id": seq,
    }
