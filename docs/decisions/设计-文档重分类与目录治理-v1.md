## 1. 现状问题盘点 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

> 数据：docs 全量文件清单 + git 最后提交日期（2026-08-06 扫描，44 个 md）。不逐文件读内容——问题仅凭命名/路径/日期即可判定。

### 1.1 命名混用（问题 A）

| 现象 | 实例 | 问题 |
|------|------|------|
| decisions/ 里带"方案-"前缀 | 方案-Skill体系 / 方案-Wiki记忆 / 方案-上下文工程开发计划…（6 个） | 与 `docs/方案/` 目录语义冲突——"方案-"到底指哪个？ |
| decisions/ 无类型前缀 | CompositeBackend文件存储-设计-v3 / 事件流与解释器-测试计划-v1 / 持久化能力开发计划-Checkpointer与Store-v1 | 前缀不统一，同一目录三种风格 |
| 无版本号 | 过程中优化记录.md | 违反文档规范（-vN 后缀） |
| 文件名含空格 | "harness 学习.md" / "2026年8月3日 官方文档学习顺序.md" | 链接/检索/脚本处理困难 |
| 中英混排无规则 | 后端开发待办清单 vs 方案-后端基础架构 vs 文件后端开发规划 | 无前缀约定 |

### 1.2 位置错位（问题 B）

| 现象 | 实例 | 问题 |
|------|------|------|
| 计划/待办性质文件在"方案/"目录 | 后端开发待办清单-v1 / 后端开发计划-v1 / 文件后端开发规划-v1 | 05-docs-placement 说 方案/=已定稿，计划≠方案 |
| 接口参考性质在"方案/"目录 | 后端接口定义-v1 / 后端接口对接文档-v1 | 是参考（Reference）不是方案（Explanation） |
| 现状分析 → 开发计划 演进留在原路径 | 学习/上下文工程-现状分析-v1 → decisions/方案-上下文工程开发计划-v2 | 用户第 5 点：初版现状分析拓展为开发文档，路径没跟上 |
| 决策记录性质散落 | 过程中优化记录.md 在 decisions/ | 性质模糊（是决策？是踩坑？） |

### 1.3 结构问题（问题 C）

- **缺根索引**：learnings/ 有 `索引.md`，但 docs 根没有全量索引（用户第 6 点）
- **空目录**：discussions/、评审/ 为空；features/ 仅 TEMPLATE.md
- **规范文件位置**：文档规范.md / SOP.md 在 docs 根（合理，但索引里要显式列出）

## 2. 分类标准 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 2.1 Diátaxis 框架（网上典型案例） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

Diátaxis 按"行动↔认知 × 习得↔应用"两轴把文档分为四类（每种类型服务一种用户问题，**绝不混用**）：

| | 习得（学习） | 应用（工作） |
|---|---|---|
| **行动（做）** | 教程 Tutorial（"从哪开始学"） | 操作指南 How-to（"怎么做 Y"） |
| **认知（思考）** | 解释 Explanation（"为什么这样"） | 参考 Reference（"X 是什么/参数"） |

### 2.2 项目映射（第一轴：性质） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

| Diátaxis | 项目目录 | 现有文件示例 | 职责 |
|----------|----------|-------------|------|
| 教程 Tutorial | `docs/学习/` | harness 学习、官方文档学习顺序、子代理差距分析 | 学习路线与能力梳理 |
| 操作指南 How-to | `docs/learnings/` | OpenSandbox 配置、bat 编码、PyCharm 索引 | 踩坑与可复现操作 |
| 参考 Reference | `docs/架构/` + 文档规范 + 接口文档 | 架构目录、文档规范、后端接口对接 | 真相源与事实查询 |
| 解释 Explanation | `docs/方案/` + `docs/decisions/` | 方案-后端基础架构、各设计文档 | 设计理由与决策记录 |

### 2.3 第二轴：状态（评审/定稿/实施/废弃） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

| 状态 | 目录 | 说明 |
|------|------|------|
| ⏳ 评审稿/待定稿 | `docs/decisions/` | 新设计/计划先落这里，评审通过后定稿 |
| ✅ 已定稿 | `docs/方案/` | 评审通过、可执行/已执行的方案 |
| 📦 已废弃/被覆盖 | `docs/archive/`（新建） | 被新版本覆盖或决策推翻的文档（保留历史） |
| 🔗 参考/真相源 | `docs/架构/`、`docs/文档规范.md` | 不随迭代变化的事实 |

### 2.4 第三轴：功能实现状态（用户第 1 点核心） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

每个功能域文档对照《后端任务总结-v1》§2 的 12 域状态，决定去留：

| 文档对应功能状态 | 文档处置 |
|------------------|----------|
| ✅ 已实现且文档过时（计划细节已被实现） | 归档 archive/ 或合并进现状记录（后端任务总结） |
| ✅ 已实现且文档仍有决策价值 | 保留 decisions/（性质=决策记录），标注"已实施" |
| ⚠️ 部分实现 | 保留为计划，标注差距（哪些没做） |
| ❌ 未实现 | 保留为计划，按 §4 优先级排列 |

### 6.1 规则 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

```
格式：`类型-主题-vN.md`
类型 ∈ {方案, 设计, 计划, 学习, 踩坑, 参考, 索引, 规范, 总结, 测试计划, 决策}
规则：
- learnings/ 用日期前缀：`YYYY-MM-DD-主题.md`（现有已合规，保持）
- 禁空格、禁特殊字符（统一用 - 分隔）
- decisions/（评审稿）用「设计-」「计划-」「测试计划-」，不用「方案-」
  ——「方案-」只留给 docs/方案/ 的已定稿文档
- 版本后缀 -vN 强制（过程性文件如 过程中优化记录 → 改名或归档）
```
