## 0. 结论（先读这里） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

**核心结论**：草案六项与项目现役规则**高度重叠但不完全一致**——直接照抄会造成双规则打架。本方案做三件事：

1. **冲突裁决**：草案"文件 800 行 / 函数 100 行"与现役"文件 750 关注 1000 强制 / 函数 80·160 铁律"冲突 → **统一为"有效代码口径 + 现役更严值"**（§2），废除草案数值，保留草案口径改进（去注释统计）
2. **现状确认**：草案第 4 条（路径统一）已由 `core/paths.py` 落地、异常分级已由 `core/errors.py` 落地、日志基础已由 `04-logging.md` 落地——**不重复造**，只做深化（§4/§6/§7）
3. **补空白**：项目缺三样——**AST 校验脚本**（现役规则"提交前过线"无工具支撑）、**统一埋点中间件**（日志只有基础配置，无链路埋点）、**backend 目录/常量/文案清单**（§3/§4/§5）

**执行顺序**（§9）：P0 先建 AST 校验脚本（`scripts/check_code_style.py`）→ P1 按目录分批校验存量（api → agent → core → mcp/sandbox/memory/db）→ P2 新增埋点中间件与常量抽离。**评审通过前不改任何后端代码**。

## 2. 阈值统一决策（文件 / 函数） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 2.1 冲突裁决原则

1. **数值冲突 → 取更严**：草案 100 行 < 现役 80 行，保留现役（防退化）
2. **口径改进 → 采纳草案**：草案"有效代码（不含注释/空行）"比现役"总行数"更科学——docstring/注释不应计入
3. **双线并存**：保留"关注线（软）+ 强制线（硬）"两级，避免单线一刀切

### 2.2 文件阈值（统一后）

| 线 | 阈值（有效代码行 = 总行 - 注释 - 空行） | 动作 |
|----|----------------------------------------|------|
| 关注线 | > 750 | 标记拆分候选，人工评估 |
| **强制线** | > 800 | **必须拆分**（草案采纳，替代现役 1000） |

> 口径：AST 扫描统计（`ast.parse` + 遍历去 docstring/注释行/空行），§8 工具实现。
> 现状核查：当前最大 `main_agent.py` 501 行 / `chat.py` 423 行——**存量无超限文件**，阈值主要约束增量。

### 2.3 函数阈值（统一后，保留现役铁律）

| 线 | 阈值（非底层函数，有效代码） | 动作 |
|----|------------------------------|------|
| 耦合信号 | > 80 行 | 必须考虑拆分（草案 100 作废，现役更严） |
| **强制** | > 160 行 | 必须拆分解耦（chat.py 171 行事故教训） |
| 底层函数 | 不设限 | 原子能力（如 tokenizer、分页计算）豁免，但需 docstring 说明不可拆理由 |

### 2.4 对现役规则的修订建议（评审通过后回写 01-coding-style.md）

- 文件线：`>750 关注` 保留 + `>1000 必须拆分` → `>800 必须拆分`（口径改"有效代码"）
- 函数铁律 80/160 不变，补一句口径："去除注释/docstring 后的有效代码行"

## 3. 目录与命名规范（backend 侧成文） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 3.1 目录归属表（backend/src/）

| 目录 | 放什么 | 禁止 |
|------|--------|------|
| `api/` | 路由/处理器（仅编排，禁业务实现） | 禁直接写 SQL、禁调 LLM 细节 |
| `agent/` | Agent 编排（main_agent）、子代理、中间件、HITL | 禁业务域实现（业务实现放对应能力目录） |
| `mcp/` | MCP 网关、工具注册表、按域工具包 | 禁跨域引用业务模型 |
| `sandbox/` | 沙箱适配层（仅 API 面，实现细节不泄露） | 禁直接依赖 api/ 层 |
| `memory/` | 记忆体系（store/agent/tasks） | — |
| `db/` | schema/DAO/repository（唯一 SQL 出口） | 禁其他目录手写 SQL |
| `core/` | 横切：config/paths/errors/logging/constants | 禁依赖业务目录（反向依赖违规） |
| `schemas/` | Pydantic 请求/响应模型 | 禁含业务逻辑 |
| `llm/` | LLM 适配/重试（唯一 LLM 出口） | 禁绕过 adapter 直接调 SDK |
| `skills/` | Skill 市场/安装 | — |

**依赖单向**（架构文档拍板，本条重申）：`api → agent → {mcp, sandbox, memory, db}`，`core/llm/schemas` 为公共底座——**禁止反向**。校验脚本检查 import 方向（§8）。

### 3.2 命名规范（backend 侧）

| 元素 | 规范 | 反例 |
|------|------|------|
| 文件/模块 | snake_case，一文件一职责 | `AgentHandler.py`、`utils.py`（万能杂物） |
| 目录 | 按能力域（见 3.1），禁 `misc/`、`common/` 万能目录 | 出现即拆 |
| 函数/变量 | snake_case，动词开头 | `get` 无宾语 |
| 类 | PascalCase | — |
| 常量 | UPPER_SNAKE（跨文件 → constants.py，§4） | — |

### 3.3 Agent 分层约束（草案③，深化检查项）

- `agent/` 下文件**只做编排**（组装节点/中间件/参数），业务具体实现 → 对应能力目录新建文件
- 判定：编排文件出现 3 行以上业务实现（SQL、LLM 提示词细节、文件格式解析）→ 抽离到能力目录
- main_agent.py 现状合规（501 行全为编排/装配），作为样板

## 4. 常量与路径统一 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 4.1 常量管理（新增判定标准）

| 常量作用域 | 归属 | 示例 |
|-----------|------|------|
| 单文件内部 | 文件头部模块级常量（现状合理，保留） | store.py 的模块级常量 |
| **跨文件共用** | **新建 `core/constants.py`**（分组注释 + UPPER_SNAKE） | 超时秒数、分页上限、截断长度、错误前缀 |
| 跨环境差异 | `core/config.py`（env 配置） | 端口、路径根 |

**判定规则**：第二个文件引用某常量时，抽入 constants.py（"用两次就抽"）。函数内禁止硬编码魔法值（现有规则重申，常量引用代替）。

> 现状核查：抽样各文件常量多为模块私有，**暂无明显跨文件重复**——本条款主要约束增量，存量抽离按 §8 分批扫描时顺带。

### 4.2 路径统一（已有，深化）

- **现状**：`core/paths.py` 已集中全部路径（dev/prod 自适应、虚拟路径、上传目录）——抽样硬编码 0 命中 ✅
- **深化规则**：① 新增数据目录（如 uploads）必须在 `paths.py` 登记，业务文件禁硬编码；② 路径拼接用 `pathlib`，禁字符串 `+ "/"`；③ 分隔符不写死（pathlib 自动适配 Windows/Linux——草案"兼容本地/云"已由 paths.py 满足）
- **校验项**：脚本扫描业务文件中的路径字符串常量（§8）

## 6. 日志体系深化（分级 + 统一埋点） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 6.1 现状与差距

- ✅ 已有：`core/logging.py` 唯一配置点、UTF-8、每日/50MB 滚动、14 保留
- ❌ 缺口：**无链路埋点**（request 级调用链追踪）、日志级别**无运行时开关**、函数内日志冗余无约束

### 6.2 统一埋点中间件设计（新增 `agent/middlewares/logging_trace.py`）

| 设计点 | 方案 |
|--------|------|
| 职责 | 每个请求/图执行注入 `request_id`，LLM 调用/工具调用/图阶段自动打点（info 级：耗时/输入摘要/异常） |
| 机制 | 复用现有 middleware 链（与 ToolAudit/TokenUsage 同构，`wrap_model_call` 挂模型调用 + 图事件钩子） |
| request_id | `api/` 层生成 → context 注入 → 中间件透传 → 日志 `extra={"request_id": ...}` |
| 分级开关 | `settings.log_level`（DEBUG/INFO/...）→ 中间件按级过滤；**埋点只打 info 关键节点**（开始/结束/耗时/错误），不逐 token |
| 约束 | **业务函数内部禁止重复堆砌日志**——只保留关键注释 + 异常日志（草案⑤）；中间件已覆盖的节点函数不再自行打点 |
| 与 04-logging 关系 | 04-logging 管"写到哪/怎么滚"，本中间件管"打什么点"——两个文件不冲突 |

### 6.3 校验项

- 函数内 `logging` 调用 > 3 处且非异常分支 → 标记"冗余日志，应移交中间件/注释"

## 7. 容错降级设计（chat 链路逐节点兜底） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 7.1 现状

- ✅ `core/errors.py`：retryable/non-retryable 分级；✅ `llm/retry.py`：超时 + 重试
- ❌ 缺口：**链路级兜底无清单**——单点失败（如记忆 store 挂了）是否断整个 chat 流无成文决策

### 7.2 chat 链路降级矩阵（设计）

| 链路节点 | 失败形态 | 降级策略 | 断流？ |
|----------|----------|----------|--------|
| 会话/消息落库 | SQLite 错误 | 重试 1 次 → 降级内存会话（响应正常，标注未持久化） | 否 |
| 记忆注入/读取 | Store 不可用 | **静默降级**：跳过记忆注入，Agent 无记忆继续 | 否 |
| 记忆写入 | 同上 | 记 error 日志 + 队列重试（P2），不阻塞响应 | 否 |
| LLM 调用 | 超时/不可用 | 现有 retry 耗尽 → SSE `error` 事件（retryable=true），前端可重试 | 是（协议设计如此） |
| 工具调用 | 工具异常 | 工具级 try → 错误结果回传 Agent（Agent 自行处理/放弃） | 否 |
| 子代理 | 子图异常 | 错误摘要回传主 agent（继续主流程） | 否 |
| 沙箱执行 | 沙箱不可用 | 返回工具错误 + `AUTH/ENV` 提示，主流程继续 | 否 |
| 审批（P1 后） | checkpointer 异常 | 拒绝审批请求（400 RUN_NOT_FOUND），会话状态保持 | 否 |

**原则**：除"LLM 主链路"外，全部**不因单点失败断流**——失败降级 + 日志留痕（草案⑤）。实施时逐节点核对现有 try/except 是否满足。

## 8. 校验工具与分批校验策略 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 8.1 AST 校验脚本规格（新增 `scripts/check_code_style.py`）

| 检查项 | 实现方式 |
|--------|----------|
| 文件有效代码行（去注释/空行/docstring） | `ast.parse` + 行号集合统计 |
| 函数有效行数（80/160 双线） | AST 遍历 FunctionDef，起止行减注释 |
| 命名检查（snake_case 文件/函数/变量） | AST + 文件名正则 |
| 依赖方向（禁止 api→core 反向等） | import 图分析（规则表来自 §3.1） |
| 魔法值扫描（函数内裸数字/路径字符串） | AST 常量节点 + 启发式（排除 0/1/枚举） |
| 输出 | 分目录报告 + 退出码（超强制线 → 非 0，可进 git hook） |

> 现役 01-coding-style 已承诺"拆分后用 AST 扫描验证"但无工具——本脚本补齐，落地后接入提交前检查（P0）。

### 8.2 分批校验策略（草案①"分批避免遗漏/降注意力"）

| 批次 | 目录 | 校验重点 | 产出 |
|------|------|----------|------|
| 批次 1 | `api/` + `schemas/` | 文件/函数阈值、依赖方向、错误文案 | 整改清单 |
| 批次 2 | `agent/`（含 memory/） | 编排 vs 业务实现、子代理规范 | 整改清单 |
