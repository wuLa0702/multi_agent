## 1. 原则 🔴 v1

**能用第三方组件就用第三方组件。**

理由：
- 第三方经大量真实场景验证，考虑到的边界远超个人设想
- demo 项目的时间应花在**领域逻辑**上，不是**通用基础设施**上
- 自研通用组件 = 长期维护一份不如别人的实现

## 2. 判定：什么算「通用能力」（该用第三方） 🔴 v1

| 类别 | 例 |
|------|-----|
| 日志 / 序列化 / 配置解析 | 滚动日志、JSON、.env 加载 |
| 网络 / 重试 / 连接池 | httpx、tenacity、asyncpg pool |
| 框架 / 协议 | FastAPI、Pydantic、LangGraph |
| 标准格式 | 时间时区、UUID、压缩、编码 |

## 3. 例外：什么该自研 🔴 v1

| 类别 | 理由 | 本项目实例 |
|------|------|-----------|
| **领域模型** | 第三方没有你的业务语义 | 审计事件模型 `core/audit.py`、工具登记表 `tools/registry.py` |
| **硬约束的安全边界** | 必须自己掌控 | 路径前缀校验（`.claude/rules/00-security.md`）、出站脱敏 `llm/redact.py` |
| **第三方确实不覆盖的** | 须留查证痕迹，见 §4 第 2 条 | 见 §5 已查证边界表 |

## 4. 落地要求 🔴 v1

1. **引入前先查证**：确认对方**真的**支持你的需求——不要凭印象假定"第三方肯定有"
2. **自研必须留查证痕迹**：代码注释写明「第三方 X 不支持 Y（附文档 / issue 链接），故自研」
   ——否则后人只会看到一个"为什么不用现成的"的自研件
3. **优先降低需求，而不是自研**：先问「这个需求真的必要吗？」
   ——需求砍掉，代码也随之消失，比写一个自研件更彻底

## 5. 已查证边界（避免重复踩） 🔴 v1

| 需求 | 结论 | 依据 |
|------|------|------|
| 日志「时间 + 大小」双触发滚动 | ❌ **第三方都没有**：stdlib 只支持单触发；loguru 明确不支持两者兼用（issue #1174 仍是 feature request） | 官方文档 / issue #1174 |
| 结构化日志 + 上下文字段自动注入 | ✅ **structlog**（2026-10-16 已接入，见 `core/logging.py`） | 已落地 |
| Windows 多进程安全滚动 | ✅ `concurrent-log-handler`（**暂未用**：dev 单进程碰不到该场景） | 备查 |
| 审计底账存储 / 队列 / 检索 | ❌ **不外包**：自持是审计的定义 | `docs/决策/2026-10-15-决策-审计与可观测-方向-v1.md` §4.3 |

> ⚠️ §5 的"❌"仅表示**该需求下第三方不适用**，不代表该领域一律自研——
> 例：日志渲染/字段注入已交给 structlog（第三方），只有"双触发滚动"这一子项无解。
