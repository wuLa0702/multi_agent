## 1. 问题提出 🔴 v1

> **co-creator 2026-10-16 提问**：
> 「是不是太复杂了？我理解应该有**统一的单独模块**去做错误处理？
> 比方说**全局异常处理**、**横切拦截**，而不是硬写死在代码中？」

这个疑问很自然——看到 14 个工具、每个都写 `try/except` 和 `status="error"`，
直觉上应该"有一个地方统一管"。

**本文档要回答三件事**：
1. 现在到底**统一了多少**（实测，不凭印象）
2. 剩下的分散是**该收**还是**本该如此**
3. 若真要再收口，收哪个、代价多大

## 2. 现状实测 🔴 v1

### 2.1 已经统一的 6 个横切点（无需再建"统一模块"）

| # | 关注点 | 落点 | 覆盖范围 |
|---|--------|------|---------|
| 1 | **HTTP 全局异常处理** | `api/error_handlers.py::install_error_handlers()` | `HTTPException` 摊平 / Pydantic 校验 → 400 / 未捕获 → 500 + trace_id |
| 2 | **工具审计（埋点）** | `tools/runtime/audit.py::ToolAuditMiddleware` | 所有工具调用（内部 + MCP）两行制 start/end |
| 3 | **工具调用校验（拦截）** | `tools/runtime/gateway.py::ToolGatewayMiddleware` | `args_schema` 校验失败 → 短路成 `ToolMessage(error)`，不中断 run |
| 4 | **错误码翻译** | `tools/contract/error_map.py` | 异常 / HTTP 状态 → 9 个归一错误码，**全项目唯一翻译处** |
| 5 | **重试机制** | `core/retry.py` + `registry._apply_retry()` | 装配期按 `is_idempotent` 门控包装，运行时不做判断 |
| 6 | **LLM 调用超时/重试** | `llm/adapter.py` | `_LLM_TIMEOUT_SECONDS` + `max_retries` 固化 |

> 📌 **结论**：所谓"全局异常处理 + 横切拦截"**不是缺失，而是早已存在**——
> 只是它们分属不同层，不是一个"大而全的错误模块"。

## 3. 核心论点：全局异常处理 **≠** 工具错误处理 🔴 v1

这是本次讨论最需要说清的一点。

```
全局 exception_handler  = 最后一道网
                          ↓ 只能给出 500 + 通用错误码
                          ↓ 信息量：几乎没有

工具三态信封 ToolResult = 主路径
                          ↓ status(ok/degraded/error) + error_code
                          ↓ + retryable（能不能救）+ data（有没部分结果）
                          ↓ 信息量：业务语义
```

**若把工具内的一切错误都抛到全局处理器：**

| 后果 | 说明 |
|------|------|
| ❌ **丢失三态** | `degraded`（部分结果可用）无法表达，只能全标成 error |
| ❌ **丢失可重试性** | 全局 handler 不知道 403 与 Timeout 的区别 |
| ❌ **丢失去重/降级依据** | 编排层无法按 `error_code` 决定"换工具 / 放弃 / 重试" |
| ❌ **一个错误码走天下** | 前端"按 code 分支"彻底失效（正是 B1 修过的坑） |

> **一句话**：**全局处理器是兜底，三态信封是主路径。**
> 兜底不能替代主路径——就像医院的急诊室不能替代门诊的分类诊疗。

## 4. 分散项逐条判定 🔴 v1

| 分散项 | 该收吗 | 理由 |
|--------|--------|------|
| **业务失败判断**（文件不存在 / 参数非法 / 配额耗尽） | ❌ **不该收** | 判断依据是**业务语义**，只有工具自己知道。集中化会让工具变成"什么都不知道" |
| **错误文案**（"请勿重试搜索，直接基于已有知识回答"） | ❌ **多半不该收** | 文案必须**贴着具体失败原因**（403 与 404 的处置不同）。集中成映射表反而制造第 7 处"两处维护" |
| **意外异常的 try/except 样板** | ✅ **可以收** | 这是纯样板：`except X: return ToolResult(error, classify_exception(X), tool=...)`，与业务无关 |
| **超时参数** | ⚠️ **暂不收**（已判定过） | 各工具**已有超时**；再包一层 registry 级超时会**重复**（见 `汇总问题` B5 旁的说明） |

**看一个典型工具的样子**（`impl/search.py`）：

```python
try:
    pages = bocha_client.search(query, max_results)
except httpx.HTTPStatusError as e:
    if e.response.status_code == 403:
        return ToolResult(status="error", message="…配额耗尽…请勿重试搜索…",   # ← 业务，不可收
                          error_code=ToolErrorCode.UNPAID, tool=_TOOL_NAME)
    raise                                        # ← 瞬时故障，交给重试层
except (httpx.TimeoutException, httpx.ConnectError, httpx.ReadError):
    raise                                        # ← 瞬时故障，交给重试层
except Exception as e:
    return ToolResult(status="error", message=f"搜索失败（…）…",              # ← 兜底样板，可收
                      error_code=classify_exception(e), tool=_TOOL_NAME)
```

前两个 `except` 是**业务决策**；最后一个 `except Exception` 是**样板**。

## 5. 可选收口：`@tool_guard` 🔴 v1

**只收"兜底样板"，不动业务判断。** 放 `tools/runtime/`（与 gateway 同层，属工具中心的横切）。

### 5.1 核心代码（形态示意，未实施）

```python
# backend/src/tools/runtime/guard.py
"""工具执行的兜底护栏：**意外异常** → 三态信封（业务失败仍由工具显式返回）。

⚠️ 只兜 `Exception`（意外）；`BaseException`（CancelledError 等）必须放行——
进程被取消不是工具失败。
"""

from functools import wraps
from typing import Any, Callable

from src.core.errors import classify_exception  # 或 tools/contract/error_map
from src.tools.contract.result import ToolResult


def tool_guard(tool: str) -> Callable:
    """把「意外异常」转成 `ToolResult(error)`；业务失败不受影响。

    Args:
        tool: 工具名（信封/审计定位用）

    Returns:
        装饰器
    """

    def decorator(fn: Callable[..., ToolResult]) -> Callable[..., ToolResult]:
        @wraps(fn)
        def wrapper(*args: Any, **kwargs: Any) -> ToolResult:
            try:
                return fn(*args, **kwargs)
            except Exception as exc:            # noqa: BLE001 —— 兜底样板，只此一处
                return ToolResult(
                    status="error",
                    message=f"工具执行失败（{type(exc).__name__}）",
                    error_code=classify_exception(exc),
                    tool=tool,
                )

        return wrapper

    return decorator
```

### 5.2 取舍

| 维度 | 收益 | 代价 |
|------|------|------|
| 代码量 | 可删约 8~10 处兜底 `except` | 新增 1 文件 + 9 个装饰器 |
| 一致性 | 兜底文案/错误码口径统一 | — |
| 风险 | — | 装饰器会**吞掉所有意外异常**；若某工具原本靠"抛出"让重试层接管（如 `fetch.py` 的瞬时网络异常），**必须确保它 `raise` 而不是被外层吞掉** ⚠️ |
| 行为变更 | — | ★ 需逐个工具确认"哪些异常该冒泡给重试层" |

> ⚠️ **最大的风险点**：现在工具靠 `raise` 往外传"瞬时故障"给重试层。
> 一个粗暴的 `except Exception` 会让重试层**永远收不到信号** —— 这恰好是
> 历史上踩过的"重试静默失效"同类坑。故作此方案**必须先逐个标注可冒泡异常**。

## 6. 结论 🔴 v1

| 问题 | 结论 |
|------|------|
| **是不是太复杂？** | **不复杂。** 6 个横切点已统一，分层清晰，每层只做一件事 |
| **要不要建"统一错误处理模块"？** | **不要。** 会退化成"一个错误码走天下"，丢掉三态与可重试性 |
| **全局异常处理有吗？** | **有** —— `api/error_handlers.py`（HTTP 边界），但它只该做兜底 |
| **横切拦截有吗？** | **有** —— `tools/runtime/`（gateway 拦截 + audit 留痕） |
| **还有值得收的吗？** | 只有**兜底样板**一类；`@tool_guard` 可选，**但要先解决"哪些异常该冒泡"** |

**默认动作：维持现状。** 若将来工具数量明显增长、兜底样板继续扩散，再评估 `@tool_guard`。
