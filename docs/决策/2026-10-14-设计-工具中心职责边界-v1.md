## 1. 定位与三桶 🔴 v1

**工具中心 ≠ MCP。** MCP 只是三种接入通道之一。

```
                      ┌───────── 工具中心（工具网关）─────────┐
  外部 Agent / 前端 ─→│ ① 接入协议   MCP │ REST API │ A2A     │  三通道平行
                      │        ↓                              │
  本 Agent 编排    ─→│ ② 执行       function call │ handler  │  handler = 鉴权/超时/重试/日志/埋点/异常
                      │        ↓                              │
                      │ ③ 契约       统一描述 + 标准 IO       │  ← 横切层，不与①②并列
                      └───────────────────────────────────────┘
```

三点校正：
1. **③ 标准输入输出层是横切层**，不跟 ①② 并列——三种通道、大小工具，出去都要过它统一编解码。
2. **① 的三层是"接入方式"**（MCP 协议 / REST 资源 / A2A Agent 间），**② 的两级是"执行深度"**（function call 直调 / handler 带治理）。
3. **"工具规范"4 条**实为两组：**描述格式 + 标准 IO = 工具契约**；**分层 + 检索加载 + 粒度 = 工具治理策略**。

**规范按三桶组织**：**输入** / **输出** / **业务兜底**。

## 2. 责任归属总表（工具中心 vs 外部配合） 🔴 v1

| # | 诉求 | 工具中心做什么 | 外部谁配合 |
|---|---|---|---|
| 1 | 细分 Pydantic 校验 | ✅ **独占**：网关侧用 `args_schema` 统一校验，**调用前拦截**，不合格不进工具体 | 工具作者写 schema；公共模型放 `schemas/` |
| 2 | Schema 否定禁止 | 🟠 定规范 + 落地：description 写"禁止…" ＋ JSON Schema 层 `not`/`pattern`/`const` 双写 | 工具作者填；否定约束效力依赖模型，非 100% 强制 |
| 3 | 枚举值限制 | 🟠 定规范（"能枚举就绝不裸 str"），校验由 Pydantic `Enum` 承担 | 工具作者 |
| 4 | 必填 vs 选填 | ✅ **独占**：Pydantic 默认必填；选填必须显式 `= None` + description 说明缺省语义 | 工具作者 |
| 5 | 合并冗余参数 + 内部转化 | 🟠 **执行者**：在网关做"外部唯一标准格式 → 内部结构"的转化 | 🔴 **格式标准本体归 `core/constants.py`**（全项目契约；工具层只是执行者，不能自定标准） |
| 6 | 参数命名所见即所得 | 🟠 定规范 + 可做成 lint（命名歧义词表审查） | 工具作者 |
| 7a | 输出字段补全 / 错字 / 翻译修复 / 单位归一 | 🟠 **单位归一 + 结构归一归它**；"修复"须分内容看（见 §4） | 上游 **LLM 结构化输出**的修复 → `llm/` 层 parser |
| 7b | 空值 / 错误码归一 | ✅ **独占**：`null` / 未提供 / 空白 / `401` / `402` 归一为内部枚举 | 无 |
| 8 | 语义重试 + 降级兜底 | 🟠 重试半个归它：按元数据（幂等性）决定重试与否（已有 `core/retry.py`） | 🔴 **"换哪个工具兜底"归编排层**（工具中心不知道备选是谁） |
| 9 | 数据脱敏 | 🟠 **入站半边归它**：工具返回结果脱敏 | 🔴 **出站半边不归它**：调远程 LLM 前遮蔽 → `llm/adapter.py`（工具中心不接触 LLM 请求体） |
| 10 | 审计留档 | 🟠 **工具调用审计归它**（已有 `ToolAuditMiddleware`） | 🔴 LLM 通话审计 → `llm/`；内部节点流转 → Graph 中间件（`agent/middlewares/`） |
| 11a | 幂等校验 | 🟠 **声明 + 门控**：元数据标 `is_idempotent`；非幂等禁自动重试（已有先例：`run_skill_script` 被排除重试）；透传幂等键 | 🔴 **幂等实现**（去重表/唯一键）在工具实现/业务层 |
| 11b | 高威胁操作 2 次审批 | 🔴 **不归它**：只声明风险级元数据 | **审批流归 HITL 层**（已有 `agent/hitl/hitl.py` + `interrupt_on`） |
| 11c | Trace ID 全链路 | 🟠 **贡献者 + 透传**：工具调用打点带 trace_id | 🔴 **owner 是请求入口中间件**（生成 + 贯穿） |

**总结**：11 点中工具中心真正"独占"的只有 **1 / 4 / 7b**；其余多为"工具中心声明 + 别处执行"或干脆不归它。

## 3. 输入侧规范（1–6）与标准落点 🔴 v1

### 3.1 六条规则

1. **Pydantic 细分校验**：网关侧统一校验，**调用前拦截**
2. **Schema 否定禁止**：description 显式写"禁止 X"（对 LLM 的约束效力优于正向暗示）＋ JSON Schema 层 `not`/`pattern`/`const` 双写
3. **枚举值限制**：能枚举就绝不裸 `str`
4. **必填 / 选填分清**：默认必填；选填显式声明并说明缺省语义
5. **合并冗余参数 + 内部转化**：外部只提供**唯一标准格式**，内部任意转化（时间格式是示例，所有参数同理）
6. **命名所见即所得**：人看得懂、AI 也看得懂，无歧义

### 3.2 标准放在哪（三层载体）

| 载体 | 放哪 | 谁用 | 强制力 |
|---|---|---|---|
| **规则文档（权威）** | `.claude/rules/07-tool-center.md` | **AI 自动加载**（写代码时天然在上下文）+ 人 | 靠自觉，但 AI 每次可见 |
| docs 镜像 | `docs/规则/工具中心规范.md` | 人读 / 评审 | 无 |
| **可执行常量** | `core/constants.py`（已存在） | 代码 `import` | **代码级强制** |
| **类型层** | `schemas/` 公共 Pydantic 模型 | 代码 | **代码级强制** |

**判断依据**：只放文档 = 靠自觉，一定被绕过；**能变成常量/类型的，就别只写文档**。项目已有先例——`.claude/rules/05-docs-placement.md`（权威）+ `docs/规则/文档治理规则.md`（镜像），照抄该模式。

**分工**：第 5 点的格式标准本体（如时间格式）落 `core/constants.py`；其余 1–4、6 是文档规则 + Pydantic 自然强制。

## 4. 输出侧规范（7）：归一是代码，不是 LLM 🔴 v1

- **"归一" = 确定性代码**：空值→枚举映射、单位→换算表、字段→默认值补齐。全是查表/换算，**没有一处需要 LLM**。
- **形态**：建适配器类 `ToolResultAdapter.adapt(tool_name, raw) -> ToolResult`（统一 envelope）；工具实现返回**结构化 dict**，适配器是**唯一出口**。
- **只有**"修复 LLM 生成内容里的错字/翻译"才用 LLM + 插件 → 落 `llm/` 层，**不在工具中心**。
- ⚠️ **关键前置**：现在工具**全返回裸 `str`**（`internet_search` 手动拼文本、沙箱返回 stdout）——必须先让工具**返回结构化**，否则"归一"无对象可归。这是"标准 IO"的真实工作量所在。

**归一 vs 修复的边界**：工具输出是**程序产出**，协议字段（code/status/单位）应**校验失败即报错**，不该"帮它补全"；只有**内容里夹带的 LLM 产物**（子代理摘要、研究结论）才适用"修复"。

## 5. 重试与降级（8）：显式降级链，不是自动挑 🔴 v1

**备选关系必须显式声明**——"谁能替代谁"是语义判断，要人拍；猜错 = 静默换错工具，比直接失败更糟。

两级做法：
1. **显式降级链**（元数据写死 `fallback_to`）：如 `exa_search → bocha_search`
2. **同域兜底**（同类工具打同一 `domain` 标签，编排层在同域内找下一个可用的）

**工具描述的作用是"辅助"不是"授权"**：提供 `domain`/能力标签，让编排层**检索候选**；授权降级到谁是**人配的**。

**执行归编排层**（持有全局视图，知道同域还有谁）；工具中心只提供"候选 + 降级能力标记"。

## 6. 脱敏层（9）：独立共享层 + 两个调用点 🔴 v1

建 `core/redaction.py`（统一脱敏工具类：遮蔽 API / 密码 / 密钥 / token），**两个调用点**：

- **出站** → `llm/adapter.py`（发远程 LLM **前**先过）
- **入站** → 工具输出适配器（工具返回结果过）

它不是"归工具层管"，而是"**独立共享层 + 两个消费者**"——工具中心只是其中一个消费者，不是 owner。

## 7. 审计留档（10）：现状两条通道与缺口 🔴 v1

**现状：两条各自残缺的通道，且记不全。**

| 通道 | 落盘 | 记什么 | 缺口 |
|---|---|---|---|
| `ToolAuditMiddleware` → audit logger | 审计日志 | ts / thread_id / **工具名** / 参数（**仅 9 个白名单工具**；`code` 换成 `code_len`、截断 300） | ❌ **完全不记结果**（钩子在**执行前**记完即 `return await handler(request)`） |
| `trace.py` TraceEvent → trace logger | `logs/agent_trace.jsonl` | `on_tool_start` 的 **input** + `on_tool_end` 的 **output**（各截断 200）/ run_id / parent_ids / session_id | ⚠️ 结果是**字符串摘要**、截断 200、**非结构化** |

**"名称 + 输入 + 核心结果"三件套盘点**：
- **名称** ✅ 两处都有
- **输入** 🟠 有，但 audit 只白名单 9 个、trace 截断 200
- **结果** 🟠 只有 trace 有，且是**摘要非结构化结果**

**补齐方式**：在 `awrap_tool_call` 包住 handler 返回值再记一条（`decision=result`，脱敏 + 截断）；或等结构化 envelope 落地后直接落库。

**⚠️ 关联真问题（11c 前提）**：现在**没有统一 `trace_id`** —— audit 用 `thread_id`、trace 用 `run_id`，**两条通道互相串不起来**，"一条 ID 串到底"目前做不到。

## 8. 业务兜底（11）：幂等 / 审批 / TraceID 🔴 v1

| 项 | 结论 |
|---|---|
| **11a 幂等** | 工具中心**校验不出**幂等，只能"**声明 + 门控**"：要求工具声明 `is_idempotent` → 非幂等**禁自动重试** → 透传幂等键。**幂等的实现**（去重表/唯一键）在工具实现/业务层 |
| **11b 审批** | **不归工具中心**。工具中心只标风险级；**二次确认审批流归 HITL 层**（已存在）。否则工具中心会背上"人在回路"重逻辑，职责糊掉 |
| **11c TraceID** | 工具中心是**贡献者 + 透传者**；**owner 是请求入口中间件**（生成并贯穿）。补法：入口生成 `trace_id` → 透传给 audit / trace / llm 三处 |

## 9. 开发顺序（阶段 0–4） 🔴 v1

> 排序原则：**先收口、后加能力**；**先轻后重**；后阶段挂在前阶段的产物上。

### 阶段 0 — 收口地基（无新能力，纯 refactor，零行为变更）

| # | 任务 |
|---|---|
| 0.1 | **工具定义单一真相源**：消除 `_build_agent` 硬编码清单 vs `mcp/registry.py TOOL_REGISTRY` 的**现存漂移**；引入**工具元数据表**（`domain` / `is_idempotent` / `risk_level` / `fallback_to` / `size`（大\|小）/ `requires_approval`） |
| 0.2 | **规则与常量落地**：`.claude/rules/07-tool-center.md`（权威）+ `docs/规则/工具中心规范.md`（镜像）+ `core/constants.py` 补格式常量（如 `TIMESTAMP_FORMAT`） |

**交付物**：一份注册表同时喂 `build_agent` / 子代理 YAML / FastMCP 暴露清单。

### 阶段 1 — 输入侧（对应 §3 的 1–6）

| # | 任务 |
|---|---|
| 1.1 | 网关侧统一 `args_schema` 校验（调用前拦截） |
| 1.2 | 参数规范落地：枚举 / 必填选填 / 否定禁止 / 命名（含可选 lint） |
| 1.3 | 参数归一：合并冗余参数 + 标准格式内部转化（依赖 0.2 常量） |

### 阶段 2 — 输出侧（对应 §4）【最大改造量】

| # | 任务 |
|---|---|
| 2.1 | **工具返回结构化**（`str` → `dict`），逐工具改造 |
| 2.2 | `ToolResultAdapter` 统一 envelope（空值/错误码归一 + 单位归一 + 字段补齐） |

### 阶段 3 — 横切能力（对应 §6 / §7）

| # | 任务 |
|---|---|
| 3.1 | `core/redaction.py` 脱敏层 + 两调用点（`llm/` 出站 / 工具入站） |
| 3.2 | 审计补全（记结果）+ 统一 `trace_id`（入口生成 → 透传 audit/trace/llm） |

### 阶段 4 — 编排侧（对应 §5 / §8，依赖 0.1 元数据）

| # | 任务 |
|---|---|
| 4.1 | 重试 / 降级（`domain` + `fallback_to` 选备选） |
| 4.2 | 幂等门控（非幂等禁自动重试）+ 幂等键透传 |
| 4.3 | 审批流接风险级（HITL 已存在，只接线） |

### 排序理由

- **阶段 0 必须先**：后续全部"挂"在统一元数据上；不收口则双清单继续漂移（现存缺陷）。
- **阶段 1 在 2 前**：输入改造轻、风险低、每个新工具都要用 → 先建立规则肌肉记忆。
- **阶段 2 重但必做**：它是 3.1（入站脱敏）、3.2（审计记结果）的**结构化前提**。
- **阶段 3 依赖 2；阶段 4 依赖 0.1。**

> **第一个可交付**：**阶段 0**（0.1 + 0.2）——一次纯 refactor 即消掉现存漂移，风险最低、立刻有产出。

**跨边界提醒**（这些不属工具中心，做计划时单列）：
- 3.1 出站半边 → `llm/adapter.py`
- 3.2 `trace_id` 生成 → 请求入口中间件
- 4.3 审批执行 → HITL 层（`agent/hitl/`）

## 10. 未决问题与关联文档 🔴 v1

### 未决

1. **第三方"修复"插件确认**：候选 **Guardrails AI**（validators 覆盖字段完整性 / 翻译 / PII）｜**BAML SAP**（Schema-Aligned Parsing，治字段缺失/类型错）｜**instructor**｜**json_repair**——四者都属"修 **LLM 结构化输出**"档，非"修程序输出"。**待用户认领后定落点。**
2. **降级链的授权方式**：配置表（DB）写死 vs 元数据 `fallback_to` 字段——待拍。
3. **大 / 小工具判定落地**：元数据 `size` 字段是标注即可，还是影响挂载/检索策略——待拍。
4. **审计结果的落盘形态**：摘要字符串 vs 结构化 envelope 入库——依赖阶段 2 结论。
