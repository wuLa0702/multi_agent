### 2.2 追问链预演（指南 §3.3 五层链 × 三问自答）

**Q1：为什么做 HITL？什么时候该停下来问人？**

- 为什么：Agent 自动执行有副作用动作（沙箱跑代码、写文件、执行技能脚本）时，人类必须保留执行权闸门——模型判断不可 100% 信任（有"模型绕过搜索自写 curl 抓取循环"的跑偏实证，见 learnings 2026-08-11 爬虫循环）。同时目标模糊时盲目执行 = 浪费 token 和出错概率上升。
- 对比过什么方案：① 全部工具无差别审批 → 打断感强，只读搜索也被审（否决：只读工具无副作用不审）；② 全部不审 → 无执行权闸门（否决：危险动作裸奔）；③ **按风险分级审**（✅ 选定）：高危（任意代码执行）→ approve+edit+reject；中危（命令/文件/技能）→ approve+reject；只读（搜索）→ 不审。选型依据：官方 InterruptOnConfig 天然支持按工具声明决策集，配置即挂中间件。
- 坑与量化：审批恢复链路是最大坑——`astream_events` 不产中断事件（旧设计假设错误），伪造 checkpoint_id 静默新跑；用 `GraphCallbackHandler.on_interrupt` 拿到真实 checkpoint_id 才闭环（§3.3 实证）。量化：需求澄清 + 审批双场景端到端实测通过（§2.3）。

**Q2：需求澄清怎么实现？为什么不靠"模型自己猜"？**

- 为什么：研究任务的用户输入天然模糊（"帮我调研一下 X 行业"——范围、深度、交付形式都不明），模型猜 = 大概率跑偏 → 返工 → 成本翻倍。**让模型在模糊时主动问**，比事后纠错便宜。
- 对比过什么方案：① 提示词"模糊时先问"（纯 prompt，模型自律不保证）；② 独立澄清接口（前端强约束流程，重）；③ **ask_human 工具 + respond 决策**（✅ 选定）：把"问人"做成工具调用，模型想不清楚就调 ask_human(message)，命中 interrupt_on 审批 → 人类回答经 respond 决策以 ToolMessage 形式回给模型——**"问"成了模型的工具能力，不需要自律**。官方 respond 决策语义正是为此设计（"仅 ask_user 类工具"）。
- 坑与量化：respond 决策绝不能配给副作用工具（官方警告：会被模型当成功结果）——ask_human 的 allowed_decisions 只开 respond；工具体内 stub 抛错防御真执行。量化：澄清场景 = 1 次工具调用 + 1 次人类回答 + 恢复后模型带答案继续（端到端实测断言，§8 用例 9）。

**Q3：审批链路怎么恢复？中断点状态怎么找？**

- 为什么：审批中断时图状态在中断点落 checkpoint（langgraph 自动），恢复必须精确回到该点继续——"从哪里断，从哪里续"，且不能重放已审动作。
- 对比过什么方案：① resume 走最新 checkpoint（不带 checkpoint_id，langgraph 默认语义）；② **中断时从 GraphInterruptEvent 取真实 checkpoint_id，approve 事件携带，resume 用它精确定位**（✅ 选定）——多轮审批场景（同会话多次中断）下，最新 checkpoint 可能是别的断点，精确 id 最稳。
- 坑与量化：发现现有 resume 链路潜伏 bug——chat.py 把自生成 UUID 当 checkpoint_id 传，langgraph 精确匹配不到 → **静默新跑**（状态丢失不报错，实证 §3.3-③）。修复 + 回归测试（§8 用例 10）。量化：resume 恢复状态一致性测试（mock 中断 → 决策 → 恢复后工具参数正确）。

**Q4：输出审核和工具审批有什么区别？为什么报告交付要单独一个闸门？**

- 为什么：工具级审批（场景 B）管"某个动作能不能执行"；输出审核（场景 D）管"交付物质量能不能出门"——**粒度不同**。研报这种交付物，风险不在单次工具调用，而在"整份报告的结论/引用是否可信"，需要在报告完整生成后、对外交付前人工审核一次。
- 对比过什么方案：① ask_human 收尾问一句"确认交付？"（复用澄清工具，轻但语义弱——只是一个问题，不是审核一个对象）；② **独立 publish_report 工具 + interrupt_on(approve/edit/reject)**（✅ 选定）——报告内容作为工具参数展示在审批卡片上，人类审核报告正文、approve/reject/edit（edit = 要求改报告后交付），语义是"交付物级闸门"，与场景 B 的工具级闸门分层。
- 坑与量化：报告内容可能很长——卡片展示需截断 + 摘要（message 带报告摘要，arguments 带正文截断 ≤300 同契约）；reject 的 note 即修改意见（复用修订回路经验）。量化：D 场景端到端实测通过 + 审批通过后工具真实执行（交付标记）断言（§8 用例 12）。

### 2.3 可量化结果（落地后预期产出）

## 4. 分·机制设计：四场景 × 一机制

### 4.1 场景总览

> **一机制**：所有场景都是"模型要做一个动作 → 命中人类决策点 → 中断挂起 → 人类决策 → 恢复继续"。区别只在**中断对象**（工具动作 vs 提问）与**决策集**。

| 场景 | 触发 | 中断对象 | 决策集 | 状态 |
|------|------|----------|--------|------|
| **A 需求澄清** | 模型目标/约束模糊，调 `ask_human(message)` | ask_human 工具 | respond（人类回答 = 工具结果）| ✅ P0 落地（§4.2） |
| **B 高风险审批** | 副作用工具命中 interrupt_on 风险分级 | run_code / run_command / 文件 / 技能 | approve / edit / reject（按风险分级）| ✅ P0 落地（§4.3） |
| **C 中途确认** | 模型计划完成，调 `ask_human("计划如上，是否开始？")` | ask_human 工具（同 A）| respond | 🟡 同一机制顺带覆盖（§4.4） |
| **D 输出审核** | 研报生成后模型调 `publish_report(内容)` 请求交付 | publish_report 工具（交付物闸门）| approve / edit / reject（edit=要求改报告）| ✅ P0 落地（§4.5，评审拍板） |

### 4.2 场景 A：需求澄清（ask_human 工具 + respond 决策）

```
用户：帮我调研一下 AI Agent 行业（模糊目标）
  → 模型：目标范围/深度不明 → 调 ask_human(message="调研范围是？侧重哪些细分？报告形式？")
  → interrupt_on 命中（ask_human 已注册）→ ⏸ 中断挂起（checkpoint 落盘）
  → 前端澄清卡片（B2 卡片 respond 模式）→ 用户回答："2026 年市场规模 + 头部玩家格局，800 字摘要"
  → POST /v1/chat/approve {action:"respond", note:"2026 年市场规模 + 头部玩家格局，800 字摘要"}
  → 恢复：Command(resume) → ask_human 收到 respond → 合成 ToolMessage(答案) → 模型带着答案继续
```

- 工具签名：`ask_human(message: str) -> str`——**真实实现是 stub（抛错防御）**，因为 respond 决策下工具永不被执行（中间件合成 ToolMessage 顶替）
- allowed_decisions **只开 `["respond"]`**（官方语义：respond 仅用于 ask-user 类工具；绝不配给副作用工具）
- 系统提示词补一行引导：*"用户目标/约束模糊时，调用 ask_human 澄清后再继续"*（prompts 分层组装增量，§7.2）
- 面试点：模型"学会先问"不是靠自律，是**把问人变成工具能力**（respond 决策语义）

### 4.3 场景 B：高风险审批（interrupt_on 风险分级，现状配置直接复用）

```
模型：调 run_code_in_sandbox({code:"rm -rf /data"})
  → interrupt_on 命中（高危：approve+edit+reject）→ ⏸ 中断挂起
  → approve 事件（run_id=流标识 + checkpoint_id=恢复键 + action_requests + allowed_decisions）→ 本次流结束
  → 前端 B2 审批卡片（按钮：批准 / 拒绝 / 编辑参数）→ 用户决策
  → POST /v1/chat/approve → 202 → resume 重连 → 图继续（approve 原样执行 / reject 跳过+反馈）
```

- 分级配置已在 `hitl.py`（§3.1-#1），本设计**只补链路**：事件、API、恢复
- reject 的 message 是质量关键（官方：反馈决定模型是否换方案）——前端 note 输入框已有

### 4.4 场景 C：中途确认（同一 ask_human，计划确认）

- 零新增代码：模型研究计划拟定后调 `ask_human("检索计划：1)…2)…，确认开始？")`——走场景 A 同链路
- 实现时机的保障：prompt 引导（计划类任务在委派子代理/沙箱前先确认）；评估体系实证过"任务跑偏"（模型跳过约束自写 curl 循环，learnings 2026-08-11），**中途确认是对跑偏的工程兜底**——面试讲"计划确认"时引这个 bad case
- 面试价值：四场景达标三个（做二超一），且每个都是同一机制的不同决策集——架构统一性好讲

### 4.5 场景 D：输出审核（publish_report 交付闸门，评审拍板纳入 P0）

> 需求：研报生成后人类审核再"交付"（发布/发送/落盘）。**粒度与场景 B 不同**：工具级审批管"某个动作能不能执行"，输出审核管"整份交付物能不能出门"——报告结论/引用的可信度在单次工具调用之外，必须在报告完整生成后、对外交付前人工审核一次。

- **工具**：`publish_report(report_content: str, title: str = "")`——报告全文作为工具参数，审批卡片直接展示（卡片 message 带报告摘要，arguments 带正文截断 ≤300，同契约口径）
- **interrupt_on**：`"publish_report": InterruptOnConfig(allowed_decisions=["approve", "edit", "reject"])`
  - approve = 交付通过（工具真执行 → P0 实现为返回成功标记"报告已交付"；落盘/对外发送 P2 扩展）
  - reject + note = 修改意见 → 模型修订重出（**修订轮次受 `settings.publish_review_max_revisions` 配置上限约束，默认 2，v1.2 评审修正：配置化不硬编码**）
  - edit + edited_arguments = 人类直接改报告内容后交付（编辑语义与场景 B 一致）
- **修订轮次控制（v1.2 评审修正）**：approve 端点收到 publish_report 的 reject 决策时，Redis INCR 会话修订计数 `hitl:revise:{session_id}`；resume 时计数 > `publish_review_max_revisions` → 注入 SystemMessage「已达修订上限，输出当前版本并停止修订」（实现：§5.3 reject INCR + §5.4 resume 注入 + §7.4 `incr_revision`）——比纯 prompt 可靠，不依赖模型自律
- **prompt 引导**：研究报告完整生成（各章节 + 引用齐全）后，调用 publish_report 请求交付——模型不自以为完成，交付由人类批准
- 面试点：**交付物级闸门 vs 工具级闸门的分层**（§2.2-Q4），四个场景覆盖指南"四选二"并满格

### 4.6 全流程时序（审批流 + 澄清流 + 输出审核流）

```
【审批流（场景 B）】
POST /v1/chat/stream {session_id, message}
  → stream_agent_events（config 挂 HitlCallback）
  → 工具命中 interrupt_on → on_interrupt 回调（真实 checkpoint_id + HITLRequest）
  → 流结束（try/finally 保证登记）→ register_interrupt 写 Redis → 产 approve 事件（run_id=流标识 + checkpoint_id=恢复键 + call_id，逐 action）→ 终止流（不发 done）
  → 前端 B2 卡片 → 用户决策
  → POST /v1/chat/approve {run_id, checkpoint_id, call_id, action, note?, edited_arguments?} → 202 {accepted}
  → POST /v1/chat/stream {session_id, resume_run_id=checkpoint_id}
  → chat.py 查 Redis 待决决策 → Command(resume={"decisions": [...]}) → 图从中断点继续

【澄清流（场景 A）】同审批流，决策 action="respond" + note=答案文本
  → 中间件合成 ToolMessage(答案) 回给模型 → 模型带答案继续（ask_human 工具不真执行）

【输出审核流（场景 D）】同审批流，中断对象=publish_report（kind=approval，message 带报告摘要）
  → approve → 工具真执行返回"报告已交付"
  → reject+note → **approve 端点 INCR 修订计数 `hitl:revise:{session_id}`** → resume 后模型修订重出
  → 计数 > `publish_review_max_revisions` → resume 注入 SystemMessage「已达修订上限，输出当前版本并停止修订」

【多 action 中断（P1 限制，§6）】一轮多工具命中 → N 条 approve 事件 → 前端逐卡提交
  → 每张卡带 **call_id** → add_decision 按 call_id 定位 action index 写入（顺序强保证，不依赖提交顺序）
  → 最后一条 accepted=true → resume（决策数与 action_requests 数一致才允许恢复）
```

## 5. 分·设计决策（D1-D8）

### 5.1 D1：ask_human 工具（新） 🔴 v1

- 位置：`backend/src/agent/tools/ask_human.py`（工具域分包，同 search.py/sandbox_tool.py 模式）

### 5.3 D3：POST /v1/chat/approve（审批 API，Redis 待决存储，评审拍板） 🔴 v1.1

```json
{ "run_id": "<chat.py 流标识>", "checkpoint_id": "<中断点真实 checkpoint_id>", "call_id": "<工具调用 id，多 action 顺序键>", "action": "approve|reject|edit|respond", "note": "可选", "edited_arguments": {"code": "..."} }
```

- 校验：checkpoint_id 无待决中断 → 404（`APPROVAL_NOT_FOUND`）；action 非法 / edit 无 edited_arguments / respond 无 note → 400
- 语义：把一条人类决策写入 **Redis 待决存储**（§7.4，评审拍板由内存改 Redis——多进程/重启不丢），**v1.2 评审修正：按 `call_id` 定位 action index 写入**（多 action 顺序强保证，不依赖前端提交顺序）；返回 `202 {status:"ok", accepted:bool}`——`accepted = 待决决策数 == 中断 action 数`（前端据此决定 resume 时机；单 action 中断下首次提交即 accepted）
- **修订计数（v1.2 评审修正）**：action=reject 且中断工具为 publish_report → 额外 INCR `hitl:revise:{session_id}`（会话级修订计数，Redis）；计数 > `settings.publish_review_max_revisions` 由 resume 侧消费（§5.4）
- Redis 不可达 → 503（审批服务不可用，前端提示稍后重试）
- 与旧预研文档 D2 的差异：旧设计"decisions 参数复用 /v1/chat/stream"——**保留前端已交付的独立 approve 端点形态**（§3.1-#5），仅新增 checkpoint_id/call_id 透传（D7 决策记录）

### 5.4 D4：恢复链路（resume 消费待决决策 → Command(resume)） 🔴 v1.1

### 7.4 `backend/src/agent/hitl/pending.py`（待决决策存储，Redis 全量）

```python
"""待决审批存储（P0 HITL 设计 §5.3/§5.4）：checkpoint_id → 中断 + 已收决策。

- **Redis 存储（v1.1 评审拍板，替代 v1 内存 dict）**：get_redis()（redis.asyncio，
  decode_responses=True，core/redis.py）；多进程/重启不丢
- key 设计：`hitl:pending:{checkpoint_id}` = JSON{action_requests, review_configs}
  （SET EX 600）；`hitl:pending:{checkpoint_id}:decisions` = LIST 按 action index
  占位写入（v1.2：list 保序 + call_id 匹配配合——分 key 简化 TTL，保持现状不合并）
- 中断时登记，approve 端点逐条写入决策，决策数 == action 数 → accepted=True；
  resume 消费即删（一次性，防重放）
- Redis 不可达 → 异常上抛（approve 路由转 503；测试 mock get_redis）
- 过期 → 404 友好提示（前端提示重开，同 RESUME_NOT_FOUND 处理）
"""

from __future__ import annotations

import json

from src.core.redis import get_redis

_PENDING_TTL_SECONDS = 600          # 10 分钟（人类决策窗口）
_PENDING_PREFIX = "hitl:pending:"   # key 前缀（防与其他业务键冲突）


def _key(checkpoint_id: str) -> str:
    """主 key（中断上下文 JSON）。"""
    return f"{_PENDING_PREFIX}{checkpoint_id}"


def _decisions_key(checkpoint_id: str) -> str:
    """决策 list key（逐条决策，RPUSH 顺序=提交顺序）。"""
    return f"{_PENDING_PREFIX}{checkpoint_id}:decisions"


async def register_interrupt(checkpoint_id: str, hitl_request: dict, session_id: str) -> None:
    """中断发生时登记（流内检测到中断后调用，设计 §5.5）。

    Args:
        checkpoint_id: 中断点 checkpoint_id（GraphInterruptEvent 提供）
        hitl_request: {"action_requests": [...], "review_configs": [...]}
        session_id: 会话 ID（存入主 key——approve 端点据此定位会话级修订计数）

    Raises:
        ValueError: action_requests 为空（v1.2 评审修正：空中断无审批对象，
            不登记——避免 add_decision 空 action 误判 accepted=True）
        RedisError: Redis 不可达（调用方转 503）
    """
    actions = hitl_request.get("action_requests", [])
    if not actions:
        raise ValueError("action_requests 为空，拒绝登记审批中断")
    body = {
        "session_id": session_id,
        "action_requests": actions,
        "review_configs": hitl_request.get("review_configs", []),
    }
    redis = get_redis()
    await redis.set(_key(checkpoint_id), json.dumps(body), ex=_PENDING_TTL_SECONDS)
    await redis.delete(_decisions_key(checkpoint_id))  # 幂等：重复中断清空旧决策


async def add_decision(checkpoint_id: str, call_id: str, decision: dict) -> bool:
    """approve 端点追加一条决策（v1.2 评审修正：按 call_id 定位 action index）。

    decisions 以 LIST 存 JSON，按 action_requests 顺序占位写入——多 action
    顺序强保证，不依赖前端提交顺序（前端逐卡提交时乱序也正确归位）。

    Args:
        checkpoint_id: 中断点 checkpoint_id
        call_id: 工具调用 id（approve 事件回传值，定位 action index）
        decision: {"type": action, "message": note, "edited_action": ...}

    Returns:
        True=决策数已达 action 数（前端可 resume）；False=还需继续审批

    Raises:
        KeyError: 无待决审批（checkpoint_id 未登记/已过期）
        ValueError: call_id 未在 action_requests 中匹配
    """
    redis = get_redis()
    body_raw = await redis.get(_key(checkpoint_id))
    if body_raw is None:
        raise KeyError(checkpoint_id)
    body = json.loads(body_raw)
    actions = body["action_requests"]
    index = _find_action_index(actions, call_id)
    if index is None:
        raise ValueError(f"call_id={call_id} 未匹配到待审 action")
    # 占位写入：LIST 预填 None 占位，按 index 覆盖——保证与 action_requests 同序
    await _set_decision_at(redis, checkpoint_id, index, decision)
    decision_count = await redis.llen(_decisions_key(checkpoint_id))
    return decision_count >= len(actions)


def _find_action_index(actions: list[dict], call_id: str) -> int | None:
    """在 action_requests 中按 call_id 定位 index。

    Args:
        actions: action_requests（action_request 含 call_id/name）
        call_id: 目标调用 id

    Returns:
        匹配的 index；无匹配 → None
    """
    for i, action in enumerate(actions):
        if action.get("call_id") == call_id:
            return i
    return None


async def _set_decision_at(redis, checkpoint_id: str, index: int, decision: dict) -> None:
    """把决策写入 decisions LIST 的指定 index（保序占位，幂等）。

    Args:
        redis: Redis 客户端
        checkpoint_id: 中断点 checkpoint_id
        index: 目标 index（0-based）
        decision: 决策 dict（JSON 序列化）
    """
    key = _decisions_key(checkpoint_id)
    # 保证 LIST 长度 >= index+1（不足补 None 占位）
    current = await redis.llen(key)
    for _ in range(current, index + 1):
        await redis.rpush(key, "null")
    await redis.lset(key, index, json.dumps(decision))
    await redis.expire(key, _PENDING_TTL_SECONDS)


async def consume(checkpoint_id: str) -> dict | None:
    """resume 时消费待决审批（一次性，读后即删）。

    v1.2 评审修正：主 key 用 `redis.getdel()` 原子消费（get+del 一步，
    Redis 6.2+）——防并发 resume 双读到同一决策；decisions LIST 读后删，
    若 getdel 后进程中断残留 LIST，靠 TTL 过期兜底（主 key 已删不会重复消费）。

    Args:
        checkpoint_id: resume_run_id（approve 事件透传值）

    Returns:
        {"decisions": [...]}（Command(resume) 输入形态）；无待决 → None
    """
    redis = get_redis()
    body_raw = await redis.getdel(_key(checkpoint_id))  # 原子 get + del
    if body_raw is None:
        return None
    decision_raws = await redis.lrange(_decisions_key(checkpoint_id), 0, -1)
    await redis.delete(_decisions_key(checkpoint_id))  # 消费即删（残留靠 TTL）
    decisions = [json.loads(d) for d in decision_raws if d != "null"]
    return {"decisions": decisions}
```

```python
"""HITL 中断检测回调（P0 HITL 设计 §5.5）：GraphCallbackHandler 采集中断点。

⚠️ 实证修正（2026-08-11，设计 §3.3-②）：astream_events 不产 on_interrupt
事件——中断检测必须经 config["callbacks"] 的 GraphCallbackHandler.on_interrupt；
事件携带真实 checkpoint_id + interrupts（value = HITLRequest 形态）。

回调只采集不决策：中断上下文写入收集器，流内循环检测到后产出
approve 事件并终止流（单一事件出口，保持 stream_agent_events 职责）。
"""

from __future__ import annotations

from langgraph.callbacks import GraphCallbackHandler, GraphInterruptEvent


class HitlCallback(GraphCallbackHandler):
    """采集 graph 中断事件（checkpoint_id + HITLRequest 负载）。

    Attributes:
        interrupted: 最近一次中断上下文（None=未中断）——
            {"checkpoint_id": str, "hitl_request": {"action_requests", "review_configs"}}
    """

    def __init__(self) -> None:
        self.interrupted: dict | None = None

    def on_interrupt(self, event: GraphInterruptEvent) -> None:
        """中断回调：记录 checkpoint_id 与审批负载（流内据此产出 approve 事件）。

        Args:
            event: langgraph 中断生命周期事件（含真实 checkpoint_id）
        """
        if not event.interrupts:
            return
        self.interrupted = {
            "checkpoint_id": event.checkpoint_id,
            "hitl_request": event.interrupts[0].value,
        }
```

```python
def _iter_action_reviews(hitl_request: dict):
    """HITLRequest → (action, review) 逐条（按序一一对应）。

    Args:
        hitl_request: {"action_requests": [...], "review_configs": [...]}

    Yields:
        (action_request, review_config) 二元组（review 缺省给空 dict）
    """
    configs = {c.get("action_name"): c for c in hitl_request.get("review_configs", [])}
    for action in hitl_request.get("action_requests", []):
        yield action, configs.get(action.get("name"), {})


def _build_approve_event(run_id: str, checkpoint_id: str, action: dict, review: dict, seq: int) -> dict:
    """approve 事件构建（对齐前端 B2 契约 + run_id/checkpoint_id 分离，设计 §5.2）。

    Args:
        run_id: chat.py 本次流 run_id（流标识，前端区分多次中断）
        checkpoint_id: 中断点 checkpoint_id（resume 恢复键，前端透传）
        action: action_request（name/args）
        review: review_config（allowed_decisions）
        seq: 流内事件序号

    Returns:
        SSE 事件 dict（approve）
    """
    allowed = review.get("allowed_decisions", ["approve", "reject"])
    name = action.get("name", "")
    message = (
        f"澄清：{str(action.get('args', {}).get('message', ''))[:200]}"
        if name == "ask_human"
        else f"交付审核：{str(action.get('args', {}).get('title', ''))[:100]}" if name == "publish_report"
        else f"工具 {name} 需要审批"
    )
    return {
        "type": "approve",
        "run_id": run_id,
        "checkpoint_id": checkpoint_id,   # v1.1 新增独立字段
        "call_id": action.get("call_id") or f"action-{seq}",  # v1.2：fallback 流内唯一，防同名工具撞
        "tool_name": name,
        "arguments": _truncate_args(action.get("args", {})),  # v1.2 评审修正：脱敏截断
        "message": message,
        "allowed_decisions": allowed,
        "kind": "clarification" if name == "ask_human" else "approval",
        "id": seq,
    }


def _truncate_args(args: dict, limit: int = 300) -> dict:
    """待审参数脱敏截断（v1.2 评审修正，对齐 §5.2「脱敏截断 ≤300」）。

    publish_report 的 report_content 可能很长——不截断会撑爆 SSE 事件；
    逐字符串字段截断到 limit（保留 dict 结构），嵌套 dict 顶层字段已覆盖
    主要场景（report_content/title/message 均为顶层 str）。

    Args:
        args: 工具调用参数 dict
        limit: 单字段截断上限

    Returns:
        截断后的 dict（长字符串字段 + "…" 后缀）
    """
    truncated: dict = {}
    for key, value in args.items():
        if isinstance(value, str) and len(value) > limit:
            truncated[key] = value[:limit] + "…"
        else:
            truncated[key] = value
    return truncated
```
