## 1. 问题的提出 🔴 v1

co-creator 原话（2026-10-15）：

> 「审计留档目前逻辑是？整个系统都需要审计留档，异步 trace。这个如何设计呢？**不应该只是对工具调用留档**。」

即：审计要从「只覆盖工具调用」扩到**系统级**，并要有**贯穿的异步 trace**。

## 2. 现状（已核实，2026-10-15） 🔴 v1

**两条独立文件流、六个写入点**（字段集逐个读过源码）：

```
logs/file_access_audit.jsonl   ← logger "audit"（5 个写入点）
logs/agent_trace.jsonl         ← logger "trace"（1 个采集器）
```

| 写入点 | layer | 标识字段 | 事件字段 | 其他 |
|---|---|---|---|---|
| `tools/audit.py`：工具审计中间件 | `tool_call` | `thread_id` | `decision="audit"` | tool、args（敏感工具脱敏） |
| `tools/audit.py`：安全拦截 | `security` | **❌ 无** | `event="blocked"` | tool、reason |
| `core/backend.py`：文件访问 | `policy_backend` | `thread_id` | `decision` | op、path、policy |
| `sandbox/pool.py`：沙箱池 | `sandbox` | `thread_id` | `event` | sandbox_id |
| `agent/memory/queue.py`：记忆队列 | `memory_agent` | `session_id` | `event` | fingerprint、detail |
| `agent/middlewares/trace.py`：推理 trace | **❌ 无 layer** | `session_id`（可空） | `event` | run_id、parent_ids、摘要 |

## 3. 四个缺口 🔴 v1

| # | 缺口 | 证据 |
|---|---|---|
| 1 | **没有贯穿 ID** | `trace_id` 全仓 **0 命中**；六个流无法互相关联 |
| 2 | **标识字段三套方言** | `thread_id` / `session_id` / **连标识都没有**（安全拦截） |
| 3 | **事件字段两套方言** | 工具审计用 `decision`，其余用 `event` |
| 4 | **审计只有"事前"，没有结果** | 工具审计只记入参；**成败 / 错误码 / 耗时全无** |

> 缺口 4 正是工具中心阶段 2.3.1 要做的子集（阶段 2 刚产出的 `status` / `error_code` 就是喂它的）。

## 4. 已定决策（co-creator 2026-10-15 拍板） 🔴 v1

| # | 决策 | 内容 |
|---|---|---|
| **D1** | **审计落点 = 双写** | JSONL 作**不可篡改的原始底账**（追加写、进程崩也不丢）+ **异步**写入 PG 供查询 |
| **D2** | **审计粒度 = 事前 + 事后两行** | 两行才留得下「操作开始了但没结束」这个信号——进程被杀 / 沙箱挂死时，单行合并方案什么都留不下，而那恰是审计最需要留的情形 |
| **D3** | **数据库 = PostgreSQL 全量迁移** | 见 `2026-10-15-计划-PG迁移-v1.md`（含 pgvector 预留，为后续向量索引） |
| **D4** | **审计 ≠ trace，分开设计** | 审计=追责/合规（必须完整、不可丢、长期保存）；trace=排障/性能（可采样、可丢、短期）。**两者共享同一个 trace_id，但存储与保留策略不同** |

## 5. 待定项（含建议） 🟠 v1

| # | 待定 | 建议 |
|---|---|---|
| **B1** | **队列实现 + 谁消费** | Redis **Stream**（有 consumer group + ack + 可回放；进程内 `asyncio.Queue` ❌ 会丢，审计不能丢）。消费者形态：独立 worker 进程（上云友好）vs FastAPI 内后台任务——**上云后倾向独立 worker** |
| **B2** | **trace 落点** | 审计进 PG 后，trace **留 JSONL**（可采样、短期、量大）——两者保留策略本就不同，不必都进库 |
| **B3** | **异步任务的 trace 归属** | 记忆抽取等后台任务：**继承发起它的 trace_id**（能追"这次会话触发的抽取成没成"）；拿不到才用孤儿 ID 并标注 |
| **B4** | **审计保留期 + 结果是否入审计** | 保留多久？工具**返回结果**要不要进审计（现仅入参 + 状态）？涉及脱敏范围 |

## 6. 与 PG 分支的接口 🔴 v1

- **PG 迁移分支不为审计预建任何表**（`计划-PG迁移-v1.md` §2.1 已写明）
- 审计表在**本方向的设计稿定稿后**，由审计分支自行建
- **但**：PG 迁移的 DSN / 连接池单例是审计写入的依赖 → 审计分支排在 PG 之后

## 7. 下一步 🔴 v1

```
工具中心分支（2.3 审计补 status/error_code —— 只写 JSONL，不依赖 PG，现在就能做）
        ↓
PG 迁移分支（计划-PG迁移-v1.md，另开新对话执行）
        ↓
审计与可观测分支：① 出完整设计稿（统一事件模型 / trace_id 贯穿 / 队列 / 双写落地）
                  ② 拍 §5 的 B1–B4
                  ③ 实施
```
