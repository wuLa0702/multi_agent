## 1. 问题的提出 🔴 v1

co-creator 原话（2026-10-15）：

> 「审计留档目前逻辑是？整个系统都需要审计留档，异步 trace。这个如何设计呢？**不应该只是对工具调用留档**。」

即：审计要从「只覆盖工具调用」扩到**系统级**，并要有**贯穿的异步 trace**。

## 2. 现状（已核实，2026-10-15） 🔴 v1

**两条独立文件流、六个写入点**（字段集逐个读过源码）：

```
logs/file_access_audit.jsonl   ← logger "audit"（5 个写入点）
logs/agent_trace.jsonl         ← logger "trace"（1 个采集器）
```

| 写入点 | layer | 标识字段 | 事件字段 | 其他 |
|---|---|---|---|---|
| `tools/audit.py`：工具审计中间件 | `tool_call` | `thread_id` | `decision="audit"` | tool、args（敏感工具脱敏） |
| `tools/audit.py`：安全拦截 | `security` | **❌ 无** | `event="blocked"` | tool、reason |
| `core/backend.py`：文件访问 | `policy_backend` | `thread_id` | `decision` | op、path、policy |
| `sandbox/pool.py`：沙箱池 | `sandbox` | `thread_id` | `event` | sandbox_id |
| `agent/memory/queue.py`：记忆队列 | `memory_agent` | `session_id` | `event` | fingerprint、detail |
| `agent/middlewares/trace.py`：推理 trace | **❌ 无 layer** | `session_id`（可空） | `event` | run_id、parent_ids、摘要 |

## 3. 四个缺口 🔴 v1

| # | 缺口 | 证据 |
|---|---|---|
| 1 | **没有贯穿 ID** | `trace_id` 全仓 **0 命中**；六个流无法互相关联 |
| 2 | **标识字段三套方言** | `thread_id` / `session_id` / **连标识都没有**（安全拦截） |
| 3 | **事件字段两套方言** | 工具审计用 `decision`，其余用 `event` |
| 4 | **审计只有"事前"，没有结果** | 工具审计只记入参；**成败 / 错误码 / 耗时全无** |

> 缺口 4 正是工具中心阶段 2.3.1 要做的子集（阶段 2 刚产出的 `status` / `error_code` 就是喂它的）。

## 3.5 覆盖边界（**不在**本次系统级审计范围） 🆕 v1.1

> **立这节的理由**：co-creator 指出——不划边界，范围会无限扩张（"系统级"三个字没有下限）。
> 下面每一条都是**明确排除**，将来若要纳入需重新拍板、并给出理由。

**总原则**：审计记的是「**谁，在何时，对这个系统做了什么动作**」——**不记**「系统处理的内容」。
内容属于 trace / 业务数据，不属于追责账本。

| # | 不纳入 | 理由 |
|---|--------|------|
| 1 | **LLM 的完整 prompt / response 正文** | 体量大 + 含用户隐私；审计只记**元数据**（模型名 / 耗时 / token 数 / 是否失败）。正文归 trace（可采样）。 |
| 2 | **文件内容本身** | 审计记 `路径 + 操作 + 结果`；**不记内容**（内容可能是敏感数据，且会让审计库膨胀到不可用） |
| 3 | **MCP 远端 server 内部发生的事** | 边界清晰：我们只记「**我们发起了对它的调用**」及其结果。它内部读写了什么，是**对方的审计责任** |
| 4 | **沙箱容器内的执行细节** | backend 物理不可达（隔离设计使然）；只记「发起了哪段代码/脚本」+ 结果摘要 |
| 5 | **健康检查 / 就绪探针**（`/health`、`/`） | 高频纯噪音；纳入会淹没真实事件 |
| 6 | **只读列表查询类接口**（会话列表、模型列表、市场列表…） | 同上。**例外**：涉及他人数据的越权尝试要记（走 `security` layer，不是 `api` layer） |
| 7 | **框架内部节点级事件**（langgraph super-step、中间件进出） | 归 trace；审计只记**业务语义事件**（工具调用 / 审批 / 会话生命周期） |
| 8 | **前端行为**（点击、路由、渲染） | 不在后端审计范围；前端埋点是另一条线（若要做，另立主题） |
| 9 | **第三方 SDK 内部日志** | 不接管、不转发（接管等于承诺维护对方的日志格式） |

**已在范围内**（现状 6 个写入点 + 本轮新增）：

| 层 | 范围 |
|---|---|
| `tool_call` | 工具调用（事前 + 事后，含三态/错误码/耗时） |
| `security` | 安全拦截（校验失败、越权尝试、审批拒绝） |
| `policy_backend` | 文件访问 |
| `sandbox` | 沙箱池生命周期 |
| `memory_agent` | 记忆抽取队列 |
| `api`（**新增**） | 请求级：谁调了哪个接口、结果状态码、耗时 |
| `hitl`（**新增**） | 审批：谁在何时批准/驳回了什么（**含决策内容**——这是追责关键） |
| `session`（**新增**） | 会话生命周期：创建 / 删除 / 压缩 |

## 4. 已定决策（co-creator 2026-10-15 拍板） 🔴 v1

| # | 决策 | 内容 |
|---|---|---|
| **D1** | **审计落点 = 双写** | JSONL 作**不可篡改的原始底账**（追加写、进程崩也不丢）+ **异步**写入 PG 供查询 |
| **D2** | **审计粒度 = 事前 + 事后两行** | 两行才留得下「操作开始了但没结束」这个信号——进程被杀 / 沙箱挂死时，单行合并方案什么都留不下，而那恰是审计最需要留的情形 |
| **D3** | **数据库 = PostgreSQL 全量迁移** | 见 `2026-10-15-计划-PG迁移-v1.md`（含 pgvector 预留，为后续向量索引） |
| **D4** | **审计 ≠ trace，分开设计** | 审计=追责/合规（必须完整、不可丢、长期保存）；trace=排障/性能（可采样、可丢、短期）。**两者共享同一个 trace_id，但存储与保留策略不同** |

## 4.1 成本与风险评估 🆕 v1.1

> **立这节的理由**：co-creator 指出 D1 只说了"双写"，但**双写本身的开销与失败模式一条没记**。
> 下面按五个维度过；**每条都给处置方向**（不是只列风险）。

### 4.1.1 性能

| 风险 | 处置 |
|---|---|
| 双写 = 每条事件 2 次 IO；若在**请求主链路同步写**，会把磁盘/网络延迟加到用户响应上 | **全链路异步**：业务侧只做「投递」，IO 全在消费者。业务侧成本 = 内存入队（µs 级），与审计后端无关 |
| 内存队列在进程崩时丢事件 | 故投递目标**不是进程内 `asyncio.Queue`**，而是 **Redis Stream**（进程外、可 ack）——D1 已定 |

**已知代价（接受）**：多一跳 Redis（本地 compose，局域网 µs 级）；换来的是"崩溃不丢"。

### 4.1.2 失败重试

| 场景 | 处置 |
|---|---|
| PG 写失败（连接抖动） | Redis Stream **consumer group + ack**：未 ack 的消息留在 PEL，消费者重启后 `XCLAIM` 重投 |
| **重试上限** | ⚠️ 无限重试会**阻塞队列**（一条坏消息卡住后续全部）→ 需**每消息重试上限 + 死信**（超限 → 写 `audit_dead_letter` + 告警），**死信不静默丢** |
| JSONL 写失败（磁盘满 / 权限） | **这是底账，失败必须显式告警**（不能像 PG 那样静默重试）。磁盘满属严重事件，应触发运维告警（当前项目仅有日志，需补） |

### 4.1.3 背压

| 风险 | 处置 |
|---|---|
| 突发流量 > 消费者吞吐 → Stream 持续增长 → **Redis 内存爆**（Redis 限额 256m，见架构文档 §3） | **三级处置**：① `XADD MAXLEN ~ N` **近似裁剪**（⚠️ 审计不允许静默丢 → 裁剪前必须落 JSONL，见下"降级"）② 消费者水平扩展（同 group 多消费者）③ **降级开关**：Stream 逼近上限时**只保 JSONL**（底账不可丢，PG 索引可追） |
| 降级期间 PG 落后 | 属**可接受**：PG 是派生索引，事后可从 JSONL **重放补齐**（见 4.1.5） |

**关键取舍**：宁可 PG 暂时落后，**绝不丢 JSONL**。

### 4.1.4 磁盘占用

```
单条审计行（估）：~300–500 B（含字段名）
demo 期（日活低）：< 1 万条/天 → < 5 MB/天 → 一年 < 2 GB
上云后（2核4g，磁盘按 40GB 算）：需监控，见保留期 B4.1
```

| 项 | 说明 |
|---|---|
| **双份存储** | JSONL + PG 各存一份 → 磁盘翻倍。**这是 D1 的自觉代价**（换"不可篡改 + 可查询"） |
| 滚动策略 | 复用 `04-logging.md` 的 `SizeTimedRotatingFileHandler`（50MB / 每天 / 保留 14 个）——⚠️ **但审计的保留期不应是 14 天**（见 B4.1，需独立策略，不复用日志滚动参数） |
| 归档 | 超保留期的 JSONL 应**压缩归档**（`.gz`，压缩比通常 5–10×）而非删除 |

### 4.1.5 数据一致性（**双写的核心风险**）🔴

**问题**：JSONL 成功而 PG 失败（或反之）→ 两处不一致。怎么判、怎么办？

**定序（本节最重要的结论）**：

```
JSONL = 权威底账（source of truth）
  ├─ append-only、单机磁盘、不依赖网络
  ├─ 先把事件落 JSONL，成功后才投递给 Stream
  └─ 崩在两者之间 → 最坏是"JSONL 有、PG 没有"（可追），不会"PG 有、JSONL 没有"

PG   = 派生索引（rebuildable）
  ├─ 只用于查询/聚合
  └─ 与 JSONL 不一致时 → **以 JSONL 为准**
```

| 不一致情形 | 判定 | 处置 |
|---|---|---|
| JSONL 有、PG 无 | 正常滞后（或 PG 丢消息） | 无需处理；需要时**重放** |
| PG 有、JSONL 无 | **异常**（说明写序被破坏，或 JSONL 被裁剪） | 告警 + 人工介入（正常时序下不该发生） |
| 两处内容不同 | 以 JSONL 为准 | 重放覆盖 |

**幂等保证**：事件自带 `(trace_id, seq)`，PG 表对该组合作**唯一约束** → 重放可安全重复执行。
**重放工具**：审计分支需提供 `rebuild_from_jsonl(时间范围)`（**必做项**，不是可选）——没有它，上述"可重建"就只是口号。

### 5.1 B4 拆分：三个子问题各带备选方案草稿 🆕 v1.1

> co-creator 指出 B4 原样"只抛问题没给选项"。拆成三个独立决策，每个给 2–3 个备选。

**B4.1 审计保留周期**

| 备选 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A. 一刀切** | 全部保留 1 年 | 实现最简 | 读类噪音占绝大多数磁盘；安全事件被"一视同仁"淹没 |
| **B. 按 layer 分档**（推荐） | `security` / `hitl` 保留 **3 年**（追责/合规）；`tool_call` / `api` **1 年**；`sandbox` / `memory_agent` **90 天** | 磁盘花在刀刃上；与"审计≠trace"的 D4 精神一致 | 配置略复杂；跨档关联查询需注意窗口 |
| **C. 全永久 + 冷归档** | PG 永久，JSONL 压缩归档 | 最安全 | 云盘成本随年限线性涨；不符合 demo 阶段的成本约束 |

**倾向 B**。⚠️ **不要复用日志的"保留 14 个"**（那是排障日志的参数，审计必须更长）。

**B4.2 工具返回结果是否入审计**

| 备选 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A. 不入**（推荐） | 只记：入参 + 三态 + 错误码 + 耗时 | 体积小；**不引入第二处敏感数据面**；结果本就在 SSE/artifact 里可查 | 事后无法从审计单独复原"当时返回了什么" |
| **B. 入 + 截断 + 脱敏** | 入库但截断 N 字符、过脱敏规则 | 信息最全 | 脱敏漏一处即泄漏；体积涨数倍 |
| **C. 入指纹** | 只记 `sha256(结果) + 长度` | **可校验不可读**（能证明"没被篡改"）；体积恒定 | 无法直接查看内容 |

**倾向 A + 采 C 的指纹**（不冲突：A 不存正文，C 的指纹是几十字节的定长字段）。
⚠️ 与 §3.5 边界第 2 条同源：**审计不记内容**。

**B4.3 脱敏边界**

| 备选 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A. 复用 `llm/redact.py` 规则表**（推荐） | 同一张 `(正则, 标签)` 表，审计与出站脱敏共用 | **规则一处**（项目的老毛病就是"同一件事两处写"）；新增规则自动两处生效 | 两处需求未来若分叉，需拆表 |
| **B. 审计专用规则表** | 独立维护 | 各自演进自由 | 两处规则迟早漂移 —— **不推荐**，与本项目反复踩的坑同型 |
| **C. 审计不脱敏** | 追责要完整 | 信息最全 | **安全红线**：审计文件本身成为泄漏源（与 `00-security` 冲突） |

**倾向 A**。补充要求：脱敏后**保留元信息**（脱了几处 / 哪类），否则审计失真——这一点
`llm/redact.py` 的 `redact()` 已返回 `dict[str,int]` 计数，**可直接复用**。

### 5.2 新增待定项 🆕 v1.1

| # | 待定 | 备选方案草稿 |
|---|---|---|
| **B5** | **trace 采样策略** | ① **首版全采**（demo 量小，见 4.1.4 估算 < 5MB/天）② 按率采样（`settings.trace_sample_rate`）③ 规则采样。**建议：全采 + 预留开关**，且采样决策必须满足两条硬约束：**(a) 错误必采**（`status=error` 永不采样）**(b) 采样决策在请求入口一次性做出、全链路继承**（否则链路会"断在中途"，排障时最需要的那段恰好没采到） |
| **B6** | **孤儿 trace_id 规则** | 场景：后台任务 / 定时任务 / 无上游的入口。**建议规则**：① **禁止留空**（留空＝回到"无法关联"，正是缺口 1）② 无上游 → **生成新 trace_id 并打标 `orphan=true`** ③ 若能拿到 `session_id`/`thread_id`，作为**弱关联字段**一并写入（可回溯到会话，只是不知道是哪次请求触发的）④ 孤儿 ID 纳入**抽样审查**（孤儿率过高说明某条链路没接上） |

## 6. 与 PG 分支的接口 🔴 v1

- **PG 迁移分支不为审计预建任何表**（`计划-PG迁移-v1.md` §2.1 已写明）
- 审计表在**本方向的设计稿定稿后**，由审计分支自行建
- **但**：PG 迁移的 DSN / 连接池单例是审计写入的依赖 → 审计分支排在 PG 之后
