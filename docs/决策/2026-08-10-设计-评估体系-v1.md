## 1. 背景与目标 🔴 v1

**Why（双动机）**：
1. **面试**（2026-08-10 调研定案）：面试第一分水岭 = 评估与可量化结果（baseline 对比）；面试指南 §3.2 标红「项目缺评估体系」为 🔴 高短板——没有数据，多 Agent 全部技术工作无法证明有效
2. **工程**：生产落地必须回答"你的 Agent 到底有没有用"——准确率、成本、延迟是可交付的底线

**目标**：建一个**可复跑、有数据的离线评估管道**——给定研究任务集，跑多 Agent 配置（主 agent + 子代理委派），输出：研报质量分 + 事实性指标 + 成本/延迟指标 + **纵向版本对比报告**（同配置优化前后，git 版本演进）。

**边界（不做）**：不做在线评测平台、不做 dashboard、不做线上灰度；**不做单/多 Agent baseline 对照**（2026-08-10 co-creator 拍板：项目主线就是多 Agent，不需要证明"单 Agent 更好/更差"——直接评估多 Agent 自身质量）。

## 2. 评估对象与指标定义（四类 10 项） 🔴 v1.1

**评估对象**：研究任务（task）→ 产出研报（report）+ 执行过程（trace 收集：消息/工具调用/耗时/成本）。

| 类别 | 指标 | 定义/公式 | 计算方式 | 可信度 |
|------|------|-----------|----------|--------|
| **A 事实性** | A1 引用编号合规率 | 合规引用数 ÷ 引用总数（引用标注 `[N]` 格式合规 **且编号在 sources 列表范围内**） | **规则自动**（正则提取 → 范围检查） | 🟢 高（确定性） |
| | A2 来源可达率 | 来源 URL 经 **HTTP 请求**确认真实可访问（2xx/3xx 可达；超时或 4xx/5xx 不可达；网络异常计 unknown 不计入）÷ 抽查数（每报告 3-5 条） | **规则自动**（httpx 可达性检查） | 🟢 高（确定性） |
| | A3 事实准确率 | 抽样 N 条论断人工核对正确 ÷ N（golden 标注对照） | 人工标注（P2，随 golden 补建） | 🟢 高（人类仲裁） |
| **B 质量** | B1 章节完整度 | judge 按 report_completeness rubric 打分 1-5 | LLM-as-judge（复用 rubrics.py 模板，盲评） | 🟡 中 |
| | B2 来源可靠性 | judge 按 source_veracity rubric 打分 1-5（无编造/区分事实与推测） | LLM-as-judge（盲评） | 🟡 中 |
| **C 过程** | C1 任务完成率 | 成功产出终稿任务数 ÷ 任务总数 | 规则自动 | 🟢 高 |
| | C2 工具调用成功率 | 成功工具结果 ÷ 工具调用总数（从 trace 审计） | 规则自动 | 🟢 高 |
| | C3 平均工具调用次数 | 总工具调用数 ÷ 完成任务数 | 规则自动 | 🟢 高 |
| **D 成本** | D1 端到端耗时 | 任务 start → done 秒数（SSE done 事件 duration_ms 已有） | 规则自动 | 🟢 高 |
| | D2 Token/费用 | 上下文用量统计（token 中间件已存库） | 规则自动 | 🟢 高 |

> **设计原则（v1.1 评审修正）**：
> - **规则可算的指标优先**（A1/A2/C/D 全自动、确定性高）；LLM-judge 只用于"质量主观维度"（B 类）且**输出走纯文本 + 规则解析**——复用项目已实证教训：国产模型 response_format 三态全挂（P1-2 实证），judge 禁止依赖结构化输出强制
> - **A1 分两阶段**：P0 只查"编号合规"（范围检查，确定性）；P1 升级"引用-来源语义匹配"（LLM 抽查引用内容与来源一致性）——面试主动说明这个演进规划
> - **A2 用 HTTP 可达性**而非 LLM 判断：LLM 不联网，无法验证 URL 真实存在（v1.1 评审修正）——脚本发请求是确定性且可靠的

## 4. 评估流程（harness 管道） 🔴 v1.1

```
eval_harness.py --tasks data/eval/tasks.jsonl [--concurrency 3]
  │
  ├─ 1. 加载任务集（含 fact_points 预填）
  ├─ 2. 逐任务（信号量并发上限 3，见 §7）：调用 chat API（真实 LLM，mock 不适用——这是 eval 不是测试）
  │     ├─ 失败自动重试 1 次（偶发错误不污染结果，重试仍失败记 errors 继续）
  │     └─ 收集：SSE 事件流（done 事件含 context_used/duration_ms）+ 工具审计 trace
  ├─ 3. 规则指标计算（A1/A2/C/D：引用对表、HTTP 可达性、完成判定、成本聚合）
  ├─ 4. LLM-judge 盲评打分（B1/B2：复用 rubric 模板 → 文本输出 → 规则解析 1-5；
  │     judge 不接收 config 标签，随机顺序，建议异模型）
  ├─ 5. 生成报告：data/eval/reports/{run_id}.json + .md（含 git_commit 版本指纹）
  └─ 6. 纵向对比：与历史报告（同任务集 + 不同 git_commit）对比 → 差值表（§5.2）
```

**复跑性**：同任务集 + 固定模型配置 → 可复现；报告带 run_id + 时间戳 + 配置指纹（§4.6 要求"可复现"）。

## 5. 评估对象配置与纵向版本对比（多 Agent 主线） 🔴 v1.2

> v1.2 拍板修正：不做单/多 Agent baseline 对照——**项目主线就是多 Agent，直接评估多 Agent 自身质量**；量化靠「绝对指标 + 纵向版本对比」。

### 5.1 评估对象配置说明（多 Agent 设计归属）

> ⚠️ 回答"多 Agent 设计在哪"：**本评估文档不设计多 Agent 架构**——多 Agent 是项目已有资产（deepagents 主编排 + 子代理委派），评估体系只是测量工具。多 Agent 的**架构演进设计**（审核子代理协作细节）属 **P0-2 计划文档**（面试指南 §9.2 顺序：P0-1 评估 → P0-2 审核子代理）。

**当前评估配置（P0-1 阶段）**：

```
主 Agent（deepagents 编译图，main_agent.py）
 ├─ 直接工具：internet_search（博查）/ 沙箱执行 / skill 脚本
 └─ 子代理委派：search_agent（YAML 声明式，model 字段按任务选模型）
产出：研报（token 流式）+ SSE 事件 + 工具审计 trace + 上下文用量
```

**P0-2 落地后扩展**：评估配置追加审核子代理（review 角色）——同一管道复用，无需改造评估脚本，只换 Agent 配置（§7 说明）。

### 5.2 纵向版本对比（替代 baseline 对照）

**对比对象**：**同一多 Agent 配置的优化前后**——按 git 版本演进（呼应 `docs/功能更新日志.md`：功能更新有时间范围和版本号，评估报告记录同源）。

**典型对比场景**：
| 对比 | 触发 | 讲什么 |
|------|------|--------|
| 评估体系 v1 首跑 vs 优化后重跑 | 优化 prompt/子代理后重跑同任务集 | "把 X 优化后，引用合规率从 Y% 提到 Z%" |
| P0-1 评估（无审核）vs P0-2 后（有审核） | 审核子代理落地后 | "加审核子代理后，来源可靠性 +X 分，成本 +Y%" |

**报告要求**：每次运行记录 `git_commit`（当前 HEAD 短哈希）——报告天然带版本指纹，两次对比即"功能更新日志"的量化补充。

> **统计显著性声明**：任务集规模有限（10-20 个），主要看**趋势**而非精确差异——面试主动说明，诚实加分。

> **面试话术模板**（§4.2 STAR 数据收尾）："多 Agent 是我的主线架构。我建了评估管道，每次优化后重跑同任务集对比：审核子代理上线后，来源可靠性从 X 提到 Y、成本涨 Z%（主动讲代价）——数据驱动迭代"。

### 7.1 代码骨架（`backend/scripts/eval_harness.py`）

```python
"""评估管道：多 Agent 研报质量评估（设计-评估体系-v1 §4，v1.2 无 single/multi 对照）。

用法：
    python scripts/eval_harness.py --tasks data/eval/tasks.jsonl
    python scripts/eval_harness.py --tasks data/eval/tasks.jsonl --concurrency 3
产出：data/eval/reports/{run_id}.json + .md（含 git_commit 版本指纹，支持纵向对比）
"""
from __future__ import annotations

import argparse
import asyncio
import json
import re
import uuid
from dataclasses import dataclass, field
from pathlib import Path

import httpx  # 顶部导入（v1.1 评审修正：不做延迟导入）

# ── 指标聚合结果 ──
@dataclass
class TaskMetrics:
    """单任务评估结果（§2 四类指标）。"""
    task_id: str
    completed: bool = False            # C1
    tool_calls: int = 0
    tool_success: int = 0              # C2 = tool_success / tool_calls
    duration_ms: int = 0               # D1
    context_used: int = 0              # D2
    citations_total: int = 0
    citations_compliant: int = 0       # A1 = compliant / total
    sources_checked: int = 0
    sources_reachable: int = 0         # A2 = reachable / checked
    completeness_score: float = 0.0    # B1（LLM-judge 1-5，盲评）
    veracity_score: float = 0.0        # B2
    errors: list[str] = field(default_factory=list)

    def a1_ratio(self) -> float:
        """引用编号合规率（规则计算，§2 A1——只查编号格式+范围，P1 升级语义匹配）。"""
        return self.citations_compliant / self.citations_total if self.citations_total else 0.0

    def a2_ratio(self) -> float:
        """来源可达率（§2 A2——HTTP 可达性，unknown 不计入分母）。"""
        return self.sources_reachable / self.sources_checked if self.sources_checked else 0.0


# ── 规则指标 A1：引用编号合规率（v1.1 改名：只查合规，不做语义匹配）──
CITATION_RE = re.compile(r"[\[【](\d{1,2})[\]】]")  # 研报中 [1] 式引用标注


def count_compliant_citations(report_text: str, sources: list[str]) -> tuple[int, int]:
    """统计合规引用数：引用标注编号是否在 sources 列表范围内。

    ⚠️ 范围合规 ≠ 内容对应（v1.1 评审修正）：sources 有 5 条、报告引 [3]，
    编号合规但第 3 条来源可能与引用内容无关——P1 升级为 LLM 语义匹配抽查。

    Args:
        report_text: 研报全文
        sources: 收集到的来源列表（搜索/文档）

    Returns:
        (compliant, total) 引用编号合规率 = compliant / total
    """
    refs = {int(m) for m in CITATION_RE.findall(report_text)}
    if not refs:
        return 0, 0
    compliant = sum(1 for r in refs if 1 <= r <= len(sources))
    return compliant, len(refs)


# ── 规则指标 A2：来源可达性（v1.1 评审修正：LLM 不联网，改 HTTP 验证）──
async def verify_source_url(client: httpx.AsyncClient, url: str) -> str:
    """检查来源 URL 是否可访问（§2 A2）。

    Args:
        client: 复用连接池的 httpx 客户端
        url: 来源 URL

    Returns:
        "reachable"（2xx/3xx）/ "unreachable"（超时/4xx/5xx）/ "unknown"（网络异常，不计入统计）
    """
    try:
        resp = await client.get(url, timeout=10.0, follow_redirects=True)
        return "reachable" if resp.status_code < 400 else "unreachable"
    except (httpx.TimeoutException, httpx.NetworkError):
        return "unreachable"
    except Exception:  # noqa: BLE001 - 网络异常多样（DNS/SSL/协议），统一记 unknown 不污染统计
        return "unknown"


# ── LLM-judge（B 类，纯文本 + 规则解析 + 盲评，规避 response_format 三态全挂）──
JUDGE_PROMPT_TEMPLATE = """你是研报质量评估员。对以下研报按两个维度打分（1-5 分，整数），
只输出两行，格式严格如下：
完整度: <1-5>
可靠性: <1-5>

评分标准：
- 完整度：{completeness_rubric}
- 可靠性：{veracity_rubric}

研报内容：
{report}
"""


def parse_judge_output(text: str) -> tuple[float, float]:
    """解析 judge 纯文本输出为 (completeness, veracity)。失败 → (0.0, 0.0) 计入错误。

    坑（P1-2 实证）：国产模型 response_format 三态全挂 → judge 输出不强制 JSON，
    用正则解析；解析失败降级为 0 分并记录（可重试一次后放弃）。
    """
    m_c = re.search(r"完整度:\s*([1-5])", text)
    m_v = re.search(r"可靠性:\s*([1-5])", text)
    if not (m_c and m_v):
        return 0.0, 0.0
    return float(m_c.group(1)), float(m_v.group(1))


# ── 单任务执行（复用 chat SSE 契约，mock 不适用——eval 走真实链路）──
async def run_one_task(
    task: dict,
    api_base: str,
    semaphore: asyncio.Semaphore,
    client: httpx.AsyncClient,
) -> TaskMetrics:
    """跑一个研究任务：调用 chat 接口 → 收集产出 + trace → 算指标。

    失败自动重试 1 次（v1.1 评审修正：偶发错误不污染结果）。

    Args:
        task: tasks.jsonl 单条（id/query/expected_sections/...）
        api_base: 后端地址（默认 http://127.0.0.1:8010）
        semaphore: 并发信号量（默认 3，防限流/成本爆炸）
        client: 共享 httpx 客户端

    Returns:
        TaskMetrics：四类指标聚合
    """
    async with semaphore:  # 并发上限（v1.1 评审修正：20 并发会触发限流）
        metrics = TaskMetrics(task_id=task["id"])
        for attempt in (1, 2):  # 重试 1 次
            # 1) POST /v1/chat/stream（session_id 新建）
            # 2) 流式收集：done 事件 → duration_ms / context_used；
            #    tool_call 事件计数 → tool_calls；error 事件 → errors
            # 3) 终稿 = 全部 token 事件拼接
            #    → count_compliant_citations(report, sources)
            #    → verify_source_url 抽查 3-5 条来源
            # 4) judge 调用（llm/adapter.get_chat_model 文本输出）→ parse_judge_output
            # 5) 失败且 attempt==1 → 记错误继续重试；attempt==2 → errors 保留
            raise NotImplementedError("§7 骨架——实施时按此形态手写核心逻辑")
        return metrics


# ── 汇总报告 ──
def build_report(run_id: str, git_commit: str, metrics_list: list[TaskMetrics]) -> dict:
    """聚合为报告 dict（写 reports/{run_id}.json + .md）。

    v1.2：固定多 Agent 配置（无 single/multi 对照）；记录 git_commit 版本指纹
    支持纵向对比（同配置优化前后两次评估对照）。

    Returns:
        报告 dict：run_id/git_commit/汇总（完成率/A1/A2/B1/B2/D1/D2）+ 逐任务明细
    """
    n = len(metrics_list) or 1
    done = [m for m in metrics_list if m.completed]
    return {
        "run_id": run_id,
        "git_commit": git_commit,
        "config": "multi",  # 主线固定多 Agent（v1.2 拍板：不做 single 对照）
        "summary": {
            "tasks": len(metrics_list),
            "completion_rate": len(done) / n,
            "avg_citation_compliance": sum(m.a1_ratio() for m in metrics_list) / n,
            "avg_source_reachability": sum(m.a2_ratio() for m in metrics_list) / n,
            "avg_completeness": sum(m.completeness_score for m in metrics_list) / n,
            "avg_veracity": sum(m.veracity_score for m in metrics_list) / n,
            "avg_tool_calls": sum(m.tool_calls for m in metrics_list) / n,
            "total_duration_ms": sum(m.duration_ms for m in metrics_list),
            "total_context_used": sum(m.context_used for m in metrics_list),
        },
        "per_task": [m.__dict__ for m in metrics_list],
    }


def get_git_commit() -> str:
    """取当前 HEAD 短哈希作为报告版本指纹（§5.2 纵向对比依据）。"""
    import subprocess

    return subprocess.run(  # noqa: S603 - 本地脚本取版本号
        ["git", "rev-parse", "--short", "HEAD"], capture_output=True, text=True, check=False
    ).stdout.strip() or "unknown"


async def main() -> None:
    """CLI 入口：--tasks / --concurrency / --api-base（固定多 Agent 配置，v1.2）。"""
    parser = argparse.ArgumentParser(description="多 Agent 研报质量评估管道")
    parser.add_argument("--tasks", type=Path, required=True)
    parser.add_argument("--concurrency", type=int, default=3, help="并发上限（防限流，默认 3）")
    parser.add_argument("--api-base", default="http://127.0.0.1:8010")
    args = parser.parse_args()

    tasks = [json.loads(line) for line in args.tasks.read_text(encoding="utf-8").splitlines() if line.strip()]
    run_id = uuid.uuid4().hex[:8]
    semaphore = asyncio.Semaphore(args.concurrency)
    async with httpx.AsyncClient() as client:
        metrics = await asyncio.gather(
            *(run_one_task(t, args.api_base, semaphore, client) for t in tasks)
        )
    report = build_report(run_id, get_git_commit(), metrics)
    out_dir = Path("data/eval/reports")
    out_dir.mkdir(parents=True, exist_ok=True)
    (out_dir / f"{run_id}.json").write_text(json.dumps(report, ensure_ascii=False, indent=2), encoding="utf-8")
    print(json.dumps(report["summary"], ensure_ascii=False, indent=2))


if __name__ == "__main__":
    asyncio.run(main())
```

### 8.2 追问链预演（§3.3 五层自答）

| 追问 | 预演答案 |
|------|----------|
| **为什么做评估体系？** | 生产落地必须回答"Agent 有没有用"；面试第一分水岭就是可量化结果 + baseline |
| **对比过什么方案？** | RAGAS（偏 RAG 检索指标，不覆盖报告质量/成本）；人工全量评测（成本高不可复跑）；LLM-as-judge（快但需防偏见）→ 组合：规则指标（确定性）+ judge（主观维度）+ 人工抽样（仲裁） |
| **遇到什么坑？** | ①国产模型 response_format 三态全挂（P1-2 实证）→ judge 纯文本 + 规则解析；②LLM 不联网无法验 URL 真实性（v1.1 修正）→ HTTP 可达性检查；③引用编号合规 ≠ 内容对应（v1.1 修正）→ P0 查合规、P1 升级语义匹配；④judge 自赞偏见 → 盲评 + 相对对比 + 建议异模型 |
| **judge 偏见怎么控制？** | 盲评（judge 不接收 config 标签，随机顺序，判断不出是 single 还是 multi）；**judge 建议用不同 provider**（项目三厂商可切：被评估 DeepSeek → judge 用豆包/智谱，跨模型家族消风格偏好）；只报相对差不报绝对分。面试主动说："我知道 LLM-judge 有偏见，所以用同一 judge 盲评 + 控制报告格式变量，尽量减少风格偏好影响" |
| **怎么量化效果？** | 绝对指标 + 纵向版本对比：同任务集（10-20 个）跑多 Agent，报引用合规率 X%、完整度 Y 分、成本 Z——优化后重跑同任务集看 Δ（git_commit 指纹可回溯）；规模有限主要看趋势，主动声明 |
| **为什么用多 Agent（无对照实验怎么答）？** | 不靠对比实验论证，靠架构论证（P0-3 决策故事）：单 Agent 遇到 prompt 膨胀/上下文污染/工具过载才拆；研究任务天然并行探索；代价（成本/延迟）用工具审计 + 用量告警主动控制 |
| **为什么这个指标集？** | 事实性（A：数据可不可信）> 质量（B：报告好不好）> 过程（C）> 成本（D）——面试官最关心可信度，先回答"信不信得过" |
