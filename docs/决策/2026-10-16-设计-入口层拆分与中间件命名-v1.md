## 2. 现状核实（实测） 🔴 v1

> 本节全部结论来自**读源码 + 读 Starlette 源码 + grep 全仓**，非推测。

### 2.1 `main.py` 的代码实际发生在**三个时间点**

混在一起看才觉得"杂"。按时间轴切开，职责立刻分明：

| 时间点 | 行 | 动作 | 为什么在这个位置 |
|---|---|---|---|
| **① 导入期** | 61 | `setup_logging()` | **必须最早**——它是第一个有副作用的语句，再往后任何一行抛错都需要日志已能落盘 |
| | 65 | `_mcp_http_app = mcp_server.http_app()` | 只是**造对象不启动**；造出来是因为下面两处要共用同一实例（中间件转发 / 启动期跑 lifespan） |
| | 188–213 | `FastAPI(...)` / CORS / 11 个 `include_router` | 纯组装，无 IO |
| | 259 | `add_middleware(McpMountMiddleware)` | 见 §2.2 |
| | 359 | `add_middleware(TraceIdMiddleware)` | 见 §2.2 |
| **② 启动期** | 121–172 | lifespan 内 6 步（详见 §5） | 见 §5 |
| **③ 关闭期** | 175–185 | lifespan 逆序释放 | 见 §5 |

> ⚠️ **易读错点**：第 65 行与第 161 行看着像"一起的"，实为**两个时间点**——
> 65 行造对象（导入期），161 行 `async with _mcp_http_app.lifespan(_)` 才是**跑起来**（启动期）。
> co-creator 问「先启动 fastmcp 吗」，准确答案是：**对象先造，lifespan 晚启动**。

### 2.2 中间件注册顺序 —— 已核 Starlette 源码

**结论：现有注释（main.py:356–358）结论正确，可补"已核源码"字样。**

依据（读 `.venv/Lib/site-packages/starlette/applications.py`）：

```python
def add_middleware(self, middleware_class, *args, **kwargs) -> None:
    ...
    self.user_middleware.insert(0, Middleware(middleware_class, *args, **kwargs))
    #                      ^^^^^^^^^^ 后加的插到【最前】

def build_middleware_stack(self) -> ASGIApp:
    middleware = ([Middleware(ServerErrorMiddleware, ...)]
                  + self.user_middleware
                  + [Middleware(ExceptionMiddleware, ...)])
    app = self.router
    for cls, args, kwargs in reversed(middleware):   # 反转后再包 → 最前的变【最外层】
        app = cls(app, *args, **kwargs)
    return app
```

三步注册后的 `user_middleware` 实为 `[TraceId, McpMount, CORS]`，故**实际执行顺序**为：

```
ServerError → TraceId → McpMount → CORS → ExceptionMiddleware → 路由
```

**验证结论**：
- ✅ `TraceIdMiddleware` 在最外层（除 ServerError 外）→ **trace 绑定覆盖全部请求，含转发给 MCP 的那条**——现有注释成立
- ⚠️ **`CORSMiddleware` 被包在 `McpMountMiddleware` 内侧** → `/mcp` 的响应**不带 CORS 头**。

  当前**无实际影响**（MCP 是服务端对服务端调用，不经浏览器）。**但需补一行注释说明"有意为之"**，否则后人当 bug 修（把 CORS 挪到最外层会顺带把 CORS 也套到 MCP 转发上，属行为变更）。

### 2.3 两套 `middlewares/` 撞名 —— 实测

| | `agent/middlewares/`（现有） | `api/…`（本设计拟新建） |
|---|---|---|
| **拦什么** | **Agent 循环**内的模型调用 / 工具调用 | **HTTP 请求** |
| **守谁的契约** | LangChain `AgentMiddleware` 基类 | ASGI 三元组 `(scope, receive, send)` |
| **触发频次** | 一轮对话内**多次** | 一个请求**一次** |
| **执行者** | deepagents 图装配 | Starlette 中间件栈 |
| **现有文件** | builder / interpreter / token_usage / trace | mcp_mount / trace_id（拟） |

**真正会咬人的撞名点不是目录名，是两边都有 `trace`**：

```
src/agent/middlewares/trace.py      ← 记推理链路 trace（写 agent_trace.jsonl）
src/api/middlewares/trace_id.py     ← 绑 trace_id（注入 ContextVar）
```

一句"改一下 trace 那个 middleware"，得先反问「**哪个 trace**」。这与工具中心「同一件事写两遍」属同类教训——**两套说法并存，迟早对不上**。

### 2.4 引用面实测（决定"改哪边"）

| 目标 | 代码引用 | 文档引用 | 结论 |
|---|---|---|---|
| `agent/middlewares/` 改名 | **11 处**（`main_agent.py` ×2、`builder.py` ×2、`api/context_usage.py` ×1、测试 ×6） | **17 份** | ❌ **不动**（伤筋动骨，收益为零） |
| `api/middlewares/`（**尚未存在**） | **0 处** | 0 份 | ✅ **改名成本 = 0**，动它 |
| `src.api.main` 的符号 | **1 处**：`tests/test_core/test_audit_trace.py` 4 行（45/59/73/87）从 `src.api.main` 导 `TraceIdMiddleware` | — | ✅ 低风险，且见 §7.1（**不会断**） |

## 3. 入口层拆分方案 🟠 v1

### 3.1 目标目录树

```
backend/src/api/
├── main.py                    ← ~65 行（现 359）：只做顶层编排
├── lifespan.py                ← ~75 行：生命周期【顺序】，只写"先谁后谁"
├── bootstrap/                 ← 各子系统启停（一件事一个文件）
│   ├── __init__.py
│   ├── infra.py               ← PG 池 / 建表 / Redis 预热 / checkpointer + store
│   ├── capabilities.py        ← 预加载：注册表 + MCP 客户端 + 治理元数据（具名函数 + 说明）
│   ├── memory_queue.py        ← 记忆队列 worker 启停 + consumer
│   └── audit_pipeline.py      ← 审计 sink/worker/retention + 入库回调 + 保留分档
├── middlewares/           ← 中间层（与 agent/middlewares 同名系**刻意**，见 §4.2）
│   ├── __init__.py            ← register_middlewares()：把注册顺序锁在一处
│   ├── mcp_mount.py           ← McpMountMiddleware
│   └── trace_id.py            ← TraceIdMiddleware + _incoming_trace_id
└── root_page.py               ← 根路径那段 20 行 HTML（抽成常量）
```

### 3.2 各文件职责与边界

| 文件 | 放什么 | 不放什么 |
|---|---|---|
| `main.py` | `setup_logging()` / 造 `mcp_http_app` / 造 `app` / 调 `register_middlewares` / `register_routers` / 挂 `/` | 任何 `async def` 实现、任何 try/except 降级逻辑 |
| `lifespan.py` | `lifespan()` 本体（**只有顺序**）+ `_mcp_http_app` 的 lifespan 包裹 | 各子系统的具体启停实现（下沉 `bootstrap/`） |
| `bootstrap/*.py` | 该子系统的 `start()` / `stop()` 实现 + 其私有常量与回调 | 跨子系统的编排顺序（留在 `lifespan.py`） |
| `middlewares/__init__.py` | `register_middlewares(app, *, mcp_http_app)` —— **注册顺序的唯一载体** | 中间件实现 |
| `root_page.py` | 根路径 HTML 常量 | 路由注册 |

### 3.3 关键收敛点

**① `register_middlewares()` 把顺序锁死在一处**

```python
# middlewares/__init__.py
def register_middlewares(app: FastAPI, *, mcp_http_app: ASGIApp) -> None:
    """注册全部 ASGI 中间件（顺序敏感，见函数内注释）。

    ⚠️ Starlette 的 add_middleware 是【后加的先执行】（user_middleware.insert(0, ...)
    + build_middleware_stack 里 reversed 包裹）——已核 starlette/applications.py。
    """
    app.add_middleware(McpMountMiddleware, mcp_app=mcp_http_app)
    # 审计贯穿：后加 → 最外层 → 先绑 trace，覆盖全部请求（含转发给 MCP 的那条）
    app.add_middleware(TraceIdMiddleware)
```

以后有人加中间件，**只能在这一个地方想顺序问题**（对应工具中心的「唯一登记处」思路）。

**② `bootstrap` 的 start/stop 用「句柄对象」而非模块级全局**

现状 `_memory_workers`（main.py:68）是**模块级可变列表**——lifespan 跑两次（测试 / uvicorn reload）会累积旧句柄。
改为 `start()` 返回句柄、`stop(句柄)` 收句柄（见 §11.3）。

**③ 预加载包成具名函数并写明"为什么在这"**

co-creator 明确要求「预加载的应该有个函数包裹说明」。落地为
`bootstrap/capabilities.py::preload()`，docstring 必须回答：**为什么必须在启动期做、为什么不能等第一个请求**（答案：`get_agent()/_build_agent()` 是**同步函数**，装配时读不到异步 DB，故治理元数据必须启动期读进内存缓存）。

## 4. 中间件命名消歧 🔴 v1.1

### 4.1 两套契约对比（决定怎么起名）

见 §2.3 表格。一句话：**一个是"对话内部"的钩子，一个是"请求进门"的钩子**，同名纯属两家 SDK 各自都管自己的东西叫 middleware。

### 4.2 结论：**保持 `api/middlewares/`，不起特殊名字** ✅

> 📌 **2026-10-16 co-creator 拍板**：先否掉本文初稿推荐的 `api/asgi_middleware/`，
> 复核后确认**保持 `middlewares`**。理由见下。

**三个理由（按分量排序）**

1. **它俩本来就是同一个角色，只是在不同层。**
   `agent/middlewares/` 与 `api/middlewares/` 都是「**本层的横切拦截**」——
   同一概念、不同层。给 api 那个起个怪名字，反而暗示"它是另一种东西"，**与实际不符**。
   对称命名（`<层>/middlewares/`）本身就在说："同一个角色，各层各有一份"。
2. **父目录已经承担了限定职责。**
   `src.api.middlewares.trace_id` vs `src.agent.middlewares.trace` —— import 是**全限定**的，
   机器与人都不会认错。目录名不是唯一防线。
3. **`api/` 本身就是 ASGI 层**，叫 `api/asgi_middleware/` 是同义反复。
   Starlette / FastAPI 生态里，这个目录的**官方叫法就是 `middlewares/`**。

**评估过、已否决的备选**（记录否决理由，防 3 个月后有人重提）

| 备选 | 否决理由 |
|------|---------|
| `api/asgi_middleware/` | **同义反复**（`api/` 即 ASGI 层）+ 全项目目录名无一处用协议缩写（`tools/` `sandbox/` `memory/` `core/` `channels/` `contract/` `guardrails/` 皆如此），破了惯例 |
| `api/http_middleware/` | 同样同义反复（`api/` 即 HTTP 层）；且 `http` 比 `asgi` 更窄——将来若有非 HTTP 的 ASGI 中间件（websocket）就名不副实 |
| `api/edge/` | `edge` 系**新造词**，项目里无先例；读代码的人得先学这个词，认知成本 > 收益 |
| `api/interceptors/` | 区分度够（词完全不同），但 ASGI 生态**不这么叫**——增认知成本，换来的只是"看起来不一样" |
| `api/pipeline/` | Starlette 文档里 "middleware pipeline" 本就是一体的说法，等于**换个说法不换概念** |

### 4.3 配套消歧动作（**这才是真正管用的那一层**）

> 📌 **核心判断**：目录同名其实**不是**主要混淆源——因为 import 全限定。
> 真正的混淆源是 **`trace.py` vs `trace_id.py`**（两边都叫 trace）。**治这个才对症。**

1. **类名不改**：`TraceIdMiddleware` 自带 `Id`，与 agent 侧 `TraceEvent` / `trace_event()` 已可辨认。
2. **架构文档 §2 目录树给两个同名目录各加一句限定注解**（翻目录的人先看这里）：
   ```markdown
   ├── api/middlewares/          # 请求管道中间件（ASGI 契约，每请求一次）
   └── agent/middlewares/        # Agent 循环中间件（LangChain 契约，每轮多次）
   ```
3. **两个目录的 `__init__.py` docstring 各写一句**"本目录中间件守 X 契约，**不是** Y"——新人第一次翻目录不走错楼层。

4. **两个 `trace*` 文件 docstring 互相指路**（沿用项目「双向链接」纪律，规则 05 §4）：
   - `agent/middlewares/trace.py` 顶部写：本文件记**推理链路** trace；请求级 `trace_id` 见 `api/middlewares/trace_id.py`
   - `api/middlewares/trace_id.py` 顶部反向指回
   - ⚠️ **可选**——`trace.py` 的归属本身是待办项 23（§9.3），若将来挪走则本条作废；**先不加也不影响本设计成立**

## 5. lifespan 顺序说明 🟠 v1

> 本节回应 co-creator「解释下 main 的顺序」。**顺序本身一字不改**，仅搬位置。

### 5.1 启动序（6 步）

```
① Redis ping          ← 只探测，失败静默（/v1/health 标 disconnected）
② PG 池 + 建表        ← 必须第二：后面全部依赖它
③ checkpointer+store  ← 依赖 ②  （断点续审 / 长期记忆的地基）
④ 记忆队列 worker     ← 依赖 ③  （consumer 要写记忆 → 要 store → 要 PG）
⑤ 审计 sink + worker  ← 依赖 ①  （走 Redis Stream）
⑥ FastMCP lifespan    ← FastMCP 硬性要求：父应用 lifespan 内必须执行它的
   └ ⑥.1 preload()    ← 夹在 ⑥ 内部
⑦ yield               ← 开始接请求
```

**为什么 ④（记忆队列）排在 ③ 之后？** consumer 的实现在主仓关闭路径上依赖 store（长期记忆写入）→ store 依赖 PG。故不能提前。

**为什么 ⑥.1 预加载必须夹在 FastMCP lifespan **内部**？**
不是技术依赖，是**位置依赖**——只要在 `yield` 之前跑完即可。放这里有个副作用：FastMCP lifespan 起不来则预加载也不跑。**可接受**（两者同时失败 → 降级为仅内部工具）。

**为什么预加载不能等第一个请求？**
`get_agent()` / `_build_agent()` 是**同步函数**——装配工具清单时读不到异步 DB。故治理元数据（哪些 MCP 工具挂载、要审批）必须启动期读进内存缓存。
> 🍅 类比：**开店前先把货架上齐**——不能等客人进门才去仓库取货，因为取货要走的那条通道（异步 DB）在收银台（同步装配）这条动线上根本不通。

### 5.2 关闭序（**严格反序**）

```
审计 worker 先停（卸 sink → 不再投递 → cancel）
  ↓ 记忆队列（先 join 等做完，再 cancel）
  ↓ store → checkpointer → PG 池 → Redis
```

**为什么审计必须最前停？** 它是唯一"边跑边往 Redis/PG 写"的长驻任务。PG 池先关、它还在写 → 报错。

### 5.3 一处**真缺陷**在关闭路径上（见 §6 B4）

`cancel()` 之后**没有 await**——worker 可能正卡在 `insert()` 里持着 PG 连接，而池随后被关。

| # | 位置 | 问题 | 性质 | 处置 |
|---|------|------|------|------|
| **B1** | `main.py:80` | `_memory_consumer` 内函数级 `from src.core.config import settings`，与模块级 `:40` **重复且遮蔽** | 死代码 | 删 |

| **B4** | `main.py:177–180` | 关闭时 `task.cancel()` **之后没有 await**——worker 可能正卡在 `insert()` 持着 PG 连接，池已被关 | **真缺陷** | 加 `await asyncio.gather(*tasks, return_exceptions=True)` |

### 11.2 `api/lifespan.py`（目标 ~75 行，**只有顺序**）

```python
"""应用生命周期：【只写先谁后谁】，实现下沉 bootstrap/。

启动序（依赖决定的，不可随意调换）：
    ① Redis 预热（可降级）→ ② PG 池+建表 → ③ checkpointer/store
    → ④ 记忆队列 → ⑤ 审计双写 → ⑥ FastMCP lifespan（内嵌 ⑥.1 预加载）→ yield

关闭序：**严格反序**（审计最先停——它是唯一边跑边写 Redis/PG 的长驻任务，
        PG 池先关它会报错）。
"""

from __future__ import annotations

from contextlib import asynccontextmanager
from typing import AsyncIterator

from fastapi import FastAPI

from src.api.bootstrap import audit_pipeline, capabilities, infra, memory_queue
from src.api.main_mcp import get_mcp_http_app  # 或由 lifespan() 参数注入


@asynccontextmanager
async def lifespan(_: FastAPI) -> AsyncIterator[None]:
    """启动各子系统（依赖序）→ 让出 → 逆序关闭。"""
    # ① Redis 预热 ② PG 池 + 建表 ③ checkpointer + store
    await infra.start()

    # ④ 记忆队列（依赖 ③：consumer 写记忆要 store，store 要 PG）
    queue_handle = await memory_queue.start()

    # ⑤ 审计双写（依赖 ①：走 Redis Stream）
    audit_handle = await audit_pipeline.start()

    # ⑥ FastMCP 硬性要求：父应用 lifespan 内必须执行它的 lifespan
    async with get_mcp_http_app().lifespan(_):
        # ⑥.1 预加载（详见 capabilities.preload 的 docstring）
        await capabilities.preload()
        yield

    # ── 逆序关闭 ──
    await audit_pipeline.stop(audit_handle)     # 最早停：卸 sink → 不再投递 → cancel + await
    await memory_queue.stop(queue_handle)       # 先 join 等做完，再 cancel + await
    await infra.stop()                          # store → checkpointer → PG 池 → Redis
```

### 11.3 `api/bootstrap/memory_queue.py`（句柄对象，替掉模块级全局）

```python
"""记忆抽取队列的启停（lifespan 调用）。

⚠️ 为什么用【句柄对象】而不是模块级 `_workers` 列表：
   模块级可变全局在 lifespan 跑两次时（测试 / uvicorn reload）会累积旧句柄，
    且 stop 时无法保证停的是"本次启动的那批"。
"""

from __future__ import annotations

import asyncio
from dataclasses import dataclass, field

from src.agent.memory.agent import build_memory_agent
from src.agent.memory.queue import _WORKER_COUNT, memory_task_queue
from src.llm.adapter import get_chat_model


@dataclass
class QueueHandle:
    """本次启动的 worker 任务句柄（stop 时凭它精确停止）。"""

    workers: list[asyncio.Task] = field(default_factory=list)


async def _memory_consumer(task) -> str:
    """队列消费：ainvoke memory_agent（工具内 get_store() 运行时解析，方案 B）。"""
    agent = build_memory_agent(get_chat_model(model_id=None))
    result = await agent["runnable"].ainvoke(
        {"messages": [
            {"role": "user", "content": task.user_message},
            {"role": "assistant", "content": task.assistant_text},
        ]}
    )
    return str(result)[:200]


async def start() -> QueueHandle:
    """起 _WORKER_COUNT 个常驻 worker（create_task 后台跑，不 await）。"""
    handle = QueueHandle()
    for _ in range(_WORKER_COUNT):
        handle.workers.append(
            asyncio.create_task(memory_task_queue.run_worker(_memory_consumer))
        )
    return handle


async def stop(handle: QueueHandle) -> None:
    """先 join 等当前任务做完，再 cancel 并【await 收尾】。"""
    await memory_task_queue._queue.join()
    for worker in handle.workers:
        worker.cancel()
    # 修 B4：cancel 后必须 await，否则 worker 可能在 PG 池关闭后才解退
    await asyncio.gather(*handle.workers, return_exceptions=True)
```

### 11.4 `api/bootstrap/capabilities.py`（预加载 + 说明）

```python
"""启动期【预加载】Agent 能力元数据。

## 🔴 为什么必须在启动期做、不能等第一个请求

`get_agent()` / `_build_agent()` 是**同步函数**——装配工具清单时读不到异步 DB。
故治理元数据（哪些 MCP 工具可挂载、是否需审批、重试策略）必须在启动期
读进**内存缓存**，供同步装配路径读取。

（缓存实现与失效策略见 `src/tools/channels/mcp_meta.py`）

## 为什么夹在 FastMCP lifespan【内部】

不是技术依赖，是**位置依赖**：只要在 `yield` 之前跑完即可。
副作用：FastMCP lifespan 起不来则预加载也不跑 —— **可接受**
（两者同时失败 → 降级为仅内部工具）。
"""

from __future__ import annotations

import logging

from src.core.model_registry import get_registry
from src.db import connection as db_conn
from src.tools.channels.mcp_client import get_mcp_client_manager
from src.tools.channels.mcp_meta import load_policies as load_mcp_policies

logger = logging.getLogger(__name__)
```

### 11.5 `api/middlewares/__init__.py`（顺序唯一载体）

```python
"""请求管道中间件（**ASGI 契约**：scope / receive / send）。

⚠️ 与 `src/agent/middlewares/` 的区别（守**不同契约**，勿混）：
- 本目录：拦 **HTTP 请求**，每请求一次，Starlette 中间件栈执行
- `agent/middlewares/`：拦 **Agent 循环**内的模型/工具调用，每轮多次，
  LangChain `AgentMiddleware` 契约，由 deepagents 图装配执行
"""

from __future__ import annotations

from fastapi import FastAPI
from starlette.types import ASGIApp

from src.api.middlewares.mcp_mount import McpMountMiddleware
from src.api.middlewares.trace_id import TraceIdMiddleware

__all__ = ["McpMountMiddleware", "TraceIdMiddleware", "register_middlewares"]


def register_middlewares(app: FastAPI, *, mcp_http_app: ASGIApp) -> None:
    """注册全部 ASGI 中间件（**顺序敏感**，本函数是顺序的唯一载体）。

    ⚠️ Starlette 的 `add_middleware` 是「**后加的先执行**」：
       `user_middleware.insert(0, ...)` + `build_middleware_stack` 里
       `for cls in reversed(middleware): app = cls(app)` —— 已核
       `starlette/applications.py`。故最终执行序为：

           ServerError → TraceId → McpMount → CORS → Exception → 路由

    ⚠️ **CORS 被包在 McpMount 内侧**：`/mcp` 响应不带 CORS 头 ——
       **有意为之**（MCP 是服务端对服务端调用，不经浏览器）。把 CORS
       挪到最外层会顺带把它套到 MCP 转发上，属**行为变更**，勿轻改。

    Args:
        app: FastAPI 应用实例
        mcp_http_app: FastMCP 的 ASGI 应用（转发目标 + lifespan 来源）
    """
    app.add_middleware(McpMountMiddleware, mcp_app=mcp_http_app)
    # 后加 → 最外层 → 先绑 trace，覆盖**全部**请求（含转发给 MCP 的那条）
    app.add_middleware(TraceIdMiddleware)
```
