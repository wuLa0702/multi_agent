## 1. 问题与诉求 🔴 v1

**co-creator 原话（2026-10-15）**：

> 这个工具注册是不是不够动态？添加个工具，还需要在 registry 里面手动改代码，耦合太严重了？
> 我理解要松耦合。**只需要改一处就行了**？比如说用数据库存储数据，还是说配置属性都在工具描述里？
> **我的要求是动态注册工具 / skill / tool 不需要重编码、重新运行。**

**拆成三个子问题**：

| # | 问题 | 本设计回答 |
|---|------|-----------|
| Q1 | 加工具必须改 registry 代码，耦合太重？ | §2 事实 1：**只有"代码工具"如此**；远程工具/skill 已零代码 |
| Q2 | 只改一处够不够？DB 存还是描述里存？ | §2 事实 2/3：声明已收敛为**一处**；DB 存的是**配置不是行为** |
| Q3 | 怎么做到不重编码、不重启？ | §3/§4 两条路 + §5 对比 |

## 2. 现状核实（实测，非推测） 🔴 v1

| # | 事实 | 证据 |
|---|------|------|
| 1 | **三类能力三种注册方式**，其中两类已"零代码" | 代码工具 → `tools/registry.py`（改代码）；远程工具 → `mcp_servers` **表**；skill → `SKILL.md` **文件** |
| 2 | **登记表已是唯一"声明处"**，四件事全派生 | `tools_for_main()`（挂载）/ `build_hitl_interrupt_on()`（审批）/ `_apply_retry()`（重试门控）/ `fallback_for()`（审计备查）——加工具时这四处**都不用碰** |
| 3 | **MCP 化基础设施齐全** | `mcp_servers` 表（`db/schema.py:91`）→ `McpClientManager`（`tools/channels/mcp_client.py`）→ `get_tools()` 注入（`main_agent.py:434,446`）；市场安装 `POST /v1/skills/install`（`api/skills.py:71`）|
| 4 | **"行为"必须可执行 → 必然有宿主** | Python 函数（要 import）/ 远程服务（MCP 协议）/ 脚本（沙箱）。→ §5 对比的**理论前提** |

### 2.1 两处实测缺口 🔴

| # | 缺口 | 证据 | 影响 |
|---|------|------|------|
| **G1** | **MCP 启停是"假热刷新"** | `api/mcp_servers.py:97` 只调 `reload()`；而 `api/skills.py:55` 的 `_refresh_agent_tools()` 是 `reload()` **+ `rebuild_agent()`**。`get_agent()` 有会话级缓存（`main_agent.py:404`）→ 已存在会话仍持旧工具 | 启停 MCP 工具对**正在用的会话**不生效，要等新会话 / LRU 逐出 / 重启 |

> ✅ **G1 已修（2026-10-15，提交 `25d7de2`）**。核实后发现**不是两处不一致，是三条路径三种行为**：
>
> | 路径 | `reload()` | `rebuild_agent()` |
> |---|---|---|
> | 市场安装 / 启停 / 卸载 | ✅ | ✅ |
> | 连接启停（PATCH） | ✅ | ❌ 缺 |
> | **连接删除（DELETE）** | ❌ 缺 | ❌ 缺 |
>
> 删除那条更严重：**已删 server 的工具仍留在图里**，模型会去调一个不存在的服务。
> 修法：新增唯一入口 `agent/services/mcp_service.py::refresh_agent_tools()`（先 reload
> 再 rebuild，顺序不可颠倒），三条路径统一转发；配套 7 条测试（含"三条路径都经过入口"
> + "skills.py 不得再长出实现"的结构锁）。**该段此前零测试**，正是漂移长期未被发现的原因。
| **G2** | **MCP 工具绕过全部治理** | ① 审批：`build_hitl_interrupt_on()` 只遍历 `TOOL_REGISTRY` → MCP 工具**永不审批**；② 三态信封：`_SafeTool._arun` 失败返回**裸字符串**（`mcp_client.py:60`）→ `artifact=None` → SSE `result_status=None`、审计 `status="unknown"`；③ 重试：由 registry 派生，MCP 工具无 | **外部工具成了"法外之地"**：高危操作不弹窗、成败无法程序化判断、无自动重试 |

> ⚠️ G2 是选方案 A 时**必须先补**的账——否则"动态"放开的是**没有护栏的口子**。

## 3. 方案 A：MCP 化（真·动态注册） 🔴 v1

**一句话**：新工具**不写 Python**，而是接一个外部 MCP server——工具定义在对方那里，我们只存"连哪里"。

### 3.1 怎么用

```
方式一（市场）：POST /v1/skills/install {skill_type: "mcp_server", ...}
                → 拉市场详情补全连接地址 → 写入 mcp_servers 表
方式二（自建）：往 mcp_servers 插一行（name/transport/url/headers/is_active）

    ↓ _refresh_agent_tools()：reload() + rebuild_agent()
模型立即可调用 —— 零改代码、零重启
```

### 3.2 覆盖能力

| 能力 | 现状 |
|------|------|
| 零代码注册 | ✅ |
| 零重启 | ✅（走 `skills.py` 路径；走 `mcp_servers.py` 路径有 G1）|
| 市场一键安装 | ✅ |
| 多 server 同名工具去重 | ✅ `tool_name_prefix=True` |
| 协议层异常降级 | ✅ `_SafeTool` 包成字符串（不中断 run）|
| **审批 / 三态 / 重试** | ❌ **全绕过（G2）** |

### 3.3 代价与边界

- **补 G1 + G2 的账**（中等工作量）：MCP 工具要能声明"要不要审批"、"结果三态"——但目前它们**不在登记表里**，需要设计"外部工具的元数据来自哪里"（对方给？本地补一张表？）
- **能力上限 = 对方的 MCP 能力**：你无法通过 MCP 拿到比对方提供的更多东西
- **调试面变大**：协议 + 网络 + 对方服务，四层排查
- **不适合自家核心工具**：沙箱执行、研报生成、审批出口——这些**必须在你手里**，MCP 化等于把核心能力外包

## 4. 方案 B：登记表 YAML 化 🔴 v1

**一句话**：把 `ToolSpec` 的**元数据**从 Python 字面量搬到 YAML（实现仍是 Python 函数）——即"声明与实现分离"。

### 4.1 长什么样（示意）

```yaml
# backend/config/tools.yaml
internet_search:
  domain: search
  description: "博查网络搜索：关键词 → 结构化结果（标题/链接/摘要）"
  is_idempotent: true
  retry: { retries: 2, extra_exceptions: ["httpx.HTTPStatusError"] }
  fallback_to: fetch_url
  mount_main: false

run_code_in_sandbox:
  domain: sandbox
  description: "在隔离 OpenSandbox 沙箱执行 Python 代码并返回输出"
  risk_level: high
  requires_approval: true
  allowed_decisions: [approve, edit, reject]
```

`registry.py` 变成"读 YAML + 按 `impl` 字段指向的函数装配"（实现函数仍从 `tools/impl/` import）。

### 4.2 覆盖能力

| 能力 | 现状 |
|------|------|
| 元数据外置（描述/审批按钮/降级备选） | ✅ 改 YAML 即可，非工程师可改 |
| 加工具**不写 Python** | ❌ **不行**——实现仍是行为，必须写 |
| 零重启 | 🟡 可做 YAML 热加载，但要处理与派生（`_apply_retry`）的时序，**谨慎** |
| 治理一致性（审批/三态/重试） | ✅ **全保留**（工具仍走 registry） |
| 与现有改动面 | 小（registry 已是唯一入口，只换"元数据从哪来"） |

### 4.3 代价与边界

- **设计成本**：YAML schema + 校验（fail fast 不能丢）+ 迁移 11 条 + 测试
- **关键限制**：**YAML 化解决不了 Q3（不重编码）**——它只把"声明"外置，"实现"仍在 Python
- 除非：YAML 的 `impl` 指向一个**脚本**而不是函数 → 那本质就退化成 **skill**（脚本进沙箱跑）

## 5. 两方案对比 🔴 v1

| 维度 | **方案 A：MCP 化** | **方案 B：YAML 化** |
|------|-------------------|---------------------|
| **加一个工具需要** | 插一行表项 / 市场安装 | 写实现（Python）**＋** 加一段 YAML |
| **要写 Python 吗** | ❌ **不要** | ✅ **要**（除非退化为脚本=skill） |
| **要重启吗** | ❌ 不要（补齐 G1 后） | 🟡 元数据可热加载；实现改了仍需重启 |
| **治理覆盖**（审批/三态/重试） | ❌ **当前全绕过（G2），需先补账** | ✅ **全保留**（仍走 registry） |
| **能力上限** | 受对方 MCP 能力限制 | **与你 Python 同能力** |
| **调试难度** | 高（协议+网络+对方服务） | 低（本地） |
| **适合** | 第三方 / 生态能力、别人写的工具 | 自家核心工具；元数据想外置 |
| **不适合** | 自家核心（沙箱/研报/审批出口） | 想"零代码加工具" |
| **成本** | 中（补 G1 + G2 的账 + 外部元数据方案） | 中（YAML schema + 迁移 + 测试） |
| **现有基础** | ✅ 表/客户端/市场/热刷新 都在 | ✅ registry 已是唯一入口 |
| **对 Q1（耦合）** | 解决"接外部"的耦合 | 解决"元数据与代码耦合" |
| **对 Q3（不重编码）** | ✅ **真做到** | ❌ **做不到** |

### 5.1 一句话区别

```
方案 A 让【工具从哪来】变动态 —— 工具是别人的，你只登记"连哪里"
方案 B 让【工具怎么描述】变外部 —— 工具是你的，描述搬出代码

A 买的是"零代码"（代价是治理要补账 + 能力受限）
B 买的是"声明与实现分离"（代价是……加了工具还是得写 Python）
```

## 6. 取舍建议 🔴 v1

**不建议二选一**——二者解决的是**不同问题**，可组合：

```
推荐组合（方案 C = A 的缺口补齐 + B 暂缓）
  ① 先补 G1（1 行：PATCH 补 rebuild_agent）—— 让已有路径真热刷新
  ② 再补 G2（MCP 工具进治理）—— 让"动态"不开口子：审批/三态/重试可声明
  ③ B（YAML 化）暂缓 —— 元数据实际很少变，收益与成本不匹配
```

**理由**：
1. 你的原始诉求是 **Q3（不重编码）**——**只有 A 能真正满足**，B 满足不了
2. A 的缺口（G1/G2）是**当前就存在的不一致**（不是 A 引入的），补它们本身就有价值
3. B 的价值是"元数据外置"，但当前 11 个工具的元数据**几乎不变**，且 YAML 化会让
   fail fast 校验、派生时序变复杂——**收益低、风险中**

**若你认为"元数据以后会频繁变"**（比如想做多环境不同审批策略），则 B 的价值上升，可并行推进。

## 7. 不做清单 🔴 v1

| 不做 | 原因 |
|------|------|
| DB 里存 Python 代码字符串（`eval` 执行） | **安全红线**：等于任意远程代码执行。动态工具的正解是 MCP/skill，不是 eval |
| 把自家核心工具（沙箱/研报/审批出口）MCP 化 | 核心能力外包，且多一层协议开销与故障面 |
| YAML 里写工具"行为"（除指向脚本） | 违背 07 §4「工具必须返回结构化数据」治理链；会退化成 skill 的劣化版 |
| 生产环境代码热重载 | 生产不该有；仅开发期体验，收益低 |

## 8. 决策结果 🔴 v1.1

| # | 决策 | 拍板（co-creator 2026-10-15） |
|---|------|------|
| **D1** | 补 G1（MCP 假热刷新）？ | ✅ **补**（成本极低、属修缺陷非新功能）——**已实施** `25d7de2` |
| **D2** | G2 的元数据从哪来？ | ✅ **选①：本地元数据表** `mcp_tool_meta`（存 ToolSpec 风格治理信息）。**不选②**（MCP 标准不自带风险等级/HITL 策略，让远端返回＝自定义扩展协议，换服务即崩）；**不选③**（不做治理＝高危外部工具绕开审批，安全漏洞） |
| **D3** | 走 A / B / C？ | ✅ **组合 C**：先补 G1 + G2，**YAML 化（方案 B）暂缓**。理由：① 核心诉求"不重编码"只有 MCP 路线能满足；② 内置工具元数据变动频率低，YAML 外置收益 < 成本；③ 分层清晰——核心工具走静态 `_IMPL_SPECS`，第三方走 MCP 动态注册，**两套共用同一治理** |

> **D3 后续触发条件**：待内置工具数量大幅上涨 / 元数据需频繁多环境变更时，再评估 YAML 化。

### 8.1 实施前定案（开工前核实补定）🔴 v1.1

拍板方向确认后，核实代码时发现三处**必须先定**的点（否则实现走偏）：

| # | 议题 | 定案 | 依据 |
|---|------|------|------|
| **X1** | **未登记的工具怎么办？** | ✅ **默认拒绝**（不挂载）+ 管理 API 暴露"待登记清单" | 默认放行＝G2 只修一半（新装 server 的工具全部无法治）。项目内同款先例：`tools/channels/base.py`「占位若'假装通过'，落在校验类接口上就是**静默放行的安全洞**」 |
| **X2** | 匹配键 | ✅ **`(server_name, tool_name)` 复合键**，存**远端原名** | `tool_name_prefix=True` → 实际名为 `{server}_{tool}`。存原名而非拼好的全名：改前缀配置时旧记录不失效 |
| **X3** | 元数据何时读（同步/异步） | ✅ **lifespan 异步预加载进内存**，之后同步可读 | `get_agent`/`_build_agent` 是**同步**函数，DB 是异步；照 `McpClientManager` 既有模式（`api/main.py:140` 已在这么做），避免把 `get_agent` 改成 async |

### 8.2 实施批次 🔴 v1.1

```
批次 1｜元数据表 + 仓储 + 预加载
        db/schema.py 建 mcp_tool_meta ｜ db/mcp_meta_repository.py ｜
        内存缓存（lifespan 预加载）｜单测
        ← 本批次不改行为（只建地基），可独立回滚
批次 2｜治理接线（G2 主体）
        HITL 审批扩成 [TOOL_REGISTRY + MCP 元数据] ｜ 重试按 is_idempotent 门控 ｜
        **未登记默认拒绝**（不挂载）｜ 管理 API 暴露"待登记清单"
        ← ⚠️ 行为变更：已配但未登记的 MCP 工具将不再挂载
批次 3｜三态信封
        MCP 工具输出适配 → ToolResult（现在 _SafeTool 失败返回**裸字符串**，
        artifact=None → SSE 只见 unknown、审计只见 unknown）
批次 4｜收口：文案 diff 表 / 文档 / 回归
```

每批次一提交，可独立回滚。
