## 1. 结论摘要 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

**多 Agent 研报评估管道首轮跑通**：10 个研究任务 → **9/10 完成（90%）**，引用编号合规率 **90%**，来源可达率 37%，LLM-judge 质量分 1-4 分（深色评审严）。

## 4. 评估发现的三处 bug（评估管道 = 质量探针） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

| # | Bug | 根因 | 影响 | 修复（commit） |
|---|-----|------|------|----------------|
| 1 | `get_chat_model() got an unexpected keyword argument 'provider'` | adapter env 回落分支传 provider=，但 `_build_chat_model` 签名无此参数（注册表加载路径不触发，脚本独立进程必炸） | 无注册表进程（脚本/异常路径）构造模型必失败 | `cb6d0c5`：删多余参数 + 3 用例回归 |
| 2 | `run_skill_script() got an unexpected keyword argument 'v__args'` | 工具参数名 `args` 与 langchain 1.x 工具转换的 versioned-args 保留字冲突 | agent 调用技能工具必炸（生产风险） | `18a3d06`：args → script_args + 测试同步 |
| 3 | A1 字段互换（task-005 出现 38/35 幻觉） | `citations_total, citations_compliant = count(...)` 解包顺序写反（count 返回 (compliant, total)） | 报告 JSON 字段错位、a1_ratio 可 >1 | `d742b0f`：顺序修正 + 回归测试 |

> **面试讲法**："评估管道首跑就抓出 3 个生产 bug——评估体系的价值是'质量探针'，不是好看的数字。"

## 7. P0-2 审核子代理纵向对比 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1.1</span>

> 3 任务样本（task-001/003/007）· run `8a3b0b19` @ `cb83033`（含 review_agent + 修订回路）

### 7.1 同任务对比（P0-1 无审核 vs P0-2 有审核）

| 任务 | 指标 | P0-1（b424e230） | P0-2（8a3b0b19） | Δ |
|------|------|------------------|------------------|-----|
| task-001 | 可靠性（B2） | 1.0 | **3.0** | +2.0 |
| | 耗时 | 101s | 860s | +8.5× |
| task-007 | 完整度（B1） | 2.0 | **3.0** | +1.0 |
| | 可靠性（B2） | 2.0 | **3.0** | +1.0 |
| | 耗时 | 281s | 605s | +2.2× |
| task-003 | 完成 | ✅（P0-1 首跑 4.0/4.0） | ❌ recursion 50 ×2 | 长任务 + 审核回路撞限 |

### 7.2 结论

1. **质量提升实证**：审核回路让产出质量分 +1~2（可靠性提升最明显——审核标准约束了"来源可核验/区分事实推测"）
2. **成本代价实证**：耗时 2-8 倍、工具调用 72→106-110——审核委派 + 修订重审的真实成本，**面试主动讲这个 tradeoff**
3. **新限制**：长任务（如 task-003）叠加审核回路更易撞 recursion 50——后续选项：recursion 再调大（成本↑）或审核跳过超长任务（智能跳过）

## 8. bad case：研究任务跑偏（审计日志定位） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1.2</span>

**场景**：P0-2 样本评估耗时异常（3 任务 24 分钟），co-creator 追问耗时构成。

**发现**（`logs/file_access_audit.jsonl` 按时间窗口过滤）：`run_command_in_sandbox` 82 次 + `edit_file` 26 次 + `run_code` 16 次，**`internet_search` 仅 3 次**——研究任务该搜索不搜、疯狂操作沙箱（124 次）。

**根因**：任务 query 未约束工具偏好，模型自由发挥倾向"写代码处理数据"路径。

**修复**：`assets/eval/tasks.jsonl` 10 任务统一追加约束句"以联网搜索（internet_search）为主要信息源，沙箱仅用于必要的数据验证"；资产防回归断言同步（`test_tasks_asset_exists`）。

### 8.1 修复验证（run 98fce243，同 3 任务重跑）

| 指标 | 修复前（8a3b0b19） | 修复后（98fce243） | 解读 |
|------|--------------------|--------------------|------|
| 博查搜索（bocha 外部计数） | 81 | **97** | 搜索量不降反升 |
| 主 agent 直调搜索（审计可见） | 3 | **0** | **搜索全部委派 search_agent——多 Agent 协作路径正确化** |
| task-007 质量 | 3.0 / 3.0 | **4.0 / 3.0（历史最佳）** | 约束 + 审核回路组合最优 |
| 完成率 | 2/3 | 1/3 | ⚠️ task-001/003 撞 recursion 50 根因仍不明 |

**审计盲区发现**：`ToolAuditMiddleware` 只审计主 agent 层——子代理内部工具调用不打点（bocha 97 次在审计中不可见）。验证了"推理层 trace 采集"的必要性（下一步）。

**教训与面试价值**：详见 `docs/learnings/2026-08-10-评估定位任务跑偏-工具审计分析法.md`——"慢的真相要靠数据，不靠直觉"；审计口径要讲清覆盖层级。
