## 1. 范围 🔴 v1

**输入**：一份外部草案 v1.0——「意图识别作为**独立 Agent**，经 **A2A 协议**对外提供能力，用**本地 cross-encoder NLI 小模型**做 7 意图多标签零样本分类，阈值 0.7」。

**本设计要回答的**：这套东西落到本项目，**该长什么样**。

| 项 | 本设计取的范围 |
|---|---|
| ✅ 做 | 形态判定（落点/协议/部署）+ 意图体系（由消费方反推）+ 判定实现选型 + 输出契约 + 单一登记处 |
| ⏳ 分阶段 | 首版只做**判定能力升级**（保持两分类，零架构变更）；多路路由等真实消费方出现再扩 |
| ❌ 不做 | 见 §6（A2A 协议实现、7 意图全量、本地 NLI 首版落地等） |

### 1.1 🔴 一句话结论（**请先拍这一条**）

```
草案把三件独立的事捆成了一个方案：
   ① 通信形态（A2A 独立服务）   ② 判定实现（本地 NLI 小模型）   ③ 意图体系（7 意图）

实测：本项目三件都不需要照抄——
   ① → 无 A2A 实现、无独立部署先例、backend 连容器都还没进 compose（§2 事实 3/4）
   ② → 零本地推理依赖、2核4G 无 GPU、RAG 设计已明确「不强制引入 PyTorch」（§2 事实 5/6）
   ③ → 意图的**消费方只存在一个**（快通道 vs 全链路），7 个意图里 5 个没有下游（§4.2）

→ 建议：三件事**拆开各自拍板**（D1 / D3 / D2），不要捆着一起上。
```

> 若 co-creator 的**本意**就是"我要一个 A2A 独立服务/本地模型"（例如作为面试/学习载体），
> 那是一个**正当但不同的目标**——本设计需切到"独立部署形态"支线重写 §4.1。
> 请先确认目标再往下读。

## 3. 差异点总表（外部草案 v1.0 ↔ 本项目） 🔴 v1

> 这是本设计的核心章节。**左列是草案原文主张**，中列是项目实测现状，右列是差异性质与建议。

| # | 草案 v1.0 主张 | 项目现状（实测） | 差异性质 → 建议 |
|---|---|---|---|
| **D1** | 意图识别做成**独立 Agent**，经 **A2A 协议**对外提供服务 | A2A 仅一行 `available=False` 占位；无 SDK 依赖、无独立部署单元、backend 未容器化；所有 Agent 逻辑同进程（§2 事实 3/4） | 🔴 **增量成本差异（最大件）**：选它要**从零补五件**——协议实现 / 服务发现 / 端口 / 部署单元 / 进程隔离。→ 建议**进程内优先**，A2A 列为独立可选项 |
| **D2** | **7 意图**：chat / query_knowledge / tool_call / code_run / task_plan / creative_write / summarize | 现有判定只输出 2 类；且现有**唯一消费方**是"快通道 vs 全链路"。7 个意图中 `query_knowledge` 依赖**未实现**的 RAG、`tool_call` 是伪意图（"要不要用工具"由模型在 loop 内决定，且工具已有 `domain` 表达）、`task_plan` 与 deepagents 自带 planning 重叠、`creative_write` / `summarize` **无任何专属下游** | 🔴 **语义差异：意图与消费方不对齐**。→ 建议**意图表由路由目标反推**，只列有下游的（§4.2）；空造意图 = 复刻工具中心已清算的「声明了没人读」死数据 |
| **D3** | 模型 = 本地 `cross-encoder/nli-MiniLM2-L6-H768`（~70MB），GPU 优先 / CPU 降级 | 零本地推理依赖；2 核 4G、**无 GPU**、backend 内存限额 **1g**；项目已明确把 PyTorch 推到可选组（§2 事实 5/6） | 🟠 **依赖差异**：镜像/环境体积增量 **由 torch 主导（数百 MB）**，远超模型本身 70MB。→ 建议首版走**远程 LLM 单次调用**（已有先例），本地 NLI 作降本/离线二档（§4.3） |
| **D4** | 阈值**固定 0.7**，多标签，分数 ≥0.7 即保留 | 现有兜底原则是「**不确定就走完整链路**」（`intent.py:6` 模块 docstring + `:42` 默认 `complex`） | 🟠 **策略差异**：NLI 的 entailment 概率**非校准置信度**，0.7 无依据（需实测标定）。→ 建议阈值**可配 + 默认 fail-safe**（宁可进全链路，不可误判进快通道） |
| **D5** | §4.5「**不做二级降级规则**：异常场景只返回 error，不启用关键词兜底」 | `.claude/rules/06-structure-optimization.md` §4：「除 LLM 主链路外，**不因单点失败断流**——降级 + 默认兜底 + 日志留痕」 | 🔴 **纪律冲突：草案直接违反项目规则**。→ 必须降级：判定失败 → 回退现有规则判定 / 兜底 `complex`（**既不新增故障面，也不丢既有能力**） |
| **D6** | 两类 unknown（业务 unknown / 系统 error），自建 `status`/`error_msg` 字段 | 项目已有统一体系：`ToolResult` 三态 `ok`/`degraded`/`error`（`tools/result.py:30`）+ `core/errors.py::ErrorMessage`（code→中文文案）+ `ErrorResponse` 三字段（error/detail/code） | 🟠 **契约差异：两套错误模型并存**。→ 并入项目现有三态/错误码体系，不自建 `status` 语义（§4.4） |
| **D7** | 超时 **5s**，同步前置在链路里；输入仅 `strip()`，不截断 | 判定点位于 `StartEvent` **之后**、`build_agent()` **之前**（`chat.py:672`）——即**串行增加首 token 延迟**；而快通道的**存在意义就是省延迟** | 🟠 **体验差异**：5s 预算与快通道目标**自相矛盾**。→ 判定预算收紧（建议 ≤300ms 量级）；超预算即降级，不阻塞主链路 |
| **D8** | 自建 A2A payload 信封（`input_text` / `model_name` / `scores` …） | 项目约定：Pydantic v2 模型进 `src/schemas/`（规则 10）；SSE 事件类型**固定 8 类**（`schemas/events.py`）——**新增事件类型属协议变更** | 🟡 **协议差异**：另起一套信封 = 两套契约要同步维护。→ 复用项目 Pydantic/错误码；若结果需透出前端，优先**塞进既有 `start` 事件 payload**（需确认），不新增事件类型 |
| **D9** | `intents` 按置信度降序返回，**下游主 Agent 自行处理多意图路由** | 项目**没有路由表**；工具侧的"该用哪个工具"由模型在 loop 内决定（工具中心 `domain` 只是人读标签）；且 `fallback_to` 已确认「**只声明不执行降级**」 | 🟠 **落点差异**：把路由责任推给主 Agent = 新造一个没有实现方的接口。→ 若要多路路由，须先补**路由表 = 单一登记处**（§4.5），否则退回两分类 |
| **D10** | 测试用例集 5 例（单意图/多意图/业务 unknown/闲聊/异常） | 规则 20 要求：正常 / 边界 / 错误 / LLM 异常四类；且面试指南 §3.2 把**评估体系列为 P0**（要有准确率/召回率/bad case） | 🟡 **测试口径差异**：5 例是样例不是回归集。→ 补：混淆矩阵 + 判定降级路径断言 + 样本集从意图表**派生**（§11.4） |

**差异归类小结**：🔴 硬冲突 3 条（D1 成本 / D2 语义 / D5 纪律）｜🟠 需调整 5 条（D3/D4/D6/D7/D9）｜🟡 建议合并 2 条（D8/D10）。
**没有一条是"草案全对、项目照抄"**——故 §8 的决策点必须逐条拍。

## 4. 设计 🔴 v1

### 4.1 落点选择（三选一 → D1）

| 方案 | 落点 | 改动面 | 是否真「前置」 | 评价 |
|---|---|---|---|---|
| **A（推荐）** | 就地升级 `agent/intent.py`，消费点 `chat.py:672` | **小**（既有函数内部升级；调用点/`ChatContext` 传递链已通） | ✅ 是（在 `build_agent()` 之前） | 零新增基础设施；**唯一已有消费者的落点** |
| B | 新增 `AgentMiddleware`（在 `middlewares/builder.py:66-83` 插一行） | 小-中 | ❌ 否（钩子在 agent loop **内部**，此时 agent 已构建完） | 适合"每轮模型调用前注入指令"（如 `awrap_model_call` 改写入站消息），**不适合入口路由** |

### 4.2 意图体系：由消费方反推（→ D2）

**原则**：**先有下游，才有意图**。理由不是保守，是工具中心刚清算过的同类问题——
"声明了没人读"的元数据是死数据（`docs/决策/2026-10-15-设计-阶段3横切与阶段4编排-v1.md` §2 事实 1/2、P2）。

| 草案意图 | 本项目对应的下游（实测） | 是否具备 |
|---|---|---|
| （现状）`simple` / `complex` | 快通道 `_fast_stream` / 完整 Agent | ✅ **已具备**（`chat.py:672` / `607-632`） |
| `tool_call` | ❌ 无——"要不要调工具"由模型在 loop 内决定；工具已有 `domain` 标签表达分类 | ❌ **伪意图**（无路由消费方） |
| `code_run` | `run_code_in_sandbox`（主 Agent 已挂） | ⚠️ 有工具，但**无"路由到它"的必要**（模型自会调） |
| `query_knowledge` | ❌ RAG **未实现**（`src/retrieval/` 目录不存在） | ❌ **目标不存在** |
| `task_plan` | deepagents 自带 planning（write_todos） | ❌ **与框架能力重叠** |
| `creative_write` / `summarize` | ❌ 无专属下游（全链路即可满足） | ❌ **无消费方** |

**建议的意图表演进路径**：

```
阶段 1（首版）：保持 2 分类 simple / complex      ← 零架构变更，只换判定器
阶段 2（有真实需求时）：扩到 N 路，每路必须有一个已存在的下游
       候选（按"下游是否已具备"排序）：
         search   → ✅ internet_search（子代理已有；主 Agent 当前不挂 mount_main=False）
         sandbox  → ✅ run_code_in_sandbox
         report   → ✅ generate_report / publish_report
         knowledge→ ❌ 等 RAG 落地（2026-09-14 设计稿）
```

> 📌 与工具中心的对齐：若走多路，意图名**优先复用工具 `domain`**（`search`/`sandbox`/`file`/`skill`/`wiki`/`report`/`hitl`），
> 避免"工具域"与"意图域"两套词汇各自演化。

### 4.3 判定实现：三档（→ D3）

| 档 | 实现 | 增量成本 | 延迟量级 | 建议 |
|---|---|---|---|---|
| **1（现状）** | 纯关键词规则 | 0 | ~0 | **保留为兜底**（D5 要求） |
| **2（推荐首版）** | **远程 LLM 单次调用**，经 `LLMAdapter.chat()` | ~0（已有设施） | 数百 ms | ✅ 有现成先例：`agent/tasks/assistant.py:21` `generate_title`；prompt 归 `agent/prompts/prompts.py:5`（"新增辅助任务先在此加 prompt"） |
| **3（可选）** | 本地 cross-encoder NLI | **+ torch 主导的体积/内存** | 单次 CPU 可接受 | ⏳ 作**降本/离线/隐私**二档；需先解决 §7 R3/R4 |

**关于草案选定模型的三个待核实点（⚠️ 未实测，接入前必须验）**：

1. **语种**：`cross-encoder/nli-MiniLM2-L6-H768` 是**英文 NLI 模型**，而草案的 7 条 NLI 描述文本全是中文——
   跨语种零样本效果**存疑**。中文场景应考察多语种 NLI（如 `mDeBERTa-v3` 系 / `xlm-roberta` 系 xnli 权重），**选型需实测对比**。
2. **分数语义**：NLI 三分类（contradiction / entailment / neutral）经 softmax 得到的 entailment 概率
   **不是校准置信度**；对 7 个假设各取一分数再以固定阈值筛选，**阈值必须用真实样本标定**，不能拍 0.7。
3. **多标签稳定性**：NLI 零样本在域外文本上常见"多个假设同时高分"或"全部低分"，
   与草案假设的"少数意图过阈"分布未必一致。

> 结论：模型选型是**可替换的内部实现**（草案 §8 已认同这一点），不要让它成为 v1 的阻塞项。
> 先把**意图表 + 消费契约 + 降级路径**定死，判定器可以后换。

### 4.4 输出契约：并入项目现有体系（→ D6 / D8）

| 项 | 草案 | 本项目建议 |
|---|---|---|
| 成功/失败语义 | 自建 `status: success\|error` | 复用三态思路（`ok`/`degraded`/`error`，`tools/result.py:30`）；**降级必须显式**（草案无此态） |
| 错误文案 | 裸字符串 `error_msg` | 进 `core/errors.py::ErrorMessage`（code → 中文文案），规则 06 §6 |
| 数据结构 | 自建 A2A payload | Pydantic v2 模型进 `src/schemas/`（规则 10） |
| 前端透出 | 未提 | **不新增 SSE 事件类型**（协议固定 8 类）——优先塞进既有 `start` 事件 payload，需确认 |

**建议的判定结果形态**（Python 层，非草案 JSON）：

```python
@dataclass(frozen=True)
class RouteDecision:
    intent: str            # "simple" | "complex" | （阶段 2 扩展）
    source: str            # "llm" | "rule" | "fallback"  ← 关键：降级来源可观测
    degraded: bool         # 是否走了降级（对应 ToolResult.degraded 精神）
    latency_ms: int
    raw: dict[str, float] = field(default_factory=dict)   # 原始分数（调试/评估用）
```

### 4.5 单一登记处（→ D9）

参照工具中心的范式（规则 07 §1）：**意图表 = 唯一真相源，消费方全部派生**。

| 消费方 | 派生自 |
|---|---|
| 判定器的语义描述 | `RouteSpec.description` |
| 路由目标 | `RouteSpec.target` |
| 回归测试样例 | `RouteSpec.examples` |
| 评估集混淆矩阵 | `RouteSpec.name`（枚举全集） |

**禁止**在 `chat.py` / 测试文件里再写一份意图字面量清单——那正是工具中心已清算的"同一件事写两遍"。

### 11.1 意图登记表 + 判定器（`backend/src/agent/intent.py` 升级形态）

```python
"""意图分类——入口分流（v2：登记表 + 语义判定 + 规则兜底）。

决定请求走「快通道」（简单概念题 → 主 LLM 单轮直答，不建 agent/不挂工具）
还是「完整链路」（挂搜索/子代理/publish_report）。

兜底原则：**不确定就走完整链路**；判定失败一律降级，不断流。
"""

from __future__ import annotations

import logging
from dataclasses import dataclass, field

from src.core.config import get_settings
from src.core.errors import ErrorMessage
from src.llm.adapter import LLMAdapter

logger = logging.getLogger(__name__)

# ── 登记表：唯一真相源（判定描述 / 路由目标 / 回归样例都从这里派生） ──
@dataclass(frozen=True)
class RouteSpec:
    """一条路由意图的声明。"""

    name: str                      # 意图 ID
    description: str               # 语义描述（规则 / LLM / 小模型共用同一份）
    target: str                    # 路由目标："fast_stream" | "full_agent"
    examples: tuple[str, ...] = () # 回归样例（测试从表取，禁止在测试文件另抄一份）


ROUTE_REGISTRY: dict[str, RouteSpec] = {
    "simple": RouteSpec(
        name="simple",
        description="概念解释、定义、原理问答等可直接单轮回答、无需工具与外部信息的请求",
        target="fast_stream",
        examples=("什么是 ReAct 循环", "解释一下向量检索的原理"),
    ),
    "complex": RouteSpec(
        name="complex",
        description="需要检索、代码执行、多步分析、生成报告或任何不确定的请求",
        target="full_agent",
        examples=("帮我查今天的气温并写一段绘图代码", "调研一下 2026 年 Agent 框架现状"),
    ),
}

# 兜底目标：判定不可信时一律走这里（fail-safe，见 R1/R2）
FALLBACK_INTENT = "complex"


def route_targets() -> dict[str, str]:
    """派生：意图 ID → 路由目标。消费方不重复声明映射。"""
    return {name: spec.target for name, spec in ROUTE_REGISTRY.items()}
```

### 11.2 判定器（三档实现 + 降级链）

```python
    """规则判定——底层兜底（原有实现保留，作为降级链最后一环）。"""
    # …… 现有 _SIMPLE_KEYWORDS / _COMPLEX_KEYWORDS 逻辑不变 ……
    ...


async def classify_intent(text: str) -> RouteDecision:
    """判定路由意图：LLM 优先 → 规则兜底 → 默认全链路。

    任一步失败都降级，绝不抛异常出函数（规则 06 §4：不因单点失败断流）。

    Args:
        text: 用户请求文本

    Returns:
        RouteDecision：含 intent / source（llm|rule|fallback）/ degraded / latency_ms
    """
    settings = get_settings()
    text = (text or "").strip()
    if not text:
        return RouteDecision(intent=FALLBACK_INTENT, source="fallback", degraded=True, latency_ms=0)

    if settings.intent_enabled:
        try:
            raw = await asyncio.wait_for(
                _llm_classify(text), timeout=settings.intent_timeout_ms / 1000
            )
            return RouteDecision(intent=raw.intent, source="llm",
                                 degraded=False, latency_ms=..., raw=raw.scores)
        except (asyncio.TimeoutError, LLMUnavailableError) as exc:
            # 可重试/不可重试均在此收敛为"降级"，不冒泡
            logger.warning("意图判定降级：%s", ErrorMessage.INTENT_DEGRADED_MSG % exc)

    return RouteDecision(intent=_rule_classify(text), source="rule",
                         degraded=True, latency_ms=...)
```
