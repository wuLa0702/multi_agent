## 1. 背景与目标 🔴 v1

### 1.1 现状（已核实，2026-10-15）

| 项 | 现状 |
|---|---|
| 数据库 | SQLite，驱动 `aiosqlite>=0.20`（实际 0.22.1） |
| 库文件 | `settings.db_path` 默认 `./data/wiki.db`，经 `core/paths.py::get_db_path()` 解析 |
| 表 | 9 张：`sessions` / `messages` / `providers` / `models` / `mcp_servers` / `installed_skills` / `settings` / `token_cost_ledger` / `cost_alerts` + 若干索引 |
| DDL 位置 | `backend/src/db/schema.py`（含一个 `ALTER TABLE ADD COLUMN` 式的老库加列辅助） |
| 数据访问 | 7 个 repository，全部手写 SQL，形参类型标注为 `aiosqlite.Connection` |
| **LangGraph 持久化** | Checkpointer = `AsyncSqliteSaver`（`main_agent.init_checkpointer`，lifespan 管理）；Store = `SqliteStore`（`main_agent.init_store`） |
| 依赖 | `langgraph-checkpoint==4.1.1` + `langgraph-checkpoint-sqlite==3.1.0` |

### 1.2 为什么迁（按重要性排序）

1. **向量索引**：后续资料检索/RAG 需要向量检索能力，SQLite 不提供 → 目标库需支持 `pgvector`
2. **审计与可观测要落库**：审计留档与 trace 需要"可查询"（SQLite 单文件 + 无并发查询，撑不住）
3. **上云多进程**：上云后 API 与后台 worker 并存，SQLite 的单写者模型会撞锁

### 1.3 ⚠️ 本迁移会**推翻一条既有已定决策**，执行方必须同步回写

`docs/决策/2026-09-14-设计-资料检索与RAG基础系统-v1.md` 当时**主动选择**了 SQLite，并写明理由：

- 第 70 行：`独立 SQLite get_retrieval_db_path()，aiosqlite`
- 第 528 行：`为什么先轻量 SQLite + 精确扫描：个人小库易部署、易验证；大规模 ANN 是后续选型，不能声称本方案拥有向量数据库的伸缩能力`

**co-creator 2026-10-15 已拍板改这条**（上 PG + pgvector）。执行方**必须同步修订上述两处**，
并在该稿的版本变更记录追加一行——否则又形成"文档与代码脱节"（正是本项目反复清理的问题）。

## 3. 技术选型（锁定，勿改） 🔴 v1

| 项 | 决定 | 理由 |
|---|---|---|
| 镜像 | **`pgvector/pgvector:pg16`** | PG 16 + pgvector 预装；后续 RAG 无需换镜像 |
| Host 端口 | **5433**（容器内 5432） | 避开本机可能已有的 5432；与项目 redis 用 6398（非默认）的约定一致 |
| 驱动 | **与 `langgraph-checkpoint-postgres` 的依赖保持一致**——执行时先 `pip show langgraph-checkpoint-postgres` 看它拉进哪个驱动，业务库复用同一个，**禁止项目内并存两套 PG 驱动** | 预期为 `psycopg` 3；**以执行时实测为准，不要凭记忆** |
| 连接管理 | 连接池单例放 `core/`，DSN 从配置读；repository **只接收连接**、不自己建连 | 规则 06 §5「第三方中间件统一单例封装」 |
| ORM | **禁止引入** | 保持现有「手写 SQL + repository」模式（规则 06 §2：db 是唯一 SQL 出口） |
| 库/schema 划分 | 业务库与 Checkpointer/Store 可同实例、**不同 database 或不同 schema**（执行方择优，但需在架构文档登记） | 隔离关注点，避免断点表混进业务表 |

## 5. 配置与连接（唯一出口） 🔴 v1

- **DSN 变量建议名**：`PG_DSN`（或按现有命名风格定，执行方定后统一）
- **只存在于** `.env.dev` / `.env.prod`；**禁止**硬编码进代码 / compose / 文档 / 聊天
- `docker-compose.yml` 内以 `${VAR}` 引用（规则 00-security §密钥安全）
- 后端连接池为**单例**（`core/` 下），全项目共用；repository **不得**自行建连
- 连接池参数（`min_size` / `max_size` / 超时）给明确默认值 + 注释说明依据（本机 2 核 4G 的资源约束见架构文档 §6）

## 6. 数据迁移策略 🔴 v1

**结论：不迁历史数据，建库后重新 seed。**

依据（已核实）：`db/schema.py` 的 `providers` 表注释写明
「**API key 不入库，按 `api_key_env` 读 .env**」——即库内**没有密钥**；
其余表内容为会话历史 / 消息 / 成本流水 / 已安装技能，个人项目可弃。

执行动作：
1. 新建 PG 库 → 跑 schema 建表
2. 调现有 seed（`model_repository.seed_defaults`）重建 `providers` / `models`
3. 若 co-creator 事后要求保留历史 → **另开任务**写一次性搬迁脚本（本次范围内不做）

## 7. 测试策略（重点） 🔴 v1

**核心冲突**：`docs/rules` 的 `20-testing.md` 写「数据库用 `:memory:`」，而 **PG 没有内存模式**。
执行方**必须**同步修订该规则条目（按 `.claude/rules/00-security.md` 的规则变更流程：说明改动与理由，等 co-creator 确认）。

**推荐做法（二选一，执行方与 co-creator 确认）**：

| 方案 | 做法 | 取舍 |
|---|---|---|
| A（推荐） | 复用 compose 里那个 PG；**每个测试用独立 schema**，测试结束 drop（或事务回滚） | 无需额外组件；隔离靠 schema，天然并行安全 |
| B | `testcontainers` 自起临时容器 | CI 友好；但本地必须有 docker，启动慢 |

**禁止**：为了让测试变绿而把 SQL 层 mock 掉——那等于没测到真实 SQL 行为（本项目已有
「改完不跑相关测试面导致回归漏网」的教训）。

**必须跑通的既有测试面**（逐项确认，别只跑一部分）：

- `test_core/test_repository.py`、`test_core/test_model_repository.py`、`test_core/test_cost.py`
- `test_agent/test_checkpointer.py`、`test_agent/test_history_checkpoint.py`、`test_agent/test_memory_store.py`
- 所有使用 `tmp_db_path` fixture 的测试（`conftest.py` 中定义）

> ⚠️ 历史教训（务必遵守）：`sync` 版 Saver 在 async `astream` 下**静默失败**——
> 必须用 **async** 版实现。参见 `main_agent.py` 中 `init_checkpointer` 的注释。

## 10. 红线与风险 🔴 v1

| 类别 | 内容 |
|---|---|
| 🔴 密钥 | DSN / 密码只进 `.env.dev` / `.env.prod`；**不打印明文**；提交前 `git status` 确认无 `.env*` 进暂存区 |
| 🔴 端口 | PG 用 **5433**；不碰 3003 / 3004；**Redis 6399 是生产，永不连** |
| 🔴 分支 | 主仓库禁止 checkout 到非 main 分支；改代码在 **worktree** 内做；**推送远程需明确指令** |
| 🟠 风险 1 | **旧 SQLite 断点作废**：Checkpointer 换实现后，已存在的会话断点格式不兼容，历史中断点无法恢复（个人项目可接受，需在交付说明里写明） |
| 🟠 风险 2 | **必须用 async 版 Saver**：sync 版在 async 下静默失败（本项目踩过） |
| 🟠 风险 3 | **测试会变慢**：真 PG 比 `:memory:` 慢；若明显拖慢（>2×），回报 co-creator 评估方案 B |
| 🟠 风险 4 | **驱动双套**：若 checkpointer 依赖与我方不同，易引两套驱动 → 统一为一套（§3） |
| 🟠 风险 5 | **`db_path` 删除的连带**：`get_db_path()` 可能被 RAG / 其它模块引用 → 删前先 `grep` 全仓确认 |

## 11. 交付物与提交规范 🔴 v1

### 11.1 分支

**从工具中心分支开**（stacked），不要从 `develop` 开：

```
git switch -c feature/20261015-pg-migration      # 当前 HEAD 即工具中心分支
```

理由：① 本工作单提交在工具中心分支上，从 develop 开会缺它；② 两条分支都改
`main_agent.py`（checkpointer / `_build_agent`），从 develop 开必然冲突。
合并顺序：工具中心 → develop，然后 PG → develop。

### 11.2 提交规范

遵循 `.claude/rules/03-git-commit.md`：`<type>: <中文摘要，动词开头，≤50 字>` + 要点 +
`Why:` 段 + `Co-Authored-By`。**代码与文档分开提交**，每个提交一件事、可独立回滚。

### 11.3 交付时必须回话的内容

1. 实际改动清单（文件级）
2. 全量 `pytest` 结果（贴输出，不是"应该没问题"）
3. 逐条对照 §9 验收标准的核对结果
4. §10 五项风险的实际处置（尤其"旧断点作废"是否发生）
5. 执行中与本文不符的地方 + 原因（**不要静默偏离**）
