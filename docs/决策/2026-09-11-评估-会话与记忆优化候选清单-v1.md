## 1. 文档定位与讨论截止点 🔴 v1

### 1.1 本文是什么

这是个人面试 Demo 的**需求候选评估稿**，用于用户重新排序、筛除条目，再进行需求细化。不是已批准的实现方案，不包含要求另一个 AI 立即执行的代码任务。

当前阶段顺序：候选评估 → 用户筛选和定级 → 选中项需求细化 → 用户确认 → 另一个 AI 开发。用户提到晚上可能交给其他 AI，不代表本表全部获得开发授权。

证据基础：本轮对话中对代码的定点阅读，以及先前的消息合并机制验证；未运行完整应用验收，也没有开展整个仓库审计。源码基线为 `D:\gtiHub\multi_agent`、HEAD `cc7ab87`。当前 Codex 工作目录是另一个初始版本 worktree，后续 AI 必须确认实际开发目录与版本，不能直接套用本文行号。工作区存在用户原有未提交文件，本文不覆盖其内容。

### 1.2 本轮讨论覆盖到哪里

本轮聚焦 Session 到 Memory：

1. Session ID、聊天记录、Graph/State、Checkpoint 的职责；会话工作区与图对象缓存。
2. SQLite 断点、Redis 审批记录、恢复与删除联动的边界。
3. 同会话上下文和跨会话记忆的区别；历史重建与 Checkpointer 的关系。
4. 长期记忆的异步抽取、分类、关键词搜索、有限范围精确查重、时间戳追加保存。
5. 画像优先、时间排序、注入条数和 token 预算；向量检索的作用。
6. 用户画像与其他事实的概念、临时要求与长期偏好的关系。
7. 完整模型消息结构：系统规则、背景数据、历史、当前问题、工具调用与工具结果。
8. 最后一处讨论停在：**为什么需要区分读取策略，以及哪些规则当前已实现、哪些仅是建议。**

本文不把更早泛谈的混合编排、行业调研业务、报表、订单退款、通用幻觉治理扩展成新需求；那些话题没有在本轮形成可执行的具体优化结论。

### 1.3 用户已表达的约束

- 个人 Demo、面试理解优先，不追求生产系统完整性。
- 暂时接受后台异步记忆，不要求新增同步保存路径。
- 暂时接受没有完善画像冲突合并，倾向保持现状。
- 相关性读取方案尚未充分理解，不能视为接受；向量检索等记忆增多后再考虑。
- 多用户隔离改进明确不执行。
- 本次仅记录和评估；不改功能、不迁移数据、不启动开发。
- 项目理解有偏差时应直接纠正，区分代码事实、常见做法和建议；不能把 Demo 选择说成行业标准。

## 2. 优先级总览 🔴 v1

优先级是助手建议，**用户状态优先于建议优先级**。P1 不代表已批准。

- **P0**：有证据的立即阻断或严重问题。本轮没有足够证据指定 P0。
- **P1**：优先筛选，影响当前正确性或面试表述准确性。
- **P2**：改善质量或边界完整性，先判断实际需要。
- **P3**：规模或可靠性诉求出现后再考虑。
- **排除**：明确不进入本轮开发候选。

规模仅指相对工作范围，不是工期承诺：小＝局部文案/规则；中＝跨调用路径或存储行为；中至大＝增加检索、持久任务等机制。

## 3. 按领域展开候选需求 🔴 v1

### 3.1 会话与消息上下文

**C01｜历史、Checkpoint 和动态记忆的合并边界**

- 当前证据：聊天入口重建历史消息，Agent 同时配置 Checkpointer；动态记忆也被加入消息列表。先前对 `add_messages` 的独立验证显示，新建消息对象且缺少稳定 ID 时，已有历史可能被再次追加。**这是机制层证据，不是已完成的接口端到端复现。**
- 为什么优先：若完整路径存在重复，可能增加上下文开销，并将旧记忆反复保留，影响后续回答。
- 候选目标：明确谁负责恢复对话历史、哪些消息只传新增内容、动态记忆是否只作用于当前请求；保留 Checkpointer 不可用时的合理处理。
- 可观察结果：同一会话连续两轮输入后，消息不会无故重复；动态记忆更新后不会仅因再次注入而不断堆叠旧副本。
- 细化前需决定：采用何种历史来源与降级策略。不在本文强行确定“全量重建”或“只传增量”的实现。
- 面试追问：聊天记录与运行状态为什么都含消息？如何避免重复？

**C02｜当前要求与历史偏好优先级**

- 当前证据：主 Agent 有系统提示词，记忆另以 SystemMessage 注入；“已有系统提示词”不等于已有完整的偏好覆盖规则。
- 候选目标：把历史偏好明确为默认值，当前明确的篇幅/语言/格式要求控制本次回答；一次例外不自动变为长期偏好。记忆与工具内容是背景数据，不得因其包含指令文字而获得系统规则权限。
- 例子：平时简短，这次要求详细，则本次详细；不能据此永久改成“用户喜欢详细”。
- 可观察结果：代表性对话遵循本次要求；没有本次特殊要求时仍可使用适用偏好。
- 边界：这是表达偏好规则，不是允许当前用户请求覆盖权限等系统约束；提示词也不是强安全保证。不要求一律换成某种消息角色或重排全部历史。
- 依赖：可独立讨论规则；最终消息装配方式应与 C01 一致。

**S01｜删除联动边界**

- 当前证据：删除服务处理会话记录、图缓存、工作区和沙箱，所读路径没有显示删除 Checkpoint 或长期 Store 记录。
- 候选目标：先明确“删除会话”是否应同时删除执行断点，再决定是否补联动。
- 可观察结果：界面/文档承诺和实际清理范围一致；若决定清理断点，已删除会话不再留下可恢复的执行状态。
- 边界：长期记忆可能跨会话使用，不自动随会话删除；本文不授权删除现有数据，也不扩展完整数据治理。

### 3.2 记忆写入与变化处理

**W01｜内容查重**

- 当前证据：提示词要求先搜索；搜索工具在每类最多 50 条内做关键词包含匹配；写入前在目标类最多 50 条内检查完全相同内容。队列指纹只防同一任务重复入队。
- 局限：换种说法可能重复，范围外的旧记录可能漏检；“先查后写”不是原子唯一性保证。
- 候选目标：先提高基础精确查重的一致性，再决定是否需要模型辅助相似判断；不以向量数据库为前置条件。
- 可观察结果：相同内容重复提交时不持续新增；明确声明是否覆盖并发写入和全库范围。
- 边界：相似不等于相同，更不等于可以覆盖；“喜欢辣”与“不喜欢辣”不能直接合并。低质量评分目前只是审计，不可宣传为拦截器；本轮不扩展完整质量评分系统。

**W02｜画像变化与冲突**

- 当前证据：时间戳键追加记录；读取按时间排序，但返回给模型的主要是内容，不能把排序等同于携带明确时间证据；`related` 不是覆盖机制。
- 候选目标：区分长期偏好、一次行为、本次要求；若以后决定支持变化处理，再明确旧值失效和来源记录。
- 可观察结果：一次吃辣不推断成长期爱辣；明确“以后不吃辣”时，旧偏好不再作为当前默认值。
- 状态：用户接受暂时不做。C02 只处理本次回答如何采用偏好，不依赖实现完整 W02。

**W03｜明确记忆请求的即时确认**

- 当前证据：完整 Agent 路径在回答后入队，等待入队不等于等待记忆落库；未见这一路径为“请记住”单独等待保存。
- 候选目标：如未来需要即时跨会话可用，明确请求保存成功后才能声称“已记住”；普通对话仍可后台处理。
- 可观察结果：保存成功与失败反馈可区分；新会话能读取已确认保存的信息。
- 边界：写入可见不代表一定被召回，需同时考虑 R01；具体是否新增入口或工具尚未决定。
- 状态：用户已选择暂缓，不能因“实现似乎简单”擅自加入开发。

**W04｜后台队列可靠性**

- 当前证据：进程内队列、容量 100、2 个 worker；满队列拒绝，处理失败记日志，不等于可靠重试或重启可恢复。
- 候选目标：只有用户需要保证后台记忆不因故障丢失时，再考虑持久任务和重试。
- 可观察结果：届时需验证重启恢复、失败重试和重复写入的关系。
- 状态：P3，仅保留已讨论过的可靠性方向；不在本稿选择中间件、扩展监控或设计任务协议。与 W01 的幂等边界相关。

### 3.3 记忆读取与注入预算

**R01｜适用性与相关性选取**

- 当前证据：画像、事实、旧记忆各取最多 5 条；排序先看类别，再看时间，最终最多 5 条。没有依据当前问题进行语义相关性判断，也没有额外 LLM 筛选步骤。
- 问题例子：问“断点如何实现”时，五条画像可能挤掉“项目使用 SQLite”的事实。
- 候选目标：回答前选取少量适用偏好与相关事实，避免把“画像”当成天然相关；具体配额只是可讨论方案，不能直接硬定成 2+3。
- 可观察结果：同样的记忆集合，换不同问题时能够选出不同的任务相关事实；不相关画像不会仅凭类别占满名额。
- 何时值得做：已出现无关内容挤占、遗漏关键事实或回答受干扰，不必等待固定记忆条数。
- 选项边界：规则、关键词、向量、LLM 判断都是可能方式；本稿不选型。用户尚未接受此项，保持现状是有效选择。
- 面试追问：为什么分类？因为适用范围可能不同；当前实现仍是简化的类别和时间规则。

**R02｜注入预算**

- 当前证据：已有最多 5 条的最终限制、单条保存最多 500 字符；注入函数默认窗口 128000、比例 10%，使用粗略 token 估算。调用处没有显式传入真实模型窗口；提示词要求约 50 字不等于程序强制 50 字。
- 候选目标：若调整预算，区分模型窗口与记忆可用预算，考虑已有历史、工具结果和回答空间；再决定估算精度是否值得提高。
- 可观察结果：选中记忆不超过配置预算，条数和长度限制含义清楚。
- 边界：默认记忆预算是 12800 token，实际往往先受 5 条限制；不能说当前“没有限制”。注入限制不等于整个数据库的容量上限，也不能消除异步落库延迟。
- 状态：可以先保留现状，仅更正描述，不必单独实施。

**R03｜向量检索**

- 当前证据：记忆已经存 SQLite，尚未进行向量语义召回。
- 候选目标：记忆增多、关键词难以找出相关内容时，按语义找候选，再筛选、裁剪。
- 可观察结果：如“低刺激饮食”能在“晚饭怎么安排”的查询中成为相关候选；仍需验证错误相似匹配。
- 边界：向量解决怎么找，不解决是否落库，不自动保证真假、去重、冲突覆盖或最新可见；不必先部署独立向量数据库。
- 状态：用户明确后置。依赖先理解 R01 的选取目标，不选模型、数据库或技术方案。

### 3.4 文档与面试准确性

**C03｜把现状、原则、候选能力分开**

- 当前需要纠正的表述：画像也是事实；`facts` 不是实时记忆；Graph 是流程而 State 是运行数据；缓存 32 不是并发 32；SQLite 保存断点而 Redis 管审批记录；时间倒序不是完整时间衰减算法；精确匹配与关键词搜索不等于向量检索。
- 候选目标：在选中的面试笔记中同步这些边界，补充系统规则、历史、动态记忆和工具消息的完整示意，示例明确不是实测请求抓包。
- 可观察结果：逐句能区分“代码已做”“机制上可能”“建议以后做”；不会把缺少端到端验证的内容讲成已确认能力。
- 追问准备：画像优先为什么、何时不适用；为什么后台保存；为什么存下了仍可能没召回；偏好和当前要求谁控制本次回答。
- 边界：本次仅写本文，不批量重写旧笔记；哪些旧文档需要改由用户筛选。变更后可使用有限对照案例说明结果，不编造准确率、吞吐量和延迟改善。

## 4. 保持现状与排除项 🔴 v1

### 4.1 已有机制，不重复立项

| 机制 | 本轮结论 |
|---|---|
| session_id 与 thread_id 对应、会话工作区 | 已有；没有提出替换方案 |
| 图对象缓存上限 32 | 控制可复用对象的内存占用；不改成并发控制，不凭感觉调数值 |
| 执行步数上限 | 已有；没有新的调整需求 |
| SQLite Checkpointer 与 Redis 审批 | 已讨论分工；不改换存储系统，不扩展完整 HITL 重构 |
| 用户画像与事实分类 | 可以保留，是项目的组织方式，不要求统一改名或拆成独立服务 |
| 异步记忆抽取 | 用户当前接受；不是必须改成同步 |
| 5 条注入上限 | 已有；不是要求无限增加条数，也不是马上升级向量库 |

### 4.2 明确排除

- X01：多用户隔离，用户明确不执行。本轮仍按个人 Demo 边界理解，不能据此宣传多人隔离能力。
- 未讨论的新能力：不新建通用评估平台、生产高可用架构、全量权限体系、业务订单/支付接入、全局并发调度、全库数据治理。
- 简单与复杂路由是否统一接入 Memory：本轮仅区分完整 Agent 路径的表述边界，没有形成统一改造决定；不顺带修改快速回答路径。
- 文件 Memory、Wiki 写入等：此前提到过，但本轮没有确定新的优化需求，不顺带重构。
- 不因清单存在而批量调整历史数据、配置或依赖版本。
