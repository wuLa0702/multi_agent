## 1. 背景与目标 🔴 v1

上游《职责边界》已定"谁负责什么"（工具中心 vs 外部配合）。本文解决两件落地的事：

1. **工具中心物理上散在 4 处**，学习与讲述都要绕——收拢为一个目录。
2. **输入侧规范**（校验 / 否定禁止 / lint）怎么落。

**判断标准（贯穿全文）**：**"这个痛点真实存在吗"**，不是"架构图上缺不缺这块"——按后者能无限加层。

## 2. 目录收拢（结构 B） 🔴 v1

### 2.1 现状：一个概念散在 4 处

| 属于工具中心的东西 | 现状位置 | 问题 |
|---|---|---|
| 工具**目录 / 真相源** | `mcp/registry.py` | **放错**——它是全项目工具目录（含 9 个非 MCP 内部工具），非 MCP 专属 |
| 工具**实现** | `agent/tools/` | 与"agent 能力子域"混在一起 |
| **调度 / 校验 / 审计** | `agent/middlewares/` | 与 Agent 自身横切（token/trace/interpreter）混在一起 |
| 开发期**检查脚本** | `backend/scripts/` | ✅ 合理（开发脚本，本就不属 `src/`） |

### 2.2 目标结构

```
backend/src/
├── tools/                       🆕 工具中心（唯一目录）
│   ├── README.md                模块 README（06 规则要求）
│   ├── registry.py              工具目录（真相源）        ← mcp/registry.py
│   ├── gateway.py               🆕 调度中心（校验 + 统一进口）
│   ├── validators.py            🆕 否定禁止收口
│   ├── channels/                🆕 接入协议（三协议并列）
│   │   ├── base.py              ToolChannel Protocol
│   │   ├── mcp.py               入站 server + 出站 client  ← mcp/client.py + mcp/server.py
│   │   ├── rest.py              占位（available() -> False）
│   │   └── a2a.py               占位（available() -> False）
│   └── impl/                    工具实现（按域分包）        ← agent/tools/*
│       ├── search.py            internet_search / fetch_url
│       ├── sandbox.py           run_code / run_command / upload / download
│       ├── skill.py             run_skill_script
│       ├── wiki.py  report.py  hitl.py
├── skills/                      技能本体 + 生命周期（**不属工具中心，不动**）
├── agent/                       只剩编排
│   ├── main_agent.py
│   └── middlewares/             只剩 Agent 自身横切（token_usage / trace / interpreter）
└── ...
backend/scripts/lint_tools.py    🆕 开发期检查脚本
```

### 2.3 三条结构原则

1. **治理在 `tools/` 顶，实现在 `tools/impl/`**——治"工具不该大通铺"（分层归纳）。
2. **三协议并列**：MCP 与 REST / A2A 同级放 `channels/`，**MCP 不特殊**。历史原因给了它一个顶级目录（`mcp/`），**该目录随之消失**。
3. **`skills/` 不进工具中心**：工具中心管"**怎么调**"，`skills/` 管"**技能包怎么装/卸/启停**"。技能本体（SKILL.md + 脚本）是**打包的能力**，不是一个函数。

### 2.4 function / handler / skill 的落位

| 概念 | 落到哪 |
|---|---|
| **function call**（工具实现） | `tools/impl/*.py` |
| **handler**（校验 / 统一进口 / 未来脱敏审计） | `tools/gateway.py` + `tools/validators.py` |
| **skill 调用面**（Agent 怎么用技能） | `tools/impl/skill.py`（即 `run_skill_script`） |
| **skill 管理面**（装/卸/启停/加载 SKILL.md） | `skills/`（不动） |
| **MCP 协议实现** | `tools/channels/mcp.py` |
| **REST / A2A** | `tools/channels/rest.py` / `a2a.py`（占位） |
| **标准 IO（envelope）** | `tools/`（阶段 2，未做） |

### 2.5 迁移清单与影响面

| 源 | 去向 | 处理 |
|---|---|---|
| `mcp/registry.py` | `tools/registry.py` | `git mv` |
| `mcp/client.py` | `tools/channels/mcp.py` | 合并（与 server 同文件） |
| `mcp/server.py` | `tools/channels/mcp.py` | 合并 |
| `agent/tools/*.py` | `tools/impl/*.py` | `git mv` + 按域合并（search/fetch → search.py 等） |
| `agent/middlewares/tool_audit.py` | `tools/` 或保留 | 见 §6 待确认 |
| `mcp/` 目录 | **消失** | — |

**影响面（实测）**：`agent.tools` 18 处 + `mcp.registry` 9 处 + `mcp.client` 4 处 + `mcp.server` 1 处 ≈ **32 处 import**，另需改 3 份文档：
- `.claude/rules/06-structure-optimization.md`（目录表 + 依赖链）
- `CLAUDE.md`（依赖链 `api → agent → {mcp,…}` → `{tools,…}`）
- `docs/架构/多agent项目-架构目录.md`（结构树）

**依赖链变更**：`api → agent → {mcp, sandbox, memory, db}` → **`api → agent → {tools, sandbox, memory, db}`**

## 3. 输入侧落地（1.0–1.4） 🔴 v1

### 1.0 目录收拢（纯 `refactor`，行为不变）

即 §2 全部内容。**先做**，因为后面的新文件（gateway / validators / channels / lint）要直接落在新结构上，**先搬再建只做一次**。

**验收**：`pytest` 全绿 + 32 处 import 全改完 + 无残留 `src.mcp` / `src.agent.tools` 引用。

### 1.1 调度中心 `tools/gateway.py`

- **形态**：第一版 = 一个 `AgentMiddleware`（挂 `awrap_tool_call` 钩子）
- **为什么便宜**：内部工具与外部 MCP 工具**都已被包成 `BaseTool`，都过同一个钩子** → 天然统一，无需分别改造两条路径
- **职责**：调用前统一校验、（未来）脱敏 / 审计 / 埋点
- **校验失败的处置**：**记录日志 + 返回错误给模型**（模型改参数后重试）

**三种失败，三套策略**（按 `06-structure-optimization.md` §4 异常四分类）：

| 失败类型 | 例子 | 适用策略 | 不适用 |
|---|---|---|---|
| **校验失败**（入参不合法） | url 是内网、filename 带 `../` | **只**能：日志 + 返回错误给模型 | ❌ 重试（参数没变必然再失败）❌ 降级（降到哪？）❌ 自修复（替模型改参数=危险） |
| **执行失败**（跑了但挂） | 超时 / 网络断 / 429 | 重试 / 超时 / 降级 | — |
| **输出失败**（结果不合约） | 字段缺 / 单位不对 | 归一 / 自修复（限 LLM 产物） | 重试 |

### 1.2 否定禁止收口 `tools/validators.py`

**现状（含已核实的缺口）**：

| 校验 | 位置 | 接统一审计？ |
|---|---|---|
| `_validate_url` | `fetch_tool.py:35` | ✅ `@security_audit(tool="fetch_url")` |
| `_validate_command` | `sandbox_tool.py:50` | ❌ 未接 |
| `_validate_sandbox_path` | `sandbox_tool.py:69` | ❌ 未接 |
| ⚠️ `run_code_in_sandbox(filename)` | `sandbox_tool.py:95` | ❌ **该参数根本没校验**（违反 CLAUDE.md 核心约束 #5「所有工具调用做路径前缀校验」） |

**规范（6 条）**：
1. 命名：`_validate_<参数名>(值) -> str | None`
2. 契约：`None` = 通过；`str` = 拦截原因（**沿用现有 `security_audit` 契约**）
3. **双写**：
   - **预防**：`args_schema` description 写"禁止…" + JSON Schema `pattern`/`not` → 让模型**事先**少试错
   - **兜底**：`@security_audit` + `_validate_*` → 真犯规时拦住 + 留审计
   - 缺一不可：前者减试错，后者保底 + 留痕
4. 收口：三个校验函数提到 `tools/validators.py`，**全部挂 `@security_audit`**
5. 补漏：`run_code_in_sandbox.filename` 补 `_validate_sandbox_path`
6. 可测：每个校验函数配越权用例（测试规范已有"错误（越权）"要求）

### 1.3 lint 初版 `backend/scripts/lint_tools.py`

**定位**：开发期**静态检查脚本**（不运行代码、不进运行时、不被 Agent 调用）。**不属 `src/`**——放 `backend/scripts/`（已有先例 `check_no_bare_except.py` / `audit_tool_descriptions.py`）。

**只查 3 件静态查得到的事**：

| # | 查什么 | 手段 |
|---|---|---|
| 1 | 工具函数参数都有类型注解 | `ast` 读 `arg.annotation` |
| 2 | 参数名不在歧义词表（`data`/`info`/`value`/`param`/`arg1`/`tmp`…） | 字符串比对 |
| 3 | 工具函数有 docstring | `ast.get_docstring` |

**明确不做**（查不了，靠规则 + review）：该不该用枚举、否定约束写得对不对、粒度划得对不对。
**先不进 CI**，手动 / 提交前跑。

**连带修复**：`backend/scripts/audit_tool_descriptions.py` 读的是 `getattr(tool, "description", "")`——改前 `TOOL_REGISTRY` 值是普通函数（无 `.description`）→ **打印全 0（脚本本就是坏的）**；阶段 0 后值是 `ToolSpec`（有 `.description`）→ 打印手写短描述。**两个版本都没读对**：LLM 真正看到的是**工具函数的 docstring**。本次一并改为读 docstring。

### 1.4 通道占位 `tools/channels/rest.py` / `a2a.py`

**只落骨架**，`available() -> False`。

> ⚠️ **占位必须显式失败，不得静默成功**：占位若返回 `True`，上层会以为"这条路走通且通过了"，实际是"压根没实现"——校验类接口上这就是**静默放行的安全洞**。

## 4. 不做清单（防过度设计） 🔴 v1

| 不做 | 原因 | 触发条件（出现才做） |
|---|---|---|
| **参数归一**（原 1.3） | 11 个工具**没有任何时间参数**，无消费场景 | 出现第一个真实归一场景 |
| **错误处理策略链**（抽象类/责任链） | 阶段 1 真正新增的策略只有 1 个（校验），撑不起一条链 | **第 2 个策略需与校验共用同一编排**时 |
| **REST / A2A 实现** | 无需求（现只有 MCP 在用） | 有第二个协议真要用 |
| **lint 进 CI / 扩项** | 11 个工具，人肉 review 更快；写 lint 在此规模是负收益 | 工具数 > 20 |
| **元数据其余 5 字段的消费** | 阶段 0 落的元数据里只有 `domain` / `mount_main` 真被消费 | 阶段 4 编排侧（重试/降级/审批） |

**阶段 0 的一处自认**：`ToolSpec` 的 `is_idempotent` / `risk_level` / `size` / `fallback_to` / `requires_approval` 目前是**死数据**（无人消费）——属提前抽象，记此备查。

## 附录 A 讨论问答留痕（2026-10-14） 🔴 v1

> 用途：改动代码前的讨论结论留痕，供后续审核（"为什么这么定"不丢失）。

### Q1 校验失败的处理策略

> **问**：初版校验失败只记日志；错误处理应支持多种策略（重试/降级/超时/格式自修复）？要不要写抽象类拆分？

**答**：三种失败三套策略（校验 / 执行 / 输出）。校验失败按项目异常四分类属"**不可重试（参数）**"，只能日志 + 返回错误给模型。形态该是**策略链**而非抽象类（抽象类会导致类爆炸 + 顺序被继承锁死）。

**结论**：初版 = 日志 + 返回错误给模型；策略链**不现在做**。

**归属**：阶段 1（校验）｜ **状态**：✅ 已定 ｜ **触发条件**：第 2 个策略需与校验共用编排

### Q2 "内部工具"指什么？调度中心？

> **问**：内部工具指什么？外部/内部工具都通过调度中心调用？A2A / REST / MCP 都是通过调度中心实现？

**答**：内部工具 = 我们自己写在 `agent/tools/` 的函数；外部工具 = 从别人 MCP server 接进来的。**两者已被包成 `BaseTool`、都过同一个 `awrap_tool_call` 钩子** → 调度中心建在中间件层天然统一两者。三协议是**入口**，调度中心是**共同内核**（非"用调度中心实现 A2A"）。注意 MCP 双向：入站 `调度中心 → server`、出站 `client → 调度中心`。

**结论**：方向对（标准 tool gateway）；阶段 1 只把 MCP 做实，协议扩展留后。

**归属**：阶段 1（1.1）｜ **状态**：✅ 已定

### Q3 lint 是什么？AST？

> **问**：lint 我不理解是什么？ast 是抽象结构树么？我没经验，你有什么意见。

**答**：AST = 抽象语法树 ✅。lint = 静态检查（不运行代码）；项目已有先例 `check_no_bare_except.py`（AST 扫描）。可查：类型注解 / 歧义命名 / docstring；查不了：该不该枚举、否定约束对不对。意见：11 个工具时人肉 review 更快，**先不写**，但用户明确要求 → **给初版（3 项）**。

**结论**：给初版，放 `backend/scripts/`，不进 CI。

**归属**：阶段 1（1.3）｜ **状态**：✅ 已定

### Q4 三个否定禁止收口

> **问**：对于三个否定禁止，请收口成统一规范。

**答**：核实现状——3 个校验函数**只有 1 个接了统一审计**（`_validate_url`），另 2 个未接；且 `run_code_in_sandbox(filename)` **完全没校验**（违反 CLAUDE.md 核心约束 #5）。

**结论**：收口进 `tools/validators.py` + 统一挂 `@security_audit` + 补漏 + 双写（预防 + 兜底）。

**归属**：阶段 1（1.2）｜ **状态**：✅ 已定

### Q5 为什么工具中心散在好几个目录？

> **问**：为啥调度中心要放 middlewares？为什么不是工具中心专门放一个文件夹？感觉拆到了好几个地方。我是新手，理解可能有问题。

**答**：**用户是对的**。工具中心物理上散在 4 处，且 `mcp/registry.py` 是**既有错位**（它是全项目工具目录，非 MCP 专属，只因"未来 MCP 化"预留而放在 mcp/）。散落的三个历史原因：① registry 历史预留；② 实现按"agent 能力子域"归类；③ 调度/审计是 langchain 中间件。**纠正**：③ 只是**惯例**不是规则——`AgentMiddleware` 放任何目录都能注册，**目录归属是可选的**。

**结论**：采纳结构 B（工具中心收拢为一个 `tools/` 目录）。

**归属**：阶段 1（1.0）｜ **状态**：✅ 已定

### Q6 `mcp/` 是不是多余？function / skill 放哪？

> **问**：这里的 mcp 管什么用？是多次一举么？function 和 skill 未来放在哪里呢？

**答**：`mcp/` 管出站 client + 入站 server。按结构 B 彻底版**应并入 `tools/channels/mcp.py`**——否则 `tools/channels` 与 `mcp/` 就是"一个概念两个地方"（正是用户一直在抱怨的问题）。三协议并列才对称，MCP 不该特殊。function → `tools/impl/`；handler → `gateway.py` + `validators.py`；skill 拆两半：**调用面** `tools/impl/skill.py`、**管理面** `skills/`（不动）。

**结论**：`mcp/` 目录消失；`skills/` 不动。

**归属**：阶段 1（1.0）｜ **状态**：⏳ 待用户确认（§6）
