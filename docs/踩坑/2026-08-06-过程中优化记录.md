## 2. 优化记录（追加式）

### 2026-08-04 #1：chat.py 超长函数拆分

- **问题**：`chat_stream` 171 行（>160 必须拆）、`event_stream` 132 行（>80 考虑拆）——
  顶层方法体超长、耦合严重（用户评审发现）
- **处理**：
  - `_resolve_session`（会话创建/校验）、`_prepare_new_messages`（新消息准备）、
    `_build_error_event`（错误事件）、`_save_memory_in_background`（记忆后台写入）、
    `_event_stream`（SSE 生成器提为模块级）——全部 ≤80 行
  - 全项目 AST 扫描确认：backend/src 无 >80 行函数
- **规则沉淀**：`.claude/rules/01-coding-style.md` 函数长度铁律（>80 考虑拆、>160 必拆）

### 2026-08-04 #2：多对话并发是否需要双 model 实例？

- **问题**：担心多个对话同时进行导致模型调用阻塞（用户疑问）
- **结论**：**不需要双实例**。`get_chat_model()` 是工厂（每次调用新建 ChatOpenAI 实例，
  非单例）；ChatOpenAI 基于 async httpx，同一进程多协程并发调用安全不阻塞。
  并发控制已有 `_stream_semaphore(4)` 限流对话流（计划文档 C.1-2）

### 2026-08-04 #3：记忆写入是否阻塞？

- **问题**：`extract_memory_fact`/`save_conversation_memory` 是否同步阻塞（用户疑问）
- **结论**：函数本身是 async（`await llm.ainvoke` / `await store.aput`）**不阻塞事件循环**；
  但真问题是它们在 SSE done 事件**之前串行执行**——一次额外 LLM 抽取调用拖慢流时长
  （用户感知 done 变慢）
- **处理**：记忆写入移出 SSE 流——`asyncio.create_task(_save_memory_in_background(...))`
  fire-and-forget（内部全容错不冒泡），done 事件先发不受拖慢
