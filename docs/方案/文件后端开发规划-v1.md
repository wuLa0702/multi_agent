## 1. 总：现状分析与目标

### 1.1 现状盘点（2026-08-04 实测）

| 能力 | 现状 | 代码证据 |
|------|------|---------|
| **REST 三接口** | ✅ 已落地（P2 拍板：独立上传接口）：POST 上传 / GET 下载 / DELETE 删除；10MB 限制；UUID 防枚举；文件名 sanitize | `api/uploads.py` |
| **路径支撑** | ✅ `get_uploads_dir()`：`data/uploads/`，路径自适应（云端 /data/uploads） | `core/paths.py:92` |
| **路由挂载** | ✅ `include_router(uploads_router)` | `api/main.py` |
| **元数据持久化** | ❌ **无 files 表**——文件信息只藏在磁盘文件名 `{file_id}_{safe_name}` 里（隐式契约，无法 list / 统计 / 会话关联 / 孤儿清理） | `api/uploads.py` 无 DB 引用 |
| **服务层** | ❌ 业务逻辑全在路由内：`write_bytes` / `glob` / `unlink` 直接操作文件系统，不可单测 | `api/uploads.py` |
| **测试覆盖** | ❌ test_api/ 下无 uploads 测试（仅 chat/health/providers/sessions） | `backend/tests/test_api/` |
| **Agent 读取** | ❌ 上传后**无人能读**——无工具可让 Agent 访问上传文件，文件是"死数据" | `mcp/tools/` 仅 search.py + sandbox_tool.py |
| **生命周期** | ❌ 无 list 接口、无孤儿清理、无配额、无 mime 记录 | — |

**结论：上传通道已通，但文件是"死数据"**——REST 层能存取，元数据缺失导致无法管理，Agent 无法消费，文件后端的核心价值（人传文件 → Agent 读取 → 对话中引用）尚未打通。

### 1.2 为什么重要

1. **文件后端的本质**：上传本身不是目的。多 Agent 产品的文件语义是"用户传文件 → Agent 读取内容 → 在对话中引用/处理"。当前链条断在最后一段
2. **工程化债**：靠 `{file_id}_{safe_name}` 文件名反查是脆弱隐式契约——无法回答"这个会话传过哪些文件"、"总共占了多少空间"、"哪些是孤儿"
3. **学习点（面试导向）**：文件生命周期管理（写盘 → 元数据 → 删除的一致性顺序）、分层边界（路由瘦身 + 业务域 + DAO）、工具注册即能力暴露（呼应架构 §2.1"手/脑/下属"对照）

### 1.3 范围与边界

| 在本计划内 | 不在本计划内（明确排除） |
|-----------|-------------|
| files 表元数据化 + DAO（A） | 鉴权/文件归属（auth ⏳ 演进预留，表留 session_id 挂点即可） |
| 业务域层 `src/files/service.py`（B） | 病毒扫描 |
| API 层瘦身 + list 接口（C） | 分片/断点续传（10MB 上限内用分块写盘足够） |
| Agent 读取工具（D） | OCR / 图片解析 / PDF 文本抽取（工具先返回元数据，解析按需后置） |
| 全套测试，先红后绿（E） | mime 强制白名单（记录 mime 不强制） |
| — | 配额与孤儿清理（M2 演进，本期只保证删除一致性） |

## 2. 分：开发计划

### A. 元数据层：files 表 + DAO

**核心设计变更：磁盘文件名只含 file_id，用户输入不再进文件名。**

现状 `{file_id}_{safe_name}` 把用户输入拼进磁盘名，sanitize 只能"截断 120 字符"（丢信息）。改为**磁盘名纯 `{file_id}`**（v1.1 评审定稿：无后缀、无任何用户输入成分），**原名完整进元数据**——防穿越从"尽量处理"变成"物理隔离"，截断问题消失，下载文件名由元数据 original_name 提供。

```sql
-- schema.py 追加（CREATE IF NOT EXISTS，与现有表同风格）
CREATE TABLE IF NOT EXISTS files (
    id            TEXT PRIMARY KEY,      -- file_id（UUID hex，沿用现语义）
    original_name TEXT NOT NULL,         -- 原始文件名（完整保存，不再截断）
    size          INTEGER NOT NULL,      -- 字节数
    mime          TEXT NOT NULL DEFAULT '',  -- 上传时 content_type，仅记录不强制
    session_id    TEXT,                  -- 可空：先全局，后接会话语义（auth 挂点）
    created_at    TEXT NOT NULL,
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE SET NULL
);
```

> **评审修正（v1.1）**：`stored_name` 列删除——磁盘名恒等于 `id`（`f"{file_id}"`），
> 存这一列是与 id 恒等的冗余；由 service 层从 id 推导磁盘路径，HTTP 下载文件名用
> `original_name`（与磁盘名解耦）。YAGNI：不为不存在的"未来磁盘布局变更"预留列。

- `db/file_repository.py`：照 `db/repository.py` DAO 模式（参数化 SQL、行工厂、`_now_iso()`、写操作 commit），提供 `create / get / delete / list_by_session`
- 迁移：新表无需 ALTER 迁移（`init_schema` 幂等 CREATE 即可）

### B. 业务域层：`src/files/service.py`

参照 `src/skills/`（marketplace.py + installer.py）的业务域落地模式——依赖单向 `api → files → {db}`，不违反分层。

- `upload(file, session_id)`：**分块写盘**（1MB chunk 流式读，替代 `await file.read()` 全量进内存）+ 元数据入库；10MB 业务上限保留；**分块累计超限 → 立即截断、删除已写半截文件、返回 FILE_TOO_LARGE**（不留残缺文件，v1.1 评审补充）
- `get(file_id)`：查元数据 → 返回磁盘路径（供 FileResponse，filename 用 original_name）
- `delete(file_id)`：**一致性顺序：先删元数据，后删磁盘文件**；磁盘删失败记日志不抛（元数据已删，剩余是孤儿，M2 清理兜底）
- `list(session_id=None)`：files 表查询

### C. API 层瘦身

- `uploads.py` **接口语义保持不动**（POST/GET/DELETE 已 P2 拍板，不推翻），路由逻辑委托 service
- POST 新增**可选** multipart 字段 `session_id`（v1.1 评审拍板：不传 = 全局文件，行为与现状完全一致；传了 = 文件挂到会话——向后兼容，不推翻 P2 协议）
- GET `{file_id}` 下载：查表拿 `original_name` 作为 HTTP filename（v1.1 评审修正：下载文件名从"截断 120 字符的 safe_name"升级为完整原名，行为改进非推翻）
- 新增 `GET /v1/uploads?session_id=xx`：list 接口（**评审定案放 M0**——files 表已建，DAO 顺手带 `list_by_session`，测试一并覆盖，成本趋近于零；响应用 ListResponse 包装，遵循 `status` 字段惯例）

### D. Agent 读取工具（核心价值）

- `mcp/tools/file_tool.py`：`read_uploaded_file(file_id, max_chars)` —— 文本文件返回内容（截断到 max_chars）；二进制/超限返回元数据 + 大小（解析后置，范围控制）
- `mcp/registry.py` 登记（照 search.py / sandbox_tool.py 模式）
- 打通后：对话"看我上传的 xx" → Agent 调工具读内容作答

### E. 测试（先红后绿）

| 文件 | 覆盖 |
|------|------|
| `test_api/test_uploads.py` | 上传成功 / 超 10MB / 缺文件名 / 非法 file_id（防枚举）/ 下载 404 / 删除幂等 / list 按 session 过滤 / **中文文件名下载原名恢复**（覆盖 v1.1 GET original_name 行为改进） |

## 3. 总：里程碑、风险与学习点

### 3.1 里程碑

| 里程碑 | 内容 | 验收 |
|--------|------|------|
| **M0**（P3 级） | A + B + C + E | 接口兼容重构完成，pytest 全绿（先红后绿） |
| **M1**（P3 级） | D Agent 读取工具 | 对话中 Agent 能读上传文本文件内容 |
| **M2**（演进，不排期） | 孤儿清理定时任务、配额、mime 白名单、前端 list 展示 | 按需启动 |

### 3.2 风险与取舍

| 风险 | 缓解 |
|------|------|
| 磁盘与元数据不一致（删除中途崩） | 先删元数据后删磁盘；删除失败记日志；M2 启动扫描补孤儿 |
| M0 重构引入回归 | 接口语义冻结 + 全套新测试兜底；重构期间先红后绿 |
| 二进制文件 Agent 读不了 | 工具降级返回元数据，明确"解析后置"，不假装支持 |
| files 表与现有库兼容 | CREATE IF NOT EXISTS 幂等；session_id 可空不破坏旧数据 |
| 旧磁盘文件（`{file_id}_{safe_name}` 命名）M0 切表后查不到 | ✅ **实测排除**（v1.1 评审）：`data/uploads/` 为空，无存量文件，零迁移需求；后续文件从 M0 起全走新布局 |

### 3.3 学习点（面试可讲）

1. **文件生命周期一致性**：为什么先删元数据后删磁盘（失败方向更安全：磁盘孤儿可清理，元数据孤儿不可恢复）
2. **分层职责**：路由（协议）→ 业务域（编排）→ DAO（数据），呼应 skills 域先例
3. **能力暴露 = 工具注册**：文件从 REST 资源升级为 Agent 可消费的工具，架构 §2.1"手/脑/下属"对照的实际应用

## 4. 自省（规划质量审视）

1. **依据性**：每条缺口均有代码证据（uploads.py / paths.py / schema.py / repository.py / main.py / mcp/tools/ 实测），无拍脑袋假设；引用"已有模式"前均 Read 原文（schema.py 建表风格、repository.py DAO 写法、skills 业务域先例）
2. **不推翻拍板**：P2 已评审定稿的接口语义（POST/GET/DELETE + file_id）冻结不动，M0 只加层不改协议
3. **范围克制**：明确排除鉴权/病毒扫描/分片上传/OCR/mime 白名单——学习项目不堆复杂度，排除项都给了理由
4. **未决点（v1.1 评审全部拍板，见 §2 C）**：
   - session_id 关联语义 → **POST 加可选 session_id 字段**（不传 = 全局，向后兼容），表列可空 + FK ON DELETE SET NULL
   - list 接口 → **放 M0**：files 表已建、DAO 顺手带 `list_by_session`、测试一并覆盖，成本趋近于零；后置 M2 反而要二次返工
5. **诚实声明**：规划未覆盖前端上传交互（前端领域，非本后端计划）；未覆盖大文件传输方案（>10MB 暂不开放，分块续传明确排除）
