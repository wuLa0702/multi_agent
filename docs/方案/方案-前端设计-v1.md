## §1 定位：旁观者 + 决策者

承接 `方案-后端接口定义-v1.md`（契约真相源）与 `方案-前端目录结构-v1.md`（评审稿，本文档修订对齐契约）。

**项目重后端** → 前端身份明确：

- **旁观者**：Agent 内部状态（工具调用、子 Agent 委派、压缩）通过 SSE 事件流「直播」给前端，前端只渲染，不调度。
- **决策者**：前端唯一的决策权 = 审批弹窗（approve/reject）。挂起时后端已持久化中断，前端可以放心关浏览器重来。

前端三件事：**发起对话、展示过程、做审批决策**。

## §2 接口契约映射（8 接口 → 前端模块）

| 后端接口（契约 §2） | 前端消费方 | 触发时机 |
|------|------|------|
| `POST /v1/chat/stream` | `lib/api/sse.ts` ★ | 发送消息 / 审批后恢复（resume_run_id） |
| `POST /v1/chat/approve` | `chatStore.approve/reject` | 审批弹窗点击 |
| `GET /v1/sessions` | `sessionStore.loadList` | 侧栏挂载 + done 后刷新 |
| `POST /v1/sessions` | `chatStore.ensureSession` | 首次发送（后端自动建，前端无感） |
| `PATCH /v1/sessions/{id}` | 侧栏改名交互 | 用户重命名 |
| `DELETE /v1/sessions/{id}` | 侧栏删除 | 用户删除（confirm） |
| `GET /v1/sessions/{id}/messages` | `chatStore.loadHistory` | 切换会话（cursor 翻页） |
| `GET /v1/health` | 顶栏状态点 | 挂载 + 30s 轮询 |

**前端不感知**（重后端内聚）：MCP 工具注册、记忆读写、压缩策略、子 Agent 拓扑、沙箱执行——只通过 SSE 事件类型感知过程。

## §3 技术决策（含自省修正）

### 3.1 ★SSE 通道：fetch + ReadableStream，放弃原生 EventSource

| 项 | 决策 | 理由 |
|----|------|------|
| 通道 | **fetch POST + ReadableStream 手工解析 SSE 帧** | 契约 `POST /v1/chat/stream` 是 POST + JSON body；**EventSource 仅支持 GET**，无法携带 session_id/message/resume_run_id |
| 取消 | AbortController | 用户取消 / 切会话需中断流；EventSource 只能 close 不能携带请求体，二者皆不可行 |
| 帧解析 | 按 `\n\n` 分帧 → 提取 `data:` 行 → JSON.parse | SSE 帧格式简单（契约 §5.1 单 data 行），手写解析 <30 行，学习项目讲得清 |

> 🔧 **自省修正 1**（对比目录结构 v1 §1「原生 EventSource（封装）」）：v1 评审稿写于契约定稿前，未发现 EventSource 的 GET-only 限制。契约 POST 设计正确（body 承载 session_id/message 二选一语义，URL 传参不优雅且有长度风险），**前端适配而非契约让步**。手写 SSE 解析器封装为 `sse.ts`，对外暴露 `streamChat(req, callbacks)` 接口，内部细节不外泄。

### 3.2 其余技术决策（承接目录结构 v1 定稿）

| 项 | 决策 | 备注 |
|----|------|------|
| 框架 | React 19 + Vite + TS 严格模式 | 决策 #5 |
| UI | shadcn/ui + Tailwind 4 | 复用 wiki-ui-v2 |
| 状态 | zustand（chatStore/sessionStore） | 对话流单向，zustand 够用；**不用 TanStack Query 管 SSE**（流式事件是 push 不是 query，Query 的缓存模型不适配） |
| 路由 | react-router v7 | 仅 1 页：`/`（ChatPage）；历史在侧栏，**不做独立 HistoryPage**（目录结构 v1 开放问题 1 定稿：MVP 减负） |
| 图谱 | vis-network | 复用 wiki-ui-v2 配置 |
| 流式 markdown | 先收集后渲染 + 200ms 节流 | 目录结构 v1 开放问题 2 定稿：token 粒度渲染开销大；`token.text` 追加到 buffer，节流期间一次性 render |

## §5 SSE 事件 → 前端状态机（核心）

### 5.1 流状态机（chatStore.streamStatus）

```
        send / resume
idle ──────────────────► connecting
connecting ──start 事件──► streaming
streaming ──approve 事件──► awaiting_approval（后端已挂起，连接已关）
streaming ──done / error──► idle
connecting/streaming ──用户取消──► idle（AbortController.abort）
awaiting_approval ──用户 approve/reject──► 调 approve 接口 → 202 → send(resume_run_id) → connecting
```

关键：`awaiting_approval` 是**持久化挂起**（后端 interrupt 落库），不是前端临时态——刷新页面后仍可通过历史恢复（见 §7.4）。

### 5.2 事件处理表（对齐契约 §5.2，8 类精确动作）

| 事件 | 前端动作 |
|------|---------|
| `start` | `resumed=false` → 清空本轮工具/子 Agent 面板缓冲，streamStatus=streaming；`resumed=true` → 只重置审批弹窗与增量缓冲，**不清空面板**（挂起前的节点保留） |
| `token` | append 到当前 assistant 消息 buffer；节流渲染 |
| `tool_call` | 按 `call_id` 幂等 upsert 到 toolCalls map：`running` → 面板新增（arguments 展示）；`success/error` → 更新 status + result（截断展示，见 §8.2 风险 3） |
| `subagent` | `start` → AgentTree 追加节点（name）；`end` → 节点标注完成 + summary 气泡 |
| `approve` | **弹 ApproveDialog**（tool_name + arguments + message + run_id），streamStatus=awaiting_approval；同时持久化 run_id 到 localStorage（刷新可恢复，§7.4） |
| `summarize` | 对话流插入系统气泡「上下文已压缩（移除 N 条）」+ summary 折叠展示 |
| `done` | streamStatus=idle；刷新会话列表（updated_at 变化）；**不重新拉历史**（本地已完整）——消息 id 对齐问题见 §8.2 风险 4 |
| `error` | retryable → 提示 + 建议重发；非 retryable → 提示原因；streamStatus=idle |

### 5.3 sse.ts 接口设计

```ts
interface StreamCallbacks {
  onEvent(e: SSEEvent): void     // 按 e.type 分发，组件层不感知帧解析
  onClose(): void                // done/error/网络断开后
  onNetworkError(): void         // fetch 层异常（区别于业务 error 事件）
}

function streamChat(req: ChatStreamRequest, cb: StreamCallbacks, signal: AbortSignal): void
```

- 帧解析：`ReadableStream` reader 逐 chunk 累积 → 按 `\n\n` 切帧 → 取 `data: ` 行 → `JSON.parse` → 校验 `type` 字段存在 → 分发。
- 网络断开（fetch reject 且非 abort）→ `onNetworkError` → 前端提示"连接中断"，**不自动重连**（Agent 执行可能已推进，盲目重连会重复执行；恢复只走 resume 语义）。

## §6 zustand 状态设计

```ts
interface ChatState {
  sessionId: string | null          // 当前会话（首条消息后由 start 事件带回）
  messages: Message[]               // 对话流（含 assistant 流式消息）
  toolCalls: Record<string, ToolCall>  // call_id → 工具调用（三栏数据源）
  agentTree: AgentNode[]            // 主→子链
  streamStatus: "idle" | "connecting" | "streaming" | "awaiting_approval"
  pendingApproval: Approval | null  // {run_id, call_id, tool_name, arguments, message}
  abortRef: AbortController | null  // 当前流的取消句柄

  send(text: string): Promise<void>            // ensureSession → streamChat(新消息)
  resume(runId: string): Promise<void>         // streamChat(resume_run_id)（approve 202 后）
  approve(): Promise<void>                     // POST /v1/chat/approve {run_id, action:"approve"}
  reject(note?: string): Promise<void>         // POST approve {action:"reject", note}
  cancel(): void                               // abort 当前流 → idle
  loadHistory(sessionId: string): Promise<void>  // GET messages → 渲染 + 置 current
}
```

**单向数据流**：SSE 事件 → store action（唯一写入口）→ 组件订阅。组件不直接调后端。

## §7 关键流程时序

### 7.1 发送新消息

```
InputBar.send(text)
 ├─ sessionId 为空 → POST /v1/sessions → sessionStore 缓存（前端无感）
 ├─ streamChat({session_id, message:text}, cb, abort)
 ├─ start → 清本轮面板缓冲 → streaming
 ├─ token×N → 节流渲染 assistant 气泡
 ├─ tool_call / subagent → 面板直播
 ├─ done → idle + 刷新会话列表
 └─ error → 提示（retryable 给重发按钮）
```

### 7.2 审批（决策者时刻）

```
approve 事件 → 弹窗（显示 tool_name/arguments/message + run_id）
用户点「通过」 → POST /v1/chat/approve {run_id, action:"approve"}
 ├─ 202 → 弹窗关闭 → resume(run_id) → 新流 connecting
 ├─ 404 RUN_NOT_FOUND / 400 NOT_PENDING → 弹窗提示"该审批已失效"，刷新历史
 └─ 5xx → 弹窗保留 + 重试按钮（approve 幂等：重复提交返回 NOT_PENDING，前端据此不重发 resume）
```

### 7.3 取消 / 切会话

- 取消：`abort()` → 后端 fetch 连接中断（后端应感知 disconnect 停止执行——**实现层待确认项 §8.3**）
- 切会话：先 abort 当前流 → `loadHistory(target)` → 渲染历史

### 7.4 刷新页面后的审批恢复

```
刷新 → sessionStore 恢复列表 → 检测 localStorage.pendingRunId
 ├─ 有 → 提示「上次有一个待审批操作」→ 点击 → resume(run_id)
 │     ├─ start{resumed:true} → 继续（挂起前节点已从历史渲染）
 │     └─ 404 RUN_NOT_FOUND → 已失效，清 localStorage 提示
 └─ 无 → 正常进入会话
```

（`pendingRunId` 在 approve/done/error 三处清理。）

## §8 自省

> 本节目的是**批判性审视**：①契约在前端视角下的问题（反哺后端）②设计自身薄弱点 ③与目录结构 v1 的差异 ④未决项。

### 8.1 对后端接口契约的前端视角审查（反哺契约 v2）

| # | 发现 | 严重度 | 建议 |
|---|------|--------|------|
| 1 | **EventSource 不支持 POST**（§3.1 已修正） | 高（已解决） | 契约保持 POST 不变，前端 fetch 流式适配——**契约无需改** |
| 2 | `approve` 202 语义 + 前端重连存在竞态窗口：202 返回时后端可能尚未进入可恢复态 | 中 | 契约 v2 补充：resume 连接建立后若 run 未就绪，后端**在流内发 `start{resumed:true}` 前可先等待**（连接保持，首个事件延迟）；前端重连带 10s 超时，超时 → 提示重试 |
| 3 | `tool_call.result` 截断 4KB：三栏面板无法看完整结果 | 低 | 前端展示截断 + 「查看完整结果」折叠（存于组件内）；如需后端完整结果，契约 v2 可加 `result_full: bool` 开关——MVP 不做 |
| 4 | **done 后消息 id 对齐**：流式消息本地渲染 id=None，会话列表刷新后重进会话会重复渲染 | 中 | MVP 方案：done 后**静默重拉一次 messages** 替换本地流（以库为准）；契约无需改 |
| 5 | `summarize.keep_from_message_id` 为 int|null：前端折叠历史需在 messages 里定位该 id | 低 | 找不到时降级为「摘要气泡置顶」展示，不阻塞 |

### 8.2 设计自身薄弱点与风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 手写 SSE 帧解析边界（半帧/多帧/粘包） | 流中断 | 帧解析器单测覆盖：分片读取、多事件一 chunk、空行容错（测试策略 §9） |
| token 节流渲染丢尾帧 | 末尾文字不显示 | 流结束（done）强制 flush 一次 |
| AbortController 中止后后端是否停止执行未定 | 取消后 Agent 可能继续跑完（浪费 token） | 契约 v2 待确认项：后端检测连接断开 → 取消 run（实现层决策） |
| AgentTree 节点数增长（长会话） | 图谱卡顿 | vis-network 只保留当前 run 的链（done 后收敛为摘要节点） |
| approve 弹窗期间用户刷新 | 审批丢失 | §7.4 localStorage pendingRunId 恢复机制 |
| 多 tab 并发操作同一会话 | 状态互相覆盖 | MVP 不锁，文档标注「单 tab 使用」限制 |

### 8.3 与目录结构 v1 的差异修订（本文档替代其评审稿）

| 项 | 目录结构 v1 | 本文档 | 原因 |
|----|------------|--------|------|
| SSE 通道 | 原生 EventSource | **fetch + ReadableStream** | EventSource GET-only，无法 POST body（§3.1） |
| 事件 payload | 旧字段（delta/request_id） | 契约 v1 精确字段（text/run_id/call_id/status/resumed） | 对齐 `方案-后端接口定义-v1.md` |
| 状态管理 | zustand + TanStack Query | **仅 zustand** | SSE 是 push 不是 query，Query 缓存模型不适配 |
| 历史页 | 独立 HistoryPage（可选） | **侧栏内完成**，无独立页 | 开放问题 1 定稿：MVP 减负 |
| 断线重连 | 3s 指数退避自动重连 | **不自动重连**，走 resume 语义 | 盲目重连会重复执行 Agent（§5.3） |
| 审批挂起 | 未设计持久化 | **awaiting_approval 持久化** + 刷新恢复（§7.4） | 契约 approve/resume 双模式的新能力 |

### 8.4 未决项（评审时定）

| # | 事项 | 建议 |
|---|------|------|
| 1 | 取消（abort）后后端是否真正停止执行 | 契约 v2 加：后端检测断连取消 run（P1） |
| 2 | resume 首事件延迟窗口（8.1 发现 2） | 契约 v2 明确「start 可延迟」语义（P1） |
| 3 | done 后静默重拉历史（8.1 发现 4） | MVP 直接做，不升级契约（P0） |
| 4 | AgentTree 完成后收敛策略 | MVP 保留全链，性能问题后置（P2） |

# A：未决项回答（2026-08-03 评审回复）

1. **取消（abort）后后端是否真正停止执行**：建议契约 v2 落地「后端检测断连 → 取消 run」（避免用户取消后 Agent 继续烧 token）。前端侧无改动需求：`cancel()` 已发 AbortController 并置 idle，等契约 v2 + 后端实现后联调验证即可。
2. **resume 首事件延迟窗口**：前端 resume 已带 10s 超时（超时提示重试），契约 v2 明确「start 可延迟」语义后仅需微调阈值，当前实现可维持，不阻塞。
3. **done 后静默重拉历史**：✅ **已实现**（commit `e8df73f`）——done 后以库为准静默重拉 messages 替换本地 id=null 流；含竞态保护（重拉期间用户切换会话不覆盖）与失败静默降级；单测 3 例覆盖（替换/失败降级/竞态），全量 38/38 + tsc + build 通过。
4. **AgentTree 完成后收敛策略**：维持 MVP 结论——保留全链（当前 run 完整调用链）。收敛策略等长会话实测出现卡顿再做（P2 后置），vis-network 按 run 收敛为摘要节点为候选方案。
