## 1. 总：背景、目标与范围

### 1.1 背景

前端已完成 v3.0 里程碑（三栏/四栏布局、主题、动效、市场、设置、输入体验），并已对接
核心真实接口：**对话流（SSE）、审批、会话 CRUD、模型列表、Skill 市场**。

但前端在开发过程中（基于当时后端已有能力）对以下功能使用了 **mock 数据**：
- 会话列表：无摘要、无自动标题、置顶仅 localStorage
- 设置页：MCP 管理为静态列表、系统配置开关无持久化
- 输入栏：上下文用量固定值、附件仅记文件名、代理模式不传后端
- 市场页：「全部」分类由前端合并两类

### 1.2 目标

把 **8 项 mock 功能全部转为真实后端接口**，形成完整能力闭环：
```
前端 v3.0 UI 层（已交付）
        ↓ 去 mock
后端接口补齐（本计划）→ 会话体验 / 设置管理 / 增强功能
```

### 1.3 范围与边界

| 在本计划内 | 不在本计划内（后续） |
|-----------|-------------------|
| 会话三件套（摘要/自动标题/置顶） | 用户体系与鉴权（单用户项目） |
| MCP 管理 / 系统配置 / 日志上报 | 向量库长时记忆 |
| 代理模式透传 / 上下文用量 / 附件 | LangGraph 手写主图演进 |
| Skill 分类聚合 | 多租户 / 云上部署细节 |

### 1.4 与现有架构的关系

- 依赖单向不变：`api → agent → {mcp, sandbox, memory, db}`
- 全部改动落在：`api/`（新路由）+ `db/`（schema/DAO）+ 少量 `core/`、`skills/`
- 复用既有模式：`repository.py` DAO 风格、`_migrate_*` 迁移函数、`McpClientManager.reload()` 热刷新

## 2. 分：分阶段开发计划

### 阶段一 P0 — 会话体验闭环（3 项，优先交付）

> 目标：会话列表从「占位信息」升级为「可读可管」，改动小、见效快。

#### 2.1 会话摘要（last_message）

| 项 | 内容 |
|----|------|
| **现状** | 列表第二行只有时间；后端无摘要字段 |
| **接口** | `GET /v1/sessions` 每个 Session 增加 `last_message: str \| null`（最后一条 user/assistant 消息截断 ≤50 字） |
| **实现** | `db/schema.py` 无需改表；`db/repository.py` `list_sessions` SQL 加 LEFT JOIN 取最新消息；`schemas/session.py` 加字段 |
| **前端** | SessionList 第二行渲染摘要（两行布局已预留，后端有值自动显示） |
| **验收** | 列表显示每会话最后消息摘要；空会话显示空 |

#### 2.2 会话自动标题

| 项 | 内容 |
|----|------|
| **现状** | 创建即「新会话」，永不更新；用户需手动改名 |
| **接口** | 无新接口——对话落库时自动更新 |
| **实现** | `api/chat.py` 首条 user 消息落库后，若标题仍为默认值「新会话」→ 截取消息前 20 字更新（`repository.update_session_title` 复用） |
| **前端** | 无改动（列表实时刷新标题） |
| **验收** | 新会话首条消息后标题自动变为内容摘要；用户手动改名不被覆盖 |

#### 2.3 会话置顶（is_pinned）

| 项 | 内容 |
|----|------|
| **现状** | 前端 localStorage mock（`multi-agent.pinned-sessions`），刷新不丢但后端不可见 |
| **接口** | `sessions` 表加 `is_pinned INTEGER DEFAULT 0`；`GET /v1/sessions` 返回该字段且**置顶优先排序**；`PATCH /v1/sessions/{id}` body 支持 `is_pinned` |
| **实现** | `db/schema.py` 加列 + `_migrate_sessions_columns`（复用 `_migrate_mcp_servers_columns` 模式）；repository 增 `update_pinned`；列表排序 `is_pinned DESC, updated_at DESC` |
| **前端** | `usePinnedSessions` 改调后端（localStorage 降级兜底）；置顶分组逻辑不变 |
| **验收** | 置顶跨刷新/跨设备保持；置顶会话排最前 |

### 阶段二 P1 — 设置与管理（3 项）

> 目标：设置页全部去 mock，管理能力真实生效。

#### 2.4 MCP 管理 API

| 项 | 内容 |
|----|------|
| **现状** | 设置页 MCP 管理为静态 3 行 mock |
| **接口** | `GET /v1/mcp-servers`（全量：name/transport/url/is_active/source/version）；`PATCH /v1/mcp-servers/{id}`（`{is_active}` → 触发 `McpClientManager.reload()`）；`DELETE /v1/mcp-servers/{id}`（含 installed_skills 关联清理） |
| **实现** | 新建 `api/mcp_servers.py`；复用 `db/skill_repository.py` 的 `update_mcp_server_active` / `delete_mcp_server_by_id`（已存在） |
| **前端** | `SettingsPage/McpSection` 改真实数据 + 空状态 |
| **验收** | 设置页增删改查真实生效；启停后工具热刷新（日志可见） |

#### 2.5 系统配置 API + 前端日志上报

| 项 | 内容 |
|----|------|
| **现状** | 3 个开关 mock（日志上报/Skill 自动更新/流式加速）；logger.ts 的 `POST /v1/frontend/logs` 是注释占位 |
| **接口** | `GET /v1/settings` + `PUT /v1/settings`（JSON 存 SQLite `settings` 表）；`POST /v1/frontend/logs`（批量日志落盘 `logs/frontend.log`） |
| **实现** | `db/schema.py` 加 `settings` 表（key/value）；`api/settings.py`；`api/logs.py`（UTF-8 落盘，遵循 04-logging 规则） |
| **前端** | 开关改真实读写；logger.ts flush 接后端（占位已留） |
| **验收** | 开关持久化；前端报错可在后端日志文件看到 |

#### 2.6 代理模式透传

| 项 | 内容 |
|----|------|
| **现状** | 四档模式（默认/规划/代理/自动）纯前端状态，不传后端 |
| **接口** | `POST /v1/chat/stream` 请求体加 `mode: "default"\|"plan"\|"agent"\|"auto"`（可选，缺省 default） |
| **实现** | `ChatContext` 加 `mode` 字段 → `main_agent.py` 按模式动态附加 system_prompt 指令（plan：先拆解任务；agent：自主多步；auto：让模型自选） |
| **前端** | ChatInput 的 mode 状态传入 send（一行改动） |
| **验收** | 不同模式下发同一任务，Agent 行为可见差异（plan 先列步骤） |

### 阶段三 P2 — 增强功能（3 项）

> 目标：体验类 mock 真实化。

#### 2.7 上下文用量统计（评审拍板：自定义 CallbackHandler）

| 项 | 内容 |
|----|------|
| **现状** | 输入栏「1.2k/128k」固定 mock |
| **接口** | SSE `start` 事件加 `context_used` / `context_total`（评审拍板：SSE 携带，零额外请求） |
| **实现** | **自定义 CallbackHandler**：拦截每次模型调用的输入输出（`prompt_tokens` / `completion_tokens`），累加得到总消耗；数值写入 **AgentState（Graph 状态）**，流结束由 API 层读取 → SSE 事件携带；前端读取渲染 当前使用/上限。✅ 官方标准扩展方式，不侵入 deepagents 底层源码 |
| **前端** | ContextUsage 组件读真实值 |
| **验收** | 进度条随对话真实增长（多轮累加） |

#### 2.8 附件上传

| 项 | 内容 |
|----|------|
| **现状** | 📎 仅本地记录文件名 |
| **接口** | `POST /v1/chat/stream` 附件字段（base64 小文件）或独立 `POST /v1/uploads`（multipart） |
| **实现** | `core/paths.py` 加 `get_uploads_dir()`（`data/uploads/`）；消息携带附件引用，Agent 可读文件内容 |
| **前端** | ChatInput 附件选择后真实上传，消息气泡展示附件 |
| **验收** | 文件真实落盘且 Agent 能读取内容回答 |

#### 2.9 Skill 分类聚合

| 项 | 内容 |
|----|------|
| **现状** | 「全部」分类由前端并行调两类合并 |
| **接口** | `GET /v1/skills/marketplace/list` 支持 `skill_type=all`（后端合并分页） |
| **实现** | `skills/marketplace.py` 加 all 分支（复用两个适配器调用） |
| **前端** | SkillsPage 去本地合并逻辑 |
| **验收** | 「全部」单接口返回混合列表 + 正确分页 |

### 2.10 技术要点（横切）

1. **Schema 迁移**：全部加列/加表沿用 `_migrate_*` try/except 模式（幂等，旧库安全）
2. **热刷新**：MCP 启停复用 `_refresh_agent_tools()`（reload + rebuild_agent）
3. **测试策略**：每项配 pytest（mock LLM、tmp_path、:memory:），覆盖正常/边界/错误三态；沿用 test_api / test_db 分层
4. **日志**：新接口日志 UTF-8（04-logging 规则）
5. **契约同步**：每完成一项，更新 `后端接口对接文档-v1.md`（mock 标注 → ✅ 真实）

## 3. 总：里程碑节奏、风险与评审决策点

### 3.1 建议节奏（每阶段独立交付、可验证）

```
阶段一 P0（会话三件套）   → 后端 1-2 次提交，前端接真实数据
阶段二 P1（设置与管理）   → 后端 2-3 次提交，设置页去 mock
阶段三 P2（增强功能）     → 后端 2-3 次提交，体验类真实化
每阶段结束：pytest 全绿 + 浏览器实测 + 接口文档同步
```

### 3.2 风险与依赖

| 风险 | 缓解 |
|------|------|
| 附件上传方案选择影响面大 | 决策点 3.3-1 先行拍板，P2 靠后实施 |
| 代理模式对 Agent 行为的真实影响有限 | 先做透传 + 提示词注入，效果不足再降级（仅记录） |
| 上下文 token 估算不精确 | 明确用近似估算（chars/4），标注后续可换 tokenizer |
| 旧库迁移遗漏 | 每项加表/列都写 `_migrate_*` + 测试断言列存在 |

### 3.3 评审决策点（2026-08-04 已拍板 ✅）

| # | 决策点 | 拍板结论 |
|---|--------|---------|
| 1 | 附件方案 | ✅ **独立上传接口** `POST /v1/uploads`（multipart + 文件引用） |
| 2 | 系统配置存储 | ✅ **SQLite settings 表**（key/value，与现有持久化一致） |
| 3 | 代理模式深度 | ✅ **先浅后深**（先透传 + 提示词注入，效果不足再改编排） |
| 4 | 前端日志上报 | ✅ **本期就接** `POST /v1/frontend/logs`（占位已留，价值高） |
| 5 | 上下文用量 | ✅ **SSE start 事件携带** + 自定义 CallbackHandler 统计（不侵入 deepagents 源码） |

> 📌 **评审结论**：计划按「会话体验 → 设置管理 → 增强功能」三阶段推进，
> 全部 8 项为前端 mock 的逐一真实化，无架构级改动，风险低、每阶段可独立验收。
>
> 📌 **学习需求**：本计划中 Agent 核心能力改动（上下文 CallbackHandler、代理模式注入、
> 自动标题落库）为学习重点，完成后向 co-creator 展示核心代码 + 流程梳理；
> 附件上传等外围功能仅需了解。
