## 1. 总：背景与分析目标

### 1.1 背景

官方 context-engineering 文档定义：**上下文工程 = 在正确格式下提供正确的信息和工具，
让 deep agent 可靠完成任务**。deep agents 内置长会话上下文管理机制。

分析目标：对照官方模型，盘点本项目上下文管理现状（已具备 vs 差距），
输出改进方向（P 级标注，供后续决策）。

---

## 2. 分·官方模型

### 2.1 四类上下文

| 类型 | 是什么 | 作用域 | 项目对应 |
|------|--------|--------|---------|
| **Input context** | 启动时进 system prompt（system prompt + memory + skills） | 静态，每次运行 | DEFAULT_SYSTEM_PROMPT + MEMORY_GUIDANCE + 记忆注入 + 技能 |
| **Runtime context** | invoke 时静态配置（用户元数据/API keys/连接） | 每 run，传播到子代理 | ChatContext（context_schema） |
| **Context compression** | 内建 offload + summarization（接近窗口上限自动） | 自动 | deepagents 默认 |
| **Context isolation** | 子代理隔离重活，只回结果——解决上下文膨胀 | 架构手段 | search_agent + 隔离 |

### 2.2 压缩机制（deepagents 内建，默认阈值）

> 🔧 v1.1 修正：两种驱逐**方向相反**——入参 vs 出参；offload 是**上下文管理**
> （从上下文移除 + 替换引用），不是文件移动（内容本就在文件系统）。

| 机制 | 默认阈值 | 行为 | 方向 |
|------|---------|------|------|
| 工具调用输入驱逐 | 20,000 tokens | agent 发给工具的**入参**太大（如 write_file 的完整文件内容）→ 从上下文移除（内容已持久化） | **入参驱逐** |
| 工具结果驱逐 | 20,000 tokens | 工具返回的**出参**太大（如 read_file 全文）→ 从上下文移除，替换为**路径引用 + 前 10 行预览**——agent 可重读 | **出参驱逐** |
| 对话压缩 | summarizer | 历史消息自动摘要压缩（主栈与子代理栈均有，graph.py:758/843） | — |
| 大文件读取 | read_file 分页 | offset/limit 分页读，不全量进上下文 | — |

### 2.3 上下文隔离（官方推荐的架构手段）

**子代理解决上下文膨胀问题**：主 agent 工具大输出（搜索/文件/数据库）会填满窗口——
把重活委派给子代理，**只回结果**给主 agent，主 agent 窗口保持干净。

## 3. 分·项目现状盘点（代码级对照）

### 3.1 Input context（启动注入）✅ 基本完备

| 源 | 项目实现 | 状态 |
|----|---------|------|
| System prompt | `DEFAULT_SYSTEM_PROMPT`（研究助理角色）+ `MEMORY_GUIDANCE_V3`（记忆维护指引） | ✅ 可控 |
| Memory | 记忆注入：`load_recent_memories_v3` → SystemMessage（chat.py:192）——画像优先排序，limit=5 | ✅ 已启用 |
| Skills | `skills=["/skills/market/"]`——**渐进披露**：启动只载 name+description 摘要，激活才读全文 | ✅ 官方原生 |

### 3.2 Runtime context ✅ 已实现

- `context_schema=ChatContext`（model_id/mode/session_id）——invoke 时经 runtime 传播
- 子代理运行时：模型经 `_configurable_model` 中间件按 context 选模型

### 3.3 Context compression ✅ 官方默认（未自定义）

| 机制 | 项目配置 | 行为 |
|------|---------|------|
| 工具结果驱逐 | **未传参 → deepagents 默认** 20,000 tokens（filesystem.py:1373） | 大出参从上下文移除，替换为路径引用 + 预览（内容本就在文件系统——offload 非文件移动） |
| 对话压缩 | summarizer 主栈默认挂载（graph.py:758）——⚠️ **代码层面有，未实测是否触发**（v1.1 修正：需长会话验证或标注存疑） | 自动摘要压缩 |
| 大文件读 | read_file 分页（offset/limit） | 不全量进上下文 |
| **窗口监控** | `TokenUsageMiddleware`——context_used/context_total(128,000) 落库，**done 事件结束时带出（查库）**——非实时流式（v1.2 补充：token 流中不推送用量，前端在对话结束才同步） | ✅ 前端可见用量（结束时） |

### 3.4 Context isolation ✅ 已具备 + 深化

- 搜索子代理（search_agent）：委派联网搜索，结果回主 agent——隔离重活
- **深化**（CompositeBackend 深化 P2）：CompiledSubAgent 独立 StateBackend——
  子代理文件不污染主会话；权限覆盖（写 deny）

### 3.5 上下文膨胀来源分析（v1.2 新增——评审小问题 4）

**项目上下文主要被什么占**（估算表，基于现有配置）：

| 来源 | 现有控制 | 估算占比（长会话） | 说明 |
|------|---------|------------------|------|
| **对话历史** | 组历史 limit=200 条 + summarizer 自动压缩 | **最高**（长会话 50%+） | 多轮对话累积，压缩前最占 |
| **工具结果** | 驱逐阈值 20k tokens + 沙箱输出截断 8KB | 高（工具密集会话） | 搜索/沙箱/文件读是大输出源 |
| **system prompt** | 角色 + 记忆指引 + 技能摘要 + 记忆注入 5 条 | 低（固定 <10%） | 组件少、有渐进披露/注入限制 |
| **工具描述** | 6 个内部工具 + MCP 工具描述 | 低-中（MCP 多时上升） | 每个描述进上下文（§4 #8） |

**结论**：当前膨胀大头 = **对话历史 + 工具结果**（deepagents 默认压缩正是针对两者）；
system prompt 当前占比小（分层管理是预防，非急救）。

## 4. 分·差距与改进方向（10 项：初版方案 + 为什么）

### 4.1 差距总表

| # | 差距 | 现状 | P 级 |
|---|------|------|------|
| 1 | 压缩阈值用官方默认 | 未针对本项目调参 | P1 |
| 2 | 记忆注入无相关性/时间衰减 | limit=5 固定 | P1 |
| 3 | 技能全文过大无拆分约定 | 渐进披露已启用 | P0（约定） |
| 4 | 上下文用量只记录不干预 | 前端可见无告警（v1.2：告警与 summarizer 互补——压缩是自动兜底动作，告警是告知用户"为什么回答变模糊了"；不替代压缩） | P2 |
| 5 | 子代理角色单一 | 仅 search_agent | P2 |
| 6 | 自定义压缩器缺失（v1.1 补） | 完全用默认 summarizer/驱逐 | P2 |
| 7 | System prompt 分层管理缺失（v1.1 补） | 角色+记忆指引+技能摘要+记忆注入全塞 | P1 |
| 8 | 工具描述优化缺失（v1.1 补） | 描述全量进上下文，无审计 | P2 |
| 9 | 上下文窗口场景化缺失（v1.1 补） | 固定 128k | P2 |
| 10 | 大文件 offload 清理 | 已闭环（cleanup + DELETE 联动） | — |

### 4.2 初版方案与为什么

**1. 压缩阈值配置化（P1）**
- 方案：config 加 `context_tool_evict_limit`（默认对齐官方 20000）+ 实测校准——
  记录实际触发次数（审计）与 token 峰值，按沙箱/搜索场景的输出特征调参
- **为什么**：20k 是官方通用值——本项目的沙箱工具输出（run_code/run_skill_script）
  与搜索结果可能远大于或远小于该值；阈值过高 = 大输出爆窗口，过低 = 频繁驱逐
  增加重读成本。先量化再调参（不拍脑袋改）

**2. 记忆检索升级（P1，接记忆方案 v3 §5）**
- 方案：关键词/标签过滤 + 时间衰减（新记忆权重高）+ 注入窗口 ≤10% 裁剪
  （优先级：画像 > 任务 > 事实 > 旧决策）
- **为什么**：记忆是 Input context 的动态部分——limit=5 固定注入在记忆膨胀后
  既可能漏关键记忆（相关性未考虑）也可能浪费窗口（无关记忆占位）。先结构化
  近似（关键词/标签），向量语义 P2

**3. 技能全文拆分约定（P0）**
- 方案：SKILL.md 拆"概览 + 分文件"（Skill 体系 §4.3）——入口 ≤阈值（如 2KB），
  深水区下沉 references/
- **为什么**：渐进披露的价值 = 摘要层足够小——SKILL.md 全文进上下文就违背了
  渐进披露的设计意图（激活后按需读）

**4. 上下文用量告警（P2）**
- 方案：TokenUsageMiddleware 扩展——context_used 超阈值（如 80% 窗口）时
  SSE 增加用量告警事件（前端提示）
- **为什么**：用量已记录但无干预——用户/agent 在接近窗口上限时无感知；
  summarizer 自动压缩是兜底，告警让人知道"为什么变模糊了"

**5. 子代理角色扩展（P2）**
- 方案：Skill/角色扩展时复用隔离模板（CompiledSubAgent 独立 StateBackend + 权限覆盖）
- **为什么**：子代理是官方推荐的上下文隔离手段（§2.3）——多角色后主 agent
  窗口更干净；隔离基建已就绪（CompositeBackend 深化 P2），扩展成本低

**6. 自定义压缩器（P2，v1.1 补）**
- 方案：① 小模型 summarizer（压缩用便宜模型，省主模型 token）② 自定义驱逐
  优先级（哪些工具结果优先驱逐——如沙箱大输出）③ 压缩质量评估（摘要后
  关键信息留存率抽样检查）
- **为什么**：默认压缩器"能用但不可控"——压缩质量直接决定长会话的可靠性；
  学习 demo 阶段先跑通默认，P2 再做质量与成本优化（官方支持自定义中间件参数）

**7. System prompt 分层管理（P1，v1.1 补）**
- 方案：prompt 分层——**核心层**（角色，必选）/ **可选层**（记忆指引、技能摘要，
  按需注入）/ **动态层**（记忆注入，随会话变化）；超限时按优先级裁剪
  （核心 > 可选 > 动态）
- **为什么**：当前角色 + 记忆指引 + 技能摘要 + 记忆注入全塞 system prompt，
  越来越大无人管——分层后"哪些必须/哪些可选"显式化，与记忆窗口控制（差距 2）
  是一类问题，可合并实施

**8. 工具描述优化（P2，v1.1 补）**
- 方案：工具描述 token 审计（统计全部工具描述总长）→ 长描述拆"摘要 + 详情"
  （工具 description 精简，细节下沉工具文档/技能）——与 Skill 渐进披露同思路
- **为什么**：每个工具描述都进上下文——工具越多（当前 6 个 + 未来 MCP 工具），
  描述冗余的浪费线性增长；先审计量化再决定拆不拆

**9. 上下文窗口场景化（P2，v1.1 补）**
- 方案：按场景选择窗口/模型——简单对话用小窗口模型（省钱），长文档分析用
  大窗口；ChatContext 扩展 context_profile（small/standard/large）→ 模型选择联动
- **为什么**：固定 128k 对小场景浪费（成本×token），大场景可能不够；
  多 provider 模型已支持（_configurable_model 运行时切换），加 profile 即可联动

**10. 大文件 offload 清理（闭环）**
- 现状已满足：workspace 清理（cleanup_workspace + DELETE 会话联动）✅ 无差距
