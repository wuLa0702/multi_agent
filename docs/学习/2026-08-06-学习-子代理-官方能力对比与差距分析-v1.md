## 1. 总：背景、目标与范围

### 1.1 背景

项目使用 deepagents 子代理（声明式 YAML：`search_agent`），但**不确定是否追上官方进度**。官方 subagents 页（含 #streaming 流式章节）与 async-subagents 页（异步子代理，预览功能）分别演进出多项新能力。本文档把两页官方文档与项目现状逐项对比，找出优化点、可增功能与取舍结论。

### 1.2 目标

1. 官方两页能力完整梳理（§2），后续不翻原文
2. 项目现状盘点（§3）→ 12 项差距矩阵（§4）
3. 优化点分级 + 权衡（§5/§6），给出推荐结论
4. §7 给出推荐项的参考核心代码（评审后落地）

### 1.3 范围

| 在本分析内 | 不在本分析内 |
|-----------|-------------|
| 同步子代理全字段 / streaming / 结构化输出 / context 传播 / dynamic subagents | async subagents 落地（§6.2 论证不做，记录触发条件） |
| 项目现状逐项对比（loader / YAML / 事件流 / interpreter） | 子代理 HITL 审批（interrupt_on，主 agent 审批链路未接，随 P2 审批一起） |

## 2. 分：官方能力梳理

> 来源：官方两页文档 + deepagents 0.7.1 本地源码核对（SubAgent spec / AsyncSubAgent API 均实测存在）。

### 2.1 同步子代理：SubAgent 声明字段表 🟠 v1

| 字段 | 语义 | 继承规则 |
|------|------|----------|
| `name` | 唯一标识；成为 AI 消息与流式元数据（lc_agent_name） | — |
| `description` | 主 agent 决定何时委派的依据（官方反复强调：具体、行动导向） | — |
| `system_prompt` | 子代理专属指令（**不继承**主 agent） | 不继承 |
| `tools` | 子代理工具集；**指定即整体覆盖**继承的工具 | 缺省继承主 agent |
| `model` | **按任务选模型**（`provider:model` 字符串或模型实例） | 缺省用主 agent 模型 |
| `middleware` | 子代理专属中间件（同名默认实例原位替换，新名追加） | 不继承 |
| `interrupt_on` | HITL 审批配置（需 checkpointer） | 缺省继承主 agent |
| `skills` | 子代理专属技能源（独立 SkillsMiddleware，双向隔离） | 不继承 |
| `response_format` | **结构化输出**（Pydantic / ToolStrategy / ProviderStrategy；父 agent 收到 JSON ToolMessage） | — |
| `permissions` | 文件权限规则（**整体替换**父级） | 缺省继承 |

0.7.1 源码核对：`middleware/subagents.py` 的 SubAgent TypedDict 含 `middleware / interrupt_on / skills / response_format`（`SUBAGENT_RESPONSE_FORMAT_CONFIG_KEY`）——字段全部可用。

### 2.2 Streaming（#streaming 锚点） 🟠 v1

- 官方推荐 `stream_events(version="v3")`：**类型化投影**，`stream.interleave("messages", "subagents")` 分别消费主 agent 消息与子代理进度
- 每个子代理句柄暴露 `.name / .messages / .tool_calls / .output`——子代理内部的中间消息与工具调用可直接流给前端
- 全部 run 带 `lc_agent_name` metadata（LangSmith 过滤 + 工具内识别调用者）

### 2.3 结构化输出与通用子代理 🟠 v1

- `response_format`（需 deepagents≥0.5.3，本机 0.7.1 ✓）：子代理结束时结果 JSON 序列化为 ToolMessage 返回父 agent——父 agent 可程序化消费、可过下游工具
- 自动附加 `general-purpose` 通用子代理（同工具同模型，自带 skills 继承）；同名替换或 `GeneralPurposeSubagentProfile(enabled=False)` 禁用

### 2.4 Dynamic subagents（beta） 🟠 v1

- 解释器 + 子代理**兼备即启用**：agent 可从代码（interpreter）内用 `task()` 派发子代理——循环/分支/并行批量扇出
- "workflow" 触发词是刻意杠杆；`CodeInterpreterMiddleware(subagents=False)` 显式关闭
- 需 `langchain-quickjs>=0.2.0` + Python≥3.11

### 2.5 Context 传播 🟠 v1

- 父 agent 的 runtime context **自动传播**到全部子代理（工具内 `runtime.context` 可读）
- per-subagent 配置：namespaced keys（`researcher:max_depth`）或 context 类型独立字段
- 工具内可经 `runtime.config["metadata"]["lc_agent_name"]` 识别调用者，同工具按 agent 分支行为

### 2.6 Async subagents（预览，0.5.0+） 🟠 v1

- `AsyncSubAgent(name, description, graph_id, url?, headers?)`——指向 **Agent Protocol server**（LangSmith Deployments 或自托管）
- `AsyncSubAgentMiddleware`（配置即入默认栈）给主 agent 5 个工具：

| 工具 | 用途 |
|------|------|
| `start_async_task` | 启动后台任务，**立即返回 task_id** |
| `check_async_task` | 查状态与结果 |
| `update_async_task` | 给运行中任务追加指令（中断重启同 thread） |
| `cancel_async_task` | 取消 |
| `list_async_tasks` | 列出全部跟踪任务（实时状态） |

- **状态管理关键设计**：任务元数据存独立 state channel（`async_tasks`），不随消息历史压缩丢失
- 传输：`url` 缺省 → ASGI 进程内（co-deployed，推荐）；设置 → HTTP 远程
- 对比表（官方原文）：同步 = 阻塞 + 无中途更新 + 无取消；异步 = 非阻塞 + 中途可改 + 可取消 + 有状态
- 0.7.1 核对：`AsyncSubAgent / AsyncSubAgentMiddleware` 已导出 ✓

## 5. 分：优化点与可增功能

### 5.1 P1-1：子代理 model 字段（按任务选模型） 🟠 v1

- **做什么**：`search_agent.yaml` 支持 `model` 声明（项目内用 DB model_id 或 model_name），loader 解析为 ChatOpenAI 实例传给 SubAgent spec
- **收益**：
  1. 搜索子代理用便宜模型（如 deepseek-v4-flash），主 agent 用旗舰（deepseek-v4-pro）——省 token + 角色分工（呼应上下文工程 #5"子代理角色单一"）
  2. 官方 common pattern "choose models by task" 的落地
- **成本**：loader 增量（解析 + 经 `get_chat_model` 构造）；YAML 加一行
- **风险/边界**（关键）：
  1. 子代理 model 是**构建期绑定**（子代理 middleware 不继承主 agent 的 `_configurable_model`，官方文档明示 middleware 不继承）→ 与主 agent"运行时切换模型"错位：改子代理模型需 `rebuild_agent()`。**这是可接受的**：子代理模型语义上就是"模型族固定分工"，不是请求级切换（与 Profiles 决策同构，见 §6.1）
  2. 不能用 `provider:model` 字符串（国产模型需自定义 base_url，deepagents 内部 init_chat_model 拼不出）→ **必须传实例**（get_chat_model 工厂，DB 真相源）
  3. P2 隔离模式（SUBAGENT_ISOLATION）已传 model 编译——P1-1 与其叠加：每个子代理 YAML 独立 model，隔离模式编译时各自用各自的模型

### 5.2 P1-2：子代理结构化输出（降级方案——官方 response_format 实测不可用） 🔴 v1.1

> ⚠️ **2026-08-06 实测修正（v1.1）**：官方 `response_format` 三条策略在国产模型（deepseek-v4-flash / doubao-seed-evolving）上**全部 400**，不可按官方字段落地。验证全景见 §7.4，根因一句话：langchain `agents/factory.py:1388` 对结构化输出工具**强制 `tool_choice="any"`**，国产模型拒绝该别名（`required` 亦被思考模式拒绝）；ProviderStrategy 则报 "response_format type unavailable"。

- **降级方案 A（推荐，P1-2 改为此形态）**：子代理 `system_prompt` 显式约束"必须输出合法 JSON + 字段格式" + 父 agent 容错解析（解析失败降级取原文，用例见 §8-3/4）
  - **收益**：与官方方案等价的功能面（父 agent 程序化消费 summary/sources、审计可解析、上下文干净）——只是从"框架保证"降为"约定 + 容错"
  - **成本**：YAML system_prompt 加一段输出格式约束；父 agent 消费处一个 `model_validate_json` try/except
  - **风险**：无框架保证 → 模型偶发输出非 JSON（思考模型输出稳定，容错兜底即可）
- **降级方案 B（P2 可选）**：子代理专属 `middleware` 字段挂 `wrap_model_call` 包装器，每次模型调用注入 `response_format={"type": "json_object"}`——DeepSeek 原生兼容（§7.4 第⑦行实测 ✅）；但 `json_object` 只保证"是 JSON"不保证 schema，且动子代理调用链，收益边际，暂缓
- **明确不做**：换 OpenAI 系模型跑官方 response_format（项目无 OpenAI key）；改 langchain 源码（依赖纪律禁止）

### 5.3 P2 备选清单 🟠 v1

| 项 | 内容 | 前置条件 |
|----|------|----------|
| P2-1 | **Dynamic subagents 验证/决策**：先实测 CodeInterpreter 内 `task()` 是否可用（PTC 白名单是否挡），再决定启用（文档化 "workflow" 触发词）或 `CodeInterpreterMiddleware(subagents=False)` 显式关闭 | 浏览器实测（现有 Fake 模型测不出） |
| P2-2 | **Streaming v3 subagents 投影调研**：stream_events v3 的 stream.subagents 是否能在国产模型栈可用（v3 messages 无逐 chunk 已定 v2 主链路，subagents 投影是独立收益）——可用则替代 v2 手工监听，去掉"待实测校准"标记 | 浏览器实测 |
| P2-3 | 子代理专属 skills（`skills` 字段）：技能市场已落地主 agent，扩展子代理隔离挂载 | 技能体系稳定后 |
| P2-4 | 多子代理模式（data-collector → analyzer → writer 流水线）：学习价值高，官方 common patterns | 需要新子代理 YAML |
| P2-5 | `lc_agent_name` 工具内分支：tool_audit 按子代理维度统计 | 审计需要时 |

## 6. 分：权衡与推荐

### 6.1 推荐结论 🟠 v1

| 优先级 | 项 | 结论 | 一句话理由 |
|--------|-----|------|-----------|
| **P1** | model 字段接线（§5.1） | ✅ 推荐做 | 省 token + 角色分工；成本低；构建期绑定语义明确（模型族固定分工） |
| **P1** | response_format（§5.2） | ✅ 推荐做 | 父 agent 程序化消费 + 审计友好；成本最低；ToolStrategy 兜底国产模型 |
| **P2** | dynamic subagents 验证（§5.3 P2-1） | ⏳ 先实测再定 | 可能已隐式启用，未知状态是风险；验证成本=一次浏览器实测 |
| **P2** | streaming v3 subagents 投影 | ⏳ 调研 | 依赖国产模型栈实测，不影响主链路 |
| **不做** | async subagents（§6.2） | ❌ 明确不做 | 部署形态不匹配 + 预览 API + 已有 peer executor 覆盖后台任务需求 |

### 6.2 async subagents 为什么不做的论证 🟠 v1

1. **部署前提不满足**：AsyncSubAgent 指向 Agent Protocol server（LangSmith Deployments 或自托管）。本项目部署形态 = 本地 FastAPI + 云端 OpenSandbox 沙箱，无 LangGraph Platform；自托管 Agent Protocol server 是一整块新基础设施
2. **预览功能**：官方标注 preview（0.5.0+），API 可能变；学习项目接预览 API 的维护成本不划算
3. **需求已被覆盖（语义不同但效果等价）**：官方 async subagent 解决"主 agent 启动后台任务并跟踪/干预"；本项目用**并列执行体 + 队列**（memory_agent，peer executor 概念已沉淀）实现了后台任务——语义差异（async subagent 是主 agent 委派的延续、peer 是系统编排）对当前需求无影响
4. **状态管理亮点值得学习**（async_tasks channel 独立于消息历史抗压缩）——记入学习笔记即可，不落地

**触发条件（未来重新评估）**：① 上 LangGraph Platform 或自托管 Agent Protocol server；② 出现"对话中启动长任务 + 用户中途干预"的真实需求（当前无）；③ API 转正

### 6.3 与 Profiles 决策的一致性 🟠 v1

上一轮 Profiles 拍板"不落地"的核心结论（构建期静态 vs 运行期动态的错位）在本文档 P1-1 上**同一逻辑，但结论相反**：
- Profiles 错位在于：按"运行时可切换的模型"配行为，profile 却构建期解析 → 帮不上忙
- P1-1 错位在于：子代理模型**本来就是构建期绑定**（middleware 不继承）→ 与"模型族固定分工"语义天然匹配，**不需要运行时**。所以 P1-1 反而是官方 model 字段的正确用法——这正是 Profiles 决策里"触发条件：子代理模型隔离落地时 profiles 是正解"的配套（子代理选模型用 model 字段，调行为用 profile——现阶段只用前者）

### 7.1 loader.py 增量：model 字段支持 🔴 v1.1

```python
# backend/src/agent/subagents/loader.py（增量，新增 import 与函数）
# ⚠️ v1.1 修正：不再接 response_format（官方三态实测不可用，§5.2/§7.4）；
#   结构化输出降级为 system_prompt 约束 + 父 agent 容错解析（§7.2/§8）。

from src.core.model_registry import get_registry
from src.llm.adapter import get_chat_model


def _resolve_model(model_name: str | None):
    """YAML model 声明 → ChatOpenAI 实例（DB 真相源；None → 主 agent 默认）。

    ⚠️ 必须传实例而非 `provider:model` 字符串——国产模型需自定义
    base_url，deepagents 内部 init_chat_model 拼不出（§5.1 风险 2）。
    model_name 经 get_chat_model 需要 model_id；这里按 name 反查注册表。
    """
    if model_name is None:
        return None
    registry = get_registry()
    for provider in registry.list_providers():
        for info in provider.models:
            cfg = registry.get_model(info.id)
            if cfg is not None and cfg.model_name == model_name:
                return get_chat_model(cfg.id)
    raise ValueError(f"子代理声明了未知模型 model_name={model_name}（DB 无此模型）")


def _parse_subagent_yaml(yaml_file: Path) -> SubAgent:
    """解析单个 YAML 文件为 SubAgent 声明（P1 增量：model 字段）。"""
    data = yaml.safe_load(yaml_file.read_text(encoding="utf-8"))
    if not isinstance(data, dict):
        raise TypeError(f"子代理 YAML 顶层必须是映射：{yaml_file.name}")
    spec: SubAgent = {
        "name": data["name"],
        "description": data["description"],
        "system_prompt": data["system_prompt"],
        "tools": [get_tool(name) for name in data.get("tools", [])],
    }
    # P1-1：按任务选模型（构建期绑定，模型族固定分工语义）
    if "model" in data:
        spec["model"] = _resolve_model(data["model"])
    # 权限逻辑不变（既有实现）
    if "permissions" in data:
        spec["permissions"] = _parse_permissions(data["permissions"])
    else:
        perms = build_subagent_permissions(spec["name"])
        if perms:
            spec["permissions"] = perms
    return spec
```

### 7.4 验证记录：response_format 国产模型实测（2026-08-06） 🔴 v1.1

> 验证脚本：`backend/examples/verify_subagent_structured_output.py`（可复跑；只读 .env.dev，密钥不打印）。
> 实测模型：deepseek-v4-flash（deepseek 官方 API）、doubao-seed-evolving（ark）。

| # | 路径 | 结果 | 根因 |
|---|------|------|------|
| ① | 裸 schema（AutoStrategy 默认路径） | ❌ 400 | profile=None → 决议为 ToolStrategy → 强制 tool_choice="any" 被拒 |
| ② | 显式 ToolStrategy | ❌ 400 | 同上（factory.py:1388 硬编码 tool_choice="any"） |
| ③ | 显式 ProviderStrategy | ❌ 400 | deepseek："This response_format type is unavailable now"（原生不可用） |
| ④ | 裸 bind_tools + tool_choice="any" | ❌ 400 | deepseek 反序列化错误（不认 "any" 别名）/ doubao InvalidParameter |
| ⑤ | 裸 bind_tools + tool_choice="required" | ❌ 400 | 思考模式拒绝强制 tool_choice（deepseek-v4-flash） |
| ⑥ | 裸 bind_tools + tool_choice=None（auto） | ✅ | 模型自主调用工具（无格式保证——主 agent 现状即此） |
| ⑦ | response_format={"type": "json_object"} 直连 | ✅ | **DeepSeek 原生兼容 OpenAI JSON mode**（仅保证是 JSON，无 schema 保证） |

**根因定性**：langchain `agents/factory.py:1388` 对结构化输出工具强制 `tool_choice="any"`——OpenAI 接受的别名，deepseek / doubao 都拒绝（OpenAI 官方命名 `required` 亦被 deepseek 思考模式拒绝）。`model.profile=None`（国产模型不在 langchain profile 注册表）→ 裸 schema 决议为 ToolStrategy，无 escape hatch。

**结论**：官方 response_format 三态在国产模型栈上不可用（框架层硬编码，无法经参数绕行）；json_object 直连可用但无 schema 保证 → 降级方案 A（§5.2）为当前唯一务实路径。
