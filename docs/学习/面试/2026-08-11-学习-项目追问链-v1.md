## 1. 项目定位与一句话 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

**一句话**：基于 deepagents 的**研究型多 Agent 平台**——主 Agent 编排委派搜索/审核子代理，产出带引用溯源的研报，配离线评估管道证明质量；**行业研究是首个落地场景**，可扩展至公司尽调/竞品分析等深度研究任务。

**定位（2026-08-10 拍板）**：Harness/框架向 + 中厂/转型岗——**场景是载体，技术深度是卖点**。**表述升维（2026-08-11）**：从"行业调查系统" → "通用研究型 Agent 平台（研究 harness）"，行业研究为首个验证场景——业务不换，讲法升维，避免"业务单薄"错觉。

**技术栈故事线**：deepagents harness（手写中间件）→ 声明式子代理（YAML）→ 受控工具（搜索+抓取双工具）→ 离线评估（四类指标 + 纵向对比）→ 观测体系（审计 + 推理层 trace）。

### 1.1 简历叙事双版本（直接可用，2026-08-11 新增） 🔴 v1.1

> 📌 **用法**：版本 A 给技术岗/深挖场景；版本 B 给讲项目背景/打动面试官。**埋点纪律**（指南 §4.1）：每个技术点要能往下挖 3 层——⚠️ 两处校准：① "Rubric 质量评估"项目实际用**自研 LLM-as-judge + 审核子代理**（RubricMiddleware grader 国产模型验证未过、默认关）→ 改口径 ② "成本核算与预算控制"**设计文档已出、代码实现中** → 面试前落地，或主动讲"设计中的模块"。

**版本 A（偏技术，推荐）**：
> 多 Agent 智能研究系统：面向深度研究类任务（行业研究 / 公司尽调 / 竞品分析）的多 Agent 协作框架，实现信息收集 → 多 Agent 分析 → 质量评估 → 报告生成的完整研究链路。核心包括多 Agent 子代理调度、工具调用与 MCP 协议、人在回路审批、**LLM-as-judge 质量评估 + 审核子代理**、成本核算与预算控制（设计落地中）、跨会话记忆体系、容错降级机制。目前已落地行业研究场景，支持多源信息聚合、引用可溯源、成本可观测。

**版本 B（偏业务，适合讲项目背景）**：
> 针对咨询 / 投资 / 市场研究场景中"手工调研慢、贵、质量参差"的痛点，设计并实现多 Agent 智能研究系统。通过多 Agent 并行搜索与分工分析将研究周期从天级压缩到小时级，通过评估体系 + 人在回路保证输出质量，通过成本核算 + 模型分级控制 API 成本。系统采用可扩展框架，已落地行业研究场景，可扩展至公司尽调、竞品分析等其他深度研究任务。

## 2. 五层追问链 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 第 1 层：业务层

| 追问 | 预演答案 |
|------|----------|
| 解决什么业务问题？ | 行业研究耗时且质量难控：研究员要搜索大量资料、核对来源、整理报告。系统把"搜索→抓取→核验→撰写→审核"流程 Agent 化，产出带引用溯源的研报 |
| 用户是谁？ | 分析师/研究员（demo 定位）；架构上可插拔到任意"调研产出报告"场景 |
| 为什么用 Agent？传统方案不行？ | 传统 RAG 问答只做检索-生成，无法自主规划多步研究（多轮搜索、跨源核验、代码验证数据）；Agent 能"计划→执行→检查"循环 |

### 第 2 层：架构层

| 追问 | 预演答案 |
|------|----------|
| 整体架构？ | 前端 SSE 流式 → FastAPI（chat 编排）→ deepagents 编译图（主 Agent + 中间件栈）→ 子代理委派（search/review）+ 受控工具（博查搜索 + fetch_url 抓取 + 沙箱计算）→ SQLite（会话/断点/记忆）+ 工具审计/推理 trace |
| 为什么拆多个 Agent？ | **决策故事见 §3**（单 Agent 的坑 → 角色分离 → 代价主动讲）|
| 每个 Agent 职责？输入输出？ | 主 Agent（编排/撰写/修订）；search_agent（搜索委派，输出结构化结果）；review_agent（质量审核，输出通过/不通过+问题清单）|
| 任务谁拆？模型还是规则？ | 模型自主规划（deepagents 内置规划），规则兜底（recursion_limit 50、审核 ≤2 轮、工具限流）——**LLM 决策 + 规则护栏** |
| 对比过什么方案？ | LangGraph（演进预留，手写主图路线）；CrewAI/AutoGen（调研过，deepagents 的声明式子代理 + 中间件栈更贴合"手写学习"目标）|

### 第 3 层：实现层

| 追问 | 预演答案 |
|------|----------|
| 工具调用怎么实现？失败怎么办？ | mcp/registry 注册表（名→实现）；工具级异常降级为错误信息回传（不中断 run）；LLM 调用 timeout+retry 固化在 adapter |
| 搜索与抓取怎么分工？ | **搜索发现（博查摘要）+ 受控抓取（fetch_url 正文）**——评估实证模型自写爬虫后补的架构决策（见 §5 坑点 1）|
| 记忆怎么做？ | 三层：文件记忆（AGENTS.md/tasks/decisions）+ 语义 Store（SQLite 跨会话回忆）+ memory_agent 并列执行体（后台队列抽取，不阻塞对话）|
| 多 Agent 怎么协作？通信？ | deepagents task 委派（子代理独立上下文，只回结构化结论防污染）；审核回路（委派→修订→重审 ≤2 轮）是 prompt 引导的循环 + recursion 兜底 |
| 断点/中断恢复？ | AsyncSqliteSaver（WAL + busy_timeout），每 super-step 落库；resume_run_id + checkpoint_id 精确恢复；HITL 审批中断链路（默认关，P0-V2 待验证）|
| 遇到过什么坑？ | **三大坑见 §5**（模型自写爬虫/prompt 约束失效/recursion 撞限）——每个都有完整 bad case |

### 第 4 层：效果层

| 追问 | 预演答案 |
|------|----------|
| 怎么评估效果？ | 离线评估管道（eval_harness）：10 任务集 → 四类 10 项指标（引用合规/来源可达/质量分/成本）→ 纵向版本对比（git_commit 指纹）|
| 数据？ | **§6 数据弹药库**——完成率 90%、引用合规 90%、审核子代理质量 +1~2 分等 |
| 怎么证明是 Agent 的贡献？ | 纵向对比（同任务集不同版本）：审核子代理上线后质量分提升；fetch_url 补上后 task-001 从失败到成功 |
| bad case？ | 模型绕过搜索自写爬虫（数据外泄风险+循环失控）——trace 三层定位，架构解（受控工具）|

### 第 5 层：优化层

| 追问 | 预演答案 |
|------|----------|
| 还有什么不足？ | 评估任务集规模小（统计显著性弱）；judge 与被评估同模型（风格偏好）；沙箱断网只在云端验证；HITL 审批链路未实测 |
| 更多时间怎么改进？ | 任务集扩到 50+；judge 异模型盲评；手写 LangGraph 主图（演进预留）；在线评估 dashboard |
| 成本怎么控制？ | 用量告警（token 中间件）+ 并发信号量（环境配置化）+ 审核 ≤2 轮封顶 + 工具限流 |
| 安全问题？ | 工具审计（全量记录只记不拦）+ 密钥只进 .env + 路径前缀校验 + 沙箱网络隔离（云端验证中）|

## 3. 单 vs 多 Agent 决策故事（必考题） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

> **讲法：先讲坑（为什么拆），再讲架构（怎么拆），最后主动讲代价。**

**① 一开始想用单 Agent 干完，遇到三个坑**：
1. **Prompt 膨胀**：系统提示词要覆盖搜索/撰写/审核全部职责，互相冲突（研究要发散、报告要收敛，同一角色难兼顾）
2. **上下文污染**：搜索过程塞满对话窗口，干扰报告撰写；子任务中间结论错误迁移
3. **工具过载**：挂太多工具后选择准确率下降（搜索/沙箱/技能描述重叠时选错）

**② 所以拆开（角色天然分离——多 Agent 拆分四前提之一）**：
```
主 Agent（编排+撰写）         独立上下文，专注报告质量
 ├─ search_agent（搜索专员）   独立上下文，专注查资料（便宜模型）
 └─ review_agent（审核专员）   独立上下文，独立评审标准（自己写自己审形同虚设）
```

**③ 代价主动讲（证明踩过坑）**：
- 成本：每次委派 = 子代理独立 LLM 调用，审核回路成本 +2-8×（实测）
- 延迟：单任务 101s→860s（审核回路实证）
- 调试：跨 Agent 链路需要 trace_id 贯穿——所以我建了**推理层 trace**（每轮模型输入摘要/工具调用/子代理启停，parent_ids 区分层级）
- 收敛：prompt 引导的回路有失控风险——规则护栏兜底（≤2 轮 + recursion_limit）

**④ 什么时候不该用多 Agent（反问展示深度）**：步骤固定、规则可穷举的流程用工作流/工具链，不拆 Agent；只有角色天然分离/工具差异大/上下文冲突/并行收益满足才拆。

## 4. 核心功能 STAR 故事库 <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

### 故事 1：评估体系（最亮）
**S**：生产落地必须回答"Agent 有没有用"；面试第一分水岭 = 可量化结果
**T**：建可复跑、有数据、能纵向对比的离线评估管道
**A**：10 任务集（assets 入库）→ eval_harness（四类 10 项指标：规则指标优先，LLM-judge 只做主观维度且纯文本解析规避国产模型 response_format 三态全挂）→ git_commit 版本指纹支持纵向对比
**R**：首跑完成率 90%、引用合规 90%；**评估当探针抓出 3 个生产 bug**（adapter provider 参数/skill args 保留字/A1 字段互换）——全修复

### 故事 2：审核子代理（多 Agent 协作）
**S**：无审核的研报质量不可控（首轮评估质量分低）
**T**：产出即检，审核回路
**A**：review_agent（rubric 同源标准 + 无工具 + 全拒绝权限）→ prompt 引导回路（委派→修订→重审 ≤2 轮）→ recursion 兜底
**R**：质量分 +1~2（实测 task-007 完整度 2.0→3.0）；主动讲代价（耗时 2-8×）

### 故事 3：受控抓取（架构决策，bad case 反转）
**S**：评估实证模型绕过搜索在沙箱自写爬虫（66 次 curl，循环 50 轮撞限）
**T**：治本——补受控内容获取能力 + 收敛网络入口
**A**：fetch_url 工具（服务端 httpx + 清洗 + 截断 + 审计自动覆盖）+ 沙箱网络隔离（云端验证）
**R**：task-001 从 4 连败到成功；沙箱调用 66→1 次——**"发现架构问题比修模型行为更重要"**

### 故事 4：观测体系（工程化深度）
**S**：撞限根因不可见（审计只覆盖主 Agent 层，子代理内部盲区）
**T**：行为层（审计）+ 推理层（trace）双层观测
**A**：ToolAudit（工具调用全量 JSONL）+ 推理层 trace（模型输入摘要/工具/子代理，TraceEvent 领域对象封装）
**R**：三层根因定位（沙箱循环→爬虫→写文件→动机冲突），**"慢的真相要靠数据，不靠直觉"**

## 5. 诚实坑点清单（主动讲短板 = 加分） <span style="color:#fff;background-color:#e11d48;border-radius:4px;padding:1px 6px;font-size:0.8em">v1</span>

| 坑 | 怎么讲的 | 后续 |
|----|----------|------|
| 模型无视 prompt 禁令自写爬虫 | "提示词管不住的行为，要用环境约束——受控工具 + 网络隔离" | 沙箱断网云端验证 |
| recursion limit 撞限（task-001 4 连败）| "研究任务多轮搜索天然吃轮次，50 上限 + 重试兜底；根因是工具链不完整而非上限小" | fetch_url 已解（完成率 0→1.0）|
| 评估跑数慢（单任务 1.5-11 分钟）| "真实 LLM 成本：186 次调用 × 6s；评估是测量不是优化目标" | 并发 5、任务集精简可选 |
| judge 分数偏低（1-2/5）| "judge 与被评估同模型有风格偏好——盲评 + 相对对比，绝对分意义有限" | 异模型 judge（三厂商可切）|
| 统计显著性弱（10 任务）| "个人项目规模有限，主要看趋势" | 扩任务集 |
| egress 断网 Windows 不可用 | "环境实证：sidecar 依赖 iptables/nftables，云端 Linux 部署时验证" | 云端验证 |

```
  ┌─────────────────────────────────────────────────┐
  │ 🟦 ④ 审核回路（review_agent）                     │
  │     🟦 产出即检 → 不通过修订重审 ≤2 轮             │
  └──────────────────────┬──────────────────────────┘
                         ▼
  ┌─────────────────────────────────────────────────┐
  │ 🟦 ⑤ 横切落库（中间件栈，图执行完自动触发）         │
  │     🟥 TokenUsage 深化：本轮增量 token × 单价      │
  │        → 落成本流水（token_cost_ledger）           │
  │     🟥 累计成本超阈值 → cost_alerts 落库           │
  │        （软告警，不硬限制）                        │
  │     🟥 LLM 缓存：相同 (prompt, model) 命中         │
  │        → 省一次调用（memory/redis 双后端）          │
  │     🟦 工具审计 · 推理 trace（原有观测）             │
  └──────────────────────┬──────────────────────────┘
                         ▼
  ┌─────────────────────────────────────────────────┐
  │ 🟦 ⑥ SSE 交付：token×N → done → 消息落库          │
  │     🟥 done 前查告警 → 发 cost_alert 事件（前端提示）│
  └─────────────────────────────────────────────────┘
```

### 7.2 分：三类新增改动（各影响哪个环节）

**🟥 A. 容错（resilience 分支，异常四分类 + 工具重试 + 降级矩阵）**

| 环节 | 新增行为 | 业务价值 |
|------|----------|----------|
| ① 会话落库 | SQLite 瞬时失败重试 → 降级内存 | 断库不打断对话 |
| ① 消息落库 | 外键/瞬时失败跳过（内存模式）| 会话建失败也能继续聊 |
| ③ 工具重试 | 只读工具（search/fetch）瞬时失败重试 2 次 | 限流/抖动不丢请求（写操作工具不重试——幂等）|
| ③ 超时统一 | settings.tool_timeout_seconds | 长挂起有兜底 |
| 全链路 | 异常四分类（可重试/不可重试/业务/系统）+ AST 扫描防裸捕获 | 故障可定位、降级精准 |

**🟥 B. 成本（成本控制分支，已合并 develop）**

| 环节 | 新增行为 | 业务价值 |
|------|----------|----------|
| ③ LLM 调用 | 缓存命中省调用（memory/redis 双后端）| 重复查询不烧钱 |
| ⑤ 成本核算 | 单价 × 增量 token → 流水 | 每会话花了多少钱可查 |
| ⑤ 软告警 | 累计超阈值 → 落库 + SSE 提示 | 超预算不硬断，提示自主决定 |
| ⑥ cost API | /v1/cost/summary + /alerts | 前端/审计查询 |

**🟥 C. 安全（安全机制分支，已合并 develop）**

| 环节 | 新增行为 | 业务价值 |
|------|----------|----------|
| ③ fetch_url | URL 严格校验（http/https + 无注入字符）| 防注入/协议攻击 |
| ③/④ 工具 | 命令/路径校验（防穿越）| 防越权写入/读取 |
| 全链路 | 校验失败 → security/blocked 审计 | 拦截可计数、可回溯 |
| 文件返回 | FileRef 对象路径校验 | 防任意路径回显 |

### 7.3 总：全景一句话

```
主流程没动（用户→api→主图→工具→审核→交付 仍是这条线）
        │
        ├─ 🟥 容错：每个环节"瞬时故障不中断"（重试+降级）
        ├─ 🟥 成本：每个 token"花多少钱可查"（流水+缓存+软告警）
        ├─ 🟥 安全：每个越权/注入"被拦+留痕"（校验+审计）
        │
        └─ 🟦 原有：模型编排/审核回路/观测底座 保持不动
```

> **改动都是"挂在主流程横切点上加固"，不重写业务编排**——新增 3 层护栏（容错/成本/安全）包裹原有能力，342+ 测试护航。
