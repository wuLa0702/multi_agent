## §1 设计目标与默认假设

**一句话**：为"社招转 AI Agent 方向、仅有个人 demo、缺少企业工程实践"的求职者，产出**符合目标岗位关键词、能抗追问、经得起查证**的技术简历。

**设计目标（按优先级）**：
1. **先定准则再写内容**——简历写作法则统一（§2），评审与后续修改都以此为标尺
2. **把两个个人项目包装到"准企业级工程"水准**——用测试/CI/架构/文档证明工程能力，弥补"无企业实践"短板
3. **可抗追问**——简历每个数据点都能在仓库里查到出处，面试不翻车
4. **产出实际可投递的简历**（步骤 ③ 实际开发）

**默认假设**（待 §6 信息采集表确认）：
- 目标岗位：**AI Agent / LLM 应用工程师**（两项目最对口）
- 求职偏好：AI 创业公司/中厂为主，兼容大厂海投（一页为主、两页上限）
- 过往工作经历：**未知，两种策略待定**（§3.5 给出，采集表确认）
- 项目一 = `D:\gtiHub\llm_wiki_selfbuild`（知识沉淀系统，明确"不是 RAG"）
- 项目二 = `D:\gtiHub\multi_agent`（多 Agent 协作系统，本仓库）

## §2 写简历准则清单（重点）

> 准则分层：**定位法则（先想清楚为谁写）→ 内容四法则（怎么写）→ 叙事法则（怎么组织）→ 量化法则（怎么证明）→ 核心法则（怎么提炼）→ 措辞细节（怎么打磨）**。
> 每条法则标注来源（网络参考见 §8），并给一个用你真实项目素材的短 demo。

### 2.1 定位法则（写之前，先定方向）

**法则 ① 目标导向法则（第一优先）**
- **定义**：简历不是"我做过什么的流水账"，而是"**为这个岗位我匹配什么**"。先定目标岗位，从 JD 里提取关键词，让简历关键词与 JD 对齐。HR 平均 **7 秒**过筛，前 1/3 首屏决定去留。
- **关键动作**：投递前拿岗位 JD 反向检查简历，把 JD 里的核心技能词自然埋入经历描述。
- **demo（目标岗 = AI Agent 工程师）**：
  - ❌ 摘要写："熟悉 Python，做过一些后端项目"
  - ✅ 摘要写："独立设计与实现**多 Agent 协作系统**（LangGraph + FastAPI + SSE），覆盖 **Agent 编排 / 人在回路审批 / 记忆抽取 / MCP 双向集成 / 沙箱执行**全链路——与 AI Agent 工程师岗位 5 项核心要求直接对齐"

**法则 ② 首屏三要素法则**
- **定义**：7 秒过筛要同时抓住 3 个要素——**岗位适配性（关键词对齐）> 量化成果（核心竞争力）> 核心技能（快速匹配）**。三要素不全，直接淘汰。
- **关键动作**：个人总结段用"3 个量化亮点 + 1 个差异化定位"句式，把最大数字放最前。
- **demo**：
  - ❌ 首屏堆砌"熟悉 C/Python/Java/HTML/CSS/JS"（无数字、无关键词）
  - ✅ "两个从 0 到 1 的 AI 系统：**3.1 万行** Python + **80 个**接口测试，**10 天**从立项到部署上线；手写核心 Agent 编排逻辑（非样板代码）"

**法则 ③ 一页纸 / 篇幅法则**
- **定义**：社招技术简历**一页为主、两页上限**（5~10 年经验才用两页）。重点放前 1/3，按"总结 → 项目 → 经历"倒序。旧传统说法"2~4 页"已不适配现代技术岗筛选节奏。
- **关键动作**：两个项目各压到 6~8 行；一条经历一行；量化数据放行首。
- **demo（两页 vs 一页）**：把"项目背景 3 行 + 细节 6 行"压缩为"定位句 1 行 + 要点 4~5 行（每条含动作+量化）"。

**法则 ④ 二八法则**
- **定义**：**80% 篇幅给最重要的 1~2 个项目**，20% 给其余。宁要一个挖透的项目，不要三个浅尝辄止的。
- **关键动作**：两个项目占正文 60%~70%，工作经历/教育压缩到 30%。
- **demo**：多 Agent 项目写 7 行、Wiki 项目写 6 行，其余全部压缩为一行列表。

**法则 ⑤ 真实性法则（诚信红线）**
- **定义**：**包装 ≠ 造假**。可以提炼价值、突出亮点、优化措辞，但禁止虚构项目/伪造数据/夸大无法站住脚的数字。HR 背调 + 面试追问会击穿造假。
- **关键动作**：简历每个数字都要能在仓库/日志里找到出处；标注"设计阶段 vs 已实现"。
- **demo（用你项目真实校准）**：多 Agent 项目"手写 LangGraph 主图"目前是**设计预留未实现**——简历只能写"基于 deepagents（LangGraph 内核）搭建"；测试数写 **235 个函数**（实测），不写"几百个"。

### 2.2 内容"四大法则"（怎么写经历）

> 技术简历最实用版本：**关键词 / 动词 / 数字 / 结果**。（另有传统版本：格式规范、内容简先诚信、四大板块、篇幅控制——不冲突，技术岗用本组为主。）

**法则 ⑥ 关键词法则（对齐 JD）**
- **定义**：多用目标岗位的行业术语（LangGraph、Agent 编排、SSE、MCP、RAG、记忆系统、人在回路 HITL、Checkpointer、沙箱执行……），让 HR/算法关键词匹配命中。
- **demo**：
  - ❌ "做了一个聊天机器人，能联网搜索"
  - ✅ "基于 **LangGraph + deepagents** 构建多 Agent 系统：**工具调用（MCP 协议）→ 审核子代理 → 人在回路（HITL）审批**全链路，SSE 流式输出"

**法则 ⑦ 动词法则（强动词开头）**
- **定义**：每条经历以**强动词**开头（主导 / 设计并实现 / 搭建 / 重构 / 优化 / 落地），不用弱动词（负责 / 参与 / 协助 / 做了）。
- **关键动作**：动词升级表见 §2.6；一条经历只用一个主动词。
- **demo**：
  - ❌ "负责了一个多 Agent 系统"
  - ✅ "**独立设计与实现**多 Agent 协作系统……"

**法则 ⑧ 数字法则（量化）**
- **定义**：结果尽可能用数字（规模 / 效率 / 质量 / 频率四维度，见 §2.4）。
- **demo**：
  - ❌ "项目很大，代码很多，测试也写了"
  - ✅ "**3.1 万行** Python / **45 个测试文件** / **80 个接口**（wiki 项目）；**235 个测试函数** / **29 个 REST 接口** / **331 次提交** / **14 天**（多 Agent 项目）"

**法则 ⑨ 结果法则（呈现成果，不只描述职责）**
- **定义**：写"做了什么、达成了什么"，不写"负责 XX 模块"这种职责描述。结果可以是：上线了 / 速度提升 / 覆盖度 / 可复现 / 通过率。
- **demo**：
  - ❌ "负责记忆模块的开发"
  - ✅ "设计并实现跨会话记忆系统：LLM 抽取单行事实 + 异步队列子代理 + 指纹去重，**断点可恢复、会话间可继承**"

### 2.3 叙事法则（怎么组织经历）

**法则 ⑩ STAR 法则（骨架）**
- **定义**：**S**ituation（背景）→ **T**ask（任务）→ **A**ction（行动）→ **R**esult（结果）。把"我做了 XX"改成"在 XX 场景下，为解决 XX 问题，我做了 XX，最终达成 XX"。
- **关键动作**：简历不写全 STAR，压缩成"行动点"（强动词开头 + 方法 + 可量化结果）；面试追问时再展开全 STAR。
- **demo（多 Agent 项目）**：
  - ❌ "支持人工审批，能中断恢复"
  - ✅ "S：多 Agent 执行不确定性高，需人工把关；T：实现可中断可恢复的审批机制；A：基于 LangGraph **interrupt 中断 + Checkpointer 断点持久化 + Redis 待审队列**；R：支持 approve/reject/edit/respond 四类决策，**中断后可精确恢复上下文**"

**法则 ⑪ 谷歌 XYZ 公式（一句话叙事）**
- **定义**：**完成 [X]，通过 [Y] 的手段，达到 [Z] 的效果**。适合项目一句话定位与 STAR 的压缩版。
- **demo**：
  - "**完成**多 Agent 系统的长任务可靠执行，**通过** HITL 审批 + Checkpointer 断点恢复，**达到**中断不丢上下文、关键操作人工可接管"
  - "**完成**知识文档的自动化沉淀，**通过** LLM 一次编译 + 增量更新（非查询时检索），**达到**知识库'越用越厚'、可溯源"

**法则 ⑫ 倒金字塔 / 重点前置法则**
- **定义**：**结论先行，细节在后**。每段首句是最大卖点（数字/定位），后文才是支撑细节。
- **demo**：
  - ❌ 先写技术栈罗列，最后才提"上线了"
  - ✅ 首句直接给定位+数字："独立搭建 **3.1 万行**的知识沉淀系统（FastAPI + LangChain），明确**区别于 RAG**：LLM 编译沉淀一次、增量更新"

### 2.4 量化法则（怎么证明）

**法则 ⑬ 量化四维度**
- **定义**：任何结果从四个维度量化，任选其一或二：
  - **规模维度**：多少行/多少个/多少表（如"9 张 SQLite 表 + Redis"）
  - **效率维度**：省了多少时间/多少步骤（如"审核流从人工 5 步降到 1 步"）
  - **质量维度**：多准/多稳/多可复现（如"235 测试全绿、WAL 模式防数据损坏"）
  - **频率/覆盖维度**：多少次/覆盖多少人（如"331 次提交、14 天迭代"）
- **关键动作**：不确定就写"约/近/超"做**模糊量化**，也比没有数字强。
- **demo**：
  - ❌ "系统很稳定"
  - ✅ "单测 **235 个**全绿，HITL 待审队列 Redis **原子消费（getdel）**，无重复审批"

### 2.5 核心法则（怎么提炼）

**法则 ⑭ 黄金公式（一条经历的终极形态）**
- **定义**：**动作动词 + 具体做法 + 量化结果 + 业务影响**。
- **demo（一条可直接上简历的要点）**：
  - ✅ "**主导**多 Agent 系统 Agent 编排层：基于 deepagents 搭建每会话 LangGraph 图 + 有界 LRU 缓存（32 会话、双检锁），**实现**运行时多模型切换与 SSE 事件分发（token/tool_call/subagent/approve/done），**产出** 235 个测试函数、29 个接口，**支撑** HITL 审批与记忆抽取等 6 大子系统"

**法则 ⑮ 一句话项目定位法则**
- **定义**：每个项目能用一句话说清"**我用什么技术、解决了什么问题、凭什么不是普通 demo**"。
- **demo**：
  - 多 Agent："基于 deepagents + LangGraph 的多 Agent 协作系统：从 Agent 编排到人在回路、记忆、MCP、沙箱、成本观测的**全链路实现**，235 单测 + 审计日志证明工程化，而非玩具 demo"
  - Wiki："基于 Karpathy LLM Wiki 模式的知识沉淀系统：LLM 将源文档**编译一次**为结构化互链 Wiki（区别于 RAG 的查询时检索），知识越用越厚，含知识图谱 + 质量 lint + 桌面打包 + CI 部署"

### 2.6 措辞细节法则（打磨）

**法则 ⑯ 动词升级表 + 能力区分**
- **定义**：弱动词升级；"描述职责"升级为"展示能力"。
- **demo 动词升级表**：

| 弱动词 ❌ | 强动词 ✅ |
|-----------|-----------|
| 负责 | 主导 / 独立设计与实现 |
| 参与 | 核心实现 / 独立完成 |
| 做了 | 搭建 / 实现 / 落地 |
| 支持 | 提供 / 打通 / 集成 |
| 写了很多代码 | 实现 3.1 万行 Python |
| 系统不崩 | 断点可恢复、降级不阻断 |

- **demo（职责 → 能力）**：
  - ❌ "负责 SSE 流式接口"
  - ✅ "设计并实现类型化 SSE 事件协议（token/tool_call/approve/done/error），与前端共享 schema，支持中断恢复"

**法则 ⑰ 诚实坑点 / 主动讲短板法则**
- **定义**：转型者最大的信任点——主动在简历/面试点出"这是个人项目、无企业实践"，但用工程规范（测试/CI/文档/双环境/安全审计）证明"以企业级标准要求自己"。面试官问短板时主动讲 = 加分。
- **demo（面试话术，非简历）**："项目为个人从 0 到 1 完成，无企业多人协作经历——但我用企业工程标准约束自己：235 个单测、CI 部署、日志审计、dev/prod 双环境、安全路径校验，证明我能按工程规范交付。"

### 3.1 个人总结（草稿，待采集表后定稿）

> 采用"强动词 + 量化 + 定位"三段式：
> 1. 两个从 0 到 1 的 AI 系统（共 **4 万+ 行** Python，**80 个测试文件**），手写核心 Agent 编排逻辑，覆盖 Agent 编排 / 人在回路 / 记忆 / MCP / 沙箱 / 知识沉淀全链路
> 2. 以企业工程标准要求个人项目：**235+ 单测**、CI 自动部署、dev/prod 双环境、日志与安全审计、文档治理
> 3. 差异化定位：**AI Agent 应用工程师**——既有工程落地（FastAPI + 前端全栈），又懂 Agent 原理（LangGraph/深挖记忆与 HITL），学习自驱（14 天 331 次提交持续迭代）

### 3.3 项目一：LLM Wiki 知识沉淀系统（写法定位）

**定位句**：基于 Andrej Karpathy「LLM Wiki」模式的**知识沉淀管理系统**——LLM 将源文档**编译一次**为结构化互链 Wiki，增量更新，**明确区别于 RAG**（不是查询时检索，而是编译沉淀，知识越用越厚）。

**初步要点（STAR 压缩，量化，待 §4 弹药定稿）**：
- 从 0 实现双后端：FastAPI + LangChain 多模型适配，JWT 认证；React 19 前端
- **双层存储**：Markdown 页面（YAML frontmatter + 7 类页面分类）+ SQLite 元数据（页面/链接图/去重/任务队列/成本日志 9+ 表）
- 知识图谱 + Louvain 社区检测；BM25 检索（语义检索按资源约束关闭——诚实点）
- 多格式解析（PDF/Word/PPTX/Excel）+ 质量 lint + 隐私规则
- 工程化：45 测试文件、GitHub Actions 自托管 CI 部署、PyInstaller 桌面 EXE
- 规模：**3.1 万行 Python**，14 天从 MVP 到可部署

### 3.4 项目二：多 Agent 协作系统（写法定位）

**定位句**：基于 deepagents + LangGraph 的**多 Agent 协作系统**——从 Agent 编排、人在回路（HITL）审批到记忆抽取、MCP 双向集成、沙箱执行、成本与审计观测的**全链路工程实现**。

**初步要点（STAR 压缩，量化，待 §4 弹药定稿）**：
- 每会话 LangGraph 图 + 有界 LRU 缓存（32 会话、双检锁）；声明式子代理（YAML）
- **人在回路（HITL）**：interrupt 中断 + Checkpointer 断点恢复 + Redis 待审队列，支持 approve/reject/edit/respond 四类决策
- **记忆系统**：LLM 抽取单行事实（跨会话）+ 异步队列子代理 + 指纹去重
- **MCP 双向**：外部 MCP 服务管理（故障隔离）+ FastMCP 服务端暴露内部工具
- **沙箱执行**：OpenSandbox（本地 Docker / 云端），资源限制 + 会话复用
- **可观测/安全**：SSE 类型化事件、工具审计、成本台账与告警、权限策略层、错误分级降级
- 工程化：**235 测试函数 / 29 接口 / 9 张表 + Redis / 331 提交 / 14 天**
- 规模：**1.04 万行 Python**（backend/src）+ 79 个前端源文件
