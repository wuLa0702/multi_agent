## 一、记忆体系整体设计

### 问题
你做了记忆系统？记忆分几层？怎么组织的？

### 标准版话术（总分总）

【总·30秒】
"记忆我做了三层：文件记忆（AGENTS.md / tasks / decisions，人可读的项目级记忆）+ 语义 Store（SQLite 跨会话回忆，存抽取出来的事实）+ memory_agent 并列执行体（后台队列抽取，**不阻塞对话**）。检索带时间衰减、窗口裁剪、质量评分。核心思路是——记忆不是把对话全存下来，是**抽取值得记的、异步写、按相关性取**。"

【分·90秒】
"三层我分别说：

**第一层，文件记忆**：项目级的 AGENTS.md、tasks、decisions 三个文件，人工可读，Agent 按需读。比如 tasks.md 的已完成任务超了 20 条就归档到 tasks_archive.md，归档文件**不注入**、Agent 想起来了再去读——防止长期对话被任务清单撑爆。

**第二层，语义 Store**：SQLite 落库，跨会话回忆。关键不是存对话全文——这里我踩过坑，最初是把整段回复存进去，结果所有对话全文进记忆库，注入时污染上下文。后来改成 **LLM 抽取式**：对话结束先让 LLM 判断这段有没有长期价值，有才把一句话事实抽出来存。按类型分 namespace：user_profile（用户画像）和 facts（事实常识），检索时画像优先。

**第三层，memory_agent**：这个最特别——它不是主链路里的工具，是**并列执行体**。SSE 跑完 done 之后，把记忆抽取任务丢进后台队列，由独立 worker 异步消费，不阻塞对话流。为什么这么做？因为记忆抽取是额外一次 LLM 调用，如果同步等它，done 事件就要等这个 LLM 跑完才能发，用户看到结果就慢了。"

【总·20秒】
"所以记忆体系是三层分工：文件记人读的，Store 记跨会话的，memory_agent 负责异步不拖慢。一句话：**抽取值得记的、异步写、按相关性取，这是我对'后台任务不阻塞主链路'的落地。**"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| 记忆和上下文什么关系？ | 记忆是持久层，上下文是注入窗口；对话开始把最近记忆注入 SystemMessage，但要控量，所以有窗口裁剪 |
| 记忆库存的是什么粒度？ | 一句话事实（LLM 抽取），不是对话全文；太短（<5 字）丢弃，超长截断 |
| 单用户为什么要做记忆？ | 跨会话回忆用户偏好和事实，不用每次重问——比如用户说过"偏好轻量方案"，下个会话直接沿用 |

### 一句话记忆
**三层记忆：文件（人读）+ Store（跨会话）+ memory_agent（异步不拖慢）；存"值得记住的"，不存全文。**

## 二、语义 Store：抽取与质量

### 问题
语义 Store 具体怎么实现的？存了什么？怎么保证质量？

### 标准版话术（总分总）

【总·30秒】
"语义 Store 的核心是 **LLM 抽取式写入**：对话结束，LLM 判断这段有没有记忆价值，有才抽出一句话事实，按类型落 SQLite。质量有评分，检索有排序和裁剪，防止垃圾记忆和上下文污染。"

【分·90秒】
"写入这条链：对话结束 → 先看对话轮次，少于 2 轮直接跳过，省 token → LLM 抽取判断有没有价值 → 有就把一句话事实抽出来 → 按类型分类（用户说'我喜欢/我偏好/请记住'这类走 user_profile，否则走 facts）→ 落对应 namespace。

质量这块我做了个轻量评分，1-5 分：信息量看长度和有没有数字专名，facts 类型加一分，重复条目扣分。但注意——**低分只审计不拦截**，还是写入，只是打日志标注，供定期整理参考。为什么不硬拦？因为启发式评分可能误判，拦截了可能把有价值的记忆丢掉，宁可比价、不硬拦。

检索这块做了上下文工程：**画像优先**（user_profile 永远排前面），同优先级内**时间衰减**（新的在前），最后**窗口裁剪**——注入的记忆 token 估算不超过上下文的 10%，超了就截断，防止记忆把 128k 窗口挤爆。"

【总·20秒】
"所以语义 Store 的取舍是：**宁可不记、不错记**——抽取式保证存的都是值得记的；**宁可比价、不硬拦**——评分只审计不拦截，防误杀；检索永远让位给主对话——窗口上限 10%。"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| 质量评分怎么评的？ | 纯函数 1-5：长度+数字/专名=信息量，facts 类型+1，重复扣分；低质只审计不拦截 |
| 关联链是什么？ | P3 轻量版：写入时带 related 字段引用相似记忆，不是真图谱，是轻量引用 |
| 记忆会不会污染上下文？ | 双重保险：注入上限 5 条 + 窗口裁剪 ≤10%；归档文件不注入只按需读 |

### 一句话记忆
**Store 存"抽取的一句话事实"，质量 1-5 分只审计不拦截，检索画像优先 + 时间衰减 + 窗口 10% 裁剪。**

## 三、memory_agent 并列执行体（后台不阻塞）

### 问题
为什么要做 memory_agent 而不是直接同步抽取？并行执行体怎么实现的？

### 标准版话术（总分总）

【总·30秒】
"记忆抽取是额外 LLM 调用，**绝不能同步阻塞 done**。我从裸 asyncio.create_task 升级到 memory_agent 并列执行体：独立子代理 + 多 worker 后台队列，可观测、不堆积、失败可追踪。"

【分·90秒】
"演进是这样的：第一版我用 asyncio.create_task 丢后台，简单是简单，但任务**不可观测**——失败不知道、堆积没上限、重复也没人管。后来升级成**队列 + 多 worker**：lifespan 启动 2 个 worker 协程，各自 while 循环消费，天然并发；队列上限 100，满了拒绝防堆积；每个任务带**指纹幂等去重**——session_id + 用户消息 + 回复一起 hash，同一个对话不会重复入队，指纹 LRU 上限 1000 防内存泄漏。

worker 内部调的是预编译的 memory_agent 子代理，它有两个特点：一是**独立 StateBackend**，不碰主会话文件，隔离干净；二是**工具集最小化**——只挂记忆工具（search_memory / write_store 那几个），不给文件/沙箱工具，防它越权乱来。模型上支持独立小模型决策，配置了 memory_agent_model 就用小模型，空着用主模型兜底。

有个实现细节值得讲：子代理编译时 store 还没初始化（lifespan 异步），闭包注入不可行，所以工具内部用 get_store() **运行时解析**，每次调用取当前实例。"

【总·20秒】
"这个设计的价值是**把'后台任务不阻塞主链路'做成工程化的**：可观测（审计日志 + pending/running/completed/failed 状态计数）、有界（队列满拒绝）、防重（指纹幂等）、隔离（独立 backend）。面试官问'你怎么保证异步任务不失控'，这就是答案。"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| 为什么不直接用 create_task？ | 能跑但不可观测：失败没日志、堆积无上限、重复无去重；队列版全解决 |
| worker 并发怎么实现的？ | 多 worker 协程（2 个），每个独立 while 消费；单 worker + Semaphore 是伪并发（串行）|
| 后台失败会影响对话吗？ | 不会，内部全容错 try/except 不冒泡；记忆是旁路能力，失败只记日志 |
| 工具集为什么最小化？ | 子代理权限隔离实践——只给记忆工具，防它越权碰文件/沙箱 |

### 一句话记忆
**memory_agent = 独立子代理 + 多 worker 队列（指纹去重 / 有界 / 审计），把异步不阻塞做成可观测、防失控。**

## 四、文件记忆与整体协同

### 问题
文件记忆和 Store 怎么分工？三者怎么协同成闭环？

### 标准版话术（总分总）

【总·30秒】
"文件记忆管'项目结构级'的长期事实（AGENTS.md 全量注入 + tasks/decisions 按需读），Store 管'用户会话级'的回忆（跨会话注入），memory_agent 管'写'——三条通道，职责不重叠。"

【分·90秒】
"文件记忆这块：AGENTS.md 是单文件全量注入（官方 MemoryMiddleware），tasks.md 和 decisions.md 按需读、不常驻——tasks 已完成超 20 条归档到 archive，都是**不注入、Agent 想起来了再去读**。它的特点是**人工可读**：你打开仓库能直接看到 Agent 记得什么，可审计。

协同链路是：对话结束 → memory_agent 后台把值得记的抽出来 → 写 Store（user_profile / facts）或维护文件记忆 → 下一轮对话开始时，检索注入（画像优先 + 裁剪）进 SystemMessage → Agent 带着记忆跑。整个体系叫**记忆闭环**：写是异步的、存是分层的、取是按相关性的。"

【总·20秒】
"一句话：**文件记忆给 Agent 项目常识，Store 给 Agent 用户记忆，memory_agent 负责写且不拖慢对话**——这是我在多 Agent 系统里对'长期记忆'的完整落地。"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| 文件记忆 vs Store 冲突怎么办？ | 职责分界：文件=项目级结构/任务，Store=用户画像/事实；检索时 Store 注入，文件按需读 |
| 记忆会不会过期/膨胀？ | 四道防线：任务归档、Store 质量评分、注入窗口裁剪、指纹去重 |
| 怎么知道记忆有没有生效？ | 审计日志（layer=memory_agent）+ 状态计数（pending/running/completed/failed）可观测 |

### 一句话记忆
**文件记忆管项目、Store 管用户、memory_agent 管写；写异步、存分层、取相关，四道防线防膨胀。**

## 五、踩过的坑（主动讲，证明实战）

### 问题
做记忆体系遇到过什么问题？怎么解决的？

### 标准版话术（总分总）

【总·30秒】
"踩过两个真坑，都是实测/评审发现的：**全文进记忆库污染上下文**、**裸 create_task 任务失控**。第一个改了抽取式，第二个升级成队列执行体，现在记忆是旁路能力，任何一步失败都不影响对话。"

【分·90秒】
"两个坑具体是：

**坑1：对话全文进记忆库**
最初实现把整段回复直接写记忆库，只做了长度过滤。结果所有对话全文都进去了，注入时把上下文污染得一塌糊涂。这是用户评审发现的。解决：改成 **LLM 抽取式**——先判断这段有没有长期记忆价值，有才抽一句话事实存。加上质量评分、短对话跳过（少于 2 轮不抽），三层过滤保证进库的都是干货。教训：记忆系统的坑不在存储，在**写什么**。

**坑2：裸 asyncio.create_task 任务失控**
第一版后台抽取用 create_task 丢出去就不管了——失败没日志、队列堆积无上限、相同对话重复抽取。解决：升级成 **memory_agent 并列执行体**——独立子代理 + 2 worker 队列 + 指纹幂等去重 + 审计日志，任务从'丢出去不管'变成'可观测、有界、防重'。教训：后台任务不是 fire-and-forget 就完了，工程化要可观测。"

【总·20秒】
"这两个坑让我对'旁路能力'的理解到位了：**旁路不是随便跑跑，是即使失败也不影响主链路，但本身要做到有界、可观测、防重**。"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| 怎么发现这些坑的？ | 全文进库是用户评审发现；任务失控是跑起来发现不可观测、没有审计 |
| 记忆写失败会影响对话吗？ | 不会，全链路 try/except 降级：抽取失败跳过、检索失败跳过、写入失败记日志，对话照常 |
| 还有什么坑？ | 子代理编译时 store 未初始化，闭包注入不可行——改成运行时 get_store() 解析 |

### 一句话记忆
**两个实证坑：全文进库污染上下文→改抽取式、裸 create_task 失控→改队列执行体；旁路能力=不影响主链路 + 本身有界可观测。**
