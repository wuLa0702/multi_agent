## 一、分层架构

### 问题
你们这个多Agent系统后端分几层？每层是干什么的？层和层之间的依赖有什么规则？

### 标准版话术（总分总）

【总·30秒】
"后端分四层：API接入层、Agent编排层、能力层、公共底座。依赖单向，上层只能调下层，禁止反向，api层也不能直连数据库。"

【分·90秒】
"具体来说：
1. **API接入层**：负责路由、SSE流式编排、会话CRUD，是前端的唯一入口
2. **Agent编排层**：主Agent编译图、子代理委派、中间件栈，是业务核心
3. **能力层**：包括MCP工具网关、沙箱、记忆双写、SQLite仓储——这四个虽然是不同目录，但都属于'被Agent调用的具体能力'，所以归为同一层
4. **公共底座**：配置、路径、日志、多provider LLM适配、Pydantic模型，是所有层都能用的基础设施

依赖规则是单向的：api只能调agent，agent调能力层，能力层调公共底座。为什么这么定？如果api能直接调db，业务逻辑就会散落在api层，以后改数据库要改好多地方。所有SQL都走能力层的仓储，改数据库只需要改一个地方，单一出口、可测试。"

【总·20秒】
"分层的核心目的是降低耦合——每层只关心自己的职责，改一层不影响其他层，这也是后续能快速迭代的基础。"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| 为什么把mcp/sandbox/memory/db都归为能力层？ | 它们的共同特点是"被Agent层调用、提供具体能力"，按职责抽象归为同一层，不是按目录分 |
| api禁直调db，那会话查询怎么办？ | 会话查询走api→agent→能力层db仓储，虽然多一跳但保证了单一SQL出口 |
| 中间件属于哪一层？ | Agent编排层，挂在主Agent执行链路上 |

### 一句话记忆
**四层架构 + 依赖单向 + api禁直调db = 低耦合、单一出口。**

## 二、演进路径（为什么多Agent）

### 问题
为什么要拆成多Agent？单体不行吗？

### 标准版话术（总分总）

【总·30秒】
"之前做过一个单体Agent的LLM Wiki项目，暴露了三个坑，所以做这个新项目时一开始就按多Agent架构设计。"

【分·90秒】
"三个坑具体是：
1. **Prompt膨胀**：一个系统提示词要同时告诉Agent'你会搜索、会写、会审核'，角色冲突，提示词越来越长
2. **上下文污染**：搜索过程返回10条结果+5篇正文，塞满对话窗口，后面写报告时这些搜索细节还在上下文里，干扰写作
3. **工具过载**：工具有搜索、抓取、沙箱、写文件十几个，Agent选工具的准确率下降，经常选错

所以新项目的设计是：主Agent只做编排和撰写，search_agent独立搜索用便宜模型，review_agent独立审核用独立评审标准，每个子代理上下文隔离、工具最小化，顶层主Agent统一协调。"

【总·20秒】
"不是为了多Agent而多Agent，是单体架构在复杂研究场景下确实扛不住，多Agent是解决这三个坑的自然选择。"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| 多Agent的代价是什么？ | 成本高2-8倍、延迟从101s到860s、协调复杂度上升，所以不是所有场景都适合 |
| 怎么平衡多Agent的成本？ | 模型分级（搜索用便宜模型）、缓存、任务分级（简单任务不调子代理） |
| 有没有考虑过其他方案？ | 比如RAG+单Agent，但RAG解决不了"角色冲突"和"工具过载"的问题 |

### 一句话记忆
**单体三坑（Prompt膨胀/上下文污染/工具过载）→ 多Agent角色分离。**

## 三、主流程（一条请求怎么走）

### 问题
讲一下一次请求的完整流程。

### 标准版话术（总分总）

【总·30秒】
"这是一个面向深度研究任务的多Agent系统。一次请求的主流程是：用户前端发消息 → 后端对话层入库并创建会话 → 主Agent编排 → 复杂任务委派给搜索和审核两个子代理 → 搜索子代理做两阶段受控抓取 → 沙箱里做数据处理和文档生成 → 审核子代理做评分细则 → 不通过就打回重做，最多N轮 → 人在回路做最终确认 → SSE事件流返回前端。"

【分·90秒】
"几个关键设计：
1. **为什么拆子代理**：单体Agent有三个坑——Prompt膨胀、上下文污染、工具过载。拆开后search_agent用便宜模型独立搜索，review_agent用独立评审标准，上下文互不干扰。
2. **受控抓取两阶段**：第一次只爬标题/概要/时间，LLM判断哪些重要，第二次才抓正文，省Token也省时间。
3. **沙箱隔离**：数据拼接、生成Word/Excel/PPT这些高风险操作都放OpenSandbox里跑，防止恶意代码影响主机。
4. **审核闭环**：评分细则达到阈值就通过，没通过打回补充，有最大轮次限制防止无限修订；关键节点还可以触发人在回路审批。
5. **流式返回**：整个过程通过10类SSE事件实时推给前端，用户能看到搜索进度、工具调用、审核结果，不是干等。"

【总·20秒】
"主流程之外还有三横切——容错、成本、安全——都是挂在主流程上的护栏。整个系统290个测试全绿，多Agent虽然成本比单Agent高2-8倍，但通过模型分级和缓存把成本控住了。"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| 简单问题怎么走？ | 主Agent直接用内置工具回答，不委派子代理，省成本省时间 |
| 审核不通过打回给谁？ | 打回主Agent，主Agent根据审核意见补充信息或重新委派搜索 |
| 人在回路在哪个环节触发？ | 高风险工具调用前、最终报告交付前，可配置 |

### 一句话记忆
**用户输入 → 编排 → 子代理分工 → 搜索抓取 → 沙箱处理 → 审核 → HITL → SSE返回。**
