## 〇、一句话理解版（锚点）🔄 2026-08-14

**上行 + 下行，两条路分开记**：

- **上行走 HTTP 请求**（一次性）：前端传数据/发指令——发消息 `POST /v1/chat/stream`、审批 `POST /approve`……一次请求一次响应，用完即断
- **下行走 SSE 长连接**（单向推流）：后端持续推事件流（token / tool_call / subagent / approve / done……），前端只收不推

```
前端 ──HTTP 请求──▶ 后端     ① 上行：传数据/发指令（一次一请求，用完即断）
前端 ◀─SSE 长连接── 后端     ② 下行：后端持续推事件流（长连接，单向）
```

**⚠️ 开流 nuance（别被面试官绕进去）**：SSE 长连接本身也是前端用**一个 HTTP 请求"开"出来的**——先 `POST /v1/chat/stream`，后端收到后把连接挂住变成长连接、开始推 SSE 事件，`done`/`error` 后才关闭。所以准确说：**HTTP 请求负责"上行 + 开流"，SSE 负责"下行持续推"**。

> **一句话记忆**：上行走 HTTP 请求（一次性），下行走 SSE 长连接（单向推流），SSE 流本身由 HTTP POST 发起。

## 一、SSE整体设计

### 问题
讲一下你们的对话流式是怎么做的？为什么用SSE？

### 标准版话术（总分总）

【总·30秒】
"对话流式我做的不是简单的token推送，而是一套前后端共享的SSE事件协议——多Agent任务最长要跑十几分钟，用户不能干等，需要实时看到'正在搜索/正在审核/成本超了'这些过程。我定义了10类事件，每个事件对应前端一个组件，用Pydantic模型做契约，前后端共享类型定义。"

【分·90秒】
"几个关键点：

**① 为什么选SSE不选WebSocket？**
多Agent场景是'客户端发一次请求，服务器长时间流式返回'，不需要双向实时通信——用户发消息用普通HTTP POST就够了，审批也是独立的REST接口。SSE单向推送刚好匹配，比WebSocket简单，还自带断线重连。

**② 协议怎么设计的？（举例子，不列清单）**
核心思路是'事件即状态'：
- token事件：逐chunk推，实现打字机效果，这个是基础
- tool_call事件：带状态机（running/completed/error），前端渲染成工具调用卡片，用户能看到'正在调用搜索工具...完成了，返回5条结果'
- approve事件：人在回路审批时推送，带run_id和checkpoint_id，前端弹审批框
- 还有subagent启停、cost_alert成本告警、todos任务规划这些，总共10类，每个都是为了让多Agent的黑盒过程变透明。

**③ 踩过的坑（主动讲）**
有个坑：deepagents的astream_events v3版本，国产模型不支持content-block协议，导致token事件直接整段输出，打字机效果毁了。后来校准回v2版本，用多事件分发的方式，逐chunk推送才恢复正常。这个坑让我意识到，流式协议不能只看官方文档，要针对实际用的模型做适配验证。"

【总·20秒】
"所以SSE在这个项目里不是'流式输出'这么简单，它是多Agent过程的可视化协议——把后端的执行状态翻译成前端能渲染的事件，让十几分钟的黑盒任务变成用户能看懂、能干预、能监控的透明过程。"

### 追问预案

| 追问 | 答题要点 |
|------|---------|
| SSE和WebSocket具体区别？ | 单向vs双向、HTTP原生vs独立协议、自动重连vs自己写、适合推送vs适合实时交互 |
| 10类事件是怎么定的？会不会太多？ | 从业务场景倒推（多Agent有哪些状态需要展示），每个事件对应一个前端组件，不多不少 |
| 前后端契约怎么共享？ | Pydantic模型定义在schemas/，前端用相同的TypeScript类型，契约即代码 |
| 断线重连怎么处理？ | SSE自带Last-Event-ID，前端记录最后收到的事件ID，重连时带上，后端从断点继续推 |
| 为什么审批不用SSE而用REST？ | 审批是客户端→服务器的操作，SSE是单向的，审批走REST POST /approve更简单清晰 |

### 一句话记忆
**SSE = 多Agent过程的可视化协议，不是简单的token流。**

## 二、事件协议设计细节

### 问题
SSE事件协议具体是怎么设计的？事件payload是什么格式？

### 标准版话术（总分总）

【总·30秒】
"每个事件都是一个JSON对象，包含event类型和payload数据，payload用Pydantic模型序列化，前后端共享类型定义，保证契约一致。"

【分·90秒】
"事件格式统一是：
```json
{
  "event": "token",
  "data": { "chunk": "你好" }
}
```

不同事件的payload结构不同：
- **token事件**：{ chunk: string }，逐字推送
- **tool_call事件**：{ tool_name, status, result? }，status是running/completed/error三态
- **approve事件**：{ run_id, checkpoint_id, call_id, description }，前端用这些信息调审批接口
- **cost_alert事件**：{ level, current_cost, threshold }，分级告警

所有payload都用Pydantic模型定义在schemas/events.py里，前端用对应的TypeScript接口，改一个地方两边同步，不会出现前后端字段对不上的问题。这就是'契约即代码'——类型定义就是协议，不用单独写API文档。"

【总·20秒】
"统一JSON格式+Pydantic契约，保证前后端类型一致，改协议不用写文档。"

### 一句话记忆
**统一JSON格式，Pydantic模型=契约，前后端共享类型。**

## 三、补充：为什么审批走 REST 不走 SSE（配代码）🔄 2026-08-14

> 对应追问：「为什么审批不用SSE而用REST？」（§一 追问预案）。下面是**带代码的完整版**，帮助理解而非背诵。

### 1. 概念对比

| | REST | SSE |
|--|------|-----|
| 方向 | 双向：客户端请求 → 服务端应答 | **单向**：只能服务端 → 客户端推流 |
| 连接 | 用完即断（一次请求 = 一次应答）| 长连接，保持打开持续推送 |
| 适合 | 一次性的操作命令 | 持续推送事件流 |

审批是**客户端 → 服务器**的命令（"我批准/拒绝这个工具调用"），SSE 是单向的推不回去，所以走 REST `POST /approve` 最自然——一个请求写一个决策，202 即返。

### 2. 完整时序（SSE 下行 + REST 上行 = 双向交互）

```
前端                          后端
 │  (SSE 长连接已建立)           │
 │◀──────── approve 事件 ────────│  ← 工具调用中断，服务端发 ApproveEvent
 │   （SSE：服务端→客户端推流）    │
 │                              │
 │   POST /approve  ────────────▶│  ← 人类点"批准"，REST 请求把决策写 Redis
 │   （REST：客户端→服务端应答）   │
 │   {"status":"ok"} ◀────────── │
 │                              │
 │◀──── 新 SSE 流（resume）─────│  ← 前端带 checkpoint_id 起新流恢复执行
```

**一句话：SSE 负责"下行推送审批卡片"，REST 负责"上行提交审批决策"**——两条单向通道组合成完整双向交互。

### 3. 代码位置

| 环节 | 通道 | 代码位置 |
|------|------|---------|
| 审批卡片下行 | SSE | `backend/src/schemas/events.py:117` `ApproveEvent`；`backend/src/api/chat.py:632` 流内 `evt_type == "approve"` 推送 |
| 审批决策上行 | REST | `backend/src/api/chat.py:685` `@router.post("/approve")`（请求体 `ApproveRequest`，`chat.py:75`）|
| 决策落地 | Redis | `src/agent/hitl/pending.py` `add_decision` 写入待决存储，`202 即返` |

REST 接口核心逻辑（chat.py:685）：按 `call_id` 定位 action index 写决策；`reject` publish_report 额外 INCR 会话修订计数（防无限修订循环）；`edit` 必须携带 `edited_arguments`；返回 `{"status": "ok", "accepted": bool}`，与前端 `ApproveRequest` 契约对齐（run_id / checkpoint_id / call_id / action / note / edited_arguments）。

### 4. 面试怎么讲（30秒）

> 面试官问"为什么审批不用SSE"：
> "SSE 是单向的，只能服务端往客户端推。审批是用户点按钮提交决策，方向正好相反，属于客户端→服务端的一次性操作，用 REST `POST /approve` 一请求一决策、202 即返最清晰。完整双向交互其实是两条单向通道组合的：SSE 下行推审批卡片，REST 上行回决策，恢复执行再开一条新 SSE 流。"

### 一句话记忆
**SSE 下行推卡片，REST 上行回决策，方向定通道。**

## 四、📝 口述练习注意事项（2026-08-14 第一次口述记录）

### 1. 口误清单（发音要准）

### 2. 表述容易绕的 2 段（背标准版）

**双向通信怎么实现**（不要绕，一句话说清）：
> "SSE本身是单向的，但配合HTTP POST就实现了完整交互——用户发消息用普通HTTP POST，服务器流式返回用SSE推送，两个通道配合，不需要WebSocket。"

**协议设计**（从场景倒推，举2-3个例子）：
> "协议是从业务场景倒推的——有对话开始就有start事件，有子代理执行就有subagent事件（启停/结果/失败），有工具调用就有tool_call事件（带running/completed/error状态机），总共10类，每个事件对应前端一个组件。"

### 3. 事实边界（别混）

- ❌ "SSE让用户可以随时中断" → SSE只负责"看"，**中断/审批是HITL的能力**
- ✅ "SSE让用户能看到执行过程，配合HITL审批机制，用户还能在关键节点介入"

### 4. 别跑题

踩坑讲到"国产模型兼容性"就停，**不要延伸到国内外模型发展对比**，说多了反而显得跑题。

### 5. 流畅度技巧

- 每段开头先给结论（"为什么选SSE？因为..."），不要铺垫半天
- 讲完一个点停1秒，再讲下一个，不要连珠炮
- 减少"嗯""然后""就是"这些口头禅
