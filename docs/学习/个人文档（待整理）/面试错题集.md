## §4 详细解析（待背诵问题的完整分析）

### 4.1 分层架构

**问题**：后端分几层？每层职责？依赖规则？

**我的薄弱点**：把代码目录和架构分层混了，漏了"能力层"整体概念，把db单独拎出来。

**详细解析**：

架构分层不是按代码目录分的，是按**职责抽象**分的。项目里虽然有 `mcp/` `sandbox/` `memory/` `db/` 四个目录，但它们都属于"能力层"——因为它们的共同特点是**被Agent层调用、提供具体能力**，所以归为同一层。

依赖单向的核心目的是**降低耦合**：如果api层能直接调db，那业务逻辑就会散落在api层，以后改db schema要改好多地方。规定api只能调agent，agent调能力层，所有SQL都在能力层的db仓储里，改数据库只需要改一个地方。

**类比**：就像餐厅——前台（api）只对接服务员（agent），服务员对接后厨（能力层），后厨里有切菜的（mcp）、炒菜的（sandbox）、备菜的（memory）、管仓库的（db），但他们都是后厨的人。前台不能直接跑去仓库拿菜，必须通过服务员。

**面试话术**：
> "后端分四层：API接入层负责路由和SSE编排，Agent编排层负责主Agent编译图和子代理委派，能力层包括MCP工具网关、沙箱、记忆双写、SQLite仓储，公共底座是配置、日志、多provider LLM适配。依赖单向，api只能调agent，agent调能力层，禁止反向，api也不能直连db——所有SQL走能力层仓储，保证单一出口、可测试。"

**关联**：架构总纲 §2 ①、`agent/` `mcp/` `sandbox/` `memory/` `db/` `core/` 目录

### 4.2 演进路径

**问题**：为什么用多Agent？单体不行吗？

**我的薄弱点**：说"项目最初就是多Agent设计"，但这样讲没有"踩坑→演进"的故事线，面试不够生动。

**详细解析**：

你说的是事实（multi_agent项目一开始就是多Agent），但面试时需要把**前身项目（LLM Wiki）** 串进来。LLM Wiki是单体Agent，做的过程中暴露了三个问题，这些问题直接催生了multi_agent的多Agent设计。这样讲既有演进故事，又诚实。

三个坑的具体表现：
1. **Prompt膨胀**：一个系统提示词要同时告诉Agent"你会搜索、会写、会审核"，角色冲突，提示词越来越长
2. **上下文污染**：搜索过程返回10条结果+5篇正文，塞满对话窗口，后面写报告时这些搜索细节还在上下文里，干扰写作
3. **工具过载**：工具有搜索、抓取、沙箱、写文件十几个，Agent选工具的准确率下降，经常选错

**面试话术**：
> "之前做过一个单体Agent的LLM Wiki项目，暴露了三个坑：Prompt膨胀（一个提示词要覆盖所有角色）、上下文污染（搜索结果塞满窗口干扰写作）、工具过载（工具太多选错率高）。所以做这个新项目时，一开始就按多Agent架构设计——主Agent只做编排和撰写，search_agent独立搜索用便宜模型，review_agent独立审核用独立评审标准，每个子代理上下文隔离、工具最小化。"

**关联**：架构总纲 §2 ③、LLM Wiki项目

### 4.3 子代理独立上下文

**问题**：子代理的独立上下文怎么实现的？主Agent调用时传什么？返回什么？

**我的薄弱点**：完全不清楚，这是子代理最核心的机制。

**详细解析**：

子代理本质上是一个**独立编译的Agent实例**，它有自己的对话历史列表（messages数组），和主Agent的messages完全是两个变量，存在不同的内存空间里。

调用过程：
1. 主Agent决定调用search_agent，生成一个工具调用，参数是`{"task": "搜索MCP协议最新发展"}`
2. 框架把这个task字符串拿出来，作为search_agent的"用户消息"，放进search_agent自己的messages里
3. search_agent开始独立执行：自己的系统提示词 + task消息 → 调搜索工具 → 整理结果
4. 执行完，search_agent把最终回答（一个字符串）返回给主Agent
5. 主Agent把这个字符串作为"工具调用结果"放进自己的上下文，继续执行

**关键：中间过程不回传**。search_agent调了几次搜索工具、每一步怎么想的，主Agent完全看不到，只看到最终结果。这就是上下文隔离——搜索的10条原始结果不会塞进主Agent上下文。

**类比**：主Agent是项目经理，子代理是外包。项目经理只说"帮我调研MCP协议"，外包自己去查资料、整理，最后交一份报告。项目经理看不到外包查了哪些网站、走了哪些弯路，只看到最终报告。

**面试话术**：
> "子代理是独立编译的Agent实例，有自己的对话历史，和主Agent完全隔离。主Agent调用时只传一个任务描述字符串，子代理独立执行（自己的系统提示词、自己的工具、自己的模型），执行完只返回最终结果字符串。中间的思考过程、工具调用细节都不回传，这样搜索产生的大量中间结果不会污染主Agent的写作上下文。"

**关联**：`subagents/loader.py`、deepagents `create_agent` + `.as_tool()`

### 4.4 YAML字段

**问题**：子代理的YAML文件里有哪些字段？

**我的薄弱点**：只说了name/description/tools/permissions，漏了model和system_prompt——这两个恰恰是角色差异化的核心。

**详细解析**：

YAML是子代理的"角色说明书"，每个字段都在定义"这个子代理是谁、能做什么、用什么做"：

| 字段 | 作用 | 为什么重要 |
|------|------|-----------|
| name | 子代理名称 | 主Agent调用时的工具名 |
| description | 功能描述 | LLM靠这个判断何时调用，写不清楚就会调错 |
| model | 使用的模型 | 搜索用便宜模型、审核用好模型，成本控制的关键 |
| system_prompt | 角色设定 | "你是搜索专员，只负责搜索和信息整理"——定义角色边界 |
| tools | 可用工具列表 | 最小权限，search_agent只有搜索工具，不能写文件 |
| permissions | 文件/沙箱权限 | 安全控制，子代理不能越权访问 |
| temperature | 随机性 | 搜索要准（低），审核要灵活（中） |

**最容易漏的是model和system_prompt**——这两个是"同一个框架，不同角色"的关键。没有model字段，所有子代理都用同一个模型，就没有"搜索用便宜模型"的成本优化了。没有system_prompt，子代理不知道自己是谁，会越权做不该做的事。

**面试话术**：
> "YAML里主要有7个字段：name（名称）、description（功能描述，LLM靠这个判断何时调用）、model（使用的模型，搜索用便宜的审核用好的）、system_prompt（角色设定）、tools（可用工具列表，最小权限）、permissions（文件和沙箱权限）、temperature（随机性）。其中model和system_prompt是角色差异化的核心——同一个框架，通过不同的模型和提示词变成不同角色。"

**关联**：`subagents/search_agent.yaml`、`subagents/review_agent.yaml`

### 4.5 子代理失败处理

**问题**：子代理执行失败了怎么办？

**我的薄弱点**：混淆了"工具失败"和"子代理本身失败"，把搜索API降级当成了子代理失败处理。

**详细解析**：

两个层面要区分清楚：

**层面1：工具失败（子代理内部）**
- 场景：search_agent调用博查搜索API，超时了/返回空
- 处理：子代理内部自己处理——两阶段抓取（先标题后正文）、多provider降级（博查→阿里云百炼）
- 这个是子代理**自己的事**，主Agent不知道也不关心

**层面2：子代理本身失败（主Agent层面）**
- 场景：search_agent整体超时（比如跑了60秒还没返回）、子代理崩溃、返回格式错误
- 处理：
  1. 容错中间件捕获异常，重试1-2次
  2. 重试还失败，主Agent收到错误
  3. 主Agent兜底：要么自己直接回答（简单问题），要么告诉用户"搜索服务暂时不可用"
  4. 记错误日志，方便排查

**类比**：工具失败=外包员工查资料时某个网站打不开，他自己换个网站继续查；子代理失败=外包员工失联了/跑路了，项目经理得自己上或者告诉客户延期。

**面试话术**：
> "分两个层面。工具层面：搜索API超时，子代理内部做多provider降级（博查→阿里云百炼→兜底），这个子代理自己处理。子代理本身层面：整体超时或崩溃，容错中间件重试1-2次，还失败就主Agent兜底——简单问题自己答，复杂问题如实告诉用户搜索失败，不用假数据继续。"

**关联**：容错处理描述点、`agent/middlewares/`

### 4.6 子代理调用准确性

**问题**：主Agent怎么知道该调哪个子代理？怎么保证不调错？

**我的薄弱点**：前半（LLM自主判断）说对了，后半（怎么保证）完全不清楚。

**详细解析**：

主Agent不是硬编码"遇到搜索就调search_agent"，而是**LLM根据工具描述自主判断**。创建主Agent时，把子代理作为工具注册，每个工具有name和description，LLM看用户问题+工具描述，自己决定调哪个。

没有100%的保证（LLM是概率性的），但有4层保障提升准确率：
1. **工具描述写清晰**：search_agent的description写"用于需要联网搜索外部信息的任务"，review_agent写"用于对已有文本内容进行质量审核和评分"——边界清晰，不重叠
2. **系统提示词引导**：主Agent的system prompt里明确"需要搜索信息时调用search_agent，需要审核内容时调用review_agent"
3. **最小工具集**：子代理工具就2个，选择空间小，不容易错（如果有10个子代理，选错概率自然高）
4. **评估验证**：用测试集跑一遍，统计"子代理调用正确率"，正确率低就优化工具描述

这是LLM系统的特点——不是确定性的if-else，是概率性的，靠工程手段（清晰描述+引导+评估）把错误率压到可接受范围。

**面试话术**：
> "不是硬编码，是LLM根据工具描述自主判断。没有100%保证，但有4层保障：一是工具描述写清晰，搜索和审核的边界不重叠；二是系统提示词里明确引导；三是子代理数量少（就2个），选择空间小；四是通过评估体系统计调用正确率，低了就优化描述。LLM系统是概率性的，靠工程手段提升可靠性。"

**关联**：`agent/main_agent.py` 工具注册、评估体系描述点
