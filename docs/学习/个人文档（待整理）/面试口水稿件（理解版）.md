## 一、分层架构

**问题**：你们这个多Agent系统后端分几层？每层是干什么的？层和层之间的依赖有什么规则？

**答**：
"后端分四层：**API接入层**（路由+SSE编排+会话CRUD）、**Agent编排层**（主Agent编译图+子代理委派+中间件栈）、**能力层**（MCP工具网关/沙箱/记忆双写/SQLite仓储）、**公共底座**（配置/路径/日志/多provider LLM适配/Pydantic模型）。

依赖单向，api只能调agent，agent调能力层，禁止反向，api也不能直连db——所有SQL走能力层的仓储，保证单一出口、可测试。"

---

## 二、演进路径（为什么多Agent）

**问题**：为什么要拆成多Agent？单体不行吗？

**答**：
"之前做过一个**单体Agent的LLM Wiki项目**，暴露了三个坑：Prompt膨胀、上下文污染、工具过载。所以做这个新项目时，**一开始就按多Agent架构设计**——主Agent只做编排和撰写，search_agent独立搜索用便宜模型，review_agent独立审核用独立评审标准，每个子代理上下文隔离、工具最小化，顶层主Agent统一协调。"

---

## 三、主流程（一条请求怎么走）

**问题**：讲一下一次请求的完整流程。

**答**：
【总・30 秒】
"这是一个面向深度研究任务的多 Agent 系统。一次请求的主流程是：用户前端发消息 → 后端对话层入库并创建会话 → 主 Agent 编排 → 复杂任务委派给搜索和审核两个子代理 → 搜索子代理做两阶段受控抓取 → 沙箱里做数据处理和文档生成 → 审核子代理做评分细则 → 不通过就打回重做，最多 N 轮 → 人在回路做最终确认 → SSE 事件流返回前端。"

【分・90 秒】
"几个关键设计：
1. **为什么拆子代理**：单体 Agent 有三个坑——Prompt 膨胀、上下文污染、工具过载。拆开后 search_agent 用便宜模型独立搜索，review_agent 用独立评审标准，上下文互不干扰。
2. **受控抓取两阶段**：第一次只爬标题/概要/时间，LLM 判断哪些重要，第二次才抓正文，省 Token 也省时间。
3. **沙箱隔离**：数据拼接、生成 Word/Excel/PPT 这些高风险操作都放 OpenSandbox 里跑，防止恶意代码影响主机。
4. **审核闭环**：评分细则达到阈值就通过，没通过打回补充，有最大轮次限制防止无限修订；关键节点还可以触发人在回路审批。
5. **流式返回**：整个过程通过 10 类 SSE 事件实时推给前端，用户能看到搜索进度、工具调用、审核结果，不是干等。"

【总・20 秒】
"主流程之外还有三横切——容错、成本、安全——都是挂在主流程上的护栏。整个系统 290 个测试全绿，多 Agent 虽然成本比单 Agent 高 2-8 倍，但通过模型分级和缓存把成本控住了。"
