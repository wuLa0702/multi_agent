## 0. 结论 🔴 v2

| # | 决策 | 方向 |
|---|------|------|
| 1 | 简单直连判断 | **规则快通道 + LM 兜底**（intent 分类，简单问题不挂搜索/子代理工具直接答），加"重新走完整链路"兜底 |
| 2 | 子代理角色池 | **当前维持2个，先加工具不拆角色**；data_agent/code_agent后置，等真实痛点出现再扩展 |
| 3 | 报表生成 | **主Agent撰写 + 沙箱工具生成文件**，不拆独立报表子代理 |

**背景**：真实测试发现"解释 LangGraph"这类简单问题被过度处理（走搜索+子代理、回答臃肿）——因为系统完全依赖模型自主判断，无简单直连。子代理固定 2 个（启动注册），非动态。

**v2 核心调整**：角色数量不是越多越好，拆子代理有明确判断标准（3条满足2条才拆）。当前2个角色是最小可用分工，新增角色等真实痛点出现再加，避免过度设计和token浪费。

## 1. 方案一：简单直连快通道（规则快通道 + LM 兜底） 🔴 v2

### 1.1 机制

请求进来 → **intent 分类**（确定性规则，零 LLM 成本）→ 分流：

```
用户请求 → classify_intent(request)
  ├─ 简单（概念问答/短问）→ 快通道：主 agent 不挂搜索/子代理工具 → 单轮直接答
  └─ 复杂/模糊 → 完整链路（挂搜索/子代理/publish_report）
```

### 1.2 `classify_intent()` 规则（关键词 + 长度启发式）

| 信号 | 判简单 | 判复杂 |
|------|--------|--------|
| 关键词 | `解释/是什么/区别/为什么/定义/简述/介绍` + 无研究意图 | `调研/分析/报告/生成/评估/对比 X 和 Y 优劣/写论文/整理资料` |
| 长度 | 短问题（<30 字）| 长/多句 |
| 结论 | 命中简单信号 → 快通道 | 命中复杂信号 → 完整链路；都无 → 完整链路（**LM 兜底**，宁复杂不错过）|

> 兜底原则：**不确定就走完整链路**（规则只拦截"确定简单"的），避免误伤复杂问题。

### 1.3 快通道实现

- 快通道 = 主 agent **不挂搜索/子代理工具**（`internet_search`/`fetch_url`/subagents 不注入），只保留基本工具（sandbox 计算可选）
- 模型没有搜索工具 → 只能基于知识直接答 → **天然不会过度拆解**
- 同时 `prompts.py` 加引导："简单问题直接回答，不要拆解搜索/委派子代理"

### 1.4 快通道兜底（v2 新增）

- 快通道回答后，前端提供"重新走完整链路"按钮（或用户输入"/full"指令）
- 触发后：同一请求重新走完整链路（挂搜索/子代理），覆盖快通道结果
- **目的**：规则分类可能误判（把复杂问题判成简单），给用户手动纠正的机会
- 实现：前端记录原始请求，点按钮后重新调用 `/v1/chat/stream` 并强制 `intent=complex`

### 1.5 落点

| 文件 | 改动 |
|------|------|
| `agent/intent.py`（新建）| `classify_intent(request) -> "simple"\|"complex"`（关键词+长度，底层豁免）|
| `api/chat.py` | 分流：simple → 快通道参数（不挂搜索工具）；支持强制 `intent=complex` |
| `agent/main_agent.py` | 按 intent 决定挂载工具集（simple 少挂）|
| `agent/prompts/prompts.py` | 加"简单直接答"引导 |

### 1.6 面试价值

"意图路由 + 快慢通道"——可控、省成本、可解释；面试讲"系统级判断 vs 模型自主"的取舍，以及"规则兜底+用户手动纠正"的容错设计。

## 2. 方案二：子代理角色池策略 🔴 v2（重写）

### 2.1 现状确认

- 子代理**服务启动时**从 `subagents/*.yaml` 加载注册（`loader.py`），**固定 2 个**（search_agent 搜索 / review_agent 审核）
- **非动态**：模型只能在已注册角色里选
- 主Agent职责：编排 + 撰写报告 + 调用工具（包括未来的报表生成、Wiki写入）

### 2.2 角色拆分判断标准（v2 新增，核心）

**一个职责要不要拆成独立子代理，用3条标准检验，满足2条才值得拆：**

| 标准 | 解释 | 反例（不满足就别拆）|
|------|------|-------------------|
| ① 上下文需要隔离 | 该角色的工作过程会产生大量中间结果，塞主上下文会污染撰写 | 简单工具调用（1次写入）不产生中间结果，不用拆 |
| ② 可以用更便宜的模型 | 该角色对模型能力要求低于主Agent，能用便宜模型省成本 | 需要好模型的任务（如撰写、代码生成）拆了也省不了钱 |
| ③ 需要独立的受限工具/权限 | 该角色只能用特定工具，不能给全量权限 | 主Agent已经有该工具，且权限不需要额外限制 |

**判断原则**：
- "思考/决策/整合"类工作 → 留主Agent（需要全局上下文）
- "执行/处理/转换"类工作 → 才考虑拆子代理（过程可隔离）

### 2.3 当前2个角色的合理性验证

| 角色 | ①上下文隔离 | ②独立模型 | ③独立工具 | 结论 |
|------|-----------|----------|----------|------|
| search_agent | ✅ 搜索结果多（10条+5篇正文） | ✅ 搜索用便宜模型 | ✅ 只有搜索工具 | ✅ 3条全中，必须拆 |
| review_agent | ✅ 审核标准独立，不能和撰写者同一上下文 | ✅ 独立上下文+独立评审标准（审核不污染撰写）；模型同为 `deepseek-v4-flash`（便宜），**价值在"独立评审"非"更好模型"**（v2.1 修正）| ✅ 只读不写 | ✅ 3条全中，必须拆 |
| 主Agent（撰写） | ❌ 撰写需要整合所有上下文，拆了反而增加数据传递 | ❌ 和主Agent同模型 | ❌ 需要全量工具 | ❌ 不拆，自己做 |

**结论**：2个是当前业务场景的**最小可用分工**，不是"只能2个"，而是"满足拆分标准的就这2个"。

### 2.4 扩展角色评估（v2 修订：后置，不立即加）

#### data_agent（数据整理）

| 标准 | 是否满足 | 说明 |
|------|---------|------|
| ①上下文隔离 | ⚠️ 视场景 | 简单写入（1次工具调用）不满足；复杂数据清洗/多文件写入才满足 |
| ②独立模型 | ✅ | 数据处理用便宜模型就行 |
| ③独立工具 | ✅ | 沙箱+数据工具，权限受限 |

**决策：后置，先不加。**
- 当前Wiki写入场景是"把最终报告存到指定目录"，属于简单工具调用，主Agent加`write_wiki`工具即可
- 等出现"研究过程中大量中间数据需要结构化整理+多文件写入+建立索引"的真实痛点时，再拆data_agent
- YAML声明式的好处是加角色很方便，一个YAML文件的事，不用提前设计

#### code_agent（代码生成）

| 标准 | 是否满足 | 说明 |
|------|---------|------|
| ①上下文隔离 | ✅ | 代码片段多 |
| ②独立模型 | ❌ | 代码生成需要好模型，和主Agent一样，省不了钱 |
| ③独立工具 | ⚠️ | 只有沙箱，但主Agent已经有沙箱 |

**决策：后置，优先级更低。**
- 3条只满足1.5条，不值得拆
- 当前代码生成需求不高频，主Agent+沙箱工具足够

### 2.5 报表生成策略（v2 新增）

**不拆独立报表子代理，采用"主Agent撰写 + 沙箱工具生成文件"方案。**

#### 为什么不拆报表子代理？

| 标准 | 是否满足 | 说明 |
|------|---------|------|
| ①上下文隔离 | ❌ | 报表核心是内容撰写，需要整合所有上下文，拆出去要传大量数据 |
| ②独立模型 | ❌ | 内容撰写需要好模型，和主Agent一样 |
| ③独立工具 | ⚠️ | 文件生成需要沙箱，但主Agent已经有沙箱 |

**3条只满足0.5条，不值得拆。**

#### 实现方案

```
主Agent（决定报告结构 + 撰写内容）
    ↓ 调用工具
generate_report工具（沙箱内执行python-docx/openpyxl，渲染模板）
    ↓ 返回文件路径
主Agent（交付文件给用户 / 触发HITL审批）
```

- `generate_report` 工具本质是"沙箱执行 + 模板渲染"，和现有 `run_code_in_sandbox` 同类
- 先做Word格式，Excel/PPT后续扩展
- 报表模板放在 `assets/report_templates/`，工具加载模板+填充内容

#### 什么时候才考虑拆报表子代理？

同时满足以下条件才考虑：
- 报表格式极其复杂（需要多轮调试排版）
- 一次要生成多种格式（Word+PPT+Excel+PDF）
- 报表生成过程产生大量中间文件污染主上下文

**当前阶段不考虑。**

### 2.6 token 成本控制（v2 新增）

**子代理确实增加 token**（独立 system_prompt 约200-500 token + 独立对话历史），但有3个控制手段：

1. **按需调用**：主Agent只有在需要时才调子代理，不是每次都调。简单问题走快通道，连子代理都不碰。
2. **结果浓缩**：子代理返回"整理后的结论"，不是原始数据。比如search_agent返回"5条关键信息+来源"，不是返回10条原始结果。
3. **模型分级**：search_agent用最便宜的模型，单次调用成本只有主Agent的1/5-1/10。

**实际效果**：快通道 + 角色精简后，**整体 token 成本反而下降**——简单问题不再走完整链路，复杂任务的主上下文更干净。

### 2.7 并行执行与角色池的关系（v2 新增，区分概念）

**两个层面，别混了：**

| 层面 | 场景 | 是什么 | 靠什么实现 |
|------|------|--------|-----------|
| 多请求并发 | 10个用户同时问10个不同问题 | 多线程/多并发请求 | FastAPI async + 多进程，每个请求独立主Agent |
| 单请求内并行 | 1个用户的任务里，同时搜索10个关键词 | 同角色多实例并行调用 | LangGraph Send API（Map-Reduce），当前不支持 |

**关键区分**：
- **角色池** = "有哪些角色可选"（search/review），是静态的，启动时注册
- **并行执行** = "同一个角色同时跑多个实例"，是动态的，需要图编排支持

**当前架构**：角色池静态，子代理调用是**串行**的（主Agent调完search再调review）。

**未来并行执行演进**（不入本期）：
- 手写 LangGraph Send API（Map-Reduce fan-out）
- 或用 asyncio.gather 同时调用多个子代理实例（简单版）
- 这和"角色池有几个角色"是两回事——即使只有search_agent一个角色，也可以并行跑10个实例
